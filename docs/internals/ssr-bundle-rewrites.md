# SSR bundle rewrites

The Tifa plugin adapts many npm packages in the SSR bundle so they render faster in beastjs. What an app author needs to know is in [Frontend output](../reference/build-output.md#frontend-output). This doc has the detail for someone who works on Tifa.

## How a rewrite finds its code

The plugin finds the code it changes by its form or its text, not by the version of the package. When a release changes that code, the build prints a warning with the package version and the file, and leaves that code as it is. Every such warning starts with `tifa rewrite not recognized: `, so `grep` finds them all, and `internal/bundle` and `test/e2e` fail on it (see [Testing](testing.md#ci)), as does the scheduled CI job that builds with the latest React.

## The rewrites

- React DOM gets fourteen changes:
  - `react-dom/server.edge` loads both of React's server renderers. The plugin reads the form of that file and keeps only the string renderer that Tifa uses. On the example app this makes the bundle 25% smaller and a pool of 4 VMs starts in 63 ms instead of 117 ms, while a render takes as long. Without this change the bundle keeps both renderers.
  - `renderToString` ignores the error of a component that throws inside a Suspense boundary. The plugin gives `renderToString` and `renderToStaticMarkup` the `onError` option of React's other renderers, so the server can report that error (see [Page requests](../reference/page-requests.md#page-requests)). Without this change such a render still fails, but the error cannot say why.
  - `renderToString` ends the render after its first pass. A component that suspends on work promises settle by themselves, such as a `React.lazy` component of a module in the bundle, then leaves its Suspense boundary to the browser, and the render fails. The plugin adds `prerenderToString` to the string renderer, which the server renders with: it renders as `renderToString` does, waits until every boundary is done, and gives the HTML `renderToString` writes for the same tree without the waits. The server runs the jobs of the VM until then, and when none is left it ends the render as `renderToString` would, so work that never settles still fails the render (see [Components that wait](../pages-and-data/server-render.md#components-that-wait)). A page that does not suspend renders in one pass, as fast as before. The plugin finds `renderToStringImpl` of React DOM 19.3 by its text. With a release that changes it, the build prints a warning, and `prerenderToString` renders as `renderToString` does, without waiting.
  - React puts each element it renders on a component stack, an object for each. The string renderer only gives that stack to the error handler of `renderToString`, as `errorInfo.componentStack`, and the handler the plugin gives `renderToString` passes on only the error. So the plugin keeps React from building the stack. It does so only together with that handler: when the plugin does not find `function onError() {}` in React DOM, the stack stays. It also counts the places that read the stack, the calls of `getThrownInfo` and the reads of `componentStack`, and keeps the stack when they are not those of React DOM 19.3. With a later version that also reads it in other places, the build prints a warning. Errors and their stack traces stay the same. Without this change pages render as fast as before.
  - For each element it renders, React looks up the name of its component and puts it into the key path of the element. In `renderToString` only one piece of code reads these names: `useActionState` hashes the key path into the key of its state when the action has a `$$FORM_ACTION`, which only a server action has, and writes that key into the form. The other readers resume or prerender a page, which `renderToString` does not do. Tifa has no server actions and renders only with `renderToString`, which creates its request without a form state, so the plugin leaves the names out. It does so only when every place in React DOM that creates a request (`createRequest` and `new RequestInstance`) passes no form state, and when the places that read the names, the hashes of key paths with `JSON.stringify` and the reads of the name in a key path, are those of React DOM 19.3. With a later version that also reads them in other places, the build prints a warning and keeps the names. When the bundle has a module outside React DOM with `$$FORM_ACTION` in its code, the build prints a warning that names the module: the key such a form gets then differs from the one React writes without the plugin. Without this change pages render as fast as before.
  - React makes an array for each element it renders, its key path: the key path of the parent, the name of the component and the key or index of the element. It also makes one for each place of the children of an array and for the fallback of a Suspense boundary. In `renderToString` only two pieces of code read them: `useActionState`, for an action with a `$$FORM_ACTION`, and a Suspense boundary, which hands the key path of its fallback on. The code that resumes or prerenders a page reads them too, but the request of `renderToString` has no postponed state and no task of it has a replay. So the plugin makes the arrays only when a module outside React DOM has `$$FORM_ACTION` in its code. For such a bundle it puts `globalThis.tifaFormActions = true` on a line before the code, and `createRequest` reads that for each request, so the key of a server action stays what it was with the key paths. The plugin tells by the text `$$FORM_ACTION` in a module: an action that gets the property from a name put together while the program runs is not recognized, and its key is hashed from empty key paths. Tifa has no server actions of its own. Without such a module a key path is `null`, which the places that hand it on pass on, and the fallback of a boundary takes `null` for its own. The plugin leaves the names out and makes the arrays only together, and only when every part of React DOM's string renderer is one it has read to the end ([Reviewing a new React](#reviewing-a-new-react)), and only when the places that make a key path are those of React DOM 19.3 and so are the reads of `[0]` and `[2]` of a key path, the assignments to `trackedPostpones` of something but `null` and the calls of `createReplayTask`. A part is a function declaration, a variable or another statement at the top of the file, and the order of the top of the file is a part too. Each is known by a fingerprint of its structure, the syntax tree without its places, its comments, its quotes and its brackets, in which a name that the part declares is written as the number of its first place (so the numbers React's compiler puts on the names it makes unique, `prevKeyPath$43`, do not matter) and every other name is kept, as are the names that code can see: those of functions and classes, of a variable that an anonymous function is set to (its `name`), and of a variable that both a `catch` parameter and a `var` of its body declare. A template keeps its raw text. So `return` followed by a line break or `returnα` is not `return α`. The plugin keeps a table of the fingerprints of React DOM 19.3.0 and 19.3.1, which differ in the line of the version alone. A release that changes a comment or white space keeps the change. A release that changes, adds or moves any part gets one warning that names up to 20 of the parts and counts the rest, and React keeps both the names and the key paths. The whole file, and not only the functions that read key paths, because key paths live in the `task` objects that the whole renderer passes around, and code can read them with `for in`, a spread, `Object.assign` or `Reflect.get` as well as by name, so only the unchanged code of every part is a proof that nothing new reads them. A render runs 1.2% fewer instructions on the shop's workbench pages, 0.7% on its storefront pages and the MUI test app and 1.8% on the bench app, with the same HTML. Without this change pages render as fast as before.
  - Every node React renders goes through `renderNodeDestructive`, a function that checks whether the task has a replay and hands the node to `retryNode` through two fields of the task. In beastjs a call of a function written in JavaScript costs several hundred instructions, more than the work of this one. The plugin writes its body in place of the calls whose first two arguments are names and whose other two are a name, a number or a property of a name, 12 places in React DOM 19.3 (`renderNode`, fragments, context providers and consumers, class components and others), so a node costs one call less. It does so for calls whose value no one reads: a statement, a branch of a conditional or a part of a sequence that is one, or the value of a `return`, which becomes a `return` of nothing, as the function returns nothing. It keeps `renderNodeDestructive` for the other calls. A render runs 1.15% fewer instructions on the shop's workbench pages, 0.76% on its storefront pages, 0.89% on the MUI test app and 2.33% on the bench app, which is about 480 instructions for each of the shop's 20,144 nodes. A stack trace of a render error has no frame for `renderNodeDestructive`, and the frame of `renderNode` names the call of `retryNode` further right on its line. The change needs `renderNodeDestructive` to be in the form the plugin knows after the component stacks are dropped: otherwise the build prints a warning and pages render as before.
  - React escapes every text and attribute value it writes with `escapeTextForBrowser`. beastjs has that function written in C (`VM.RegisterEscapeText`), and `ssr.Load` gives every VM of the pool it as `__tifa_escape`. When the VM has it, the plugin makes `escapeTextForBrowser` in the string renderer that function itself, so an escape is one call into the engine, with no search by a regular expression, no cache lookup and no loop over characters in JavaScript. It gives the text React's function gives for every argument: a string, a number, an object with its own `toString`, or a symbol, which throws as it does there. A string with nothing to escape comes back as it is. The tests compare it with React's function on every UTF-16 code unit, alone and in a row, on 3,000 random strings, on texts of 1 to 100,003 code units with a character to escape at each end and in the middle, and on values that are not strings. Unlike React's function it does not call a `charCodeAt`, `slice` or `exec` that a page replaced. A render runs 2.5% fewer instructions on the shop's workbench pages of the example app, 2.4% on its storefront pages, 0.7% on the MUI test app and 4.5% on the bench app, with the same HTML. Timed at 8 code positions on linux/amd64 (one core of an AMD EPYC 7B13, without PGO), the shop's workbench pages render in 0.974 of the time, faster at all 8 positions where the positions of the unchanged build differ by 2.5%, its storefront pages in 0.975 and the bench pages in 0.938. The MUI pages, under 2% fewer instructions, were not timed. The declaration of `escapeTextForBrowser` becomes a variable, so the plugin does this only when the module does not name the function before it. A VM without `__tifa_escape` keeps React's own function, and a React DOM the plugin does not know keeps its function and gets a warning.
  - React keeps the HTML of a page as segments. Each segment is a list of chunks, with child segments between them, which come from Suspense boundaries, from parts of the page that suspended and from the preamble. React hands the chunks one at a time to a function that adds each to the result. A page has thousands of them, and each call is slow in beastjs. The plugin makes React join the chunks between two child segments of a segment and hand them over at once. The HTML stays the same: that function skips a `null` chunk, and joining turns it into an empty string. On the example app warm renders take 5% to 7% less time, and on pages of plain text 6% to 11% less. Without this change pages render as fast as before.
  - React writes every attribute of every element with `pushAttribute`. For the common ones (`class` for `className`, `tabindex`, `dir`, `role`, `viewBox`, `width`, `height` and the XLink and XML names) it calls `pushStringAttribute`, for any other name it calls `isAttributeNameSafe`, and it pushes each attribute as five chunks: a space, the name, `="`, the value and `"`. A call in beastjs costs about as much as the work of such a short function. The plugin writes the common attributes without the call: `pushAttribute` holds the test of `pushStringAttribute` in the case, and where the name is a string the chunk before the value is one string, ` class="`. A name that `isAttributeNameSafe` has seen is found in its cache before the call. The text is the same, since the test is the body of `pushStringAttribute` and `isAttributeNameSafe` starts with that lookup. The chunks are still pushed one by one: joining them with `+` as well saved 0.3% of the instructions of the shop's workbench pages where this saves 0.8%, since a join copies short strings. A render runs 0.8% fewer instructions on the shop's workbench pages, 0.7% on its storefront pages, 1.0% on the bench app and 0.1% on the MUI test app. Timed at 8 code positions on linux/amd64, the shop's workbench pages take 0.995 of the time, its storefront pages 0.993 and the MUI pages 0.997. The rule for code positions counts none of them as a change, since the positions of the unchanged build differ by 1.9% to 2.7%, and the median of none is slower. A string is the value of almost every attribute, and React asks the type of the value up to three times, whether it is a function, a symbol or a boolean, which it does not write. The plugin asks first whether the value is a string, one question where React asks three, in the cases that write a string attribute, in `src`, `href`, `action`, `formAction` and `xlinkHref`, and in the default branch. A value of another type is asked the three questions after that one, so the HTML is the same for a value of every type. The type goes into no variable: one more local in `pushAttribute` costs every call of it about what the questions it saves cost, and a variable took 0.02% to 0.06% more instructions than asking again. A render runs 0.30% fewer instructions on the shop's workbench pages, 0.24% on its storefront pages, 0.19% on the bench app and 0.07% on the MUI test app (page by page, the workbench pages 0.21% to 0.58% fewer, the storefront pages 0.05% to 0.49%, the MUI pages 0.02% to 0.14%, the spiral page 0.38% fewer and the table page 0.03% more, which is within the 0.02% to 0.04% by which two runs of one bundle differ), on top of the rewrite above. When `pushStringAttribute`, `isAttributeNameSafe`, one of the tests of the type or the default branch of `pushAttribute` differs from React DOM 19.3's, the build prints a warning and pages render as fast as before.
  - React picks what to write for an attribute or a tag with a `switch` on its name, and beastjs compares the name with one case after the other. The attribute switch has 71 cases, so a name that is not one of them, such as `id`, `type` or `aria-label`, costs 71 comparisons before it reaches the default branch. The plugin reads the syntax tree of the renderer and puts a `Set` lookup in front of each `switch` that compares a variable with at least 8 strings and nothing else, so such a name goes to the default branch at once. It only changes a `switch` where the result is the same: the default branch, if any, comes last and no case runs on into it, and no case declares `let`, `const`, a class or a function. In React DOM 19.3 that is 5 switches, on attribute names and on tag names. On the example app warm renders take 6% to 7% less time, and on pages of plain text 9% to 12% less. The bytecode of the example app grows by 5 KB, and each VM by a few KiB. When React DOM has no such `switch`, the build prints a warning and pages render as fast as before.
  - `pushAttribute` still did the same work for a name each time it saw it: ask a `Set` whether the name has a case among the 71, and for any other name check whether it starts with `on`, look up its alias in a `Map` and check that it is valid. The answer for a name never changes, so the plugin makes `pushAttribute` keep it. A `Map` in the module holds, for each valid name React writes, the chunk that goes before the value (` data-slot="`, or ` for="` for `htmlFor`), and an empty string for a name that starts with `on`, which writes nothing whatever the value. A string or a number is the value of almost every attribute, and it goes out as that chunk, the value and `"`, three chunks where React pushed five. A function, an object, a boolean or a value of another type goes through React's own code as before, so the HTML is the same. `className` and `style` are answered before the lookup: they are the most common names, and two comparisons cost less than a lookup for the pages that have no `style`. The `Map` starts with `tabIndex`, `dir`, `role`, `viewBox`, `width` and `height`, fills in as names are first seen, and stops at 4,096 names, so an app that spreads its users' keys into a tag cannot make it grow without end. A render runs 2.54% fewer instructions on the shop's workbench pages, 2.28% on its storefront pages, 0.43% on the MUI test app and 1.81% on the bench app. A lookup of a name that is not in the `Map` costs about 170 instructions, so a name with a case, such as `href` or `ref`, pays that on top of the `Set`: on the shop's pages these are 16% of the attributes, and `className` and the names without a case are 84%. When `pushAttribute` or its default branch in React DOM differs from 19.3, the build prints a warning and pages render as before.
  - React writes the start tag of most elements with `pushStartGenericElement`, which calls `pushAttribute` for each prop, `pushStyleAttribute` for `style` and the escape for each value, and pushes the tag as many chunks. The end tag comes from `endChunkForTag`. Each call of a JavaScript function costs a few hundred instructions in beastjs, and one element makes ten or more. beastjs has these functions written in C (`VM.RegisterStartTag` and `VM.RegisterEndTag`), and `ssr.Load` gives every VM of the pool them as `__tifa_start_tag` and `__tifa_end_tag`. The plugin makes `pushStartInstance` ask the engine for the start tag of each element it would hand to `pushStartGenericElement`, and `renderElement` for the end tag of such an element. An `a` whose `href` is not `""` and a `button` with none of `name`, `formAction`, `formEncType`, `formMethod` and `formTarget` also go to the engine: React writes them with a case of its own that, for these props, does what `pushStartGenericElement` does. An `a` with `href=""` and a button with a form prop stay in React's case, which handles an empty `href` and the form action and its hidden fields. An engine whose start tag takes a seventh argument, the mode, also writes `img` (after React's image preload) and the void elements (`br`, `hr`, `wbr`, `col`, `source` and the like) with mode 1, `input` with mode 2 and the `style` element that React writes where it is, as emotion's are, with mode 3. The bundle asks only when `__tifa_start_tag.length` is 7 or more, since an engine without modes would write a void element as a generic one, and an engine declines a mode it does not know, so React writes the tag. The engine writes the whole start tag as one string, with the text of a child that is a string, the same text React pushes in pieces. For an element where it cannot be sure to write what React writes, it hands back a mark and changes nothing, and React writes the tag: props or a style that are not plain objects, a getter, `dangerouslySetInnerHTML`, a rare attribute (`xlinkHref`, `capture`, `download`, `cols`, `rows`, `size`, `span`, `rowSpan`, `start`), a value React turns into a string by calling its `toString`, a `javascript:` URL, and a page that replaced `Array.prototype.push` or `hasOwnProperty.call`. On the pages of the shop, the MUI test app, the bench app and the extreme app, the engine writes all 469,530 start tags and leaves none to React, with the same HTML. A render of every page of an app runs 10.1% fewer instructions on the shop's workbench pages, 9.6% on its storefront pages, 5.7% on the MUI pages and 31.9% on the bench pages, and takes 7.9%, 7.5%, 4.4% and 32.0% less time (callgrind, and one VM on one core with its hyperthread sibling idle, 16 code positions, 2 rounds, linux/amd64, AMD EPYC 7B13, no PGO). The engine alone, with the plugin not writing the calls, is within 1% of the time on the shop and MUI pages (0.5% to 0.7% faster) and on the bench pages 1.6% slower at the formal layout and 0.2% slower averaged over the layouts, inside the delta. The C functions were written from the text of React DOM 19.3, so the plugin changes the two calls only when each of the 29 parts they stand for has the fingerprint it has in 19.3.0 and 19.3.1 (`reviewedEmitPieces`): `pushStartGenericElement` with every function, cache and table it uses on the way to the tag, `endChunkForTag`, and the two functions that make the calls. With another React DOM the build prints a warning that names the parts, and React writes every tag (see [Reviewing a new React](#reviewing-a-new-react)). A VM without the functions also renders as before. The other changes to `pushAttribute` above still apply to the tags React writes.
  - In a server render, `useCallback` makes a new function on every call, which only returns the callback, and hands it to `useMemo`. The plugin adds `tifaUseCallback`, a copy of `useMemo` that keeps the callback itself where `useMemo` keeps what the function returns, and makes `useCallback` call it. The callback a component gets, the reads of its dependencies and the errors are the same: the tests compare renders again with dependencies that stay, change, change length, are missing or `null`, compare with `Object.is`, or are read through getters, and hooks that change order between two renders. A stack trace of an error thrown while the dependencies are compared names `tifaUseCallback` where it named `useMemo`. A render runs about 0.6% fewer instructions on the shop's workbench pages, 0.5% on its storefront pages and 0.40% on the MUI test app, with the same HTML. When `useMemo` or `useCallback` differs from React DOM 19.3's, the build prints a warning and `useCallback` stays as it is.
- React's `createElement` and `cloneElement` copy the keys of their config into the props of the element with a loop, and each key costs about 250 ns in beastjs (a pass of `for in`, a call of `hasOwnProperty.call` and a set). A render makes 1,500 to 3,400 elements through them on the example app and the MUI test app. beastjs has that loop written in C (`VM.RegisterCopyProps`), and `ssr.Load` gives every VM of the pool it as `__tifa_copy_props`. The plugin makes both functions read `config.key`, as the head of the loop does, and then ask it. It answers `true` when it copied the config and `false` when it changed nothing, and then React's own loop runs, as it does in a VM that has no such function. It copies a config only where the loop cannot do otherwise: an ordinary object whose prototype is `Object.prototype`, with at most 32 own keys, none of them an array index, `__proto__` or `stack`, and a plain value on every key the loop reads, into props of the same kind, while `Object.prototype` has no setter or read-only property and `hasOwnProperty.call` is the built-in. A proxy, an array, a class instance, an object without a prototype, a getter on a key the loop reads, and a page that gave `Object.prototype` a setter after React loaded all go through the loop, so the key, the props with their order and attributes, the errors and every read and call a page can see are what React makes. The plugin changes a function only when its whole text is the one of React 19.3, and only its loop. When anything in the function differs, the build prints a warning with the version of React and the file, and that function keeps React's loop. Each line stays where it was. On the example app a render runs 2.9% fewer instructions on the shop's workbench pages, 2.1% on its storefront pages and 4.1% on the MUI test app, with the same HTML, and the pages take 0.988, 0.989 and 0.980 of the time (linux/amd64, 8 code positions, a change smaller than the 2.7% to 3.9% by which the code positions of one build differ, so the instruction counts carry it). Without this change pages render as fast as before.
- React's `jsx` and `jsxs` make the element of every JSX tag your components and most libraries write. In production the two are one function, and it returns an object of five fields: `$$typeof`, `type`, `key`, `ref` and `props`. A call takes about 34 steps of the interpreter in beastjs, and one pass over the six workbench pages of the example app runs 14,446 of them. When the config is an object literal, the plugin writes the call as the object it returns: `jsx("div", { className: "a" })` becomes `{ $$typeof: Symbol.for("react.transitional.element"), type: "div", key: null, ref: null, props: { className: "a" } }`, with the symbol taken once in a variable before the first statement of the bundle. It does this in the SSR bundle only, before the minifier, and only for a call whose config has no `...spread`, no computed name and no property named `key`, `ref` or `__proto__`, which `jsx` would copy, read or treat apart, and whose third argument, the key, is missing, a string or a number, or a plain variable. A variable key is written `(void 0 !== key ? "" + key : null)`, as `jsx` turns it, so `undefined` is no key and `null` is the key `"null"`. A key that is a member, a call or another expression, a variable that the config assigns to, a config that is a variable and a call with a spread or a `ref` stay calls. On the example app that leaves 85% of the 2,559 calls of the workbench and the storefront as objects, 69% of the 627 of the MUI test app and 88% of the 59 of the bench app, and in one render of a page 60% of the calls of the workbench, 78% of the storefront, 43% of the MUI pages and 84% of the bench pages. The plugin finds the calls by the variable that holds the module `react/jsx-runtime` in the bundle, and it does this only when the file `react/cjs/react-jsx-runtime.production.js` has the pieces of React 19.3.0 and 19.3.1 and nothing else can touch them: the declaration of the symbol for elements, the function `jsxProd` and the two statements `exports.jsx = jsxProd` and `exports.jsxs = jsxProd`, each known by a fingerprint of its structure. The symbol and `jsxProd` are set once and never again, and the top of the file holds only a directive, function declarations, variables with no value, a literal or `Symbol.for("a string")`, and one `exports.name = value` statement for each name. A call, a condition, a loop, a destructuring or `delete` of `exports.jsx`, an update, a use of `module`, `arguments` or a top-level `this`, or `exports` given to a function, has the file keep the calls. A comment, the Fragment symbol, a new function or a new export elsewhere in the file does not matter. With a file that differs, the build prints a warning that names the pieces or says what it found, and the calls stay, since a later React may add a field to the element or change how a key turns into a string. The objects have the same fields in the same order with the same attributes, and a page sees the same reads and calls. Two differences remain, both of programs no page is: `jsx` reads `key` and `ref` of the config through its prototype, so a page that sets `Object.prototype.ref` or `Object.prototype.key` sees it in the element `jsx` makes and not in the object, and a variable key turns into a string before the values of the config run, where `jsx` does it after, which shows only when turning the key into a string runs code or throws and the config runs code too. The change keeps every line in the bundle where it was. The bundle grows by 4.5% (1.51 MB to 1.58 MB on the shop). A render runs 1.6% fewer instructions on the shop's workbench pages, 1.0% on its storefront pages, 3.0% on the bench app and 0.5% on the MUI test app, with the same HTML. Timed at 8 code positions on linux/amd64 (one core of an AMD EPYC 7B13, without PGO), the workbench pages take 0.987 of the time, the storefront pages 0.992, the bench pages 0.959 and the MUI pages 0.995. The same bundle timed against itself gives 0.999 over all pages, and the positions of the unchanged build differ by 2.1% to 5.0% on their own. Without this change pages render as fast as before.
- A call of a short function costs a frame, its arguments and a return, about 350 to 400 instructions in beastjs, more than the work of a test, a forward to another call or a few assignments. In the SSR bundle, before the minifier, the plugin writes such a call as the body of the function. It reads the shape of the function and of the call and knows no library or name, so it treats your code and every package alike. A function counts when its name is set once (a declaration, or `const f = function () {}` or an arrow), it is not async or a generator, its parameters are plain names, and its body has at most 64 syntax nodes and is one expression, a few expression statements, or expression statements and ifs that end in a return or a throw on every path, which become a sequence and a conditional expression. A `throw` becomes a call of `tifaThrow`, a function the plugin adds at the end of the bundle when a call needs it (a bundle that already has a top-level `tifaThrow` that only throws its argument, as the host script has, uses that one, and any other `tifaThrow` keeps every body that throws as it is), and a body that only throws keeps its calls. The body must not use `this`, `arguments`, `super`, `new.target`, a private name, a nested function or class, or the function's own name, and no code may call the function with `new` or read its `prototype`. A call `f(...)` is written out when it has no spread and no `?.`, when every name in the body means the same at the call (no variable, parameter, catch variable or class there hides it), when the call is not in the default value of a parameter, when a function that a variable holds is called only where its declaration has surely run (in the rest of the list of statements that holds it, also inside a function of the module that is used only there), when no argument is a name that no declaration gives, and when each argument is worked out as often and in the same order as before. An argument that is a value that cannot throw (not `+1n`), or a name that nothing sets again and that is surely set (a `var`, `let`, `const` or `class` before its statement is not, nor is a parameter in the default value of an earlier one or a binding of a catch pattern before it, nor a `var` that a loop sets), may be used any number of times. A template, a computed name and `+` convert their values when the next one is worked out, which counts as an effect. Any other argument must be used exactly once, not in a branch, in the order of the arguments, and until it is used the body may only use parameters, compare with `===` or `!==`, and read names of the module that nothing sets again and that are surely set at the call. A property may be a getter or one that the argument sets, and a name from outside the module is a property of the global object, so a read of either before an argument with effects keeps the call, as does a call, a conversion or an assignment. A parameter that is called keeps an empty `this`, as in `(0, o.m)(v)`, and so does a value that is called, or that `typeof` or `delete` takes. An argument that is a function or class with no name is written `(0, …)`, so it does not take the name of the property or variable it lands in. A call at the start of a line that the line before may run into, such as one after an object literal with no semicolon, stays, and so does a body with a shorthand `__proto__`. A call in an argument or in a body is written out in a second round. The lines stay where they are, so the source map fits, and the functions stay with their `name`, `length` and `toString`. The plugin then reads the new code and compares the names that no declaration gives with those before: if they differ, the code stays as it was and the build prints a warning. It also keeps calls of functions that use a stand-in of a Node module (see below), since the error of a stand-in names the place that called it. An error that a written-out body throws shows the place of the call, one frame less in the stack. On the example app it writes out 1,366 calls in the SSR bundle of the shop, 740 in the MUI test app's and 268 in the bench app's, and the bundles grow by 1.0%, 1.1% and 0.8%. A render runs 0.63% fewer instructions on the shop's workbench pages, 2.63% on its storefront pages (0.32% to 0.63% on four of them, 6.2% on the journal page, which renders Markdown), 1.58% on the MUI pages and 0.83% on the bench pages, with the same HTML. The pass adds about 0.9 s to the build of the shop, 0.4 s to that of the MUI test app and 0.2 s to that of the bench app. Writing out also the bodies with expression statements before their return or an if that throws, with up to 64 syntax nodes in place of 32, takes the shop's bundle to 1,658 calls written out, was 1,366, and runs 0.66% fewer instructions on its workbench pages, 0.29% on its English storefront pages and 0.77% on the MUI pages, with the same HTML. - Most component libraries import React as a namespace, as in `import * as React from 'react'`. React and React DOM are CommonJS modules, and rolldown gives such an import their exports through `__toESM`, which defines a getter for each export. Each `React.createElement` or hook call through the namespace then calls a getter, which is slow in beastjs. React and React DOM set their exports once, when their modules run, and never change them, so the plugin gives these imports a namespace of plain values instead: the same values, prototype, names and enumerability. The namespaces of other packages keep their getters, since a package may change an export later and its importers must see the change. For the same reason, if a library changes a property of the exports of `require('react')` after an ES module imported React, that module does not see the change. React itself never does this. The plugin makes this change after rolldown wrote the bundle and before it is minified, and finds rolldown's helpers and calls by the form rolldown writes them in. When that form is another, the build prints a warning that names the packages and why, and pages render as fast as before. The change keeps every place in the bundle where it was, so the source map stays right.

For each variant it read `variant.props` three times and each value of it twice. The plugin reads `variant.props` once and each value of it once, and keeps the `for in` loop over the same object, so the same keys come in the same order, the inherited ones too. `props.ownerState` is read where it was, only when the value of `props` does not match, so a value that matches directly never reads it. One difference is known and no real app has it: a getter or a `Proxy` on `variant.props` that answers differently when asked twice, or has an effect, sees one read of each value, made before the read of the value in `props`. The plugin changes both createStyled files (`createStyled.mjs` and `createStyled.js`) only when the whole function is the text it knows, white space aside: a change to any line of it leaves it as it is. The tests render components whose styles and theme have variants that match by props, by `ownerState`, by a function, by nothing, by a value that is `undefined`, `null` or `NaN`, and through an inherited or a hidden key, with an `ownerState` that throws when read beside a prop that matches directly, in both files, and compare with the unchanged code. The MUI test app's pages run 0.3% to 0.6% fewer instructions, with the same HTML. Together the three changes run 2.5% to 3.2% fewer instructions on the MUI pages (2.9% fewer over the three), and the shop's pages, which have no MUI or emotion, get the same bundle. When the function is not the text the plugin knows, the build prints a warning and the file stays as it is.
- MUI's components make much of their style with `memoTheme` of `@mui/system`, which keeps those styles as long as the theme is the same object. On the server `ThemeProvider` spreads the theme into a new object on every render, so the MUI test app made 107 such styles again on each render of its three pages. The plugin changes `memoTheme.mjs` and `memoTheme.js` of @mui/system 6.1 to 9.5 (`esm/memoTheme.js` and `modern/memoTheme.js` up to 7), which all have the same function: a theme that is a plain object (its prototype is `Object.prototype`, as MUI makes every theme) counts as the first such theme it saw with the same own keys in the same order, each a plain value with the same enumerability and the same value. A theme of any other prototype stands for itself, as before, since its prototype may have getters that read something of each theme. `ThemeProvider` builds such a theme on each render from the same objects, so the styles of the first render are taken again. Each VM keeps the last 8 themes it saw. A theme with a getter or with a changed, added or removed key makes the styles again, as does a theme of CSS variables (`cssVariables: true` or `colorSchemes`), for which `ThemeProvider` makes new objects inside the theme on every render. The plugin counts on what MUI already asks: that the app does not change a theme or the objects in it after a render used them. It compares only the top level of a theme. If the app changes an object inside a theme that a render used, such as setting `theme.palette.primary.main`, and then passes a new theme object that holds the same objects, the pages keep the styles from before the change. To change a theme, make a new one, for example with `createTheme`, so that its top-level values are new objects. The MUI test app makes each of these styles once per VM, and its pages take 0.917 of the time and run 9.3% fewer instructions on linux/amd64, with the same HTML. Apps without MUI get the same bundle. When a release changes `memoTheme`, the build prints a warning and the styles are made on every render as before.
- The minifier writes `if (a) b` as the statement `a && b`, and `a || b` and `a ? b : c` as statements too, and `true` as `!0`. beastjs compiles such a statement to a copy of the value and a drop on each path, and `!0` to a push and a negation, where an `if` statement and `true` take a jump or one push. After the minifier has run, the plugin turns each of these statements in the SSR bundle into an `if` statement, splits a statement that joins several with commas, and writes `!0` and `!1` as `true` and `false`. The operands keep their order, comments and lines, so nothing evaluates differently, and `ssr.js.map` is shifted to fit, so the places in error stacks stay those of the source. Statements in parentheses, a branch that starts with `{`, `function`, `class`, `async` or `let`, and `??` stay as they are. The browser bundle is not changed. The pages of the MUI test app take 1.1% less time to render and the shop's about 0.6% less, with 2.5% to 3.7% fewer instructions run by the engine and the same HTML. The build fails with an error if the changed bundle does not parse.

## Reviewing a new React

React DOM 19.3.0 and 19.3.1 are the versions of which the plugin has read every function. With a release in which any function, variable or statement of `react-dom/cjs/react-dom-server-legacy.browser.production.js` differs, the build prints `tifa rewrite not recognized: ... N parts the tifa plugin has not read: ...` and leaves the names of components and the key paths in. Pages render the same and take longer. To make the change work with the new release:

1. Install the release in `internal/bundle/testdata` (`pnpm add react@<version> react-dom@<version>`) and run `TIFA_REACT_UNITS=1 go test -run TestListUnreviewedReactDOMUnits -v ./internal/bundle`. It prints each part that is not in the table (`reviewedReactDOM`, at the end of `js/vite/plugin.js`), as `new` or `changed`, with its lines in the file, and the table lines to add. A release that changes little prints a few parts.
2. Read only those parts. For each ask: does it read, store, copy, enumerate or compare a key path (`task.keyPath`, `contentKeyPath`, a variable that holds one, the `task` object itself), and does it still work when `task.keyPath` is `null` and the name of the component is `null`? The comments on `dropKeyPaths` and `dropKeyPathNames` in the plugin say what the two changes assume.
3. Check that the places `dropKeyPaths` and `dropKeyPathNames` change are still in the form they expect, and the counts the plugin keeps as a second guard (`keyPathUses`, `keyPathReaders`). The build warns when they are not.
4. Add the printed lines to `reviewedReactDOM`, run `go test ./internal/bundle` and `TIFA_E2E=1 go test -timeout 30m ./test/e2e/`, and name the version in this section and in the bullet on key paths above.

The weekly job `latest-react` (see [Testing](testing.md#ci)) installs the latest React and prints the same list in its log under `parts of react-dom <version> to read`, so the reviewer finds the parts to read in the log. With `TIFA_REACT_UNITS=all` the test lists every part, which is how the table was first made.

The start and end tags that the engine writes have a table of their own, `reviewedEmitPieces` in the plugin: the 29 parts of React DOM that the C functions of beastjs do the work of. When a release changes one of them, the build prints `... parts that differ from those the engine's start and end tags were written from: ...` and React writes every tag. Pages render the same and take longer. The list above names these parts on a line of their own, which the `latest-react` job prints too. To turn the engine's tags back on:

1. Read each changed part against `RegisterStartTag` and `RegisterEndTag` of beastjs and their C functions. What the new code does differently, the C function must do too, or hand such an element back to React. That is a change and a release of beastjs.
2. Put the new fingerprints of those parts into `reviewedEmitPieces`. The lines the test prints for `reviewedReactDOM` have them.
3. With the new beastjs, run `go test ./internal/bundle` and `TIFA_E2E=1 TIFA_EXTREME=1 go test -run TestEngineTagsAreReacts -v ./test/e2e/`, which compares the engine's tags with React's on every page of the example apps (see [Testing](testing.md#end-to-end-tests-teste2e)).

## The i18next cache

The cache is described for app authors in [i18next cache](../reference/i18next.md#i18next-cache). These are the rules inside it and what it gained.

A call is looked up by the i18next instance, the language, namespace and key prefix of `t`, the language of the instance when `t` has none, the key, the `interpolation.defaultVariables` of the instance, the `formats` of an `i18nFormat` module such as i18next-icu, and the options of the call. Only calls whose key and options are strings, numbers, booleans, `null`, `undefined` or arrays of strings, in a plain object without Symbol keys, are kept. Everything else translates as before:

- a key or option that is a function or an object, such as `replace`, `formatParams` or a `Date`
- a result that is not a string (`returnObjects`, `returnDetails`)
- a call during which i18next logs something, as it does for each missing key. So a missing key reaches `missingKeyHandler`, the `missingKey` listeners and the logger on every call. i18next 27 writes a few warnings only once for each instance, and only with `debug` on, such as the name of a post-processor nobody added. The call that writes one is not kept, and the calls after it, which write nothing in i18next either, are.
- every call of an instance made with `cloneInstance`, of an instance with a `missingInterpolationHandler`, and of an instance with a formatter module of its own (`use({ type: 'formatter' })`)
- the `t` of the instance itself (`i18n.t`), which `Trans` uses unless it gets a `t`

The cache empties when the app changes what a translation it holds depends on through i18next's API: `addResource`, `addResources`, `addResourceBundle`, `removeResourceBundle`, `init` again, `loadNamespaces`, `loadLanguages`, `reloadResources`, `setDefaultNamespace`, `use`, `hydrate` (i18next 27), a formatter added to an instance whose translations it holds, and a post-processor. Up to i18next 26.5 a post-processor belongs to all instances, so adding one empties the whole cache. In i18next 27 it belongs to the instance `use` was called on, and `use` empties the cache when that instance held strings. `hydrate` always empties it, since it adds namespaces to the `ns` array, which instances made from one options object share. A backend such as i18next-http-backend adds what it loads with `addResourceBundle`, so loading empties the cache too. `changeLanguage`, `cloneInstance` and a new instance keep it, since the language is part of each entry and the entries of each instance are its own. The strings an instance kept go when the instance does, so an app that makes an instance for each request does not fill the cache with strings no later request finds. It holds at most about 1 MB in each VM, counting two bytes for each character of a key or string and 80 bytes for each entry, and starts over empty when the next string would not fit.

A key whose calls the cache seldom answers, such as one that gets a user's name in its options, stops using the cache once its calls have missed 64 times more than four times they found their string. It then tries the cache again for one call in 33, and uses it again once those calls find their string. Its other calls cost what they cost without the cache, apart from one lookup of the key.

Most of what a call is looked up by is the same from one call to the next: the instance, the language, namespace and key prefix of `t`, `defaultVariables` and `formats`. The cache reads them on every call as before, but builds the part of the lookup they make only when one of them is not what it was on the call before (compared with `Object.is` written out in place), and a call with a key and no options is looked up by its key alone. The shop's storefront pages run 0.43% fewer instructions than when each call built its whole lookup.

On the shop, which uses the one instance of the adapter and gives it formatters of its own for money and dates in `setup.ts`, the ten storefront pages take 0.778 of the time to render (0.774 to 0.783), each page 0.709 to 0.917, with the same HTML. The same pages, with i18next used the other ways apps use it:

| How the app uses i18next | Time of the ten pages |
| --- | --- |
| One instance for each language | 0.765 (0.757 to 0.773) |
| `cloneInstance` on each request, as i18next-http-middleware does | 1.001 (0.997 to 1.004) |
| A new instance on each request | 0.916 (0.908 to 0.924) |
| A value that changes on each render, such as a counter, in the options of every call | 0.912 (0.904 to 0.921) |
| The same with a value of 400 characters, so the cache fills its 1 MB and starts over | 0.924 (0.918 to 0.930) |

The workbench pages, which do not translate, take 1.000 (0.997 to 1.003). After the storefront pages have rendered again and again, a VM of the shop holds about 0.2 to 0.4 MB more than without the cache, and about 2 MB more when every call carries a value that changes on each render. [Optimizations](../studies/optimizations.md#build) has how these were measured.

The cache works the same on i18next 27 as on 26. In one VM with one instance, a call that finds its string took 0.95 µs on i18next 27.0.1 against 14.7 µs without the cache (0.96 µs and 14.1 µs on 26.5.3), and a call that missed took 0.5 µs more (0.6 µs on 26.5.3). The tests compare the translations with and without the cache on both versions. The ratios of the shop's pages above were measured on i18next 26.5.3 and not measured again on 27.

## The host script

`runtime/host.js`, the script that adds what beastjs lacks (see [The SSR bundle](../reference/build-output.md#frontend-output)), is prebundled from `js/host/host.ts` by `go generate ./js` and checked in. Its dependency versions are locked in `js/host/package.json` and `pnpm-lock.yaml`. To upgrade, run `pnpm install --frozen-lockfile` in `js/host` (or `pnpm install` after changing versions), then `go generate ./js`. `TestHostScriptIsUpToDate` in `internal/bundle` checks that the regenerated result matches the checked-in file, and skips when `js/host/node_modules` does not exist. `abort-controller` and its dependency `event-target-shim` are patched (`js/host/patches`, registered in `js/host/pnpm-workspace.yaml`): each object keeps its internal state in a symbol property on the object itself instead of a WeakMap. The property is defined once when the object is created and never redefined, so cancellation still works when the app seals or freezes a signal (`TestHostScriptAbortsFrozenSignals`). The only state that changes later, the signal's aborted flag, lives in a box, and only the value in the box changes. The rest of the state is not boxed: boxing every piece of state adds about 1.5 ms to P99. beastjs needs several GC rounds to collect dead cycles that pass through WeakMap values, and some cycles are never collected. So the routes, AbortControllers and listeners left by each render waited several GC rounds, and the VM heap grew. With properties, one GC collects them all at once, and `TestHostScriptFreesDeadAbortSignalsInOneCollection` guards this.

## Upgrading TanStack Router

The tested pair is `TestedReactRouter` and `TestedRouterCore` in `internal/bundle/tanstack.go`. Change them, the version in every `package.json` that pins the router (`examples/shop` and the apps under `test/apps`, with `pnpm install --no-frozen-lockfile` in each), and run these tests:

- `TestTanStackMembersStay` (`internal/codegen`) builds a server router and a browser router the way the runtime does and checks that every member of TanStack Router that Tifa uses and TanStack does not document for apps is still there. Each failure says what member is gone, what in Tifa breaks and which file uses it. When one fails, read the new TanStack source for that member, then change the runtime in `js/runtime` to the new way, or to a public interface if there is one now. Do not make the check pass by loosening it.
- `TestTanStackCopiesAreUnchanged` (`internal/bundle`) hashes the pieces of TanStack source that Tifa keeps its own copy of, in the packages of `test/apps/pages`, against the hashes in `internal/bundle/tanstack_copies.go`. Each entry says whether it hashes a whole file or one function and which Tifa function to compare again. When one fails, read the diff of that source between the two versions, change the Tifa copy if the behavior changed, and then put the new hash in the table. A hash that is updated without that read guards nothing.
- `TestGeneratedRouterIDsMatchGo` (`internal/codegen`) checks that the route IDs TanStack builds are the ones Go computed.

Then run the router tests and the SSR tests in `internal/bundle`, build `examples/shop` and run its SSR test, and run `go run ./test/compare/cmd/compare deps` if the shop changed.

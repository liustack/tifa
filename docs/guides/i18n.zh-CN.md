# 多语言站点 {#a-site-in-several-languages}

你有一个站点，希望每个访客都用自己的语言来读。做完之后，每种语言有自己的 URL，界面文字被翻译，每个页面在 `<html lang>` 里写明自己的语言，搜索引擎拿到把一个页面各个版本联系在一起的 `hreflang` 链接。

带有 `_locales` 文件夹的文件夹就是多语言的。声明就这么多：Go 里没有语言列表，没有路由常量，文件夹名里也没有语言参数。下面的代码来自 [test/apps/i18n](../../test/apps/i18n)，[examples/shop](../../examples/shop/app/store) 里的店面是一个大的、可运行的版本，默认语言是英文。每项设置的参考见 [config.md](../build-and-deploy/config.zh-CN.md)，Tifa 生成的文件见 [build.md](../build-and-deploy/build.zh-CN.md)。

## 添加语言 {#add-the-languages}

在要支持多种语言的文件夹里放一个 `_locales` 文件夹，每种语言一个 JSON 文件。一个中英文的店面，以中文为默认：

```text
app/
  store/
    _locales/
      zh-CN.json
      en-US.json
    page.tsx             /store and /en-US/store
    cart/page.tsx        /store/cart and /en-US/store/cart
    mine/route.go        /store/mine and /en-US/store/mine (an API route)
  projects/page.tsx      /projects only
```

带有 `_locales` 文件夹的文件夹是一个区域，它的语言就是它的 `<language>.json` 文件的名字。区域里以及它下面的每个页面和 API 路由，都以这些语言提供。在所有区域之外的路由没有语言，只有一个 URL。把 `_locales` 放在 `app/` 本身里，整个站点就是一个区域。嵌套在另一个区域下面的区域，对它自己的路由，会替换上层文件夹的语言。

区域里的 API 路由也在每个前缀下提供服务，比如 `/api/issues` 和 `/en-US/api/issues`。这是有意的：处理函数用调用它的页面的语言来回答（`c.Language()`），Tifa 生成的函数用当前前缀调用它。要让一个 API 只在一个 URL 下提供服务，就把它放在所有区域之外，也就是上面没有 `_locales` 的文件夹里。当 `_locales` 在 `app/` 本身里时，每个文件夹都在区域里，所以给 API 文件夹单独一个区域，里面只放默认语言的文件：`app/api/_locales/zh-CN.json`（以 `zh-CN` 为默认）会让 `app/api` 和它下面的一切只在 `/api/...` 下响应，别处没有。

页面也可以这样。你不翻译的文件夹，比如有两种语言的站点里的员工区域，也单独有一个区域，只有一个文件，就是默认语言的（`app/staff/_locales/en-US.json`，内容是 `{}`）。它的页面只在一个 URL 下响应。默认语言的前缀会重定向（308）到它，任何其他语言的前缀是 404。

文件名必须是常见写法的语言标签：`en-US`，不是 `en_US` 或 `en-us`。然后在 `tifa.yaml` 里写明默认语言和站点的地址：

```yaml
i18n:
  default: zh-CN
site:
  url: https://shop.example.com
```

站点只有一种语言时，`i18n.default` 可以不写。有多种语言时，它必须是其中之一，而且每个区域都必须有它的文件。`site.url` 是站点所在的协议和主机，不带路径。`hreflang` 链接需要完整的它，而从请求猜出来的地址，在 CDN 后面会出错。两者都只是项目文件里的设置，和 `build.*` 一样。

## URL {#the-urls}

默认语言没有前缀。其他每种语言是路径的第一段：

| URL | 响应 |
| --- | --- |
| `/store/cart` | `zh-CN` 的页面，也就是默认语言 |
| `/en-US/store/cart` | `en-US` 的页面 |
| `/zh-CN/store/cart` | 308 跳到 `/store/cart` |
| `/en-US/projects` | 404：`/projects` 在所有区域之外，所以它没有 `en-US` |
| `/fr/store/cart` | 404，因为店面没有 `fr` 文件 |

每次重定向都会保留查询。带语言前缀的 URL，就是路由之后一切环节所用的 URL：渲染记忆 memo、ETag、重定向和 CDN 保存的副本，都按带前缀的 URL 工作，所以同一个路径的两种语言绝不会共用一个条目。

设置 `i18n.prefix: always` 会让默认语言也出现在 URL 里。这样 `/store` 会以 308 跳到 `/zh-CN/store`。在所有区域之外的路由保持原样。

```yaml
i18n:
  default: zh-CN
  prefix: always
```

构建会拒绝两件事：`app/` 的顶层文件夹的名字和站点的某种语言相同（`app/en-US/` 会是那种语言的 URL 的第一段），以及在 `documentHead` 或 `head` 的 `htmlAttributes` 里写语言，因为 Tifa 自己写 `<html lang>`。

## 代码里的语言 {#the-language-in-code}

在 Go 里，`c.Language()` 给出正在响应的路由的语言。它在 `Load`、`Layout`、方法处理函数和 API 路由里都能用：

```go
// app/store/route.go
func Load(c *tifa.Ctx) (Data, error) {
	return Data{Language: c.Language(), Q: c.Query("q")}, nil
}
```

在 React 里，`tifa/client` 的 `useLanguage()` 给出同样的东西：

```tsx
import { useLanguage } from 'tifa/client'

const language = useLanguage() // "zh-CN" or "en-US"
```

在有多种语言的站点上，处于所有区域之外时，两者都给出默认语言。在没有语言的站点上，它们给出 `""`。Tifa 为区域里的处理函数生成的函数，用当前前缀来调用 URL，所以 `c.Language()` 在处理函数里和在调用它的页面里是一样的。

在测试里，`tifatest.NewCtx` 的 Ctx 带有请求路径的语言：`httptest.NewRequest("GET", "/en-US/store/mine", nil)` 给出 `en-US`，没有前缀的路径给出默认语言。

## 翻译界面 {#translate-the-interface}

核心没有翻译库。Tifa 为 [i18next](https://www.i18next.com/) 和 react-i18next 提供了一个适配器，在 `tifa/i18n` 里。两个都要装：

```sh
pnpm add i18next react-i18next
```

当站点有多种语言、`package.json` 又列出了 `react-i18next` 时，Tifa 会把适配器写进 `.tifa/`。`tifa new` 生成的 `tsconfig.json` 已经映射了 `tifa/*`，其中就包括 `tifa/i18n`。

字符串是嵌套的 JSON，每种语言一个文件：

```json
{
  "title": "Store",
  "cart": { "title": "Cart", "items_one": "{{count}} item", "items_other": "{{count}} items" }
}
```

区域的命名空间是它相对于 `app/` 的文件夹：`app/store/_locales` 是 `store`，`app/admin/store/_locales` 是 `admin/store`，`app/_locales` 是默认命名空间。在根布局里，只一次，用 `I18nProvider` 包住页面：

```tsx
// app/layout.tsx
import { Outlet } from '@tanstack/react-router'
import { I18nProvider } from 'tifa/i18n'

export default function Shell() {
  return (
    <I18nProvider>
      <Outlet />
    </I18nProvider>
  )
}
```

然后用通常的 hook 翻译：

```tsx
// app/store/cart/page.tsx
import { useTranslation } from 'tifa/i18n'

export default function Cart() {
  const { t } = useTranslation('store')
  return <h1>{t('cart.title')}</h1>
}
```

在组件之外，比如路由的 `head` 里，用实例来翻译：`i18n.t('store:cart.title')`，`i18n` 来自 `tifa/i18n`。在那里它也是页面的语言。

每种语言都和应用一起打包，所以服务端渲染和浏览器都有全部字符串，不用取任何东西。像金额这样的 formatter 放在应用根目录 `setup.ts` 的顶层，它在服务器上和浏览器里都在第一次渲染之前运行（见 [setup.ts](../pages-and-data/hooks.zh-CN.md#setupts)）。formatter 拿到的语言是 `lng`，所以一个 formatter 服务所有语言：

```ts
// setup.ts
import { i18n } from 'tifa/i18n'

i18n.services.formatter?.addCached('currency', (lng, options) => {
  const f = new Intl.NumberFormat(lng, { currency: 'USD', ...options, style: 'currency' })
  return (value) => f.format(value)
})
```

自己把语言传给 `Intl` 调用，这样服务器和浏览器输出的文字就一样（见 [格式化要让水合一致](../pages-and-data/server-render.zh-CN.md#formatting-so-hydration-matches)）。服务器会保存它翻译出的字符串，所以对同样的语言、选项和值，formatter 必须给出同样的文字，React 组件也是这样要求的：把时间或请求里的任何东西放进 `t` 的选项里，不要放进 formatter。更多见 [i18next 适配器](../build-and-deploy/build.zh-CN.md#the-i18next-adapter)。

某个区域在某种语言里没有字符串，也仍然需要它的文件：写 `{}`。没有字符串的键会显示键本身。Tifa 不会去别的语言里找。

## 校验消息 {#validation-messages}

`Validate` 方法放在 `tifa.Fields` 里返回的消息，会到达访客，所以它需要访客的语言。有两种办法，一个应用可以两种都用。

**在 Go 里翻译。** `Validate` 可以接收 Ctx，`c.Language()` 是这个调用所用的 URL 的语言：

```go
var nameMissing = map[string]string{"en-US": "Enter your name.", "zh-CN": "请输入姓名。"}

func (in SignUp) Validate(c *tifa.Ctx) error {
	fields := tifa.Fields{}
	if strings.TrimSpace(in.Name) == "" {
		fields["name"] = nameMissing[c.Language()]
	}
	return fields.Err()
}
```

区域里生成的函数用当前前缀调用它的处理函数，所以 `Validate` 里的语言就是页面的语言。`tifa.Languages()` 里的每种语言都要有一段文字，并让一个测试遍历这个列表，因为缺了哪个就会给出空消息。在没有语言的站点上，`c.Language()` 是 `""`。

**返回代码，在页面里翻译。** `Validate` 返回一个简短的代码，页面用它已经在用的翻译库把它变成文字：

```go
fields["name"] = "name_missing"
```

```tsx
const { t } = useTranslation('signup')
// fields comes from the TifaError of the call, see the forms guide
{fields.name && <span className="error">{t(`errors.${fields.name}`)}</span>}
```

每个 `_locales` 文件里都要有 `"errors": { "name_missing": "Enter your name." }`。

哪种合适：

- **代码** 适合页面是唯一的调用者、它的文字又已经放在 `_locales` 里的情况。译者在一个地方工作，库处理复数和格式化，同一个代码在两个地方可以有不同的读法。代价是：处理函数的任何其他调用者（API 客户端、脚本）拿到的是代码，页面没有对应文字的代码会显示成键。
- **Go 里的文字** 适合处理函数有其他调用者的情况，因为响应就是他们语言里的一句话，不需要表。它也适合含有只有服务器才知道的事实的消息，比如带着名字的「这个名字已被占用」，以及根本不在页面里翻译的应用。代价是：文字放在 Go 里，和界面的其他字符串分开。

同一个字段不要两种混用，否则页面分不清哪个是代码、哪个是一句话。

## 链接和语言切换 {#links-and-the-language-switch}

写链接时，就当站点只有一种语言：

```tsx
<Link to="/store/cart">Cart</Link>
```

在 `en-US` 文档里，Tifa 会把它变成 `/en-US/store/cart`，并在原地导航。链到区域之外的路由，比如 `/projects`，或者指明了另一种语言的链接，会加载一个新页面，因为一个文档只含一种语言。`navigate`、`Load` 里的重定向，以及内容条目 HTML 里的链接也是如此。这些你什么都不用写。

Go 里的重定向遵循同样的规则：响应 `en-US` 请求的 `tifa.Redirect("/store/cart", 303)` 会跳到 `/en-US/store/cart`。以语言开头的路径，比如 `/zh-CN/store/cart`，会去它所写的地方。

做语言切换时，`tifa/client` 的 `useAlternates()` 返回这个页面每种语言的 URL。用普通的 `<a>` 链接到它们，因为另一种语言是另一个文档：

```tsx
import { useAlternates, useLanguage } from 'tifa/client'

const names: Record<string, string> = { 'zh-CN': '中文', 'en-US': 'English' }

export function LanguageSwitch() {
  const versions = useAlternates()
  const current = useLanguage()
  return (
    <nav>
      {versions.map((v) => (
        <a key={v.language} href={v.url} aria-current={v.language === current ? 'page' : undefined}>
          {names[v.language]}
        </a>
      ))}
    </nav>
  )
}
```

只有一个版本的页面和在所有区域之外的页面，这个列表是空的，所以切换在那里什么也不显示。

这些 URL 没有查询字符串：`useAlternates()` 对 `/store/products?page=2` 和 `/store/products` 给出同一个路径，所以链到它们的切换会丢掉筛选和页码。切换自己加上地址栏的查询，就能保留它们。在 effect 里读它，因为服务器渲染时没有它的 `Load` 不读的参数，渲染时去读会对不上（[服务端渲染里的查询参数](../pages-and-data/ssr-and-cache.zh-CN.md#query-parameters-in-the-server-render)）。比如：

```tsx
import { useEffect, useState } from 'react'
import { useRouter } from '@tanstack/react-router'

// The query of the address bar, such as "?q=shirt&page=2". It is empty on the server and in the
// first render of the browser, and follows every navigation of the router.
function useAddressQuery() {
  const router = useRouter()
  const [query, setQuery] = useState('')
  useEffect(() => {
    const read = () => setQuery(window.location.search)
    read()
    return router.subscribe('onResolved', read)
  }, [router])
  return query
}
```

然后在上面的切换里写 `const query = useAddressQuery()` 和 `<a href={v.url + query}>`，就保留了查询。另一个页面只显示它自己的 `Load` 读取的参数，所以两种语言读取的名字相同时，它的筛选方式也相同。

## 搜索引擎得到什么 {#what-search-engines-get}

在有多个版本的页面上，Tifa 会在 head 里加上：

- 每个版本一个 `<link rel="alternate" hreflang="...">`，包括页面自己
- `hreflang="x-default"`，指向默认语言的版本

每个页面，不管有一个版本还是多个，还会得到一个指向自己的 `<link rel="canonical">`，以及一个 URL 相同的 `og:url` meta（见[搜索引擎](seo.zh-CN.md)）。URL 是完整的，来自 `site.url`。各版本没有查询。canonical URL 保留页面的 `Load` 和布局读取的查询参数，和服务器渲染它时一样（见 [查询参数](../reference/memo.zh-CN.md#query-parameters)），所以列表的第 2 页是它自己的页面。你在自己的 `head` 里写的 canonical 优先于 Tifa 的。404 页面和错误页面没有链接，只有一个版本的页面没有 `hreflang` 链接。

`/sitemap.xml` 每个页面每种语言列一次，带同样的 `hreflang` 链接（见 [搜索引擎和语言模型](seo.zh-CN.md)）。

默认情况下，一个页面存在于它所在区域的每种语言里，路径相同，只是前缀不同，带参数的页面也一样。当页面在另一种语言里有另一个 slug，或只存在于一种语言里时，这就是错的。在它的 `Load` 里用 `c.SetAlternates` 说明。每个路径按访客看到的样子写，已转义，不带前缀和查询，并且包括页面自己：

```go
// app/store/journal/slug+/route.go
func Load(c *tifa.Ctx) (Data, error) {
	slug := c.Param("slug")
	translations, ok := entries[slug] // e.g. {zh-CN, ni-hao}, {en-US, hello}
	if !ok {
		return Data{}, tifa.ErrNotFound
	}
	var versions []tifa.Alternate
	for _, t := range translations {
		versions = append(versions, tifa.Alternate{Language: t.Language, Path: "/store/journal/" + t.Slug})
	}
	c.SetAlternates(versions)
	return Data{Slug: slug}, nil
}
```

hreflang 链接和 `useAlternates()` 都遵循这个列表，所以切换会把 `/store/journal/ni-hao` 链到 `/en-US/store/journal/hello`。列表里没有的语言，就是这个页面没有那个版本。空列表表示这个页面只有一个版本。当某种语言不是页面的语言之一、被列了两次，或路径不是普通的转义路径时，页面会失败，并在日志里留下错误。把同样的列表交给 sitemap，放在页面的 `Alternates` 里，这样它和 head 就一致了（见 [多种语言](seo.zh-CN.md#several-languages)）。

## 每种语言的文章 {#posts-in-each-language}

带 `Languages: tifa.Languages()` 的内容集合，在 `content/` 下每种语言有一个文件夹：

```go
// content.go
var Journal = content.Define[Entry](content.Source{Dir: "journal", Languages: tifa.Languages()})
```

```text
content/journal/
  zh-CN/hello.md
  en-US/hello.md
```

`tifa.Languages()` 是站点的语言，默认语言在最前。在 `tifa build`、`tifa dev`、`go test` 和 `go run` 下它给出同样的列表。用 `c.Language()` 读取条目：

```go
e, err := Journal.Get(c.Language(), "hello")
```

某种语言里缺失的条目，在那种语言里没有页面：`Get` 返回 `tifa.ErrNotFound`，页面是 404，也不会回退到另一种语言。按 `date` 定时发布的翻译，到了那个日期会自己出现。`entry.Translations` 列出现在能看到的版本，条目的页面就是把它传给 `SetAlternates`。其余内容见 [内容](../pages-and-data/content.zh-CN.md)。

在 Markdown 里，把链接写成以根路径开头的路径，比如 `[cart](/store/cart)`。页面有那种语言时，构建会加上条目语言的前缀：`en-US` 条目里是 `/en-US/store/cart`。已经以语言开头的链接保持原样。

## 从 `lang+` 文件夹迁移 {#moving-from-a-lang-folder}

把语言放在 `lang+` 文件夹里、没有 `_locales` 文件夹的应用，照旧能用。要迁过来：

1. 把页面和 `route.go` 从 `lang+` 文件夹挪到它的父文件夹，并在那里把字符串写成 `_locales/<language>.json`。
2. 删掉检查语言的 `Layout`、它 `head` 里的 `lang`，以及手写的 `hreflang` 链接。Tifa 会写它们。
3. 在原来读 `params.lang` 的地方，用 `c.Language()` 和 `useLanguage()` 读取语言。
4. 删掉从 `/store` 按 `Accept-Language` 或 cookie 做的重定向，除非你还想要它：`/store` 现在就是默认语言的页面。

## 你工作的时候 {#while-you-work}

- `tifa dev` 不用重启就能识别新的 `_locales/fr.json`。`/fr/store` 马上就能用。删掉这个文件，它就是 404。
- `fr.draft.json` 不会发布。在文件改名为 `fr.json` 之前，这种语言对站点来说不存在。用它放正在进行的翻译。
- 普通的 `go test` 也能用 `tifa.Languages()`。它读取模块的 `_locales` 文件夹和 `tifa.yaml`。

## 什么会让构建失败 {#what-fails-the-build}

`tifa build` 和 `tifa check` 会停下，给出文件和原因，遇到这些情况：

- 某个区域没有默认语言的文件
- 有多种语言却没有 `i18n.default`，或者它不是任何区域有的语言
- 有多种语言却没有 `site.url`
- 文件名不是常见写法的语言标签
- `_locales` 文件夹里没有语言文件
- `app/` 的顶层文件夹的名字和站点的某种语言相同
- 在有多种语言的站点上，`htmlAttributes` 里有 `lang`
- 内容集合的 `Languages:` 既不是 `tifa.Languages()`，也不是字符串字面量的列表

## Tifa 不做的事 {#what-tifa-does-not-do}

- 它不替访客选语言。没有按 `Accept-Language`、cookie 或地址做的重定向。URL 就是选择，所以每个 URL 对所有人都是同一个页面，搜索引擎能找到它，CDN 也能保存它（见 [给 CDN 用的缓存](../pages-and-data/ssr-and-cache.zh-CN.md#cache-for-cdns)）。如果你的站点想把第一次来的访客送到他们的语言，就在所有区域之外的路由上为它写一个处理函数，并关掉 `Cache`。
- 它不记住这个选择。如果你想记住，就在访客选了语言时，在应用里设置一个 cookie，并在上面那个处理函数里读它。
- 它没有回退语言。缺失的字符串显示它的键，缺失的条目是 404，区域没有文件的语言也是 404。

# 性能

Tifa 在 quickjs 里渲染页面。quickjs 是用 C 写的 QuickJS，编译成 Go 汇编，跑在 linux 和 darwin（amd64 和 arm64）以及 windows/amd64 上。它没有 JIT，所以一次渲染比 Node 慢。这篇文档给出数字和按这些数字怎么配机器。从[哪些改动让它变快](#哪些改动让它变快)起的后半篇是写给维护者的。

quickjs v0.29 换掉了把 QuickJS 从 C 翻译成 Go 的那个引擎。C 引擎渲染 shop、MUI 和 bench 应用的页面，耗时是原来引擎的 0.83 到 0.86（见[引擎](#引擎)）。2026-10-24 的测量（怎么测的、一个页面渲染多快、和 Next.js、TanStack Start 比里的第二张表、随核数怎么扩展、配机器里除内存以外的部分、压缩）用的是 quickjs v0.28.6，也就是原来的引擎，所以其中 Tifa 的耗时现在大约少 15%，每个核的吞吐大约高同样的比例。改版后的商店、和 Next.js、TanStack Start 比里的第一张表、[内存](#内存)、[极端页面](#极端页面)和剖析是用 C 引擎重新测的。

## 一眼看

- **一次渲染**：用 C 引擎之前的引擎，在 shop 的页面上耗时是 C QuickJS 的 0.94 倍，在不用 `Intl` 的页面上是 1.15 倍，是 Node 关掉 JIT 时的约 2 倍，是 Node 有 JIT 时的 6.6 倍。C 引擎只用其中的 0.84 倍时间。
- **整个请求**：在改版后的工作台页面上，单核 Tifa 每秒答 29 个页面请求，Next.js 是它的 2.8 倍，TanStack Start 是 3.6 倍。Next.js 关掉 JIT 后是 Tifa 的 0.85 倍。Tifa 的内存峰值是 54 MiB，Next.js 是 466 MiB。Tifa 一个请求里 95% 的时间是渲染。
- **多核**：4 个物理核答的请求是 1 个核的 3.76 倍。同一个核的第二个超线程忙起来，约多 30%。
- **怎么配**：像 shop 工作台这样的页面，按每个物理核每秒约 73 个请求、约 45 MiB 加每个 VM 12 到 16 MiB 准备。

示例商店在 2026-10-28 改了版，页面变重了。这篇文档里其他数字都是在改版前的页面上测的，只有[改版后的商店](#改版后的商店)里的渲染耗时、内存数字和[和 Next.js 与 TanStack Start 比](#和-nextjs-与-tanstack-start-比)里的第一张表例外。

## 这些数字怎么测的

[哪些改动让它变快](#哪些改动让它变快)之前的数字都是 2026-10-24 在同一台机器上、用同一个构建测的，只有[改版后的商店](#改版后的商店)、[内存](#内存)和[极端页面](#极端页面)除外，它们自己写明了什么时候、用什么测的。

- **机器**：Google Cloud 上一台 8 vCPU 的虚机，AMD EPYC 7B13（Zen 3），Linux。8 个 vCPU 是 4 个物理核，每核 2 个超线程：cpu `n` 和 cpu `n+4` 共用一个核。每次运行先锁住要用的核，等它们空闲 30 秒再开始。别的程序占用不到一个 CPU 的 8%。
- **构建**：Tifa c729ad2，quickjs v0.28.6，Go 1.27.2，按发布时的样子用 `tifa build` 构建。quickjs v0.28.6 把 QuickJS 从 C 翻译成 Go，解释器循环在 linux/amd64 上是 Go 汇编。当时 Tifa 构建时用的剖析（PGO）已经没有了。
- **应用**：[examples/shop](../examples/shop/README.zh-CN.md) 的生产构建，React 19.3 和 TanStack Router，加 Tailwind CSS 和 shadcn/ui。工作台是六个页面：两家店各自的订单列表、一个订单、统计。店面是 14 个页面，两种语言各 7 个，用 i18next 翻译。有些表还渲染 MUI 测试应用（`test/apps/mui`）和 `test/apps/bench` 里不用 `Intl` 的页面。
- **单次渲染**：一个热 VM 跑在一个核的一个线程上，另一个线程空着，渲染方式和 `test/ssr` 的 `BenchmarkShop` 相同。先热 256 次，再测 500 次（工作台）、300 次（店面）或 200 次（MUI），跑 5 轮，取每轮 P50 的中位数。
- **Node**：Node 24.13.0 跑同一份 `ssr.js`，给同样的输入，跑在另一个空闲的核上，先热 600 次，再跑 5 轮、每轮 200 次。HTML 和 Tifa 的相同。
- **C QuickJS**：QuickJS 2026-06-04，由 quickjs 的[引擎对比](https://github.com/liustack/quickjs/blob/main/docs/benchmarks.md)工具构建和运行，用同样的包。C 没有 `Intl`，要用的页面跑 FormatJS polyfill。
- **完整请求**：构建出的 `bin/shop`，用 `SHOP_OPEN=1` 启动（否则工作台要登录），加 `--cache-size 0`，让每个页面请求都渲染（同时到的同一页请求即使这样也共用一次渲染，所以在途请求多时，渲染次数会少于请求数），用 [oha](https://github.com/hatoo/oha) 从别的核上压测。没有另外说明时页面以 gzip 发出。每一档先热几秒，再测 15 到 20 秒，跑两到三轮。

| 店面：商品 | 132 KB | 22.8 | 25.4 | 11.7 | 3.65 |
| 店面：购物车 | 76 KB | 14.1 | 16.0 | 7.27 | 2.38 |

| 店面：手记文章，中文 | 49 KB | 60.9 | 47.3 | 26.7 | 9.86 |

Tifa 的耗时除以对方的，取各页的几何平均（小于 1 就是 Tifa 快）：

| 页面 | 对 C QuickJS | 对 Node `--jitless` | 对 Node 有 JIT |
| --- | --- | --- | --- |
| shop，20 个页面 | 0.94 | 2.04 | 6.58 |
| MUI，3 个页面 | 0.38 | 1.15 | 4.5 |
| `test/apps/bench`，2 个不用 `Intl` 的页面 | 1.15 | 没测 | 没测 |

MUI 几行用 C 引擎重新测过（quickjs 0cc6d332，2026-10-29，同类机器上一个 VM 一个核，8 个代码位置各 3 轮），它们的 C QuickJS 和 Node 两列是 2026-10-24 的。这里其余 Tifa 的数字都是 C 引擎之前的引擎测的，C 引擎渲染同样的页面只用其中的 0.83 到 0.86，而这张表里的 shop 页面在改版后的商店里已经不存在，所以没有重测。

- **和 C 比**：跑一样的 JavaScript（连 polyfill 一起）时，C 引擎之前的引擎在 bench 和 shop 页面上的耗时是 C 的 1.17 到 1.26 倍。Tifa 在多数页面上仍然领先，因为它的 `Intl` 用 Go 写，C 只能跑 FormatJS polyfill，MUI 页面上还因为 Tifa 在 Go 里算 emotion 样式的哈希。手记文章比 C 慢，它们的时间大多花在语法高亮的正则表达式上。C 那一列和它的比值来自 quickjs 的对比工具，工具里 Tifa 的耗时和 Tifa 那一列相差不到 5%。
- **和 Node 比**：差距在 JIT。关掉 JIT，Node 在 shop 上约快 2 倍，在 MUI 上快 1.3 倍。
- **P99**：Tifa 每个工作台页面的 P99 都在 P50 的 11% 以内，因为池在两次渲染之间、响应发出之后才回收垃圾（见[内存](#内存)）。同样的页面上，Node 有 JIT 时 P99 是 5.3 到 20.5 ms，`--jitless` 时是 9.2 到 26.2 ms。
- **第一次渲染**：程序启动后，1 个 VM 时 293 ms 开始监听，2 个时 342 ms，4 个时 413 ms，再过 44 到 46 ms 答出第一个页面，这时就已经是稳定速度。新起的 Node 进程第一次渲染订单页要 55 ms。

## 和 Next.js 与 TanStack Start 比

shop 的六个工作台页面做成三个版本：Tifa，Next.js 16.4.2（App Router，每个路由都是动态的，React 组件相同）和 TanStack Start 1.169.3（路由和 loader 相同），跑在 Node 24.13.0 上。三个版本的可见文本相同，由一个测试检查。每个请求里，两个 Node 应用都跑一份用 TypeScript 移植的 Go 数据加载代码，订单是进程启动时在内存里建好的，和 Tifa 跑 Go 代码一样。第二个测试检查移植的代码返回的和 Go 代码返回的一样，第三个测试在三个服务器里数着，证明每个请求都查了订单、重新渲染了页面。应用在 [test/compare](../test/compare)，怎么构建、检查和再测一遍见[测试文档](testing.md#comparison-with-nextjs-and-tanstack-start-testcompare)（英文）。测的是走 HTTP 的完整请求，六个页面轮流，一次一个，`Accept-Encoding: identity`。测法、全部数字和[还有哪些不对等](studies/nextjs-and-tanstack-start.md#what-is-not-equal)见 [Tifa 对比 Next.js 和 TanStack Start](studies/nextjs-and-tanstack-start.md)（英文）。

2026-10-29 用 quickjs v0.29.0 测，页面是改版后的工作台页面，单核：服务钉在 0 号核，oha 钉在 4 号核，它们是同一个物理核的两个线程（2026-10-24 那次用的是 1 号和 6 号核，不共用物理核）。两轮，每轮新起服务器。

| | Tifa | Next.js | Next.js `--jitless` | TanStack Start |
| --- | --- | --- | --- | --- |
| 每秒请求数 | 28.8 到 29.1 | 80.8 到 82.9 | 24.8 | 102.4 到 105.0 |
| 是 Tifa 的几倍 | 1 | 2.81 到 2.85 | 0.85 到 0.86 | 3.56 到 3.61 |
| P50 / P99 | 28.9 到 29.3 / 66 到 70 ms | 10.4 到 10.5 / 30 到 32 ms | 34.9 到 36.8 / 69 到 72 ms | 7.4 到 7.5 / 28 到 29 ms |
| RSS 峰值 | 54 MiB | 461 到 471 MiB | 301 到 349 MiB | 349 到 356 MiB |

- **分页面看**：Next.js 每秒答的请求是 Tifa 的 2.82 到 3.33 倍，Start 是 3.62 到 4.24 倍。Tifa 渲染第一个店铺的订单列表（42 个订单，223 KB）要 64 ms，其他页面 22 到 36 ms。
- **渲染和其余部分**：六个页面单独测，整个请求的 P50 平均 33.2 ms，同一个页面在热 VM 里不走 HTTP 的渲染平均 31.6 ms。路由、`Load`、JSON、写 HTML 和 net/http 共 1.6 ms，占 5%，分页面是 0.4 到 5.1 ms。Next.js 和 Start 从外面拆不开。
- **数据计算的代价**：当天第一轮里，两个应用是查表拿数据，不自己算，Next.js 每秒 83.5 到 85.0 个，Start 104.7 到 112.0 个。改成自己算以后，它们少了 3% 到 5%。

## 多核怎么扩展

页面轮流请求，gzip，VM 数等于核数，在途请求数等于 VM 数。物理核的意思是每个核只用一个超线程，另一个空着。

| 页面 | CPU 和 VM | 请求/秒 | 是 1 核的几倍 | P50 | P99 | 每个请求的 CPU | RSS 峰值 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 工作台，6 个页面 | 1 个物理核 | 73.0 到 74.4 | 1 | 9.1 ms | 24.9 ms | 13.7 ms | 56 MiB |
| | 2 个物理核 | 141.7 到 145.6 | 1.90 到 1.99 | 9.2 到 9.4 ms | 26.5 到 27.1 ms | 13.5 ms | 70 到 71 MiB |
| | 4 个物理核 | 279.3 到 280.0 | 3.76 | 9.6 ms | 28.5 到 28.8 ms | 13.8 ms | 100 MiB |
| | 1 个核的两个超线程 | 95.2 | 1.30 | 14.0 ms | 39.8 ms | 20.8 ms | 70 到 71 MiB |
| | 4 个核的全部 8 个超线程 | 355.0 | 4.8 | 15.5 ms | 48.1 ms | 20.5 ms | 157 到 158 MiB |
| 店面，14 个页面 | 1 个物理核 | 34.6 | 1 | 21.7 ms | 81.0 ms | | 66 MiB |
| | 2 个物理核 | 67.2 | 1.94 | 23.2 ms | 82.7 ms | | 88 到 89 MiB |
| | 4 个物理核 | 133.0 | 3.84 | 23.2 ms | 85.2 ms | | 129 到 131 MiB |

- 在 4 个物理核以内，吞吐近似线性增长，是 1 个核的 3.76 到 3.84 倍。吞吐跟着单次渲染的时间走：一个请求 13.7 ms 的 CPU 里，HTTP、压缩和其他部分不到 1 ms。
- 同一个核上加第二个超线程，吞吐约多 30%，但每次渲染慢约 1.5 倍，因为两个线程在抢同一个核。
- 混合请求的 P99 由最慢的页面决定：工作台上是订单列表，店面上是英文的手记文章。

## 机器怎么配

### CPU 和 `ssr.vms`

- [`ssr.vms`](config.zh-CN.md#配置项) 保持默认就好。默认值是 Go 看到的 CPU 数（`GOMAXPROCS`），在容器里跟着 CPU 限额走。
- 像 shop 工作台这样的页面，每个物理核按每秒约 73 个页面请求准备，每个请求连 HTTP 约 13.7 ms CPU。店面约 34 个，每个约 29 ms。渲染时间不同的页面按比例换算。
- 云上的一个 vCPU 通常是一个超线程，2 个 vCPU 常常就是 1 个物理核。所有超线程都忙时，每个 vCPU 按约 0.63 个物理核算：6 个忙着的超线程每秒答 276 个请求，每个 vCPU 46 个。这时每次渲染慢约 1.5 倍：P50 是 14.7 ms，物理核上是 9.6 ms。
- VM 比 CPU 多不会多出吞吐，反而让每次渲染变慢。7 个 CPU 上 8 个 VM 每秒答 338 个请求、P50 16.6 ms，7 个 VM 答 334 个、P50 14.7 ms。
- VM 比 CPU 少也没好处：同样 7 个 CPU，4 个 VM 每秒答 235 个、P50 11.9 ms，因为系统仍会把其中两个放到同一个核的两个超线程上。只给程序和物理核一样多的 CPU，两样都更好：4 个物理核上 4 个 VM 每秒答 279 个、P50 9.6 ms。
- cpuset（比如 Docker 的 `--cpuset-cpus`）能把程序钉到每个核的一个超线程上，但管不了别的程序用它们的兄弟超线程。Kubernetes 的 static CPU manager 策略按整核分配，一个核的两个超线程一起给，就是上面超线程都忙的情况。只设 CPU 配额（比如 Docker 的 `--cpus`）时线程不绑核，这种情况没有测过。

只有整页加载才渲染。在浏览器里切换页面取的是 Go 直接写的 JSON，不经过 VM，API 路由和整页缓存（`Cache`，见[应用](app.zh-CN.md#整页缓存)）答出的页面也不渲染。整页缓存连 `Load` 也不跑，还没有测过。渲染缓存对所有页面默认开，写 `RenderCache = false` 的页面除外，命中比渲染快约 80 倍：一个 VM、一个在途请求时每秒 2,865 个请求，渲染是 38 个（见[研究](studies/nextjs-and-tanstack-start.md#cache-hit-against-cache-hit)）。命中时仍然要跑 `Load` 并算数据的哈希，下表里是每个请求 0.15 ms 的 CPU。3 个物理核（6 个超线程）上 6 个 VM，64 个在途请求，gzip：

| 请求 | 请求/秒 | P50 | P99 | 每个请求的 CPU |
| --- | --- | --- | --- | --- |
| 列表的导航数据 | 17,989 | 2.65 ms | 14.4 到 14.9 ms | 0.32 ms |
| 订单的导航数据 | 26,949 | 1.68 到 1.74 ms | 9.7 到 10.0 ms | 0.21 ms |
| 统计的导航数据 | 18,448 | 2.57 到 2.60 ms | 14.0 ms | 0.31 ms |
| 命中渲染缓存的页面 | 37,094 | 1.30 到 1.33 ms | 6.2 到 6.3 ms | 0.15 ms |
| 同一页面回 304 | 36,985 | 1.33 到 1.34 ms | 6.1 到 6.2 ms | 0.15 ms |
| API 用 `PATCH` 改一个订单 | 53,275 | 1.51 到 1.53 ms | 3.5 到 3.6 ms | 0.07 ms |

这些请求的成本很大一块在应用自己：shop 的 `Load` 每个请求都把全部订单复制、排序一遍。`PATCH` 那一行压测工具占满了一个 CPU，可能是被它限住了。

同时没命中缓存的请求共用一次渲染（见 [SSR 与缓存](app.zh-CN.md#ssr-与缓存)），所以冷页面上的突增（比如刚部署完）只花一次渲染，而不是每个请求一次。对一个冷的订单页同时发 50 个请求，每轮起一个新进程，跑五轮：每轮只渲染一次，10 个 VM、8 个 CPU 时 50 个请求在 32.5 到 33.2 ms 内全部答完，2 个 VM、2 个 CPU 时是 30.9 到 38.0 ms。这一次渲染是新 VM 里的第一次，比热的 VM 慢。

### 过载

日常到达率应低于实测渲染容量。接近容量时，渲染时间的小幅变化也会让队列增长。增加超过 CPU 能力的 VM 不能解决持续过载。

默认最多允许 32 次渲染等待空闲 VM，每次最多等 1 秒。队列满或等待超时返回 503，带 `Retry-After: 1` 和 `Cache-Control: no-store`。响应由 Go 写出，不占 VM。这是预期的拒绝，不调用 `OnError`，详见[渲染队列](config.zh-CN.md#渲染队列)。

数量和时间两项限制都需要。只限制时间，等待数量仍随到达率增长。只限制数量，所有 VM 都很慢或正在替换时，请求仍可能一直等待。按 shop 的容量，32 次等待约相当于三分之一秒的工作。1 秒等待给短暂突发留出空间，又不把整个 HTTP 写预算都花在排队上。页面成本不同时，应按它们的实测容量和可接受等待时间设置 `ssr.queue_limit`、`ssr.wait_timeout`。`ssr.queue_limit: 0` 表示没有空闲 VM 就拒绝。

六个工作台页面，每个 URL 都不同，让每个请求都渲染，默认 2 个 VM 跑在一个核的两个超线程上，`MemoryMax=1G`，不用 swap。另一个核上的开放到达客户端按固定速率发 gzip 请求，每档 60 秒，速率按实测容量每秒 89.5 个请求的比例算，跑两轮：

| 到达率 | 回 503 的比例 | 成功请求 P50 / P99 | 503 的 P99 | RSS 峰值 |
| --- | --- | --- | --- | --- |
| 50% | 0% | 12 / 31 ms | | 77 MiB |
| 75% | 0% | 16 / 40 ms | | 78 MiB |
| 100% | 0% | 104 到 147 / 153 到 289 ms | | 82 到 83 MiB |
| 150% | 34% | 385 到 389 / 445 到 452 ms | 45 ms | 84 MiB |
| 200% | 51% | 389 到 390 / 469 到 473 ms | 47 ms | 84 MiB |
| 300% | 68% | 395 到 399 / 493 到 499 ms | 50 到 52 ms | 85 MiB |
| 300%，180 秒 | 67% | 395 / 490 ms | 52 ms | 84 MiB |

- 没有传输错误或超时，每个拒绝都带 `Retry-After: 1`，每档结束后 10 次恢复探测全部成功。每档直到最后都有成功的响应。
- 300% 时全部请求的 P50 只有 26 ms，因为多数请求很快被拒了。要看成功请求的延迟，不要只看全部请求的。
- 正好 100% 时，渲染时间的小变化决定队列排多长，所以两轮差别大。
- 队列限制计算渲染任务数，不计算字节数或 HTTP 请求数。`Load` 在准入前运行，共用一次缓存未命中的请求仍各自占用 HTTP 状态。这些 RSS 不代表大量连接、大量加载数据或应用自己的内存。`ssr.vm_memory` 限制的是每个 VM，不是进程，渲染队列也不保证进程永不内存不足。

### 内存

整个程序的 RSS 峰值（内核记的最高值），渲染六个工作台页面，VM 数和在途请求数如第一行所示，跑在 3 个 CPU 上。这是 2026-10-24 用 quickjs v0.28.6 测的，那时还没有 C 引擎。C 引擎的一个 VM 渲染后占进程 shop 12.8 MiB、MUI 7.4 到 7.6 MiB（见下面的表），在这里估算用的每个 VM 12 到 16 MiB 之内：

| VM 数和在途请求数 | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| 不压缩 | 57 到 58 MiB | 67 到 68 MiB | 92 到 93 MiB | 141 到 142 MiB |
| gzip | 56 MiB | 70 MiB | 100 到 101 MiB | 158 MiB |
| zstd | 57 到 58 MiB | 73 到 74 MiB | 108 MiB | 174 到 175 MiB |

店面每个物理核一个 VM，gzip：1 个 VM 66 MiB，2 个 88 到 89 MiB，4 个 129 到 131 MiB。

所以按约 45 MiB 加每个 VM 12 MiB 准备，每个同时在压缩的请求 gzip 再多约 2 MiB，zstd 多约 4 MiB。Chrome 123 起浏览器会要 zstd，所以按每个 VM 约 16 MiB 准备。店面的页面更大，每个 VM 约 21 MiB。

shop 的一个 VM 按引擎的统计（quickjs 的 `MemorySize`，`ssr.vm_memory` 限制的就是它）占多少，像池那样把每个页面轮流渲染 300 次：加载后 8.47 MB，渲染后 9.09 MB。包的字节码 4.52 MB，所有 VM 共用。引擎数的是它自己的分配器持有的内存，同一份堆比它之前的引擎数出来少 13% 到 15%，所以同样的 `ssr.vm_memory` 能多装这么多。引擎按块向系统要内存，所以 VM 实际占的比它数的多：加载后 10.7 MB（18 块），渲染后 13.4 MB（19 块）。渲染后再做一次完整回收，什么也没多收回：每次渲染后的年轻回收已经把能收的都收了。一个 VM 在 RSS 里的其余部分是 Go 的内存和引擎自己的栈，每个 VM 有 32 MiB 的地址空间，渲染 shop 的页面碰过的页约 1 MiB。

**空闲的 VM 把空闲内存还回去。** 渲染需要的内存比 VM 平时留着的多，渲染完留下一批空闲页：shop 2.6 MiB，MUI 1.4 MiB，再加上渲染碰过的引擎栈，分别是 0.8 和 1.0 MiB。一个 VM 一秒没有渲染（`internal/ssr/pool.go` 里的 `idleRelease`），就把这些页还给系统，两次渲染之间的完整回收也会还。一个 VM 占进程多少，按（8 个 VM 的 RSS 减 1 个 VM 的 RSS）除以 7 算，分别是加载后、池把每个页面渲染 32 遍之后，和 VM 空闲等了 1.5 秒之后（`TestShopVMResident`，shop 各跑三次，MUI 两次，AMD EPYC 7B13，quickjs v0.29，即 0cc6d332）：

| 应用 | 加载后 | 渲染后 | 空闲等待后 | 少了 |
| --- | --- | --- | --- | --- |
| shop | 8.5 到 8.6 MiB | 12.8 MiB | 9.6 MiB | 3.2 MiB（25%） |
| MUI | 3.9 MiB | 7.4 到 7.6 MiB | 5.3 到 5.5 MiB | 2.1 MiB（28%） |

等待之后的第一次渲染要把这些页重新取回来，shop 的页面多花 1 到 2.5 ms（3% 到 9%），MUI 多花 1.2 到 2.5 ms（2.5% 到 6.6%），不还内存的版本在同样的停顿之后也会多花最多 1.3 ms。至少每秒渲染一次的 VM 留着自己的内存，因为还回去会让每次渲染都付一次重新取回的代价，每 MiB 约 0.9 ms：持续有负载时上面的数字不变，每个 VM 12 到 16 MiB 的估算也不变。渲染时间和不还内存时一样，1 个 VM 时每个页面差在 0.5% 以内，2 个 VM 时差在 0.4% 以内（8 个代码位置各 3 轮，所以这个比值不是代码布局的巧合）。

- 池子用 quickjs 的 `SharedBytecode` 加载包，所以字节码、包里函数的源码（`toString` 返回的文本）和给错误栈提供行号的表整个进程只存一份，在所有 VM 之外，不算进 `ssr.vm_memory`。
- 每个 VM 在对象没了以后留住最近 2048 个普通对象的形状（形状记录一个对象有哪些键、按什么顺序），还按大小各留一张表，存放释放掉的小块，垃圾回收时交回去。两次回收之间这些表最多存 1.6 MiB 的块。引擎的回收阈值把它们算在内，分配碰到内存上限时会先把缓存的块还回去再试一次。
- 留住的形状算在 `ssr.vm_memory` 里。一个页面如果建很多键和别的对象都不一样的对象，能用这样的形状把 2048 个位置填满：一个形状有 32 个键、键名约十个字符时，连键名约占 3 KiB，合起来每个 VM 约 6 MiB。引擎的 `VM.SetShapeCache` 设一个 VM 留多少个形状，默认是 `quickjs.DefaultShapeCache`（2048）。Tifa 用默认值，没有对应的配置项。

垃圾什么时候回收：QuickJS 在建对象时发现内存过了阈值就回收，然后把阈值设成回收后剩下的 1.5 倍。池子把一个 VM 上次在两次渲染之间做完整回收（或加载完）后剩下的大小记作它的活大小。每次渲染完、请求答完以后，它跑一次年轻回收（quickjs 的 `VM.RunYoungGC`），只看上次回收以后新建的对象，释放其中的垃圾，回收完才让 VM 接下一个渲染。年轻回收留下的对象变成老对象，之后的年轻回收不再看它们。年轻回收后还占着活大小的 1.5 倍、这次渲染里引擎自己回收过、或者满 256 次渲染时，改做一次完整回收，收掉年轻回收留下的老垃圾，比如经过老对象的循环和 WeakMap 的值。渲染中途的阈值是活大小的两倍，所以渲染很少中途回收。有的页面渲染到结束前一直拿着比活大小还多的东西，比如 `test/apps/bench` 的螺旋页，它会让引擎在渲染中途回收一次，那次引擎设的阈值留给这个 VM 之后的渲染用。留下的阈值最多到活大小的四倍，之后每次不在中途回收的渲染都让它往活大小的两倍回落 1/1024：跑过一次大页面的 VM 会回到平常的阈值，真需要这么多空间的页面大约每 1000 次渲染在中途回收一次。阈值最多到活大小和 `ssr.vm_memory` 的中点，所以一次渲染的垃圾比这还多时，用完内存之前也会回收。

VM 回收后的活大小超过增长上界时，池会在后台替换它。基线是加载完成并做完预热回收后的活大小。上界是基线的 2 倍，如果 `ssr.vm_memory` 的 75% 更小就用这个值，但不低于基线的 175%，避免刚加载就接近限额的包反复重载却收不回空间。这些值用引擎的 `MemorySize`，不是进程 RSS。如果限额低于加载后活大小的 1.75 倍，保护下限可能高于限额，替换也没法让这个包装得下。

- 池在后台加载一个备用 VM，旧 VM 继续参与渲染。只有存在符合条件的空闲 VM，且渲染队列无人等待时，才开始加载。加载完成后，也要等队列为空，才与符合条件的空闲 VM 交换，随后关闭移出池的旧 VM。整个池同时只做一次这种替换。内存预算要多留一个 VM 的空间，包括它的 Go 内存和引擎栈，从加载开始一直保留到允许交换的空闲时刻。持续繁忙会推迟替换。单次渲染仍可能在下一次渲染间回收之前就触及内存限额。
- 加载失败时，旧 VM 继续服务，1 秒后重试，间隔逐次加倍，最多 30 秒，恢复之前只记录一次警告。每次成功交换都记录基线、旧活大小、上界和新活大小，并增加池的替换计数。关闭池时会等待正在加载的 VM，并关闭未用上的备用 VM。被替换 VM 的模块状态会丢失，与渲染失败后的替换一样。需要持久保存的应用状态应放在 Go 中。
- 异常、超时、内存失败或 panic 会让 VM 处于未知状态，它仍要立即退出服务，在替换的 VM 加载好之前池里少一个 VM。后台替换只处理渲染成功的 VM。

`ssr.vm_memory`（默认每个 VM 128 MiB）远高于这些。有一种情况要另外留内存，[栈深度](config.zh-CN.md#栈深度)讲了它，以及小机器上怎么调低：无限递归的代码会让每个 VM 一时多占约 26 MB。

- **每次失败都干净。** 没有哪一档让程序退出或卡住。每次失败都是时间预算内的 500，VM 换新，下一个页面照常渲染。`TestExtremeApp` 还要求程序跑完所有档位始终不超过 1 GiB。
- **大数据和长列表先用完内存**：注入 40 MB 数据、5000 行的表、长 Markdown。**长 Markdown 和后台忙碌的一天（300 条 Markdown 回复）先用完时间**：`/markdown/200` 和 `/console/100` 在 M4 上用 0.9 到 1.1 秒，在 EPYC 上用 2.1 到 2.6 秒，接近 `ssr.timeout` 的 3 秒。
- **Markdown 几行是修 micromark 之后的数字。** react-markdown 底下的解析器 micromark 4.0.3 每应用一次编辑就把整个文档的事件拷一遍，时间随文档体积的平方涨（[micromark#246](https://github.com/micromark/micromark/issues/246)，还没修）。触发它的是列表，高亮只占页面时间约 2%。本仓库的应用打了补丁（`patches/micromark-util-edit-map@1.0.0.patch`，即那个 issue 里提的改法），表里的行都带着补丁：在 EPYC 上，改用 1 GiB 和 60 秒时，200 KB 要 2.3 秒，1 MB 要 13 秒，2 MB 要 25 秒，每 KB 约 11 到 13 ms。不打补丁时同样三行是 2.7 秒、22 秒和超过 60 秒，用的是 quickjs main 0c8c338。用 react-markdown 渲染长 Markdown 的应用也要打同样的补丁，或者用 micromark 4.0.2，等 micromark 发版修好。
- **长 Markdown 的内存峰值约为每 KB 0.45 MiB**，在已加载 VM 的占用之上：100 KB 要 45 MiB，400 KB 要 171 MiB，1 MB 要 447 MiB。默认的 128 MiB 大约够到 270 KB。表格里的内存是渲染结束后读的，渲染中做过 GC 时会低于峰值。大头来自这些库：解析器在读完整篇文档之前把每个 token 都留着，Node 跑同样的库也要差不多的量（堆峰值每 KB 0.3 到 0.5 MiB，400 KB 要 138 MiB，1 MB 要 281 MiB）。引擎的峰值到 200 KB 和 Node 相当，从 400 KB 到 1 MB 是 Node 的 1.3 到 1.6 倍。原因是解析器留着不放的那些数据在引擎里占的内存是 V8 里的 2.2 到 2.6 倍（一个对象 64 字节，属性另放一块），而 Node 留着更多等 GC 的垃圾。
- **JSON 最多嵌套 2000 层**，所以 `/json/2001` 在 1 到 2 ms 后失败，报 `RangeError: JSON nesting too deep`，C 引擎之前的引擎能解析它。
- **深层调用**占的是 goroutine 栈，不是 VM 内存。渲染时 goroutine 栈的增长：500 到 1000 层组件或 Provider、400 到 600 层嵌套 `div` 涨 1 到 4 MiB，5000 层和 10000 层组件涨 8 MiB，两台机器一样。宽而不深的页面最多涨 512 KiB。
- **注入数据**：在 M4 上，带 5 MB 数据的页面渲染用 40 ms，其中 32 ms 花在 VM 里解析数据。渲染之前，Go 加载数据并写成 JSON 用 21 ms，转义用 2 ms。长的数据文本由 Go 在 VM 渲染完之后写进页面（[数据协议](build.zh-CN.md#数据协议)），VM 里只留解析出来的数据：20 MB 渲染用 160 ms，其中 131 ms 是解析，40 MB 在解析时用完内存。
- **一个 VM 被停下会让别人慢几毫秒**：在 M4 上开 4 个 VM，其中 3 个渲染 `/table/25`，单独跑时 P99 是 5 到 6 ms，第 4 个渲染 `/markdown/200` 时是 5 到 6 ms，第 4 个在十秒里被停下并换新 7 次时是 9 到 10 ms（`TestExtremeIsolation`，跑三次）。测试允许一次停下多加 5 ms。

## 压缩

[`server.compress`](config.zh-CN.md#配置项) 默认开着（见[压缩](build.zh-CN.md#压缩)）。压缩一个页面花的时间是它渲染时间的 1% 到 2%，浏览器包直接发构建写好的 gzip 文件，不花 CPU。

压缩一个页面要多久：一个核上，编码器像服务端一样复用，取 200 次的平均，旁边是[一个页面渲染多快](#一个页面渲染多快)里的渲染 P50：

| 页面 | HTML | gzip 5 级 | zstd 默认级别 | 占渲染时间 |
| --- | --- | --- | --- | --- |
| 订单列表 | 82 到 87 KB | 261 到 281 µs 压到 9.5 到 10.0 KB | 146 到 155 µs 压到 9.2 到 9.7 KB | gzip 1.1% 到 1.2%，zstd 0.6% 到 0.65% |
| 订单 | 39 到 40 KB | 181 到 185 µs 压到 8.4 到 8.6 KB | 128 到 131 µs 压到 8.7 到 8.8 KB | gzip 2.2%，zstd 1.5% |
| 统计 | 35 KB | 133 到 138 µs 压到 7.1 到 7.2 KB | 109 到 111 µs 压到 7.4 到 7.5 KB | gzip 1.9%，zstd 1.5% |

整个请求：服务端在一个物理核上（两个超线程，2 个 VM），oha 在另一个物理核上，每档 15 秒，跑两轮。页面用 `--cache-size 0` 渲染，缓存的订单页（两个轮流）从渲染缓存里出。zstd 那一列请求带 `Accept-Encoding: gzip, zstd`：

| 请求 | 不压缩 | zstd | gzip |
| --- | --- | --- | --- |
| 六个页面轮流，在途 1 个 | 每秒 75.8 个，P50 8.84 ms，每个 52 KB | 75.0 到 75.5，P50 9.10 ms，8.5 KB | 72.8 到 73.3，P50 9.12 到 9.15 ms，8.5 KB |
| 六个页面轮流，在途 2 个 | 95.4 到 98.0，P50 13.7 到 13.9 ms | 95.2 到 97.3，P50 13.9 到 14.0 ms | 95.4，P50 14.1 ms |
| 列表的导航数据，在途 64 个 | 7,852 到 7,860，6,632 字节 | 7,368 到 7,448，1,227 字节 | 6,934 到 6,987，1,258 字节 |
| 订单的导航数据，在途 64 个 | 12,880 到 12,920，1,350 字节 | 11,268 到 11,280，739 字节 | 10,677 到 10,694，737 字节 |
| 统计的导航数据，在途 64 个 | 8,077 到 8,280，2,947 字节 | 7,601 到 7,622，777 字节 | 7,372 到 7,380，734 字节 |
| 缓存的订单页，在途 1 个 | 6,076 到 6,163，P50 0.15 ms，39,412 字节 | 6,900 到 6,903，P50 0.14 ms，8,796 字节 | 6,780 到 6,854，P50 0.14 ms，8,502 字节 |
| 缓存的订单页，在途 64 个 | 10,812 到 10,974，P99 15.0 ms | 12,813 到 13,044，P99 12.5 到 12.7 ms | 12,716 到 12,927，P99 12.7 到 12.9 ms |
| 浏览器包里最大的 chunk，在途 64 个 | 7,039 到 7,300，456,594 字节 | `.gz` 文件：14,958 到 15,287，147,331 字节 | 同一个 `.gz` 文件 |

- 对页面来说，三种编码相差不到 4%，页面发出去小了约 6 倍。
- 导航数据回答起来很便宜，所以压缩的开销看得出来：核跑满时每秒少 6% 到 17% 的请求，回答小 1.8 到 5.4 倍。
- 命中缓存时直接发缓存和页面一起存好的 gzip 或 zstd 版本，要写的字节少，所以压缩的命中反而比不压缩的省 CPU。接受压缩的请求没命中时，页面压成两种版本，发出其中一种。共用这次渲染的请求不会再压一遍。
- 浏览器包发 `.gz` 文件，每秒答的请求约是发原文件的 2 倍，因为要写的字节少。

## Content-Security-Policy

开了 `server.csp` 时，Go 把 VM 渲染出的每个页面里的记号去掉，再给记号标出的脚本和样式算哈希（见 [Content-Security-Policy](config.zh-CN.md#content-security-policy)）。`internal/ssr` 的 `BenchmarkTakeMarks` 用一个 140 KB 的页面，里面有五个打了记号的元素，其中一个装着 6 KB 数据，在 Apple M4 上约 31 µs，大部分是多复制一次页面和查找 nonce。商店工作台页面在一个核上渲染一次要几十毫秒，所以这大约是一次渲染的 0.1%。渲染缓存和整页缓存命中时，头随页面一起存着，不再多花时间。关掉 `server.csp` 时渲染不做这些。

## 哪些改动让它变快

所有改动都让 HTML 逐字节不变。效果指 shop 页面一次渲染花的时间，没有另外注明的都在上面那台机器上测。

### 引擎

[github.com/liustack/quickjs](https://github.com/liustack/quickjs) 的 [docs/changes](https://github.com/liustack/quickjs/blob/main/docs/changes/README.md) 列了每项改动，细节和测试都在那里。和速度有关的改动中，对这篇文档里的数字有影响的是换掉前一个引擎的那一项。前一个引擎到 v0.28.6 为止的较小改动，在 git 历史里：

| 改动 | 版本 | 效果 |
| --- | --- | --- |
| 整个引擎是用 C 写的 QuickJS，由 LLVM 编译成 Go 汇编，替代 ccgo 从它写出的 Go | v0.29 | 对比 v0.29.0 之前的 quickjs（当时 Tifa 自带剖析来构建，C 引擎不用剖析），AMD EPYC 7B13，一个 VM 一个核，每边 8 个代码位置，4 轮交替：shop 的六个工作台页面耗时是原来的 0.834 到 0.843，MUI 测试应用的三个页面是 0.853 到 0.860，`test/apps/bench` 的两个页面是 0.844 到 0.849，每个位置都更快。shop 的 160 个页面、pages 应用的 33 个、MUI 的 60 个和极端应用的 30 个，HTML 逐字节一致，只有 JSON 嵌套 2001 层的那一页例外，它现在会失败。渲染时 Go 垃圾回收让程序停多久和原来一样：1 个 VM 时 P99 是 131 到 164 µs，3 个 VM 时是 197 µs |

quickjs v0.29.9 整体和 v0.29.8 比，Tifa 和 SSR 包都相同，2026-11-03 在 AMD EPYC 7B13（linux/amd64）上测：一个 VM 跑在一个核上，超线程兄弟核空闲，16 种代码布局交替 2 轮，取一个应用所有页面 P50 之和，按 quickjs 的[测量规程](https://github.com/liustack/quickjs/blob/main/docs/measuring.md)判定，delta 取 1%。这个版本改了 amd64 上生成的引擎（两处内存不足的修复），并增加了对其他平台的支持。各布局的均值：商店的 6 个工作台页面 -0.20%（-0.54% 到 +0.14%），MUI 测试应用的页面 -0.25%（-0.60% 到 +0.11%），bench 应用的页面 +0.06%（-0.48% 到 +0.61%），店面页面 -0.47%（-0.73% 到 -0.21%，更快）。四个都是没有超过 delta 的退步。在实际发布的那个布局上，四个总和是 +0.02%、+0.11%、+0.18% 和 -0.55%，有一个页面（另一家店的统计页）在那里慢 0.95%，各布局上是 +0.07%。布局是解释器函数体的每一种起点偏移（平移为 0），加上 8 个 64 的倍数的平移（64、576、1088、1664、2176、2752、3264 和 3840），因为规程里 32 的奇数倍在这个引擎上移动解释器的距离和它的检查预期不符。

小函数这一行数的是 callgrind 下每个页面热渲染 3 次的指令数，再除以 3：一个 VM 从保存好的 bundle 字节码加载，先渲染 2 次预热，Go 回收器关掉，SSR 包分别用 main 和分支构建，在 AMD EPYC 7B13 上，一个代码位置。shop 是它的六个工作台页面，店面是五个页面，MUI 应用三个，bench 应用两个。同一个 bundle 跑两次最多差 0.06%，spiral 页就是这样（少 0.04%）。店面里渲染 Markdown 的文章 journal 页少 6.23%，另外四个店面页面少 0.32% 到 0.63%。三个 SSR 包分别大了 1.05%（shop，16,723 字节）、1.24%（MUI，9,181 字节）和 0.85%（bench 应用，2,826 字节）。十六个页面的 HTML 逐字节相同，渲染时钟写入的时间除外。计时用 `BenchmarkApp` 的池，一个 VM 跑在 cpu 2 上，它的超线程兄弟核空闲，每个页面先热渲染 32 次再计时渲染 50 次，代码位置是 0.0、0.16、32.0 和 32.16，轮流 3 轮。比值是各轮配对的页面 p50 之和的中位数，范围是没改的 bundle 在各位置上自己的差：0.9%（工作台）、1.0%（店面）、3.7%（MUI）和 1.4%（bench）。机器是共用的，兄弟核或别的任务忙时，进程最多重跑 3 次，一个应用的 24 个进程里仍有 0 到 12 个受了干扰。差距在 3% 以下，结果以指令数为准，这些时间只说明没有页面变慢。这些时间是插件在对「函数何时已经赋值」判断得更严格之前测的（见前端产物），那一版多写开约 3% 的调用，指令数与上面的相差在 0.2 个百分点以内。

转义链（已删除）、组件栈、命名空间和 key path 这四项改写在上面那台机器上用 C 引擎之前的引擎并开 PGO 测，1 个 VM 钉在一个核上，每一步和前一步比，轮流跑 12 轮。shop 的第六页是一家店的统计页，在它上面命名空间这一步测得慢 2.4%，key path 这一步快 5.3%，两步合起来快 3.3%，接近其他页面的 3.8% 到 5.4%。四项合起来，shop 快 6.5% 到 7.5%，纯文字页面快 17.6% 到 18.3%，落地页快 10.1%，小页面快 5.4% 到 5.9%。HTML 逐字节不变。为了让报错栈里的位置准确，所有改写都保持 React DOM 每一行的位置不变，这一点本身让渲染时间上下浮动不超过 1.4%。

## 试过但没做的

每项写了能带来什么、为什么放弃。再试其中某项之前先看这里。

### 引擎

下面各项是在 C 翻译成 Go 的那个引擎上试的，quickjs v0.29 已经换掉了它。这些想法对 C 引擎同样适用，所以留着，数字则是旧引擎的。只对 Go 翻译有意义的部分（TLS 帧、libc 的锁、解释器的 Go 栈帧）已经删掉。

- **字节码里放字面量模板**，像 V8 那样复制一个建好的对象：要改编译器和字节码格式，quickjs-ng 试过，没看出明显差别。
- **按最终大小分配字面量的属性数组**：建对象的 opcode 不知道属性数，换一种增长方式会让每个小对象都更占内存。只有和留住形状一起做才划算，v0.26.16 已经留住形状，还没在它上面试过。
- **读属性的内联缓存**：quickjs-ng 加了又删了。在 17 个真实工具上从慢 11% 到快 54% 都有，平均只快 4%，还更占内存。没试。
- **新对象的位字段从 9 次写合成 2 次**：没有变化（0.991 到 1.010）。时间花在第一次写新对象时的缓存缺失上，少写几次只是把它挪了地方。
- **对象展开的快路径**（`JS_CopyDataProperties`）：Apple M4 上的微基准里一次展开从 415 ns 降到 240 ns，shop 却没变（0.997 到 1.005）。
- **从字节码里去掉函数源码**（`JS_SetStripInfo`）省 VM 内存：seroval 用 `toString` 读自己辅助函数的源码写进页面，去掉后浏览器端会坏。现在改成池子里的 VM 共用一份源码，见[内存](#内存)。
- **用 Go 实现 `TextEncoder`、`URL` 等兼容代码**：渲染时几乎不调用它们，渲染时间没有可省的。

评估过但没做的引擎办法：

- **用纯 Go 写 JIT**，把热函数的字节码变成机器码。在 shop 的页面上数过，机器码每次渲染要调回引擎 3.9 万到 13.7 万次（每 1000 个 opcode 约 100 次）。每次调出比今天的 Go 调用多花 3.7 到 14 ns（AMD EPYC，Apple M4 上是 1.5 到 2 ns），吃回渲染时间的 1.6% 到 5.8%。净收益估计是快 1.11 到 1.30 倍，约 1.2 倍，要做 3 到 6 个月，而且前提是机器码能省掉解释器自身时间的 40% 到 60%，这个数没人测过。2026-10-21 的纯 Go 引擎对比里，go-quickjs 开 JIT 比它自己的解释器慢（一次 React 渲染 19.0 ms 对 14.9 ms），jsc2go（14.1 对 20.0）和 goant（28.0 对 34.1）则更快。没开始做。除非找到和 jsc2go、goant、go-quickjs 都不一样的做法，否则不再提。
- **融合字节码**（超指令）：40 个融合的二连、三连能少掉 19% 的分发（MUI 页面 31%，工作台页面 5%），按模型估计少 1.3% 到 2.2% 的指令。真做出来的那一个融合对子和对照组一样快，但它太小，数不出指令数，所以这次测试什么也证明不了。先搁下，等算术快路径做完，再数着指令数重做。
- **从 VM 里去掉一部分内建对象**：裸 context 里全部内建对象约占 67 KB 和 0.14 ms（在 quickjs v0.26.16 上测的），最大的一组带类型数组只有 12.6 KB 和 34 µs，内存和启动时间都没有可省的。去掉 Atomics 的 `wait` 和 `notify`、`SharedArrayBuffer`、`HTMLDDA` 或模块，各省几 KB 到 100 KB，test262 会失败，每次跟上游同步还要多费功夫。页面用到的语言特性比看上去多：`Proxy`（i18next、immer、zod、TanStack Query）、`BigInt` 和 `new Function`（zod）、带类型数组、生成器、async 函数和 `\p{}` 正则。

### 构建

- **给 React 转义加的 JavaScript 缓存和 `replaceAll` 链**：它们是没有引擎 `__tifa_escape` 的 VM 用的转义，而池里的每个 VM 都有这个函数，所以没有哪次渲染跑过它们。关掉它们之后，一次渲染的指令数在 shop 工作台页面上变化 -0.05% 到 -0.09%，店面页面 -0.02% 到 -0.03%，MUI 页面 +0.02% 到 -0.14%，bench 页面 +0.02% 到 +0.03%（callgrind，一个应用每页热渲染一次，quickjs v0.29.8，linux/amd64），都在同一个包两次运行相差的 0.11% 以内。没有引擎函数的 VM 现在跑 React 自己的转义。
- **`retryNode` 只在 key path 或 replay 要读元素的 key 时才去算它**：key path 去掉以后，只有带 replay 的任务会读它，而 `renderToString` 的任务都没有 replay。关掉这项改写后，一次渲染的指令数在 shop 工作台页面上多 0.05%，店面页面多 0.03%，MUI 页面少 0.04%，bench 页面多 0.11%（callgrind，一个应用每页热渲染一次，quickjs v0.29.8，linux/amd64），都在同一个包两次运行相差的 0.11% 以内。渲染不读的 key 多做的三次判断，花的指令比解释器自己的波动还少。
- **把静态 JSX 提到组件外**，像 Babel 的 transform-react-constant-elements：shop 的页面每次少建 44 到 83 个元素，渲染只快 0.5% 到 0.9%，几乎全静态的页面快 5.4%。每少建一个元素约省 0.8 µs，时间主要花在 React 遍历和拼字符串上。它管不到 `node_modules` 里库的 JSX，要么得装 Babel，要么得自己写一个转换。提上去的元素被一个 VM 的所有请求共用，某个库要是改了它，改动会带到下一个请求。
- **构建时把参数全是字面量的 `cn`、`clsx`、`cva` 调用折成字符串**：example shop 的 SSR 包里 143 处 `cn` 调用只有 1 处全是字面量（`cn("min-h-[50vh] border")`），MUI 测试应用的 99 处 `clsx` 调用没有，bench 应用也没有。其余的参数是 prop（`className`）、条件或成员（`classes.root`）。shop 的 6 处 `cva` 调用参数全是字面量，但每处在模块加载时只跑一次，返回的函数拿变量里的 props 调用（`buttonVariants({ variant, size })`）。一次渲染里没有可折的调用。
- **按字符串参数缓存 `clsx` 和 `cn` 的结果**：`cn` 0.5 已经按最近几次调用的参数和合并的字符串缓存。在它前面再加一层缓存的原型，shop 工作台页面多执行 0.47% 的指令，店面页面多 0.19%。`clsx`（MUI 测试应用 99.9% 的调用只有字符串和假值）的缓存包装要用参数拼 key 再查 `Map`，用 MUI 页面的参数形状做微基准，每次 390 到 650 ns，`clsx` 自己只要 315 到 400 ns。用字符串拼 key 的花费和 `clsx` 拼这些字符串差不多。把拼接写成不带循环的形式反而有收益，见[构建](#构建)。
- **降低 SSR 包的语法目标**：ES2021 到 ES2018 差 1% 以内。从 ES2017 起对象展开变成辅助函数，shop 慢 33% 到 45%。目标保持 ES2022。
- **SSR 包不压缩**：包本来就压缩了。在加店面之前的 shop 上，不压缩时渲染慢约 1%，包从 772 KB 变成 1,799 KB，VM 加载后从 7,634 KiB 变成 9,133 KiB。
- **在 `createElement` 和 `cloneElement` 的展开前用 JavaScript 先检查**：插件先检查 config（原型、symbol、`__proto__`、`__self` 和 `__source`、`key` 背后有没有 getter），再用解构的 rest 拷贝。检查每次调用要 310 到 380 ns，比 React 的循环处理没有键、1 个键或 2 个键的 config 还多，那些元素最多慢到 1.57 倍，页面最好也只有 0.99（少跑 1.6% 到 2.5% 的指令）。Proxy、会删掉后面键的 getter、以及页面在 React 加载后给 `Object.prototype` 加的 setter，它也排除不了。引擎里的函数用 C 做同样的检查，这几处都排除了，少跑 2.1% 到 4.1% 的指令。
- **React 字符串渲染器的 tree context 在溢出之前用数字**：React 给每个数组的每个孩子建一个对象 `{id, overflow}`，让 `useId` 知道自己的位置。`overflow` 为空时用一个数字就够，给出的 id 一样，连超过 30 位、开始溢出的地方也一样（拿它和 React 自己的比过，包括 70 层深的数组链和 1,500 个孩子的数组）。整体不更快：从数字 push 省 11 ns，从对象 push 因为多一次判断反而多 18 ns（Apple M4 上 300 万次调用），所以页面只有在 id 还没溢出的那一段才占便宜。和没有这项的构建比，shop 工作台页面多跑 0.07% 的指令，店面页面多 0.09%，MUI 页面多 0.28%，bench 页面少 0.29%。
- **把 `renderNode` 捕获到抛出值之后的处理搬进单独的函数**：`renderNode` 给每个节点包一层 `try` 和 `catch`，catch 占了函数的大半。搬出去之后（两处 `renderNodeDestructive` 调用仍在原来的行上），shop 页面少跑 0.01% 的指令，店面页面多 0.04%，MUI 页面少 0.02%，bench 页面 0.00%：帧里还是那 10 个局部变量，因为保存下来的值仍要传给处理函数。
- **属性值的类型放进变量**，`"string" === (t = typeof value) || "function" !== t && ...`，或者放进 `pushAttribute` 的第四个参数：变量比重新问一遍 `typeof value` 多跑 0.02% 到 0.06% 的指令，参数多 0.1% 到 0.3%，因为每次调用 `pushAttribute` 都要为多出来的那一格付钱，不管这个属性用不用得上。
- **改 `flushSegment`、`flushSubtree` 和写 chunk 的方式**：shop 的六个工作台页面渲染一轮，`flushSegment` 跑 18 次，`flushSubtree` 12 次（五个店面页面 15 和 10 次，三个 MUI 页面 9 和 6 次），每个页面不到三次，因为页面里的 Suspense 边界很少。上面的属性改写之前，这六个页面 push 了 74,855 块，每一段把它的块一次 `join` 交出去，也就是调一次引擎。页面里不写 HTML（拼的地方换成空字符串）时，一轮少跑 4.6% 的指令，所以拼接加上之后对这个页面字符串的处理，加起来不会超过这个数。用 JavaScript 改写没有能省的地方。剩下的办法是少几块，属性那项改写已经做到了（一个属性从 5 块变成 3 块）。
- **对 React 的小改写**，每项都不到 1%：`push(x)` 改成按下标赋值（0.1% 到 0.9%），`jsxProd` 里的 `for...in` 拷贝改成展开（会多拷 symbol 键，语义不同，`createElement` 和 `cloneElement` 改问引擎，见[构建](#构建)），`startChunkForTag` 和 `endChunkForTag` 的 `Map` 换成对象（不到 0.5%），`for...in` 换成 `Object.keys`（微基准里更慢），`hasOwnProperty.call` 换成 `Object.hasOwn`（每个键省约 25 ns）。
- **用 `+` 把一个属性的几个块拼起来**，在 `pushAttribute` 和 `pushStringAttribute` 里把 `" " + name + '="' + value + '"'` 当成一个块 push：在调用已经写开的基础上，shop 工作台页面只少 0.3% 的指令，而一块一块 push 能少 0.8%。拼接要复制短字符串，花的和省下的 push 差不多。这就是 React PR 37022 的做法（[研究](studies/react-layer.md)），它也让渲染变慢了。
- **`isAttributeNameSafe` 的两个缓存用 `=== true` 代替 `hasOwnProperty.call`**：在测试用的 EPYC 核上每次调用省 9 ns（58.7 ns 对 49.6 ns，200 万次调用，22 个缓存里有的名字）。quickjs v0.29.1 给 `hasOwnProperty.call` 加了快路径后，两种写法耗时几乎一样，所以不改页面。
- **在 C 转义前面加缓存**，像 JavaScript 转义以前那样：缓存里有的一个 30 个字符的类名，带缓存的 JavaScript 函数处理一次要 340 ns，C 函数转义同一个类名只要 70 ns，所以池里的 VM 不用缓存。只有一种情况缓存更快：缓存里有一段 512 个字符、其中 171 个要转义的文本（899 ns 对 2,061 ns），页面里几乎没有这样的文本。
- **React 转义和它查找要转义字符的别的写法**：`indexOf` 查五次、逐字符循环都比它的正则慢，查找时五次 `indexOf` 和 `search` 也都比 `exec` 慢。每个字符串都先查转义缓存（已删除）再跑正则，纯文字页面慢 4%，在只测转义的基准里，一个订单列表的 1,188 次转义慢 22%，因为多数字符串不用转义，而 `Map` 查一次比搜一次更贵。所以缓存只收需要转义的字符串。搜索剩下的开销在引擎里。要是缓存满了就不再收，早先请求的文本会一直占着位置。要是淘汰最久没用的那条，每次命中都要多一次删除和一次写入。在 Go 里转义（转义在跑正则之前先调一个 builtin）让 shop 慢 1.3% 到 2.0%，HTML 不变：每次调用都要把字符串从引擎拷出来，再把结果拷回去，比搜一次加查缓存还贵。在引擎里用 C 转义就没有这次拷贝：quickjs 提供了这个函数（`RegisterEscapeText`），插件现在用的就是它（见上面的构建一节）。
- **把 React 的组件栈和 key path 里的名字换成更省的写法，而不是去掉**：把 `pushComponentStack` 内联到调用处，或者对字符串和函数类型不调 `getComponentNameFromType` 直接取名字，都在 1% 以内（shop 上 0.994 到 1.024）。花时间的是建对象和字符串，不是函数调用。
- **在插件里改写 react-spring 和 TanStack Table**：react-spring 做颜色插值时拿每个值去匹配一个有 148 个颜色名的正则，QuickJS 里一次 24 µs，Node `--jitless` 是 0.175 µs（占订单列表 2.1%）。TanStack Table 通过 `fn(this, ...args)` 调用，约 1 µs，对比 67 ns（占 1.2%）。改写它们就把插件绑在两个库的写法上。两处都该在引擎里做：正则的每个分支先比首字符再试，展开普通数组时不走迭代器。
- **把请求之间不变的页面片段缓存成 HTML**：Tifa 不知道页面是怎么写的。渲染缓存按数据缓存整个页面。
- **React Compiler**：`@vitejs/plugin-react` 的 `reactCompilerPreset()` 只编译浏览器端的构建，开不开 SSR 包都逐字节相同，shop 的 20 个页面渲染相差 1% 以内（0.994 到 1.010），两个 VM 的吞吐也一样。浏览器端 JS 压缩后大 6.1%（31 KB），HTML 和 hydration 不变。Tifa 默认不开。应用想在浏览器端用，可以在自己的 `vite.config.ts` 里打开，再量自己的交互速度和包大小。
- **构建时预先写好静态开始标签**：SSR 插件在构建时让 React DOM 自己生成字符串，预先写好属性全是常量的 JSX 元素的开始标签。shop 工作台 6 页、店面 12 页和 MUI 5 页渲染时间不变，每轮比值都在 1 的两边。只有 `test/apps/bench` 里专门为它写的两个页面变快（列表 8.1%，螺旋 7.3%）：真实页面里这些标签只占渲染的一小块，时间主要花在组件、hooks 和样式上。它让 shop 的 SSR 包大 4.9%，每个 VM 多占约 200 KB，还要按哈希校验 React DOM 的内部函数，React 每发一个版本都要跟着改。
- **数据里没有要等的东西时，用 seroval 的 `crossSerialize` 写页面数据**，代替 TanStack Router 用的流式写法：写出的文字一样，但没有页面变快（shop 工作台是原来的 1.004，店面 1.002，1,000 行表格 0.999），还要先认一份插件名单、先扫一遍数据。
- **用现成工具在压缩器之前展开小函数**：oxc（rolldown 的压缩器和 `oxc-minify` 0.156.0）和 esbuild 0.28.2 不展开这个大小的函数声明的调用。terser 5.51.2（`inline: 3`）只展开返回常量的函数和只调用一次的函数，运行的调用只少了 0.02% 到 0.6%。swc 1.16.21（`compress.inline: 3`）让调用少了 0.2% 到 1.3%，但它别的改写让 shop 工作台和 MUI 的页面多跑 2.8% 到 3.2% 的指令。所以由插件自己展开。
- **给破坏顺序规则的实参加临时变量**（见[展开小函数](build.zh-CN.md#前端产物)）：按 shop 工作台页面运行的调用数算，临时变量能多展开 1.5 个百分点的调用（6.0% 对 4.6%），扣掉变量本身的代价之前约省 0.3% 的指令。没做。

### 服务端

- **调高回收阈值**，设成活大小的两倍、三倍或固定 32 MiB，仍由引擎在渲染中途回收：一次回收花的时间差不多跟着它释放的垃圾走，回收次数减半只省下约 15% 的回收时间，不到渲染的 1%，量不出来。P99 和 P999 反而变差，一个 VM 多占 40% 到 50% 的内存，`ssr.vm_memory` 设得低时更早用完内存。
- **在年轻回收之外每 64 次或 1024 次渲染做一次完整回收**，和每 256 次比：每 64 次让 shop 的 P99 高 1.5% 到 4%，每 1024 次的 P99 和内存都和 256 次一样，一轮做 2 次完整回收，256 次时是 8 次。
- **每 2、4、8 次渲染才做一次年轻回收，或者多分配 1 MiB 才做**，和每次渲染后都做比：shop、店面和 MUI 页面每次渲染的 CPU 都在各轮的波动范围里，每 4 次时 shop 上引擎还多跑 0.4% 的指令，而每个 VM 的堆峰值大了 7% 到 50%。年轻回收的成本差不多按它看过的对象数算（每个 130 到 145 ns，大多是缓存缺失），少做一半，下次就要看两倍的对象。每次回收后不清空小空闲块的缓存也没省下什么：之后的释放更快把它填满，走慢路径。每次渲染后的年轻回收占 shop 一个请求 CPU 的 2.0%，MUI 的 1.1%。
- **请求里的其他部分。** 一个核一个 VM，gzip，shop 的页面：渲染占一个请求 CPU 的 94%（MUI 是 97%），年轻回收 2.0%，gzip 2.2%，处理器、`Load`、Go 的 GC、数据槽和渲染输入的 JSON 合计 1.0%。gzip 用 1 级能省 0.7%，页面大 21%。`GOGC=400` 最多省 0.2%，多用约 25 MB。没有一项够得上吞吐的 1%，所以渲染以外的部分都没改。
- **两次渲染之间要到活大小的两倍才回收**，渲染中途到三倍：P99 和 1.5 倍时一样，但一个 VM 多占 22% 到 45% 的内存，`ssr.vm_memory` 设得低时更早用完内存。
- **`onError` 没收到错误时，跳过对交给浏览器的 Suspense 边界的查找**：运行时每次渲染后在整页 HTML 里找 `<!--$!-->`，约占商店渲染的 1%，MUI 页面的 0.4%，跳过后商店耗时为原来的 0.987，MUI 页面为 0.995。但在 React 19.3 里，组件调用 `use(browser())` 时，边界交给了浏览器却不调 `onError`：`renderToString` 把它报给一个自己不接收的 `onBrowserBailout` 选项。所以查找留着，把它变快是引擎的事。
- **zstd 最快级别和 brotli**：用 gzhttp 默认的 zstd 最快级别，一页只要 82 到 138 µs，但页面比 gzip 大 3% 到 11%。brotli 用纯 Go 的 github.com/andybalholm/brotli，4 级和 5 级耗时是 gzip 的 4 到 6 倍，页面只小 3% 到 16%。构建时压缩的文件，zstd 和 brotli 用最高级别，比 gzip 最高级别小 5% 和 14%。Tifa 压缩页面用 gzip 5 级和 zstd 默认级别，和 Caddy、Traefik 一样，构建写 gzip 文件。
- **用 React 的流式渲染器渲染，让页面等懒加载组件**：`react-dom/static` 的 `prerender` 和等到 `allReady` 的 `renderToReadableStream` 给出同样的 HTML，但在 Tifa 6e062d6 上商店慢到 8.7 到 8.8 倍，MUI 页面慢到 4.2 倍，每个 VM 最多多占 1.7 MiB。先用 `renderToString` 渲染，只在它把边界交给浏览器时再用流式渲染器渲染一次，普通页面一样快，但这些页面要渲染两遍。Tifa 改用 `prerenderToString`：插件给 React DOM 加的字符串渲染，会等 VM 的任务能完成的事。在 GCP 机器上3 种布局各 6 轮，商店耗时为 `renderToString` 的 0.995，MUI 页面为 1.001，HTML 一样，每个 VM 大约多 20 到 40 KiB。
- **内置 TanStack Query**：Tifa 只给页面路由器自带的缓存，想用 Query 的应用仍可在浏览器里自己用。在早期原型的订单页上，官方的 `@tanstack/react-router-ssr-query` 让渲染慢 12.1% 到 12.9%（P50，3 轮）。它还要在每个 VM 里补 `ReadableStream`，在浏览器里留下两个全局变量，让 SSR 包大 27%。手写的 Query 自带 `dehydrate()` 慢 8.1% 到 8.3%，只传 `[key, data, updatedAt]` 慢 4.0% 到 4.3%。每个路由一个 loader 量不出代价（在 0.3% 以内）。
- **比 JSON 文本更快的 `Load` 数据交接形式**：VM 用 `JSON.parse` 读数据，它在引擎里是 C 写的。callgrind 里，它在 1,000 行的表格上每字节 61 条指令（一次渲染 1.31 亿条指令里占 560 万，数据 92 KB），在 shop 订单列表上每字节 136 条（2.77 亿里占 140 万，数据 10 KB），占一次渲染的 0.5% 到 4.3%。把 Go 字符串变成文本对应的 JavaScript 字符串每字节 2.7 条指令（表格 25 万条），所以换一种交接办法，在引擎之外能省的只有这一次拷贝：约占解析的 4%，最多占一次渲染的 0.2%。直接从 Go 的缓冲区解析需要 quickjs 没有的调用，别的形式都要在 VM 里建出同样的对象。更快的解析是引擎的事（`JSON.parse` 可以记住刚读过的键对应的 atom 和 shape，表格的每一行键都一样），这里没有测。
- **去掉 router 自身水合数据的固定开销**：router 的 matches（id、状态、时间和 loader 数据）与构建 ID 经 seroval 的 `crossSerializeStream` 写进页面，不论页面数据多少，这一步的工作量都一样。在 shop 的六个工作台页面上用 callgrind 量（每页的指令数，上面那台机器约每纳秒 4.8 条指令）：这次调用 190 万条（占一次渲染的 1.3%，约 0.4 ms），它周围的读 matches、建插件和构建 ID 10 万条，水合脚本标签 7 万条。MUI 测试应用的页面是 70 万条，没有数据的 bench 页是 180 万条。这 190 万条里 90 万条（0.19 ms）是 TanStack Router 给每个页面加的三个插件（处理错误和两种流），它们对 matches 里的每个值都要问一遍：不带它们，页面少跑 0.61% 的指令。Tifa 的 `Load` 返回 JSON，没有流，但 matches 里的 `Error` 靠插件才能进页面，而这份列表是 TanStack 的，要去掉就得在每个版本的文件里改写 TanStack Router 的一个函数。自己写 TanStack 客户端读回的 `$R` 引用，下个版本就会坏。没做。

## 怎么复测

[docs/testing.md](testing.md#performance-comparisons) 有渲染基准和 VM 内存的命令，[Reading BenchmarkShopParallel](testing.md#reading-benchmarkshopparallel) 讲怎么检查多个 VM 是否还能扩展（英文）。让数字能比的规矩：

- 在同一台机器上比，新旧两个构建一轮一轮交替跑。只有同一批轮次的比值能比：机器忙的时候绝对时间能差好几倍。
- 每次跑都钉在一个核上，并让它的超线程兄弟空着。Linux 上 `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list` 写着兄弟是谁。记下每轮的机器负载，别的任务占了约 10% 以上的 CPU 就重测。
- 比较两个构建每个页面的 HTML。路由会把渲染的时刻写进每个 match（`u:` 后面跟 13 位数字），先遮掉它。
- 只有 1 个 VM 的基准看不出 VM 之间的争用。改动碰到内存分配时，还要同时用多个 VM 渲染，看 mutex profile。

完整请求：构建 `examples/shop`，用 `taskset` 把环境里有 `SHOP_OPEN=1` 的 `bin/shop --server-addr 127.0.0.1:0 --cache-size 0` 钉在几个核上，从另一个物理核压测，在途请求数等于 VM 数。每次先热几秒，测扩展曲线时服务钉的 CPU 数等于 VM 数。

Next.js 和 TanStack Start：`go run ./test/compare/cmd/compare measure` 构建三个应用并按这个方法测，核位置用参数给（见[测试文档](testing.md#comparison-with-nextjs-and-tanstack-start-testcompare)，英文）。

Node：SSR 包是 ES 模块，把同一份 `.tifa/dist/ssr.js` 复制成 `ssr.mjs`，用 `import()` 加载，渲染同样的输入，先热几百次，在 QuickJS 基准用的那个核上各跑一遍有 JIT 和 `--jitless`。导入之前，先把 Node 在 `globalThis` 上的 getter（比如 `crypto` 和 `navigator`）换成普通值，因为包会给它们赋值，再补上 `Iterator.concat`，TanStack Router 会调用它，而 Node 24.13 没有。找下一个该改的地方时，比较每个函数在 QuickJS 和 `--jitless` 的 Node 里各花多少时间：倍数远高于整体的函数就是候选。

## 还能从哪里继续

单次渲染的时间几乎就是全部成本：一个工作台请求 13.7 ms 的 CPU 里，HTTP、压缩和其他部分不到 1 ms。渲染快多少，吞吐就涨多少。按可能的收益大致排序：

1. **C 引擎和 C QuickJS 比。** 用 C 引擎之前的引擎时，跑一样的 JavaScript，quickjs 的耗时是 C 的 1.17 到 1.26 倍。C 引擎跑的就是 C 本身，编译成了 Go 汇编，所以剩下的差距是这次编译和调进 Go 的开销。先用 quickjs 的引擎对比量出来，看清剩下的耗时去了哪里，再决定改什么。
2. **正则表达式。** 手记文章的渲染耗时是 C 的 1.24 倍，而 shop 的其他页面都比 C 快：它们的时间大多花在语法高亮的正则表达式上。
3. **建对象和释放对象。** React 给每个元素、hook 和栈上的组件都建一个对象。插件已经让 React 不再构建没人读的组件栈，剩下的只有引擎能解决。
4. **用更少内存留住形状。** 留住对象字面量的形状省了渲染时间，但每个 VM 要多占内存。在 C 里改，比如让每个子形状引用它的父形状，可能用更少的内存拿到同样的速度。可以考虑提交给上游。
5. **新的 Go 版本。** 引擎是汇编，依赖 Go 怎么排栈和寄存器。Go 出新版本时，跑 quickjs 的 `docs/upgrading.md` 列的检查，再重测。
6. **整页缓存命中。** 在 shop 的店面页面（首页、商品页、手记文章，都开了 `Cache`）上，测 `Cache` 的命中对 Next.js ISR 的命中，两者都是把页面对所有人存一段时间。渲染缓存的命中（上面的 80 倍）仍要跑 `Load`，`Cache` 的命中不跑，所以两个 Tifa 的数字不能混。在一个核上，带压缩和不带压缩各测一次。
7. **还没做的对比。** Next.js 和 TanStack Start 在改版后的页面上两核、带压缩和启动的对比，在两个核以上和店面页面上的对比，以及整个 shop 在 1 核 1 GB 内存的 VPS 上的实测。

# 性能

tifa 在 QuickJS 里渲染页面。QuickJS 是用 C 写的 JavaScript 解释器，被翻译成了 Go。一次渲染比 Node 慢，因为 Node 会把 JavaScript 编译成机器码。这篇文档给出数字和按这些数字怎么配机器，再给维护者讲做过什么、放弃了什么、下一步从哪里做。

## 这些数字怎么测的

各节没有另外说明时：

- 机器：Google Cloud 上一台 8 vCPU 的虚机，AMD EPYC 7B13（Zen 3），Linux。8 个 vCPU 是 4 个物理核，每核 2 个超线程：cpu `n` 和 cpu `n+4` 共用一个核。
- 软件：Go 1.27，quickjs v0.26.13，tifa 升级到 v0.26.13 时的版本，构建不带 PGO。`tifa build` 现在默认开 PGO，它让 linux/amd64 上的渲染再快约 3%（见[构建](#构建)）。
- 应用：[examples/shop](../examples/shop/README.zh-CN.md) 的生产构建，React 19.3 和 TanStack Router，加 Tailwind CSS 和 shadcn/ui。六个页面：两家店各自的订单列表、一个订单、统计。
- 单次渲染：`test/ssr` 的 `BenchmarkShop`，一个热 VM 钉在一个核上，取多次渲染的中位数（P50）。
- 完整请求：构建出的 `bin/shop` 加 `--cache-size 0`，让每个页面请求都渲染，用 [oha](https://github.com/hatoo/oha) 压测，核够用时 oha 和服务钉在不同的核上。压页面时 oha 只占一个 CPU 的 1% 到 2%。每一档先热几秒，再测 15 到 20 秒。

## 一个页面渲染多快

| 页面 | HTML | 渲染 P50 | 请求 P50 | 请求 P99 |
| --- | --- | --- | --- | --- |
| 订单列表 | 81 到 86 KB | 40.6 到 42.4 ms | 41.7 到 43.7 ms | 51.7 到 54.2 ms |
| 订单 | 约 38 KB | 15.0 到 15.4 ms | 15.7 到 15.9 ms | 24.9 到 25.0 ms |
| 统计 | 约 34 KB | 12.5 ms | 12.9 到 13.0 ms | 21.9 到 22.1 ms |

每个范围包括两家店。「渲染」是基准测试的数。「请求」是走 HTTP、一次一个请求，多出 Go 的 `Load`、JSON 和 net/http。请求那几列是另一次测的，服务在 3 个物理核上跑 6 个 VM。在同一时段用 1 个 VM 测，真实请求和基准只差约 1%。一次一个请求时，每秒能出 22 到 24 个订单列表，或者约 75 个统计页。

程序启动时把 SSR 包编译成字节码一次，再把字节码逐个加载进池里的每个 VM。shop 编译约 0.2 秒，每个 VM 加载约 45 ms，这是在 quickjs v0.26.9 上测的。v0.26.12 让加载快了约 11%。

## 和 Node 比

同一份 `ssr.js` 放进 Node 24，用 `vm.runInThisContext` 加载，给同样的输入，同一台机器、同一个核。Node 先热 600 次渲染，再跑 5 轮，表里是每轮 P50 的中位数。有 JIT 就是平常的 Node。`--jitless` 关掉 V8 编译成机器码的部分，V8 只解释执行，更接近 QuickJS 的做法。

| 页面 | Node 有 JIT | Node `--jitless` | QuickJS | QuickJS 比有 JIT 慢 | QuickJS 比 jitless 慢 |
| --- | --- | --- | --- | --- | --- |
| 订单列表 | 4.30 到 4.37 ms | 12.67 到 12.79 ms | 40.70 到 42.25 ms | 9.5 到 9.7 倍 | 3.2 到 3.3 倍 |
| 订单 | 1.50 到 1.56 ms | 4.56 到 4.73 ms | 15.00 到 15.45 ms | 9.9 到 10.0 倍 | 3.3 倍 |
| 统计 | 1.18 到 1.21 ms | 3.76 到 3.80 ms | 12.48 到 12.50 ms | 10.3 到 10.6 倍 | 3.3 倍 |

- P99：Node 有 JIT 是 4 到 16.5 ms，`--jitless` 是 4 到 25 ms，QuickJS 是 18 到 51 ms。
- 冷启动的 Node 进程第一次渲染订单列表要 76 ms。
- 在 quickjs v0.26.12 和 v0.26.13 之前，也在 SSR 包的三项改写之前（合并 React 写出的 chunk，React 的长 `switch` 前先查 `Set`，以及调低 seroval 改用 `JSON.stringify` 的长度，seroval 是 TanStack Router 用来把页面数据写进 HTML 的库），同样的测法是比有 JIT 慢约 13.6 倍，比 `--jitless` 慢 4.45 倍。
- 这里只比渲染。Node 自己的 HTTP 服务和多核下的 Node cluster 没有测。

## 多核怎么扩展

六个页面轮流请求，在途请求数等于 VM 数。服务钉在和 VM 数一样多的 CPU 上：先每个物理核一个（1 到 4），再加同一批核的超线程（5 到 8）。

| VM 数 | 请求/秒 | 是 1 个 VM 的几倍 | P50 | P99 |
| --- | --- | --- | --- | --- |
| 1 | 42.7 | 1.00 | 15.5 ms | 49.1 ms |
| 2 | 81.7 | 1.91 | 15.7 ms | 53.3 ms |
| 3 | 125.3 | 2.93 | 15.7 ms | 53.6 ms |
| 4 | 158.1 | 3.70 | 16.1 ms | 54.9 ms |
| 5，从这里起用超线程 | 167.4 | 3.92 | 21.5 ms | 74.7 ms |
| 6 | 177.3 | 4.15 | 25.4 ms | 85.4 ms |
| 7 | 180.5 | 4.23 | 26.5 ms | 89.1 ms |
| 8 | 191.0 | 4.47 | 27.4 ms | 92.3 ms |

- 在测过的 4 个物理核以内，吞吐近似线性增长：4 个核走 HTTP 是 1 个核的 3.70 倍，不走 HTTP、直接用渲染池是 3.87 倍。每个核损失的那几个百分点像是共用的 L3 缓存或内存造成的，虚机上没有硬件计数器，证实不了。
- 超线程只多约 20%。1 个核跑 2 个 VM 是每秒 51.1 个请求，跑 1 个是 42.7。一次渲染的 CPU 时间从约 24 ms 涨到 39 到 40 ms，摊在解释器的所有函数上：两个线程在抢同一个核。
- libc 分配器的锁、垃圾回收、HTTP 和内核合计约占 3% 的 CPU。整个程序 99.5% 的 CPU 在用户态，内核占 0.3% 到 0.5%。所以吞吐跟着单次渲染的时间走。
- 请求比 VM 多时吞吐不掉，只是排队变长：3 个核上 6 个 VM、24 个在途请求，仍有每秒 144.7 个，P50 是 161 ms。

## 机器怎么配

### CPU 和 `ssr.vms`

- [`ssr.vms`](config.zh-CN.md#配置项) 保持默认就好。默认值是 Go 看到的 CPU 数（`GOMAXPROCS`），在容器里跟着 CPU 限额走。
- VM 比 CPU 多不会多出吞吐。渲染不会排队，而是在抢 CPU，每次都变慢：7 个 CPU 上 8 个 VM 是每秒 181 个请求、P50 30.8 ms，7 个 VM 是 183 到 185 个、26.4 ms。
- VM 比 CPU 少，是拿吞吐换一点延迟：同样 7 个 CPU，4 个 VM 是每秒 137 个请求、P50 20 ms。系统仍会把两个渲染线程放到同一个核的两个超线程上，而别的核还空着。只给程序和物理核一样多的 CPU，两样都更好：4 个物理核上 4 个 VM 是每秒 158 个、16 ms。
- 云上的一个 vCPU 通常是一个超线程，2 个 vCPU 常常就是 1 个物理核。超线程都忙起来时吞吐更高，但每次渲染更慢：shop 的页面在物理核上 P50 约 16 ms，每个核的两个线程都在渲染时约 26 ms。
- 16 ms 的条件是程序钉在每个物理核的一个超线程上，另一个超线程几乎空着。cpuset（比如 Docker 的 `--cpuset-cpus`）能把程序钉到这样的 CPU 上，但管不了别的程序用它们的兄弟超线程。Kubernetes 的 static CPU manager 策略倾向于整核分配，一个核的两个超线程一起给，那就是下面 26 ms 的情况。只设 CPU 配额（比如 Docker 的 `--cpus`）时线程不绑核，结果可能更像上面 VM 比 CPU 少的情况。这种情况没有测过。
- 按 shop 六个页面轮流、每次渲染平均约 24 ms CPU 的情况，每个物理核每秒约 40 次渲染，vCPU 是超线程而且都忙时每个 vCPU 约 25 次（6 个 vCPU 每秒 148.8 次）。渲染时间不同的页面按比例换算。

只有整页加载才渲染。在浏览器里切换页面取的是 Go 直接写的 JSON，不经过 VM，API 路由和命中缓存的页面也不渲染。3 个物理核上 6 个 VM、64 个在途请求时：

| 请求 | 请求/秒 | P50 | P99 |
| --- | --- | --- | --- |
| 列表、订单、统计的导航数据 | 20,161、33,030、21,264 | 1.5 到 2.5 ms | 8.1 到 14.1 ms |
| `Cache = true` 的页面命中缓存 | 22,538 | 2.1 ms | 13.1 ms |
| 同一页面回 304 | 31,165 | 1.5 ms | 8.8 ms |
| API 用 `PATCH` 改一个订单 | 57,905 | 1.4 ms | 3.3 ms |

这些请求的成本很大一块在应用自己，不在 tifa。导航数据和命中缓存的请求里，20% 到 24% 花在 shop 自己的 `Load` 上，它每个请求都把全部订单复制、排序一遍，13% 到 20% 花在写响应的系统调用上。`PATCH` 用 3 个核只比 1 个核多 56%，像是卡在 shop 自己的订单锁（`ordersMu`）上，这一类没有剖析过。命中缓存和导航数据请求一样贵：缓存键里有数据，所以查缓存之前每个 `Load` 都要先跑完。

### 内存

渲染六个页面时整个程序的 RSS 峰值（内核记的最高值），每个 CPU 一个 VM，在途请求数等于 VM 数：

| VM 数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| RSS 峰值 | 60 MiB | 77 MiB | 94 MiB | 111 MiB | 128 MiB | 142 MiB | 161 MiB | 180 MiB |

CPU 固定为 7 个、只改 VM 数时，1 到 8 个 VM 每档结束时的 RSS 是 61、79、97、115、133、149、160、179 MiB。所以 shop 大约要 44 MiB 加上每个 VM 约 17 MiB。在途请求数是 VM 数两倍时，8 个 VM 的峰值是 191 到 193 MiB。6 个 VM 只回导航数据、API 和缓存页面时，每档结束时的 RSS 是 88 到 98 MiB。

一个 VM 占多少：

- 刚加载完 shop 的包约 7.8 MB，渲染几百次后约 8.6 到 8.8 MB。其中垃圾回收后真正在用的约 4.9 MB，其余是分配器取整和留着的块。
- React 转义的缓存（见[构建](#构建)）满了约 0.5 到 2 MB，shop 只用了它的一小部分。
- 在 Linux 上还有约 1 MB 不在引擎的统计里：libc 的 TLS 栈的块，引擎翻译成 Go 后把 C 的局部变量放在这里，VM 到过的每一层调用深度各一块，留到 VM 关闭。

这些加起来约 10 MB。每个 VM 17 MiB 里剩下的约 7 MiB 还没有拆开看过。

`ssr.vm_memory`（默认每个 VM 128 MiB）远高于这些。有两种情况要另外留内存，[栈深度](config.zh-CN.md#栈深度)讲了这两种情况，以及小机器上怎么调低：

- 无限递归的代码会让每个 VM 一时多占约 24 MB 的 goroutine 栈。
- 在 Linux 上，一个 VM 递归到过 10000 层后，会一直多占约 20 MB 的 TLS 块，直到 VM 关闭。

## 哪些改动让它变快

所有改动都让 HTML 逐字节不变。效果指 shop 页面一次渲染花的时间，没有另外注明的都在上面那台机器上测。

### 引擎

fork [github.com/liustack/quickjs](https://github.com/liustack/quickjs#quickjs-liustack-fork) 的 README 列了每项改动，细节和测试都在那里。和速度有关的：

| 改动 | 版本 | 效果 |
| --- | --- | --- |
| JavaScript 调用不再分配内存。原来每次调用的参数和局部变量空间来自 libc 的 malloc，darwin、freebsd、windows 上还要分配 Go 内存 | v0.26.12 | linux/amd64 上少花约 11% 的时间，darwin/arm64（Apple M4）上少约 14%。Linux 上把字节码加载进 VM 少花约 11%。顺带把 libc 分配器的锁从每次调用里拿掉了，见[从基线到现在](#从基线到现在) |
| 解释器主循环少做栈上的读写：对 ccgo（把 C 翻译成 Go 的工具）写出的 Go 代码做三项机械改写 | v0.26.13 | linux/amd64 上少约 12.5%，darwin/arm64 上少约 17%。解释器的 Go 栈帧在 amd64 上从 2608 字节降到 896，在 arm64 上从 7744 降到 944 |
| 给普通对象加新属性时跳过通用路径 | v0.26.13 | 对象字面量的一个属性从约 95 ns 降到 55 ns，一次渲染少约 6% |

v0.26.13 整体的渲染时间是 v0.26.12 的 0.823，8 轮在 0.821 到 0.825 之间。

### 构建

[docs/build.zh-CN.md](build.zh-CN.md#前端产物) 讲了 Vite 插件对 SSR 包的每项改写，[按剖析优化](build.zh-CN.md#按剖析优化)讲了剖析：

| 改动 | 效果 |
| --- | --- |
| React DOM 只留字符串渲染器 | 在早期更小的 shop 上：包小 25%，4 个 VM 的池启动时间约减半。渲染时间不变 |
| 每个 VM 缓存 React 的 HTML 转义 | shop 少 8% 到 10%（Apple M4），它的 Tailwind 类名里满是要转义的字符。纯文字页面不变 |
| React 把两个子段之间的 chunk 先拼好再交出去 | shop 少 5% 到 7%，纯文字页面少 6% 到 11% |
| React 按属性名和标签名的长 `switch` 前先查一次 `Set` | shop 少 6% 到 7%，纯文字页面少 9% 到 12% |
| seroval 从 2 个 UTF-16 码元起就用 `JSON.stringify` 转义字符串 | 小页面少 6% 到 10%，大页面最多 2.5% |
| 每个 `Load` 的数据以 Go 写的 JSON 文本交给浏览器（[数据协议](build.zh-CN.md#数据协议)） | TanStack 默认的序列化处理同样的数据要慢好几倍 |
| 用页面渲染的剖析编译程序（PGO） | linux/amd64 上少约 3%，darwin/arm64 上少约 7% |

中间三项改写合起来，shop 快 11% 到 14%，纯文字页面快 17.5% 到 22%，小页面快 8% 到 11%。

### 从基线到现在

基线是 tifa 0673723 配 quickjs v0.26.8。它已经有转义缓存、裁掉的渲染器和 JSON 文本适配器，没有另外三项改写，也没有 v0.26.12 和 v0.26.13。现在是 tifa 362ce92 配 v0.26.13。两边都不带 PGO，在同一时段交替测：

| | 基线 | 现在 | 快了 |
| --- | --- | --- | --- |
| 1 个 VM，单次渲染，六个页面各自 | 19.8 到 66.2 ms | 12.5 到 42.4 ms | 1.56 到 1.62 倍（时间是 0.617 到 0.640） |
| 1 个 VM，走 HTTP 一次一个请求 | 一个订单列表 66.9 ms | 同一列表 42.6 ms | 六个页面 1.57 到 1.63 倍 |
| 3 个核 6 个 VM，六个页面，6 个在途 | 每秒 66.6 个请求（54.8 到 72.8） | 每秒 146.4 个（145.7 到 150.7） | 2.2 倍 |
| 同上，P50 和 P99 | 54 到 82 ms，173 到 287 ms | 26.2 到 26.6 ms，87.8 到 90.1 ms | |

单核整体约快 1.58 倍。多核快得更多，是因为基线被一把锁拖住了。原来每次 JavaScript 调用都经 libc 分配内存，libc 的分配器只有一把全局锁。6 个 VM 时 20% 的 CPU 耗在 `sync.Mutex.Lock` 上，一次渲染要 81 ms 的 CPU，1 个 VM 时只要 38 ms。v0.26.12 去掉了这次分配，锁的争用也跟着没了。只有 1 个 VM 的基准测试看不出这一点。

## 试过但没做的

每项写了能带来什么、为什么放弃。再试其中某项之前先看这里。

### 引擎

- **再给 135 个小函数去掉 TLS 帧**（TLS 帧是 libc 的 TLS 栈里的一块，引擎翻译成 Go 后把函数里取了地址的 C 局部变量放在这里）：约占渲染时间的 0.24%，测不出来，却要多维护 135 条。
- **让调用空间在 TLS 帧里放到 768 字节以上**：1024 字节只多覆盖 0.02% 的调用，却让 Linux 每层调用深度留的块从 2 KB 翻到 4 KB。
- **把不常用的 opcode 搬出解释器主循环**：在 amd64 上单做最多 8%，这是把 shop 从没跑过的 56 个 opcode 的 handler 换成空桩测出的上限，叠在「让 15 个值留在栈槽里」那项改写上只剩 1.4%，arm64 上 0.5%。还得把主循环的局部变量收进一个结构体。
- **用闭包或函数表分发 opcode**，有些 Go 写的解释器这么做：等于重写解释器，违背 fork 只做机械改写的规矩。没试。
- **等 Go 1.28**：开发版让没改的引擎在 amd64 上快 5%、arm64 上快 2%，却让改写后的引擎在 amd64 上慢 5% 到 6.5%，原因没找到。在开发版上改写仍然赢，amd64 4.2%，arm64 15.5%。
- **留住对象字面量的中间形状**（形状记录一个对象有哪些属性、按什么顺序）：在新属性快路径之上再快约 2%。两个列表页跑到 VM 内存上限失败了，因为留下的形状拉着原型和原型能连到的一切。正确的做法要给引擎的一个结构体加字段，得从 C 重新生成 Go 代码。
- **字节码里放字面量模板**，像 V8 那样复制一个建好的对象：要改编译器和字节码格式，quickjs-ng 试过，没看出明显差别。
- **按最终大小分配字面量的属性数组**：建对象的 opcode 不知道属性数，换一种增长方式会让每个小对象都更占内存。只有和留住形状一起做才划算。
- **读属性的内联缓存**：quickjs-ng 加了又删了。在 17 个真实工具上从慢 11% 到快 54% 都有，平均只快 4%，还更占内存。没试。
- **每个 VM 一个 libc 分配器**，绕开它的全局锁：8 个 VM 时这把锁现在只占 0.4% 到 0.9% 的 CPU。
- **从字节码里去掉函数源码**（`JS_SetStripInfo`）省 VM 内存：seroval 用 `toString` 读自己辅助函数的源码写进页面，去掉后浏览器端会坏。
- **用 Go 实现 `TextEncoder`、`URL` 等兼容代码**：渲染时几乎不调用它们，渲染时间没有可省的。

### 构建

- **把静态 JSX 提到组件外**，像 Babel 的 transform-react-constant-elements：shop 的页面每次少建 44 到 83 个元素，渲染只快 0.5% 到 0.9%，几乎全静态的页面快 5.4%。每少建一个元素约省 0.8 µs，时间主要花在 React 遍历和拼字符串上。它管不到 `node_modules` 里库的 JSX，要么得装 Babel，要么得自己写一个转换。提上去的元素被一个 VM 的所有请求共用，某个库要是改了它，改动会带到下一个请求。
- **降低 SSR 包的语法目标**：ES2021 到 ES2018 差 1% 以内。从 ES2017 起对象展开变成辅助函数，shop 慢 33% 到 45%。目标保持 ES2022。
- **SSR 包不压缩**：包本来就压缩了。不压缩时渲染慢约 1%，包从 772 KB 变成 1,799 KB，VM 加载后从 7,634 KiB 变成 9,133 KiB。
- **对 React 的小改写**，每项都不到 1%：`push(x)` 改成按下标赋值（0.1% 到 0.9%），`jsxProd` 和 `createElement` 里的 `for...in` 拷贝改成展开（会多拷 symbol 键，语义不同），`startChunkForTag` 和 `endChunkForTag` 的 `Map` 换成对象（不到 0.5%），`for...in` 换成 `Object.keys`（微基准里更慢），`hasOwnProperty.call` 换成 `Object.hasOwn`（每个键省约 25 ns）。
- **React 转义的别的写法**：`indexOf` 查五次、逐字符循环都比它的正则慢。每个字符串都去查转义缓存会让纯文字页面慢 4%，所以缓存只收需要转义的字符串。要是缓存满了就不再收，早先请求的文本会一直占着位置。要是淘汰最久没用的那条，每次命中都要多一次删除和一次写入。
- **把请求之间不变的页面片段缓存成 HTML**：tifa 不知道页面是怎么写的。`Cache = true` 按数据缓存整个页面。

## 怎么复测

[docs/testing.md](testing.md#performance-comparisons) 有渲染基准和 VM 内存的命令，[Reading BenchmarkShopParallel](testing.md#reading-benchmarkshopparallel) 讲怎么检查多个 VM 是否还能扩展（英文），[The engine profile](testing.md#the-engine-profile) 讲升级 quickjs 或 modernc.org/libc 后怎么重采 PGO 剖析（英文）。让数字能比的规矩：

- 在同一台机器上比，新旧两个构建一轮一轮交替跑。只有同一批轮次的比值能比：机器忙的时候绝对时间能差好几倍。
- 每次跑都钉在一个核上，并让它的超线程兄弟空着。Linux 上 `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list` 写着兄弟是谁。记下每轮的机器负载，别的任务占了约 10% 以上的 CPU 就重测。
- 比较两个构建每个页面的 HTML。路由会把渲染的时刻写进每个 match（`u:` 后面跟 13 位数字），先遮掉它。
- 只有 1 个 VM 的基准看不出 VM 之间的争用。改动碰到内存分配时，还要同时用多个 VM 渲染，看 mutex profile。

完整请求：构建 `examples/shop`，用 `taskset` 把 `bin/shop --server-addr 127.0.0.1:0 --cache-size 0` 钉在几个核上，从另一个物理核压测，在途请求数等于 VM 数。每次先热几秒，测扩展曲线时服务钉的 CPU 数等于 VM 数。

Node：用 `vm.runInThisContext` 加载同一份 `.tifa/dist/ssr.js`，渲染同样的输入，先热几百次，在 QuickJS 基准用的那个核上各跑一遍有 JIT 和 `--jitless`。找下一个该改的地方时，比较每个函数在 QuickJS 和 `--jitless` 的 Node 里各花多少时间：倍数远高于整体的函数就是候选。

## 还能从哪里继续

单次渲染的时间几乎就是全部成本：整个程序 99.5% 的 CPU 在用户态，解释器函数自己就占约 32%。渲染快多少，吞吐就涨多少。按可能的收益大致排序：

1. **引擎里的相等比较和属性访问。** 严格相等（`js_strict_eq2`）和属性读写是剖析里接下来该看的热点。赋值（`o.x = v`、`Object.assign`）还走慢路径，约占一次渲染的 1.5% 到 1.9%，做快路径要检查原型上的 setter 和只读属性。
2. **建对象和释放对象。** 加了新属性快路径之后，`JS_NewObjectFromShape` 和 `free_object` 各占约 4%，对象展开（`JS_CopyDataProperties`）约 3%。React 给每个元素、hook 和组件栈都建对象，所以 `createHook`、`pushComponentStack`、`jsxProd` 当时比 `--jitless` 的 Node 慢 6 到 12 倍。这只能在引擎里解决。
3. **只在冷路径上分配 TLS 帧。** 只在少见路径上用到 TLS 帧的函数，可以只在那里分配。估计约 3%。
4. **每个 VM 少占内存。** 所有 VM 共用一份只读的函数源码和行号表，指向字节码，`toString` 照常能用。估计每个 VM 省约 380 KB。要改 C 补丁（fork 对 QuickJS 的 C 源码做的改动）、fixlib（fork 里改写生成的 Go 代码的工具）和 Go API。
5. **用 C 改动留住形状。** 等引擎的 Go 代码能从 C 重新生成时，让子形状引用父形状，可能拿到上面那 2%，又不让内存涨。也可以提给上游。
6. **amd64 上的 Go 1.28。** 正式发布后重测改写后的引擎。如果还是比 Go 1.27 慢，做一个最小复现报给 Go。
7. **转义缓存。** QuickJS 给 `Map` 的键算哈希时不加盐，同一哈希的字符串一多查找就变慢。每条按多 64 个码元算，把链长压在约 3,700 条以内，再加一个条数上限可以更短。不是 Latin-1 的长串（8,192 码元起）实际占内存约是内容的 4 倍：查一下字符串拼接是否留了多余的空间。
8. **arm64。** 栈上的改写之后，在 arm64 上存字节码位置当时最多占解释器自身时间的约 11.6%，原因没找到。这是上限：这条存储正好在读下一个 opcode 的依赖链上，采样可能把等在那里的时间算到了它头上。
9. **还没做的对比。** Node 自己的 HTTP 服务和 Node cluster，以及同一台机器上用 TanStack Start 和 Next.js 跑同样的页面。

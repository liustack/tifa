# 性能

tifa 在 QuickJS 里渲染页面。QuickJS 是用 C 写的 JavaScript 解释器，被翻译成了 Go。一次渲染比 Node 慢，因为 Node 会把 JavaScript 编译成机器码。这篇文档给出数字和按这些数字怎么配机器，再给维护者讲做过什么、放弃了什么、下一步从哪里做。

## 这些数字怎么测的

各节没有另外说明时：

- 机器：Google Cloud 上一台 8 vCPU 的虚机，AMD EPYC 7B13（Zen 3），Linux。8 个 vCPU 是 4 个物理核，每核 2 个超线程：cpu `n` 和 cpu `n+4` 共用一个核。
- 软件：Go 1.27，quickjs v0.26.15，tifa 790b746，构建不带 PGO。`tifa build` 默认开 PGO，它让 linux/amd64 上的渲染再快约 2.4%（见[构建](#构建)）。用旧版本测的小节会注明。
- 应用：[examples/shop](../examples/shop/README.zh-CN.md) 的生产构建，React 19.3 和 TanStack Router，加 Tailwind CSS 和 shadcn/ui。六个页面：两家店各自的订单列表、一个订单、统计。
- 单次渲染：`test/ssr` 的 `BenchmarkShop`，一个热 VM 钉在一个核上，取多次渲染的中位数（P50）。
- 完整请求：构建出的 `bin/shop` 加 `--cache-size 0`，让每个页面请求都渲染，用 [oha](https://github.com/hatoo/oha) 压测，核够用时 oha 和服务钉在不同的核上。oha 用它默认的 `Accept-Encoding: gzip, compress, deflate, br` 请求，所以 [`server.compress`](config.zh-CN.md#配置项) 开着时页面以 gzip 发出，除非某节写明请求要的是 identity。压页面时 oha 只占一个 CPU 的 1% 到 2%。每一档先热几秒，再测 10 到 20 秒。

## 一个页面渲染多快

| 页面 | HTML | 渲染 P50 | 请求 P50 | 请求 P99 |
| --- | --- | --- | --- | --- |
| 订单列表 | 81 到 86 KB | 34.3 到 35.4 ms | 36.0 到 38.0 ms | 46.2 到 49.4 ms |
| 订单 | 约 38 KB | 12.5 到 12.9 ms | 13.4 到 13.8 ms | 22.4 到 23.5 ms |
| 统计 | 约 34 KB | 10.4 ms | 11.1 到 11.8 ms | 19.6 到 21.6 ms |

每个范围包括两家店。「渲染」是基准测试的数。「请求」是走 HTTP、一次一个请求，多出 Go 的 `Load`、JSON、gzip 和 net/http，服务在 3 个物理核上跑 6 个 VM。用 1 个 VM 时，一个请求比一次渲染多花 0.5 到 1.3 ms，其中 0.13 到 0.28 ms 是压缩（见[压缩](#压缩)）。一次一个请求时，每秒能出 26 到 28 个订单列表，或者约 88 个统计页。

程序启动时把 SSR 包编译成字节码一次，再把字节码逐个加载进池里的每个 VM。shop 编译约 0.2 秒，每个 VM 加载约 45 ms，这是在 quickjs v0.26.9 上测的。v0.26.12 让加载快了约 11%。

## 和 Node 比

同一份 `ssr.js` 放进 Node 24，用 `vm.runInThisContext` 加载，给同样的输入，同一台机器、同一个核。Node 先热 600 次渲染，再跑 5 轮，表里是每轮 P50 的中位数。有 JIT 就是平常的 Node。`--jitless` 关掉 V8 编译成机器码的部分，V8 只解释执行，更接近 QuickJS 的做法。

| 页面 | Node 有 JIT | Node `--jitless` | QuickJS | QuickJS 比有 JIT 慢 | QuickJS 比 jitless 慢 |
| --- | --- | --- | --- | --- | --- |
| 订单列表 | 4.28 到 4.36 ms | 12.77 到 12.99 ms | 34.38 到 35.49 ms | 8.0 到 8.2 倍 | 2.7 倍 |
| 订单 | 1.48 到 1.57 ms | 4.60 到 4.79 ms | 12.55 到 12.87 ms | 8.3 到 8.5 倍 | 2.7 倍 |
| 统计 | 1.16 到 1.21 ms | 3.79 到 3.86 ms | 10.40 到 10.43 ms | 8.7 到 8.9 倍 | 2.7 倍 |

- P99：Node 有 JIT 是 4 到 16.5 ms，`--jitless` 是 4 到 25 ms，QuickJS 是 15.5 到 44.4 ms。
- 冷启动的 Node 进程第一次渲染订单列表要 74 到 75 ms。
- 在 quickjs v0.26.12 和 v0.26.13 之前，也在 SSR 包的三项改写之前（合并 React 写出的 chunk，React 的长 `switch` 前先查 `Set`，以及调低 seroval 改用 `JSON.stringify` 的长度，seroval 是 TanStack Router 用来把页面数据写进 HTML 的库），同样的测法是比有 JIT 慢约 13.6 倍，比 `--jitless` 慢 4.45 倍。
- 这里只比渲染。整个请求的对比见 [和 Next.js 与 TanStack Start 比](#和-nextjs-与-tanstack-start-比)。

### 和 Next.js 与 TanStack Start 比

shop 另外照着写了 Next.js 16.4.2 版（App Router，每个路由都是动态的，数据在服务端组件里取，React 组件相同）和 TanStack Start 1.169.3 版（路由和 loader 相同），跑在 Node 24.13.0 上。这两个版本只为这次测量而写，不在本仓库里。三边六个页面的可见文本相同。测的是走 HTTP 的完整请求，六个页面轮流，带 `Accept-Encoding: identity`，同一台 GCP 机器，同一时段。两核时，Next.js 和 Start 用 Node 的 cluster 模块开两个进程（Start 用 Nitro 的 `node-cluster` preset），tifa 开 2 个 VM。

| | tifa | Next.js | TanStack Start |
| --- | --- | --- | --- |
| 单核，每秒请求数 | 49 到 52 | 185 到 199 | 284 到 293 |
| 两核，2 个在途，每秒请求数 | 100 到 102 | 312 | 513 到 520 |
| 两核是单核的 | 1.98 倍 | 1.67 倍 | 1.81 倍 |
| 内存峰值（RSS），单核 | 62 MiB | 466 MiB | 356 到 366 MiB |
| 内存峰值（RSS），两核 | 83 MiB | 989 到 1000 MiB | 781 到 784 MiB |
| 进程启动到第一次响应 | 273 ms | 659 ms | 294 ms |
| 从第几个请求起延迟稳定 | 第 7 个 | 第 260 到 530 个 | 第 310 到 510 个 |

- 单核时，Next.js 每秒答的请求是 tifa 的 3.7 到 3.9 倍，Start 是 5.6 到 5.8 倍。Next.js 加 `--jitless` 时是 1.27 倍，统计页上 tifa 比它快 2% 到 4%。
- 压测工具用默认的 `Accept-Encoding` 时，tifa 和 Next.js 发 gzip，Start 不压缩（每页约 53 KB，压缩后约 8.5 KB）。压缩让 tifa 每秒请求数少 1.3%，让单核的 Next.js 少 16%，这时 Next.js 是 tifa 的 3.1 倍。

## 多核怎么扩展

六个页面轮流请求，以 gzip 发出，在途请求数等于 VM 数。服务钉在和 VM 数一样多的 CPU 上：先每个物理核一个（1 到 4），再加同一批核的超线程（5 到 8）。

| VM 数 | 请求/秒 | 是 1 个 VM 的几倍 | P50 | P99 |
| --- | --- | --- | --- | --- |
| 1 | 49.4 | 1.00 | 13.4 ms | 43.9 ms |
| 2 | 96.0 | 1.94 | 13.4 ms | 45.6 ms |
| 3 | 141.8 | 2.87 | 13.7 ms | 47.1 ms |
| 4 | 185.3 | 3.75 | 13.9 ms | 48.4 ms |
| 5，从这里起用超线程 | 195.5 | 3.96 | 18.0 ms | 65.7 ms |
| 6 | 206.4 | 4.18 | 21.6 ms | 73.1 ms |
| 7 | 214.2 | 4.34 | 22.3 ms | 77.0 ms |
| 8 | 222.6 | 4.51 | 23.5 ms | 80.2 ms |

每行是两轮的平均。

- 在测过的 4 个物理核以内，吞吐近似线性增长：4 个核走 HTTP 是 1 个核的 3.75 倍。quickjs v0.26.13 时不走 HTTP、直接用渲染池是 3.87 倍。每个核损失的那几个百分点像是共用的 L3 缓存或内存造成的，虚机上没有硬件计数器，证实不了。
- 超线程只多约 20%。1 个核跑 2 个 VM 是每秒 59.3 到 60.4 个请求，跑 1 个是 49.4。一次渲染的 CPU 时间从约 20 ms 涨到 33 到 34 ms，摊在解释器的所有函数上：两个线程在抢同一个核。
- 用 quickjs v0.26.13 测、当时还没有压缩：libc 分配器的锁、垃圾回收、HTTP 和内核合计约占 3% 的 CPU。整个程序 99.5% 的 CPU 在用户态，内核占 0.3% 到 0.5%。所以吞吐跟着单次渲染的时间走。
- 请求比 VM 多时吞吐不掉，只是排队变长：3 个核上 6 个 VM、24 个在途请求，仍有每秒 170.0 到 174.8 个，P50 是 133 到 137 ms。

## 机器怎么配

### CPU 和 `ssr.vms`

这一部分的请求拿到的页面都是 gzip。

- [`ssr.vms`](config.zh-CN.md#配置项) 保持默认就好。默认值是 Go 看到的 CPU 数（`GOMAXPROCS`），在容器里跟着 CPU 限额走。
- VM 比 CPU 多不会多出吞吐。渲染不会排队，而是在抢 CPU，每次都变慢：7 个 CPU 上 8 个 VM 是每秒 212 到 218 个请求、P50 25.9 到 26.4 ms，7 个 VM 是 211 到 214 个、22.4 到 22.5 ms。
- VM 比 CPU 少，是拿吞吐换一点延迟：同样 7 个 CPU，4 个 VM 是每秒 155 到 162 个请求、P50 17.2 到 17.8 ms。系统仍会把两个渲染线程放到同一个核的两个超线程上，而别的核还空着。只给程序和物理核一样多的 CPU，两样都更好：4 个物理核上 4 个 VM 是每秒 182 到 188 个、13.8 到 13.9 ms。
- 云上的一个 vCPU 通常是一个超线程，2 个 vCPU 常常就是 1 个物理核。超线程都忙起来时吞吐更高，但每次渲染更慢：shop 的页面在物理核上 P50 约 14 ms，每个核的两个线程都在渲染时约 22 ms。
- 14 ms 的条件是程序钉在每个物理核的一个超线程上，另一个超线程几乎空着。cpuset（比如 Docker 的 `--cpuset-cpus`）能把程序钉到这样的 CPU 上，但管不了别的程序用它们的兄弟超线程。Kubernetes 的 static CPU manager 策略倾向于整核分配，一个核的两个超线程一起给，那就是上面 22 ms 的情况。只设 CPU 配额（比如 Docker 的 `--cpus`）时线程不绑核，结果可能更像上面 VM 比 CPU 少的情况。这种情况没有测过。
- 按 shop 六个页面轮流、每次渲染平均约 21 ms CPU 的情况，每个物理核每秒约 46 次渲染，vCPU 是超线程而且都忙时每个 vCPU 约 29 次（6 个 vCPU 每秒 172.0 到 173.9 次）。渲染时间不同的页面按比例换算。

只有整页加载才渲染。在浏览器里切换页面取的是 Go 直接写的 JSON，不经过 VM，API 路由和命中缓存的页面也不渲染。3 个物理核上 6 个 VM、64 个在途请求时，用 quickjs v0.26.13 测：

| 请求 | 请求/秒 | P50 | P99 |
| --- | --- | --- | --- |
| 列表、订单、统计的导航数据 | 20,161、33,030、21,264 | 1.5 到 2.5 ms | 8.1 到 14.1 ms |
| `Cache = true` 的页面命中缓存 | 22,538 | 2.1 ms | 13.1 ms |
| 同一页面回 304 | 31,165 | 1.5 ms | 8.8 ms |
| API 用 `PATCH` 改一个订单 | 57,905 | 1.4 ms | 3.3 ms |

这些请求的成本很大一块在应用自己，不在 tifa。导航数据和命中缓存的请求里，20% 到 24% 花在 shop 自己的 `Load` 上，它每个请求都把全部订单复制、排序一遍，13% 到 20% 花在写响应的系统调用上。`PATCH` 用 3 个核只比 1 个核多 56%，像是卡在 shop 自己的订单锁（`ordersMu`）上，这一类没有剖析过。命中缓存和导航数据请求一样贵：缓存键里有数据，所以查缓存之前每个 `Load` 都要先跑完。

### 内存

渲染六个页面时整个程序的 RSS 峰值（内核记的最高值），每个 CPU 一个 VM，在途请求数等于 VM 数，页面以 gzip 发出：

| VM 数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| RSS 峰值 | 64 MiB | 84 MiB | 102 MiB | 122 MiB | 141 MiB | 158 MiB | 180 MiB | 201 MiB |

CPU 固定为 7 个时，4、7、8 个 VM 的峰值是 136 到 138、178 到 181、202 到 204 MiB。所以用 gzip 时 shop 大约要 45 MiB 加上每个 VM 约 19 MiB。其中一部分不是 VM 占的：每个正在压缩的回答都拿着一个编码器。服务钉在 3 个 CPU 上，`GOMAXPROCS` 和 VM 数都是 k，在途 k 个请求，各测两轮：

| VM 数和在途请求数 | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| 不压缩 | 62 MiB | 79 MiB | 115 MiB | 180 MiB |
| gzip | 64 MiB | 83 到 84 MiB | 121 到 123 MiB | 199 到 200 MiB |
| zstd | 65 MiB | 85 到 86 MiB | 126 到 129 MiB | 213 MiB |

不压缩时每个 VM 约 17 MiB，和 quickjs v0.26.13、v0.26.14 时一样。在途 8 个请求时，每个正在压缩的请求 gzip 多占约 2.4 MiB，zstd 多占约 4 MiB。Chrome 123 起浏览器发的是 `gzip, deflate, br, zstd`，拿到的是 zstd，所以按每个 VM 约 21 MiB 准备。用 quickjs v0.26.13 测的：在途请求数是 VM 数两倍时，8 个 VM 的峰值从 180 MiB 涨到 191 到 193 MiB，6 个 VM 只回导航数据、API 和缓存页面时，每档结束时的 RSS 是 88 到 98 MiB。

一个 VM 占多少，用 quickjs v0.26.13 测：

- 刚加载完 shop 的包约 7.8 MB，渲染几百次后约 8.6 到 8.8 MB。其中垃圾回收后真正在用的约 4.9 MB，其余是分配器取整和留着的块。
- React 转义的缓存（见[构建](#构建)）满了约 0.5 到 2 MB，shop 只用了它的一小部分。
- 在 Linux 上还有约 1 MB 不在引擎的统计里：libc 的 TLS 栈的块，引擎翻译成 Go 后把 C 的局部变量放在这里，VM 到过的每一层调用深度各一块，留到 VM 关闭。Linux 以外，从 quickjs v0.26.15 起，每个 VM 给这个栈留一块 1 MiB，到 VM 关闭为止，其中只有栈到过的页真正占内存。

这些加起来约 10 MB。不压缩时每个 VM 约 17 MiB，剩下的约 7 MiB 还没有拆开看过。

`ssr.vm_memory`（默认每个 VM 128 MiB）远高于这些。有两种情况要另外留内存，[栈深度](config.zh-CN.md#栈深度)讲了这两种情况，以及小机器上怎么调低：

- 无限递归的代码会让每个 VM 一时多占约 24 MB 的 goroutine 栈。
- 在 Linux 上，一个 VM 递归到过 10000 层后，会一直多占约 20 MB 的 TLS 块，直到 VM 关闭。

## 压缩

[`server.compress`](config.zh-CN.md#配置项) 默认开着（见[压缩](build.zh-CN.md#压缩)）。压缩一个页面花的时间不到它渲染时间的 1.5%，浏览器包直接发构建写好的 gzip 文件，不花 CPU。

压缩一个页面要多久：在上面那台机器的一个核上，编码器像服务端一样复用，取 200 次的平均，旁边的渲染 P50 来自[一个页面渲染多快](#一个页面渲染多快)：

| 页面 | HTML | gzip 5 级 | zstd 默认级别 | 占渲染时间 |
| --- | --- | --- | --- | --- |
| 订单列表 | 81 到 86 KB | 256 到 280 µs 压到 9.3 到 9.8 KB | 143 到 152 µs 压到 9.0 到 9.5 KB | gzip 0.7% 到 0.8%，zstd 0.4% |
| 订单 | 约 38 KB | 180 µs 压到 8.3 到 8.4 KB | 126 到 128 µs 压到 8.6 到 8.7 KB | gzip 1.4%，zstd 1.0% |
| 统计 | 约 34 KB | 131 到 138 µs 压到 7.0 KB | 107 到 108 µs 压到 7.2 到 7.3 KB | gzip 1.3%，zstd 1.0% |

整个请求，用 quickjs v0.26.14 测：服务端在一个物理核上（cpu 0 和 4，2 个 VM），oha 在另一个物理核上，每步 15 秒，跑两轮。页面用 `--cache-size 0` 渲染，缓存的订单页（两个轮流）从 HTML 缓存里出。「不压缩」是请求不要压缩，zstd 是 `Accept-Encoding: gzip, zstd` 拿到的，gzip 是 `Accept-Encoding: gzip` 拿到的：

| 请求 | 不压缩 | zstd | gzip |
| --- | --- | --- | --- |
| 六个页面轮流，在途 1 个 | 每秒 43.4 到 44.5 个，P50 14.9 到 15.0 ms，每个 51 到 52 KB | 43.3 到 43.7，P50 15.1 到 15.2 ms，8.3 到 8.4 KB | 41.6 到 43.6，P50 15.2 到 15.4 ms，8.3 KB |
| 六个页面轮流，在途 2 个 | 52.1 到 53.3，P50 24.6 到 24.8 ms | 53.0 到 53.8，P50 24.7 到 24.9 ms | 51.4 到 51.8，P50 25.1 到 25.2 ms |
| 列表的导航数据，在途 64 个 | 8,108 到 8,159，6,632 字节 | 7,383 到 7,484，1,227 字节 | 6,951 到 7,002，1,258 字节 |
| 订单的导航数据，在途 64 个 | 12,875 到 13,356，1,350 字节 | 11,091 到 11,102，739 字节 | 10,689 到 10,761，737 字节 |
| 统计的导航数据，在途 64 个 | 8,729 到 8,743，2,947 字节 | 7,833 到 7,837，777 字节 | 7,564 到 7,636，734 字节 |
| 缓存的订单页，在途 1 个 | 6,077 到 6,115，P50 0.15 ms，38,469 字节 | 6,737 到 6,852，P50 0.14 ms，8,607 和 8,609 字节 | 6,943 到 6,975，P50 0.14 ms，8,317 字节 |
| 缓存的订单页，在途 64 个 | 10,653 到 11,174，P99 13.8 到 14.6 ms | 13,140 到 13,245，P99 12.6 到 12.8 ms | 13,230 到 13,294，P99 12.7 ms |
| 浏览器包里 700 KB 的 chunk，在途 64 个 | 3,854 到 5,105，699,833 字节 | `.gz` 文件：11,549 到 12,182，224,176 字节 | 同一个 `.gz` 文件 |

- 对页面来说，压缩的开销淹没在整个请求的波动里：一个请求的 CPU 在两次之间能差 1 ms，是压缩时间的好几倍。页面发出去小了约 6 倍。
- 导航数据回答起来很便宜，所以压缩的开销看得出来：每个请求多 23 到 43 µs 的 CPU，核跑满时每秒少 8% 到 20% 的请求，回答小 1.8 到 5.4 倍。这里 gzip 也比 zstd 贵。
- 命中缓存时直接发缓存和页面一起存好的 gzip 或 zstd 版本，所以压缩的命中反而比不压缩的省 CPU，每个 0.15 ms 对 0.18 到 0.19 ms，因为要写的字节少。要是每次命中都把存着的 HTML 再压一遍，每次命中一共要 0.45 ms（zstd）和 0.54 ms（gzip）的 CPU，其中压缩约占 0.26 到 0.34 ms，在途 64 个时每秒只剩 4,410 到 4,423 和 3,711 到 3,712 个命中，P99 是 34 到 37 ms。接受压缩的请求没命中时，页面压成两种版本，发出其中一种，所以比不带 `Cache` 的页面多压一次：占它渲染时间的 1.0% 到 1.4%，是用第一张表的压缩时间除以渲染 P50 算出来的。不接受压缩的请求没命中时只存 HTML，什么也不压。
- 浏览器包发 `.gz` 文件比发原文件还省 CPU，因为要写的字节少：每秒请求数是原来的 2.4 到 3 倍。
- 用 gzhttp 默认的 zstd 最快级别，一页只要 82 到 138 µs，但页面比 gzip 大 3% 到 11%。用默认级别（Caddy 和 Traefik 都这样），订单列表比 gzip 小 3%，其他页面大约大 4%。
- brotli 用纯 Go 的 github.com/andybalholm/brotli，4 级和 5 级一页要 648 到 1,183 µs，是 gzip 的 4 到 6 倍，页面只小 3% 到 16%。
- 构建时压缩的文件，gzip 最高级别把 700 KB 的 chunk 压到 224 KB。zstd 最高级别是 213 KB，brotli 11 级是 192 KB。
- shop 的程序大了 1.12 MiB：0.35 MiB 是 `.gz` 文件，其余是 gzip 和 zstd 的代码。
- 测的时候，机器上其他 cpu 最多忙 3%。

## 哪些改动让它变快

所有改动都让 HTML 逐字节不变。效果指 shop 页面一次渲染花的时间，没有另外注明的都在上面那台机器上测。

### 引擎

fork [github.com/liustack/quickjs](https://github.com/liustack/quickjs#quickjs-liustack-fork) 的 README 列了每项改动，细节和测试都在那里。和速度有关的：

| 改动 | 版本 | 效果 |
| --- | --- | --- |
| JavaScript 调用不再分配内存。原来每次调用的参数和局部变量空间来自 libc 的 malloc，darwin、freebsd、windows 上还要分配 Go 内存 | v0.26.12 | linux/amd64 上少花约 11% 的时间，darwin/arm64（Apple M4）上少约 14%。Linux 上把字节码加载进 VM 少花约 11%。顺带把 libc 分配器的锁从每次调用里拿掉了，见[从基线到现在](#从基线到现在) |
| 解释器主循环少做栈上的读写：对 ccgo（把 C 翻译成 Go 的工具）写出的 Go 代码做三项机械改写 | v0.26.13 | linux/amd64 上少约 12.5%，darwin/arm64 上少约 17%。解释器的 Go 栈帧在 amd64 上从 2608 字节降到 896，在 arm64 上从 7744 降到 944 |
| 给普通对象加新属性时跳过通用路径 | v0.26.13 | 对象字面量的一个属性从约 95 ns 降到 55 ns，一次渲染少约 6% |
| 引擎函数在每个 return 前释放 TLS 帧，不再放进 `defer`。Go 不内联带 `defer` 的函数，所以几百个小的引擎函数原来都是真调用 | v0.26.15 | linux/amd64 上少约 10%，开不开 PGO 都一样 |
| 以一个字符或一类字符开头的正则（比如 React 的 `/["&<>]/`）先找到这个字符下一次出现的位置，从那里开始匹配 | v0.26.15 | 少约 3% |
| `===` 和取键名只在少走的路径上才占 TLS 帧：比较两个 BigInt，以及取整数键的名字 | v0.26.15 | 开 PGO 少 0.7%，不开少 2% |
| Linux 以外，每个 VM 在 TLS 栈上留一块 1 MiB。原来渲染中 libc 在它分配器唯一的那把锁下反复 malloc 和 free 这个栈的段 | v0.26.15 | 在 quickjs 仓库里单测这一项：Apple M4 上 10 个 VM 每秒渲染数是原来的 1.39 到 1.55 倍，等锁时间从 3.8% 到 5.3% 降到约 0.5%，1 个 VM 的速度不变。在 tifa 里连同整个版本一起测：10 个 VM 等锁的时间占 0.67% 到 0.76%，原来是 4.2% 到 4.5%，相对 1 个 VM 的加速比是 4.91 到 5.09，原来是 3.39 到 3.62。Linux 不受影响 |

v0.26.13 整体的渲染时间是 v0.26.12 的 0.823，8 轮在 0.821 到 0.825 之间。v0.26.15 配重新采集的剖析，渲染时间是 v0.26.14 配它的剖析的 0.859，6 轮在 0.857 到 0.861 之间，不开 PGO 是 0.843，在 0.842 到 0.846 之间。HTML 逐字节不变。整个请求在 3 个物理核上跑 6 个 VM、六个页面轮流、6 个在途、两边都以 gzip 发出时，涨到 1.17 倍：开 PGO 每秒 177.4 个请求（176.3 到 182.3），原来是 151.9（150.5 到 155.8），P50 是 21.3 到 21.9 ms，原来是 25.7 到 25.9 ms，P99 是 72.3 到 74.8 ms，原来是 84.7 到 87.1 ms。不开 PGO 是 172.2（171.7 到 174.1），原来是 147.3（147.1 到 150.0）。Apple M4 上两边都不开 PGO，1 个 VM 每秒渲染 108 个页面，原来是 84 到 86，10 个 VM 是 532 到 549，原来是 288 到 305，是原来的 1.80 到 1.88 倍。在上面那台机器的 2 个物理核上跑 2 个 VM，两个版本相对 1 个 VM 的加速比都在 1.96 到 2.03，等锁都不到 0.01%，所以在 Linux 上多个 VM 和 1 个 VM 快得一样多。

### 构建

[docs/build.zh-CN.md](build.zh-CN.md#前端产物) 讲了 Vite 插件对 SSR 包的每项改写，[按剖析优化](build.zh-CN.md#按剖析优化)讲了剖析：

| 改动 | 效果 |
| --- | --- |
| React DOM 只留字符串渲染器 | 在早期更小的 shop 上：包小 25%，4 个 VM 的池启动时间约减半。渲染时间不变 |
| 每个 VM 缓存 React 的 HTML 转义 | shop 少 8% 到 10%（Apple M4），它的 Tailwind 类名里满是要转义的字符。纯文字页面不变 |
| React 把两个子段之间的 chunk 先拼好再交出去 | shop 少 5% 到 7%，纯文字页面少 6% 到 11% |
| React 按属性名和标签名的长 `switch` 前先查一次 `Set` | shop 少 6% 到 7%，纯文字页面少 9% 到 12% |
| React 的 HTML 转义改用五次 `replaceAll`，不再逐个字符循环，查有没有要转义的字符改用 `exec` | 纯文字页面少 8.7% 到 9.8%，落地页少 0.7%。shop 和小页面上下浮动不超过 1.6%，它们的转义大多已由上面的缓存直接给出 |
| React 不再构建组件栈。栈只进 `onError` 的第二个参数 `errorInfo`，tifa 给 `renderToString` 的处理函数丢掉这个参数 | shop 少 1.2% 到 4.2%，纯文字页面和落地页少 7.2% 到 7.8%，小页面少 2.3% 到 2.6% |
| 导入 React 和 React DOM 的模块拿到的命名空间是普通值，不再是 getter | shop 六页里的五页少 1.3% 到 2.9%。其他页面上下浮动不超过 1% |
| React 的 key path 里不再放组件名 | shop 六页里的五页少 2.1% 到 2.7%，其他页面少 1.4% 到 2.9% |
| seroval 从 2 个 UTF-16 码元起就用 `JSON.stringify` 转义字符串 | 小页面少 6% 到 10%，大页面最多 2.5% |
| 每个 `Load` 的数据以 Go 写的 JSON 文本交给浏览器（[数据协议](build.zh-CN.md#数据协议)） | TanStack 默认的序列化处理同样的数据要慢好几倍 |
| 用页面渲染的剖析编译程序（PGO） | linux/amd64 上少约 2.4%，darwin/arm64（Apple M4）上少约 7%，用的是 quickjs v0.26.15 和它的剖析 |

转义缓存、拼好的 chunk 和 `Set` 检查这三项合起来，shop 快 11% 到 14%，纯文字页面快 17.5% 到 22%，小页面快 8% 到 11%。

转义链、组件栈、命名空间和 key path 这四项改写在上面那台机器上测，开 PGO，1 个 VM 钉在一个核上，每一步和前一步比，轮流跑 12 轮。shop 的第六页是一家店的统计页，在它上面命名空间这一步测得慢 2.4%，key path 这一步快 5.3%，两步合起来快 3.3%，接近其他页面的 3.8% 到 5.4%。四项合起来，shop 快 6.5% 到 7.5%，纯文字页面快 17.6% 到 18.3%，落地页快 10.1%，小页面快 5.4% 到 5.9%。HTML 逐字节不变。为了让报错栈里的位置准确，所有改写都保持 React DOM 每一行的位置不变，这一点本身让渲染时间上下浮动不超过 1.4%。

### 从基线到现在

基线是 tifa 0673723 配 quickjs v0.26.8。它已经有转义缓存、裁掉的渲染器和 JSON 文本适配器，没有另外三项改写，也没有 v0.26.12、v0.26.13 和 v0.26.15。现在是 tifa 790b746 配 v0.26.15。两边都不带 PGO，在同一时段交替测：

| | 基线 | 现在 | 快了 |
| --- | --- | --- | --- |
| 1 个 VM，单次渲染，六个页面各自 | 19.3 到 64.2 ms | 10.4 到 35.6 ms | 1.80 到 1.88 倍（时间是 0.532 到 0.555） |
| 1 个 VM，走 HTTP 一次一个请求 | 一个订单列表 65.1 ms | 同一列表 36.3 ms | 六个页面 1.79 到 1.86 倍 |
| 3 个核 6 个 VM，六个页面，6 个在途 | 每秒 68.5 个请求（64.8 到 72.2） | 每秒 174.3 个（170.6 到 176.5） | 2.5 倍 |
| 同上，P50 和 P99 | 53.7 到 56.1 ms，239 到 285 ms | 21.6 到 22.6 ms，74.9 到 78.4 ms | |

基线没有压缩，所以走 HTTP 的两行两边都要的是 identity，各测三轮。

单核整体约快 1.83 倍。多核快得更多，是因为基线被一把锁拖住了。原来每次 JavaScript 调用都经 libc 分配内存，libc 的分配器只有一把全局锁。6 个 VM 时 20% 的 CPU 耗在 `sync.Mutex.Lock` 上，一次渲染要 81 ms 的 CPU，1 个 VM 时只要 38 ms。v0.26.12 去掉了这次分配，锁的争用也跟着没了。只有 1 个 VM 的基准测试看不出这一点。

## 试过但没做的

每项写了能带来什么、为什么放弃。再试其中某项之前先看这里。

### 引擎

- **再给 135 个小函数去掉 TLS 帧**（TLS 帧是 libc 的 TLS 栈里的一块，引擎翻译成 Go 后把函数里取了地址的 C 局部变量放在这里）：约占渲染时间的 0.24%，测不出来，却要多维护 135 条。
- **让调用空间在 TLS 帧里放到 768 字节以上**：1024 字节只多覆盖 0.02% 的调用，却让 Linux 每层调用深度留的块从 2 KB 翻到 4 KB。
- **把不常用的 opcode 搬出解释器主循环**：在 amd64 上单做最多 8%，这是把 shop 从没跑过的 56 个 opcode 的 handler 换成空桩测出的上限，叠在「让 15 个值留在栈槽里」那项改写上只剩 1.4%，arm64 上 0.5%。还得把主循环的局部变量收进一个结构体。
- **用闭包或函数表分发 opcode**，有些 Go 写的解释器这么做：等于重写解释器，违背 fork 只做机械改写的规矩。没试。
- **等 Go 1.28**：开发版让没改的引擎在 amd64 上快 5%、arm64 上快 2%，却让改写后的引擎在 amd64 上慢 5% 到 6.5%，原因没找到。在开发版上改写仍然赢，amd64 4.2%，arm64 15.5%。
- **留住对象字面量的中间形状**（形状记录一个对象有哪些属性、按什么顺序）：在新属性快路径之上再快约 2%。两个列表页跑到 VM 内存上限失败了，因为留下的形状拉着原型和原型能连到的一切。正确的做法要给引擎的一个结构体加字段，得从 C 重新生成 Go 代码。
- **字节码里放字面量模板**，像 V8 那样复制一个建好的对象：要改编译器和字节码格式，quickjs-ng 试过，没看出明显差别。
- **按最终大小分配字面量的属性数组**：建对象的 opcode 不知道属性数，换一种增长方式会让每个小对象都更占内存。只有和留住形状一起做才划算。
- **读属性的内联缓存**：quickjs-ng 加了又删了。在 17 个真实工具上从慢 11% 到快 54% 都有，平均只快 4%，还更占内存。没试。
- **在解释器主循环里给 `===` 加快路径**：反而慢 1.0% 到 1.3%，是在 tifa a2084b4、quickjs v0.26.14 开 PGO 时测的，下面两项也是。解释器函数太大，Go 只往里内联最小的函数，所以在那里加一个辅助函数就多一次真调用。把中断检查的倒计数挪进一个小函数，也因为同样的原因没有变化（时间是原来的 0.998 到 1.001）。
- **新对象的位字段从 9 次写合成 2 次**：没有变化（0.991 到 1.010）。时间花在第一次写新对象时的缓存缺失上，少写几次只是把它挪了地方。
- **对象展开的快路径**（`JS_CopyDataProperties`）：Apple M4 上的微基准里一次展开从 415 ns 降到 240 ns，shop 却没变（0.997 到 1.005）。
- **每个 VM 一个 libc 分配器**，绕开它的全局锁：Linux 上 8 个 VM 时这把锁只占 0.4% 到 0.9% 的 CPU，v0.26.15 起 Apple M4 上 10 个 VM 等锁的时间约占 0.7%。
- **从字节码里去掉函数源码**（`JS_SetStripInfo`）省 VM 内存：seroval 用 `toString` 读自己辅助函数的源码写进页面，去掉后浏览器端会坏。
- **用 Go 实现 `TextEncoder`、`URL` 等兼容代码**：渲染时几乎不调用它们，渲染时间没有可省的。

### 构建

- **把静态 JSX 提到组件外**，像 Babel 的 transform-react-constant-elements：shop 的页面每次少建 44 到 83 个元素，渲染只快 0.5% 到 0.9%，几乎全静态的页面快 5.4%。每少建一个元素约省 0.8 µs，时间主要花在 React 遍历和拼字符串上。它管不到 `node_modules` 里库的 JSX，要么得装 Babel，要么得自己写一个转换。提上去的元素被一个 VM 的所有请求共用，某个库要是改了它，改动会带到下一个请求。
- **降低 SSR 包的语法目标**：ES2021 到 ES2018 差 1% 以内。从 ES2017 起对象展开变成辅助函数，shop 慢 33% 到 45%。目标保持 ES2022。
- **SSR 包不压缩**：包本来就压缩了。不压缩时渲染慢约 1%，包从 772 KB 变成 1,799 KB，VM 加载后从 7,634 KiB 变成 9,133 KiB。
- **对 React 的小改写**，每项都不到 1%：`push(x)` 改成按下标赋值（0.1% 到 0.9%），`jsxProd` 和 `createElement` 里的 `for...in` 拷贝改成展开（会多拷 symbol 键，语义不同），`startChunkForTag` 和 `endChunkForTag` 的 `Map` 换成对象（不到 0.5%），`for...in` 换成 `Object.keys`（微基准里更慢），`hasOwnProperty.call` 换成 `Object.hasOwn`（每个键省约 25 ns）。
- **React 转义和它查找要转义字符的别的写法**：`indexOf` 查五次、逐字符循环都比它的正则慢，查找时五次 `indexOf` 和 `search` 也都比 `exec` 慢。每个字符串都先查转义缓存再跑正则，纯文字页面慢 4%，在只测转义的基准里，一个订单列表的 1,188 次转义慢 22%，因为多数字符串不用转义，而 `Map` 查一次比搜一次更贵。所以缓存只收需要转义的字符串。搜索剩下的开销在引擎里。要是缓存满了就不再收，早先请求的文本会一直占着位置。要是淘汰最久没用的那条，每次命中都要多一次删除和一次写入。
- **把 React 的组件栈和 key path 里的名字换成更省的写法，而不是去掉**：把 `pushComponentStack` 内联到调用处，或者对字符串和函数类型不调 `getComponentNameFromType` 直接取名字，都在 1% 以内（shop 上 0.994 到 1.024）。花时间的是建对象和字符串，不是函数调用。
- **在插件里改写 react-spring 和 TanStack Table**：react-spring 做颜色插值时拿每个值去匹配一个有 148 个颜色名的正则，QuickJS 里一次 24 µs，Node `--jitless` 是 0.175 µs（占订单列表 2.1%）。TanStack Table 通过 `fn(this, ...args)` 调用，约 1 µs，对比 67 ns（占 1.2%）。改写它们就把插件绑在两个库的写法上。两处都该在引擎里做：正则的每个分支先比首字符再试，展开普通数组时不走迭代器。
- **把请求之间不变的页面片段缓存成 HTML**：tifa 不知道页面是怎么写的。`Cache = true` 按数据缓存整个页面。

## 怎么复测

[docs/testing.md](testing.md#performance-comparisons) 有渲染基准和 VM 内存的命令，[Reading BenchmarkShopParallel](testing.md#reading-benchmarkshopparallel) 讲怎么检查多个 VM 是否还能扩展（英文），[The engine profile](testing.md#the-engine-profile) 讲升级 quickjs 或 modernc.org/libc 后怎么重采 PGO 剖析（英文）。让数字能比的规矩：

- 在同一台机器上比，新旧两个构建一轮一轮交替跑。只有同一批轮次的比值能比：机器忙的时候绝对时间能差好几倍。
- 每次跑都钉在一个核上，并让它的超线程兄弟空着。Linux 上 `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list` 写着兄弟是谁。记下每轮的机器负载，别的任务占了约 10% 以上的 CPU 就重测。
- 比较两个构建每个页面的 HTML。路由会把渲染的时刻写进每个 match（`u:` 后面跟 13 位数字），先遮掉它。
- 只有 1 个 VM 的基准看不出 VM 之间的争用。改动碰到内存分配时，还要同时用多个 VM 渲染，看 mutex profile。

完整请求：构建 `examples/shop`，用 `taskset` 把 `bin/shop --server-addr 127.0.0.1:0 --cache-size 0` 钉在几个核上，从另一个物理核压测，在途请求数等于 VM 数。每次先热几秒，测扩展曲线时服务钉的 CPU 数等于 VM 数。

Node：用 `vm.runInThisContext` 加载同一份 `.tifa/dist/ssr.js`，渲染同样的输入，先热几百次，在 QuickJS 基准用的那个核上各跑一遍有 JIT 和 `--jitless`。找下一个该改的地方时，比较每个函数在 QuickJS 和 `--jitless` 的 Node 里各花多少时间：倍数远高于整体的函数就是候选。

## 还能从哪里继续

单次渲染的时间几乎就是全部成本：quickjs v0.26.13 时整个程序 99.5% 的 CPU 在用户态，v0.26.15 上解释器函数自己就占约 36%。渲染快多少，吞吐就涨多少。按可能的收益大致排序：

1. **引擎里的属性访问。** v0.26.15 上读属性约占一次渲染的 16%，光 `find_own_property` 就占 5.5%。赋值（`o.x = v`、`Object.assign`）还走慢路径，约占 2%，做快路径要检查原型上的 setter 和只读属性。
2. **建对象和释放对象。** 引擎的 malloc 和 free、建对象和释放对象、引用计数合计约占一次渲染的 13%。React 给每个元素、hook 和组件栈都建对象，所以 `createHook`、`pushComponentStack`、`jsxProd` 当时比 `--jitless` 的 Node 慢 6 到 12 倍。插件现在让 React 不再建没人读的组件栈，其余的只能在引擎里解决。
3. **所有函数都只在冷路径上分配 TLS 帧。** 分配和释放 TLS 帧仍占一次渲染的约 4.3%。v0.26.15 把 `===` 和取键名里要用帧的少见路径挪进了各自的函数。如果让 fixlib 对所有帧地址不传出去的函数都这样做，可能再快 1% 到 2%。
4. **每个 VM 少占内存。** 所有 VM 共用一份只读的函数源码和行号表，指向字节码，`toString` 照常能用。估计每个 VM 省约 380 KB。要改 C 补丁（fork 对 QuickJS 的 C 源码做的改动）、fixlib（fork 里改写生成的 Go 代码的工具）和 Go API。
5. **用 C 改动留住形状。** 等引擎的 Go 代码能从 C 重新生成时，让子形状引用父形状，可能拿到上面那 2%，又不让内存涨。也可以提给上游。
6. **amd64 上的 Go 1.28。** 正式发布后重测改写后的引擎。如果还是比 Go 1.27 慢，做一个最小复现报给 Go。
7. **转义缓存。** QuickJS 给 `Map` 的键算哈希时不加盐，同一哈希的字符串一多查找就变慢。每条按多 64 个码元算，把链长压在约 3,700 条以内，再加一个条数上限可以更短。不是 Latin-1 的长串（8,192 码元起）实际占内存约是内容的 4 倍：查一下字符串拼接是否留了多余的空间。
8. **arm64。** 栈上的改写之后，在 arm64 上存字节码位置当时最多占解释器自身时间的约 11.6%，原因没找到。这是上限：这条存储正好在读下一个 opcode 的依赖链上，采样可能把等在那里的时间算到了它头上。
9. **还没做的对比。** Node 自己的 HTTP 服务和 Node cluster，以及同一台机器上用 TanStack Start 和 Next.js 跑同样的页面。

# 性能

tifa 在 QuickJS 里渲染页面。QuickJS 是用 C 写的 JavaScript 解释器，被翻译成了 Go。一次渲染比 Node 慢，因为 Node 会把 JavaScript 编译成机器码。这篇文档给出数字和按这些数字怎么配机器，再给维护者讲做过什么、放弃了什么、下一步从哪里做。

## 这些数字怎么测的

各节没有另外说明时：

- 机器：Google Cloud 上一台 8 vCPU 的虚机，AMD EPYC 7B13（Zen 3），Linux。8 个 vCPU 是 4 个物理核，每核 2 个超线程：cpu `n` 和 cpu `n+4` 共用一个核。
- 软件：Go 1.27，quickjs v0.26.15，tifa 790b746，构建不带 PGO。`tifa build` 默认开 PGO，它让 linux/amd64 上的渲染再快约 2.4%（见[构建](#构建)）。用旧版本测的小节会注明。quickjs v0.26.16 只在[引擎](#引擎)一节和[内存](#内存)一节里讲它给每个 VM 多占多少的那段测过，v0.26.17 只在[内存](#内存)和[服务端](#服务端)里讲两次渲染之间回收的地方测过，其余各处的数字都是 v0.26.15 或更早版本的。引擎在 v0.27.3 及之前叫 quickjs，从 v0.28.0 起叫 slowjs，所以本文里 v0.27.3 及之前的版本仍用旧名。
- 应用：[examples/shop](../examples/shop/README.zh-CN.md) 的生产构建，React 19.3 和 TanStack Router，加 Tailwind CSS 和 shadcn/ui。六个页面：两家店各自的订单列表、一个订单、统计。在加店面（`app/store`）之前的 shop 上测。加了店面后 SSR 包从 772 KB 涨到 1,288 KB，所以跟包有关的数字，也就是程序启动和每个 VM 的内存，这里比现在的 shop 低。六个页面的 HTML 不变。
- 单次渲染：`test/ssr` 的 `BenchmarkShop`，一个热 VM 钉在一个核上，取多次渲染的中位数（P50）。
- 完整请求：构建出的 `bin/shop` 加 `--cache-size 0`，让每个页面请求都渲染，用 [oha](https://github.com/hatoo/oha) 压测，核够用时 oha 和服务钉在不同的核上。oha 用它默认的 `Accept-Encoding: gzip, compress, deflate, br` 请求，所以 [`server.compress`](config.zh-CN.md#配置项) 开着时页面以 gzip 发出，除非某节写明请求要的是 identity。压页面时 oha 只占一个 CPU 的 1% 到 2%。每一档先热几秒，再测 10 到 20 秒。

## 一个页面渲染多快

| 页面 | HTML | 渲染 P50 | 请求 P50 | 请求 P99 |
| --- | --- | --- | --- | --- |
| 订单列表 | 81 到 86 KB | 34.3 到 35.4 ms | 36.0 到 38.0 ms | 46.2 到 49.4 ms |
| 订单 | 约 38 KB | 12.5 到 12.9 ms | 13.4 到 13.8 ms | 22.4 到 23.5 ms |
| 统计 | 约 34 KB | 10.4 ms | 11.1 到 11.8 ms | 19.6 到 21.6 ms |

用 quickjs v0.26.15 测，不开 PGO。v0.26.16 渲染更快，见[引擎](#引擎)。

每个范围包括两家店。「渲染」是基准测试的数。「请求」是走 HTTP、一次一个请求，多出 Go 的 `Load`、JSON、gzip 和 net/http，服务在 3 个物理核上跑 6 个 VM。用 1 个 VM 时，一个请求比一次渲染多花 0.5 到 1.3 ms，其中 0.13 到 0.28 ms 是压缩（见[压缩](#压缩)）。一次一个请求时，每秒能出 26 到 28 个订单列表，或者约 88 个统计页。

程序启动时把 SSR 包编译成字节码一次，再把字节码逐个加载进池里的每个 VM。在加店面之前的 shop 上，编译约 0.2 秒，每个 VM 加载约 45 ms，这是在 quickjs v0.26.9 上测的。v0.26.12 让加载快了约 11%。

在 quickjs v0.27.0 和当前 shop 上，惰性注册 Temporal 后加载时间基本不变。同一进程后续 VM 的 `Load` 单独耗时从 41.69 ms 变为 41.43 ms，不含编译和关闭。进程里第一个被测 VM 从 49.17 ms 变为 49.95 ms，包含占位实现的首次注册。现有加载基准还会检查内存和关闭 VM，其同轮时间比值中位数是 1.008。以上是在 linux/amd64 上关闭 PGO、交替六轮的结果。真正首次使用 Temporal 的成本另计，见[内存](#内存)。

SSR 包是 ES 模块，每个 VM 把它当模块运行，这样包里可以用顶层 `await`（见[顶层 await 和严格模式](app.zh-CN.md#顶层-await-和严格模式)）。和原来的 IIFE 比，shop 的十六个页面 HTML 都不变：工作台页面耗时为 0.997（0.988 到 1.007），店面页面为 1.000（0.969 到 1.021），加载一个 VM 为 0.991 到 0.998，编译少约 7%。字节码从 5.36 MB 降到 4.04 MB，因为包住整个包的那个函数的源码不用再存。一个 VM 加载后多占 31 KB（8,884 KiB 对 8,853），渲染后多 19 到 31 KB。这要靠 slowjs 在模块跑完后释放它的顶层函数：QuickJS 原本让它连同所有顶层变量一直留到 VM 关闭，在 shop 的 VM 里约 0.8 MB。测量在 linux/amd64 上，不开 PGO，一个 VM 跑在一对空闲了 30 秒的核的其中一个线程上，同一个程序轮流跑两个包，覆盖 3 种代码布局，每种 6 轮：工作台先热 256 次，每轮每页 30 次，店面先热 256 次，每轮每页 12 次。比值取三种布局中位数的中间那个，范围是全部 18 轮的。

## 和 Node 比

同一份 `ssr.js` 放进 Node 24，用 `vm.runInThisContext` 加载，给同样的输入，同一台机器、同一个核。Node 先热 600 次渲染，再跑 5 轮，表里是每轮 P50 的中位数。有 JIT 就是平常的 Node。`--jitless` 关掉 V8 编译成机器码的部分，V8 只解释执行，更接近 QuickJS 的做法。

| 页面 | Node 有 JIT | Node `--jitless` | QuickJS | QuickJS 比有 JIT 慢 | QuickJS 比 jitless 慢 |
| --- | --- | --- | --- | --- | --- |
| 订单列表 | 4.28 到 4.36 ms | 12.77 到 12.99 ms | 34.38 到 35.49 ms | 8.0 到 8.2 倍 | 2.7 倍 |
| 订单 | 1.48 到 1.57 ms | 4.60 到 4.79 ms | 12.55 到 12.87 ms | 8.3 到 8.5 倍 | 2.7 倍 |
| 统计 | 1.16 到 1.21 ms | 3.79 到 3.86 ms | 10.40 到 10.43 ms | 8.7 到 8.9 倍 | 2.7 倍 |

- P99：Node 有 JIT 是 4 到 16.5 ms，`--jitless` 是 4 到 25 ms，QuickJS 是 15.5 到 44.4 ms。
- 冷启动的 Node 进程第一次渲染订单列表要 74 到 75 ms。
- 在 quickjs v0.26.12 和 v0.26.13 之前，也在 SSR 包的三项改写之前（合并 React 写出的 chunk，React 的长 `switch` 前先查 `Set`，以及调低 seroval 改用 `JSON.stringify` 的长度，seroval 是 TanStack Router 用来把页面数据写进 HTML 的库），同样的测法是比有 JIT 慢约 13.6 倍，比 `--jitless` 慢 4.45 倍。
- 这里只比渲染。整个请求的对比见 [和 Next.js 与 TanStack Start 比](#和-nextjs-与-tanstack-start-比)。

### 和 Next.js 与 TanStack Start 比

shop 另外照着写了 Next.js 16.4.2 版（App Router，每个路由都是动态的，数据在服务端组件里取，React 组件相同）和 TanStack Start 1.169.3 版（路由和 loader 相同），跑在 Node 24.13.0 上。这两个版本只为这次测量而写，不在本仓库里。三边六个页面的可见文本相同，tifa 跑的是加店面之前的 shop。测的是走 HTTP 的完整请求，六个页面轮流，带 `Accept-Encoding: identity`，同一台 GCP 机器，同一时段。两核时，Next.js 和 Start 用 Node 的 cluster 模块开两个进程（Start 用 Nitro 的 `node-cluster` preset），tifa 开 2 个 VM。

| 两核，2 个在途，每秒请求数 | 100 到 102 | 312 | 513 到 520 |

## 和别的纯 Go 引擎比

slowjs 的[引擎对比](https://github.com/liustack/slowjs/blob/main/docs/benchmarks.md)在每个能跑现代 JavaScript 的纯 Go 引擎上渲染 tifa 的页面，拿 C QuickJS、QuickJS-NG 和 Node 当参照，每次 slowjs 发版都重跑。v0.26.17，GCP 的一个核，不开 PGO，渲染耗时和 tifa 用的引擎相比（大于 1 就是更慢）：

| --- | --- | --- |
| go-quickjs v0.28.0，解释器 | 1.13 | 1.24，20 页里 2 页失败 |
| go-quickjs v0.28.0，JIT | 1.20 | 1.43，20 页里 2 页失败 |

## 多核怎么扩展

六个页面轮流请求，以 gzip 发出，在途请求数等于 VM 数。服务钉在和 VM 数一样多的 CPU 上：先每个物理核一个（1 到 4），再加同一批核的超线程（5 到 8）。

| VM 数 | 请求/秒 | 是 1 个 VM 的几倍 | P50 | P99 |
| --- | --- | --- | --- | --- |
| 1 | 49.4 | 1.00 | 13.4 ms | 43.9 ms |
| 2 | 96.0 | 1.94 | 13.4 ms | 45.6 ms |
| 3 | 141.8 | 2.87 | 13.7 ms | 47.1 ms |
| 4 | 185.3 | 3.75 | 13.9 ms | 48.4 ms |
| 5，从这里起用超线程 | 195.5 | 3.96 | 18.0 ms | 65.7 ms |
| 6 | 206.4 | 4.18 | 21.6 ms | 73.1 ms |
| 7 | 214.2 | 4.34 | 22.3 ms | 77.0 ms |
| 8 | 222.6 | 4.51 | 23.5 ms | 80.2 ms |

每行是两轮的平均。

- 在测过的 4 个物理核以内，吞吐近似线性增长：4 个核走 HTTP 是 1 个核的 3.75 倍。quickjs v0.26.13 时不走 HTTP、直接用渲染池是 3.87 倍。每个核损失的那几个百分点像是共用的 L3 缓存或内存造成的，虚机上没有硬件计数器，证实不了。
- 超线程只多约 20%。1 个核跑 2 个 VM 是每秒 59.3 到 60.4 个请求，跑 1 个是 49.4。一次渲染的 CPU 时间从约 20 ms 涨到 33 到 34 ms，摊在解释器的所有函数上：两个线程在抢同一个核。
- 用 quickjs v0.26.13 测、当时还没有压缩：libc 分配器的锁、垃圾回收、HTTP 和内核合计约占 3% 的 CPU。整个程序 99.5% 的 CPU 在用户态，内核占 0.3% 到 0.5%。所以吞吐跟着单次渲染的时间走。
- 在队列限制以内，请求比 VM 多只会增加等待，不会提高吞吐：3 个核上 6 个 VM、24 个在途请求，仍有每秒 170.0 到 174.8 个，P50 是 133 到 137 ms。

## 机器怎么配

### CPU 和 `ssr.vms`

这一部分的请求拿到的页面都是 gzip。

- [`ssr.vms`](config.zh-CN.md#配置项) 保持默认就好。默认值是 Go 看到的 CPU 数（`GOMAXPROCS`），在容器里跟着 CPU 限额走。
- VM 比 CPU 多不会多出吞吐。渲染不会排队，而是在抢 CPU，每次都变慢：7 个 CPU 上 8 个 VM 是每秒 212 到 218 个请求、P50 25.9 到 26.4 ms，7 个 VM 是 211 到 214 个、22.4 到 22.5 ms。
- VM 比 CPU 少，是拿吞吐换一点延迟：同样 7 个 CPU，4 个 VM 是每秒 155 到 162 个请求、P50 17.2 到 17.8 ms。系统仍会把两个渲染线程放到同一个核的两个超线程上，而别的核还空着。只给程序和物理核一样多的 CPU，两样都更好：4 个物理核上 4 个 VM 是每秒 182 到 188 个、13.8 到 13.9 ms。
- 云上的一个 vCPU 通常是一个超线程，2 个 vCPU 常常就是 1 个物理核。超线程都忙起来时吞吐更高，但每次渲染更慢：shop 的页面在物理核上 P50 约 14 ms，每个核的两个线程都在渲染时约 22 ms。
- 14 ms 的条件是程序钉在每个物理核的一个超线程上，另一个超线程几乎空着。cpuset（比如 Docker 的 `--cpuset-cpus`）能把程序钉到这样的 CPU 上，但管不了别的程序用它们的兄弟超线程。Kubernetes 的 static CPU manager 策略倾向于整核分配，一个核的两个超线程一起给，那就是上面 22 ms 的情况。只设 CPU 配额（比如 Docker 的 `--cpus`）时线程不绑核，结果可能更像上面 VM 比 CPU 少的情况。这种情况没有测过。
- 按 shop 六个页面轮流、每次渲染平均约 21 ms CPU 的情况，每个物理核每秒约 46 次渲染，vCPU 是超线程而且都忙时每个 vCPU 约 29 次（6 个 vCPU 每秒 172.0 到 173.9 次）。渲染时间不同的页面按比例换算。

只有整页加载才渲染。在浏览器里切换页面取的是 Go 直接写的 JSON，不经过 VM，API 路由和命中缓存的页面也不渲染。3 个物理核上 6 个 VM、64 个在途请求时，用 quickjs v0.26.13 测：

| 请求 | 请求/秒 | P50 | P99 |
| --- | --- | --- | --- |
| 列表、订单、统计的导航数据 | 20,161、33,030、21,264 | 1.5 到 2.5 ms | 8.1 到 14.1 ms |
| `Cache = true` 的页面命中缓存 | 22,538 | 2.1 ms | 13.1 ms |
| 同一页面回 304 | 31,165 | 1.5 ms | 8.8 ms |
| API 用 `PATCH` 改一个订单 | 57,905 | 1.4 ms | 3.3 ms |

这些请求的成本很大一块在应用自己，不在 tifa。导航数据和命中缓存的请求里，20% 到 24% 花在 shop 自己的 `Load` 上，它每个请求都把全部订单复制、排序一遍，13% 到 20% 花在写响应的系统调用上。`PATCH` 用 3 个核只比 1 个核多 56%，像是卡在 shop 自己的订单锁（`ordersMu`）上，这一类没有剖析过。命中缓存和导航数据请求一样贵：缓存键里有数据，所以查缓存之前每个 `Load` 都要先跑完。

`Cache = true` 的页面同时没命中缓存的请求共用一次渲染（见 [SSR 与缓存](app.zh-CN.md#ssr-与缓存)），所以冷页面上的突增（比如刚部署完）只花一次渲染，而不是每个请求一次。在 Apple M4 上（同时有别的任务在跑），对 shop 一个冷的订单页同时发 50 个请求，两种做法交替各跑五轮，不开 PGO：

| VM 数 | 各自渲染：渲染次数、全部答完、P50 | 共用一次渲染：渲染次数、全部答完、P50 |
| --- | --- | --- |
| 10，`GOMAXPROCS=10` | 50，146 到 221 ms，103 到 133 ms | 1，30 到 52 ms，29 到 51 ms |
| 2，`GOMAXPROCS=2`（三轮） | 50，332 到 354 ms，187 到 201 ms | 1，33 到 40 ms，32 到 38 ms |

这一次渲染是新 VM 里的第一次，比热的 VM 慢。渲染完之后才到的请求直接命中缓存。

### 过载

日常到达率应低于实测渲染容量。接近容量时，渲染时间的小幅变化也会让队列增长。增加超过 CPU 能力的 VM 不能解决持续过载。

默认最多允许 32 次渲染等待空闲 VM，每次最多等 1 秒。队列满或等待超时返回 503，带 `Retry-After: 1` 和 `Cache-Control: no-store`。响应由 Go 写出，不占 VM。这是预期的拒绝，不调用 `OnError`，详见[渲染队列](config.zh-CN.md#渲染队列)。

数量和时间两项限制都需要。只限制时间，等待数量仍随到达率增长。只限制数量，所有 VM 都很慢或正在替换时，请求仍可能一直等待。按 shop 的实测容量，32 次等待约相当于半秒的工作。1 秒等待给短暂突发留出空间，又不把整个 HTTP 写预算都花在排队上。页面成本不同时，应按它们的实测容量和可接受等待时间设置 `ssr.queue_limit`、`ssr.wait_timeout`。`ssr.queue_limit: 0` 表示没有空闲 VM 就拒绝。

2026-10-22 用 shop 的六个工作台页面测量，Go 1.27.2、quickjs v0.26.17，不开 PGO。服务用 CPU 1、5，也就是一个 AMD EPYC 7B13 物理核的两个超线程，`MemoryMax=1G`，不使用 swap，默认 2 个 VM。开放到达客户端在 CPU 0、4 上发 gzip 请求，每档注入 60 秒，每个请求最多等 90 秒。唯一 URL 和 `cache.size=0` 让每个请求都渲染。两种构建的到达率都按原实现实测容量每秒 69.47 次计算。有界版本实测每秒 70.69 次，这个小幅变化也会影响接近容量的一行。这里测的是 HTTP 请求，并带临时的池计时日志，不是单次渲染微基准。

| 到达率 | 原实现错误率 | 原实现全部 P99 | 原实现峰值 RSS | 有界队列 503 比例 | 有界队列成功请求 P99 | 有界队列峰值 RSS |
| --- | --- | --- | --- | --- | --- | --- |
| 50% | 0.0% | 0.039 s | 100.9 MiB | 0.0% | 0.039 s | 97.0 MiB |
| 75% | 0.0% | 0.052 s | 102.5 MiB | 0.0% | 0.051 s | 99.3 MiB |

最先失效的是延迟。原有 3 秒渲染超时不计算等待 VM 的时间。HTTP 服务的 10 秒写超时也不会取消这种等待，请求可能等到写截止时间之后才渲染，最后以 EOF 失败。在 150%、200%、300% 下，注入阶段最后 10 秒都没有成功响应，但 VM 还在工作。队列排空后服务能恢复。60 秒的测试没有达到 cgroup 限额。另一次 300% 的 180 秒测试把客户端超时设为 300 秒，开始注入约 92 秒后，内核杀死了原进程。unit 记录 `oom-kill`，内存峰值为 1 GiB。

在 300% 下，有界版本成功响应的 P50/P99 为 501/627 ms，503 响应的 P99 为 53 ms。全部请求的 P50 只有 28 ms，因为多数请求被拒绝了，所以只看整体延迟会掩盖已接受请求的等待。所有拒绝响应都带 `Retry-After: 1`，没有传输错误或客户端超时。这组默认值是小机器的起点，不是遍历所有队列大小后得到的最优解。

显式设置 VM 数量的结果一致。1 VM 在 300% 下，成功请求 P50/P99 为 581/680 ms，峰值 RSS 为 80.8 MiB。2 VM 则为 491/611 ms 和 105.0 MiB。有界版本的 18 组测试共 102,717 次请求，没有传输错误或客户端超时，各组排空后的 10 次恢复探测全部通过。按同样的 300% 到达率持续 180 秒，峰值 RSS 为 105.9 MiB，成功请求 P99 为 609 ms。

去掉池计时日志后，同样的 180 秒测试在第 104 秒杀死了原进程，仍然触及 1 GiB 的 cgroup 限额。有界进程一直存活，峰值 RSS 为 107.3 MiB，成功请求 P50/P99 为 497/601 ms。37,514 次到达中有 24,984 个 503，没有传输错误或客户端超时，恢复探测全部通过。

队列限制计算渲染任务数，不计算字节数或全部 HTTP 请求。`Load` 在准入前运行，共享一次缓存未命中的请求仍各自占用 HTTP 状态。下面低并发时的 RSS 不能代表任意连接数、大量加载数据或应用内存的占用。`ssr.vm_memory` 限制的是每个 VM，不是进程，限制渲染队列也不保证进程永不 OOM。

### 内存

VM 回收后的 live 大小超过增长上界时，池会安排后台替换。基线是加载完成并做完预热回收后的 live 大小。两次渲染之间回收后，上界默认是基线的 2 倍。如果 `ssr.vm_memory` 的 75% 更小，就用这个值，但不低于基线的 175%，避免刚加载就接近限额的 bundle 反复重载却收不回空间。这些值采用引擎的 `MemorySize`，与现有 GC 策略相同，不是进程 RSS。如果限额低于加载后 live 的 1.75 倍，保护下限可能高于限额，主动替换无法保证先于 OOM。重载不能让原本过大的 bundle 变小。没有新增配置项。

| 页面 | 基线，MiB | 1 VM 的最高 live | 2 VM 的最高 live | 相对基线的最大倍数 |
| --- | --- | --- | --- | --- |
| 工作台 | 10.97 | 12.29 MiB | 12.28 MiB | 1.120 |
| 商城 | 10.97 | 15.00 MiB | 14.93 MiB | 1.367 |
| MUI | 5.23 | 8.68 MiB | 8.72 MiB | 1.666 |

基线的 2 倍比测得的正常 live 最大值还高 20%。低内存限额下的 1.75 倍保护下限仍高出 5%。这 24,576 次渲染记录的 live 都低于基线的 1.75 倍。对这些应用，测量支持使用固定上界，无需再增加一个配置项。

池在后台加载一个备用 VM，旧 VM 继续参与渲染。只有存在符合条件的空闲 VM，且渲染队列无人等待时，才开始加载。加载完成后，也要等队列为空，才与符合条件的空闲 VM 交换，随后关闭已移出池的旧 VM。整个池同时只做一次这种替换。内存预算要多留一个 VM 的空间，包括它的 Go 分配和 TLS 内存，从加载开始一直保留到允许交换的空闲时刻。持续繁忙会推迟替换。单次渲染仍可能在下一次渲染间回收之前就触及内存限额。

加载失败时，旧 VM 继续服务，1 秒后重试，间隔逐次加倍，最多 30 秒，恢复之前只记录一次警告。每次成功交换都记录基线、旧 live、上界和新 live，并增加池的替换计数。关闭池时会等待正在加载的 VM，并关闭未用上的备用 VM。被替换 VM 的模块状态会丢失，与渲染失败后的替换一样。需要持久保存的应用状态应放在 Go 中。

异常、超时、内存失败或 panic 会让 VM 处于未知状态，仍要立即退出服务。不能让这样的 VM 在新 VM 加载时继续接请求，所以现有失败恢复仍会暂时少一个 VM。主动替换只处理渲染成功的 VM。

quickjs v0.26.16 给每个 VM 多出来的，用现在的 shop（含店面）测，不能和上面旧 shop 的约 4.9 MB 直接比：

- 对象没了以后，它留住最近 2048 个普通对象的形状（形状记录一个对象有哪些键、按什么顺序），还按大小各留一张表，存放释放掉的小块，垃圾回收时交回去。垃圾回收后，shop 的一个 VM 多占约 722 KiB，按引擎的统计是 8.03 MiB，原来是 7.33 MiB，其中 647 KiB 是形状。块在引擎的 arena 里怎么分布，会让这些数每次运行差到 0.5 MiB。
- 两次回收之间，这些表最多存 1.6 MiB 的块。缓存的块还会让它所在的 4 KiB arena 留到下次回收才释放，极端情况下每张表都满、每个块各占一个 arena，约 31 MiB。引擎的回收阈值把这些 arena 算在内，分配碰到内存上限时会先把缓存的块还回去再试一次。
- 留住的形状算在 `ssr.vm_memory` 里，VM 内存不够时引擎也不会放掉它们。一个页面如果建很多键和别的对象都不一样的对象，能用这样的形状把 2048 个位置填满。一个形状有 32 个键、键名约十个字符时，连键名约占 3 KiB，合起来每个 VM 约 6 MiB，键名更长会更多。这些形状放掉以后，键名表还保持长到的大小。这样的页面可能在原来够用的 VM 里用完内存。
- 引擎的 `VM.SetShapeCache` 设一个 VM 留多少个形状，默认是 `slowjs.DefaultShapeCache`（2048）。tifa 用默认值，没有对应的配置项。

池子用 slowjs 的 `SharedBytecode` 把 bundle 加载进各个 VM，所以 bundle 里函数的源码（`toString` 返回的文本）和给错误栈提供行号的表整个进程只存一份，不再每个 VM 一份。按引擎的统计，shop 的一个 VM 加载后占 9,043,000 字节，原来是 11,509,568，少 2.35 MiB，渲染 64 次再完整回收后占 9,989,080，原来是 12,428,920。MUI 测试应用的一个 VM 加载后占 4,155,576 字节，原来是 5,436,184，少 1.22 MiB。8 个 VM 时，进程加载后的 RSS 在 shop 上从 122.0 MB 降到 100.9 MB，在 MUI 上从 72.7 MB 降到 57.9 MB。共用的那份就是整份字节码，shop 是 5.3 MB，在所有 VM 之外，不算进 `ssr.vm_memory`，以前池子在 Go 堆上也存着同样一份字节码。`toString`、错误栈和行号都不变，HTML 也不变。渲染时间不变：一个 VM 跑在空闲核对的一个线程上，main 和分支在 3 种代码布局上轮流跑（23 对），六个工作台页面的耗时中位数是原来的 0.994（0.979 到 1.015），MUI 页面是 0.994（0.981 到 1.005），池子做的年轻回收和完整回收次数也和原来一样。 在 linux/amd64 上不开 PGO 测得。

垃圾什么时候回收：QuickJS 在建对象时发现内存过了阈值就回收，然后把阈值设成回收后剩下的 1.5 倍。池子把一个 VM 上次在两次渲染之间做完整回收（或加载完）后剩下的大小记作它的活大小。每次渲染完、请求答完以后，它跑一次年轻回收（slowjs 的 `VM.RunYoungGC`），只看上次回收以后新建的对象，释放其中的垃圾，回收完才让 VM 接下一个渲染。年轻回收留下的对象变成老对象，之后的年轻回收不再看它们。年轻回收后还占着活大小的 1.5 倍、这次渲染里引擎自己回收过、或者满 256 次渲染时，改做一次完整回收，收掉年轻回收留下的老垃圾，比如经过老对象的循环和 WeakMap 的值。渲染中途的阈值是活大小的两倍，所以渲染很少中途回收。有的页面渲染到结束前一直拿着比活大小还多的东西，比如 `test/apps/bench` 的螺旋页，它会让引擎在渲染中途回收一次，那次引擎设的阈值留给这个 VM 之后的渲染用。留下的阈值最多到活大小的四倍，之后每次不在中途回收的渲染都让它往活大小的两倍回落 1/1024：跑过一次大页面的 VM 会回到平常的阈值，真需要这么多空间的页面大约每 1000 次渲染在中途回收一次。阈值最多到活大小和 `ssr.vm_memory` 的中点，所以一次渲染的垃圾比这还多时，用完内存之前也会回收。按引擎的统计，shop 的一个 VM 渲染后最多占 17.3 到 20.0 MiB，引擎在渲染中途自己回收时是 18.6 到 23.3 MiB。

`ssr.vm_memory`（默认每个 VM 128 MiB）远高于这些。有两种情况要另外留内存，[栈深度](config.zh-CN.md#栈深度)讲了这两种情况，以及小机器上怎么调低：

- 无限递归的代码会让每个 VM 一时多占约 24 MB 的 goroutine 栈。
- 在 Linux 上，一个 VM 递归到过 10000 层后，会一直多占约 20 MB 的 TLS 块，直到 VM 关闭。

## 压缩

[`server.compress`](config.zh-CN.md#配置项) 默认开着（见[压缩](build.zh-CN.md#压缩)）。压缩一个页面花的时间不到它渲染时间的 1.5%，浏览器包直接发构建写好的 gzip 文件，不花 CPU。

压缩一个页面要多久：在上面那台机器的一个核上，编码器像服务端一样复用，取 200 次的平均，旁边的渲染 P50 来自[一个页面渲染多快](#一个页面渲染多快)：

| 页面 | HTML | gzip 5 级 | zstd 默认级别 | 占渲染时间 |
| --- | --- | --- | --- | --- |
| 订单列表 | 81 到 86 KB | 256 到 280 µs 压到 9.3 到 9.8 KB | 143 到 152 µs 压到 9.0 到 9.5 KB | gzip 0.7% 到 0.8%，zstd 0.4% |

- 对页面来说，压缩的开销淹没在整个请求的波动里：一个请求的 CPU 在两次之间能差 1 ms，是压缩时间的好几倍。页面发出去小了约 6 倍。
- 导航数据回答起来很便宜，所以压缩的开销看得出来：每个请求多 23 到 43 µs 的 CPU，核跑满时每秒少 8% 到 20% 的请求，回答小 1.8 到 5.4 倍。这里 gzip 也比 zstd 贵。
- 命中缓存时直接发缓存和页面一起存好的 gzip 或 zstd 版本，所以压缩的命中反而比不压缩的省 CPU，每个 0.15 ms 对 0.18 到 0.19 ms，因为要写的字节少。要是每次命中都把存着的 HTML 再压一遍，每次命中一共要 0.45 ms（zstd）和 0.54 ms（gzip）的 CPU，其中压缩约占 0.26 到 0.34 ms，在途 64 个时每秒只剩 4,410 到 4,423 和 3,711 到 3,712 个命中，P99 是 34 到 37 ms。接受压缩的请求没命中时，页面压成两种版本，发出其中一种，所以比不带 `Cache` 的页面多压一次：占它渲染时间的 1.0% 到 1.4%，是用第一张表的压缩时间除以渲染 P50 算出来的。没命中时的那次渲染不管发起它的请求接不接受压缩都压出两种版本，所以共用这次渲染的请求不会再压一遍。
- 浏览器包发 `.gz` 文件比发原文件还省 CPU，因为要写的字节少：每秒请求数是原来的 2.4 到 3 倍。
- 用 gzhttp 默认的 zstd 最快级别，一页只要 82 到 138 µs，但页面比 gzip 大 3% 到 11%。用默认级别（Caddy 和 Traefik 都这样），订单列表比 gzip 小 3%，其他页面大约大 4%。
- brotli 用纯 Go 的 github.com/andybalholm/brotli，4 级和 5 级一页要 648 到 1,183 µs，是 gzip 的 4 到 6 倍，页面只小 3% 到 16%。
- 构建时压缩的文件，gzip 最高级别把 700 KB 的 chunk 压到 224 KB。zstd 最高级别是 213 KB，brotli 11 级是 192 KB。
- shop 的程序大了 1.12 MiB：0.35 MiB 是 `.gz` 文件，其余是 gzip 和 zstd 的代码。
- 测的时候，机器上其他 cpu 最多忙 3%。

## 哪些改动让它变快

所有改动都让 HTML 逐字节不变。效果指 shop 页面一次渲染花的时间，没有另外注明的都在上面那台机器上测。

### 引擎

fork [github.com/liustack/slowjs](https://github.com/liustack/slowjs#slowjs) 的 README 列了每项改动，细节和测试都在那里。和速度有关的：

v0.26.16 那几行没有另外注明的都不开 PGO 测，一个 VM 钉在一个核上，每一步和前一步比，分轮交替测。TLS 帧和 `set_value` 两项合起来，渲染时间是 v0.26.15 的 0.971，8 轮在 0.966 到 0.974 之间。另外三项合起来，渲染时间是前两项的 0.955，一个核的两个超线程上跑 2 个 VM，每秒多渲染 2.9% 的页面。HTML 逐字节不变。

v0.27.0 整体和 v0.26.17 比，用商店工作台的六个页面，一个 VM 跑在一个核上，交替 4 轮，两个版本各用自己采的 profile 构建：不开 PGO 时耗时为 0.982（0.980 到 0.986），开 PGO 时一样（1.002，1.000 到 1.007）。likely 判断带来的那部分，PGO 原本就拿到了：开 PGO 后 v0.27.0 的渲染少 4.0%，v0.26.17 少 5.9%。每个版本只构建了一次，1% 到 2% 的差别在代码布局带来的波动之内。

v0.27.1 整体和 v0.27.0 比，tifa 相同，一个 VM 跑在一个核上，3 种代码布局交替 6 轮，开 PGO 时两个版本各用自己采的 profile 构建：商店工作台的六个页面，不开 PGO 时耗时为 0.991（0.967 到 1.009），开 PGO 时 0.982（0.968 到 1.007），MUI 测试应用的四个页面是 0.986（0.980 到 1.019）和 0.980（0.968 到 0.991）。和 Temporal 合并时的 tifa 比（还在 v0.27.0 上，emotion 哈希还没改在 Go 里算），商店不开 PGO 时耗时为 0.987（0.971 到 1.012），开 PGO 时 0.984（0.971 到 0.995），MUI 页面是 0.701（0.685 到 0.708）和 0.700（0.691 到 0.711）。一个核的两个超线程上跑 2 个 VM，每个版本每秒渲染的页面都是 1 个 VM 的 1.20 到 1.27 倍，等锁不到 0.01%。用 v0.27.1 时每秒比 v0.27.0 多渲染 1.5% 到 2.2% 的页面，开不开 PGO 都是。三者的 HTML 逐字节相同，VM 的内存和 v0.27.0 一样，精确到 KiB。

v0.27.2 整体和 v0.27.1 比，tifa 和 SSR 包都相同，一个 VM 跑在一个核上，3 种代码布局交替 12 轮，开 PGO 时两个版本各用自己采的 profile 构建：商店工作台的六个页面，不开 PGO 时耗时为 1.006（0.976 到 1.035），开 PGO 时 0.993（0.973 到 1.031），MUI 测试应用的四个页面是 0.991（0.978 到 1.023）和 0.996（0.979 到 1.006）。只看单一代码布局，商店不开 PGO 时的中位数就在 0.995 到 1.022 之间，所以这个版本和 v0.27.1 一样快，差别在代码布局带来的波动之内。一个核的两个超线程上跑 2 个 VM，每个版本每秒渲染的页面都是 1 个 VM 的 1.24 到 1.27 倍，等锁不到 0.03%。用 v0.27.2 时，不论 1 个 VM 还是 2 个，开不开 PGO，6 轮里每秒渲染的页面都是 v0.27.1 的 0.995 到 1.008 倍。HTML 逐字节相同，VM 用的内存相同，精确到 KiB。GC 之后，10 个页面里有 9 个的 VM 从分配器占的内存少 0.1 到 0.6 MiB，MUI 的订单页多 0.3 MiB。

### 构建

[docs/build.zh-CN.md](build.zh-CN.md#前端产物) 讲了 Vite 插件对 SSR 包的每项改写，[按剖析优化](build.zh-CN.md#按剖析优化)讲了剖析：

| 改动 | 效果 |
| --- | --- |
| React DOM 只留字符串渲染器 | 在早期更小的 shop 上：包小 25%，4 个 VM 的池启动时间约减半。渲染时间不变 |
| 每个 VM 缓存 React 的 HTML 转义 | shop 少 8% 到 10%（Apple M4），它的 Tailwind 类名里满是要转义的字符。纯文字页面不变 |

| React 的 HTML 转义改用五次 `replaceAll`，不再逐个字符循环，查有没有要转义的字符改用 `exec` | 纯文字页面少 8.7% 到 9.8%，落地页少 0.7%。shop 和小页面上下浮动不超过 1.6%，它们的转义大多已由上面的缓存直接给出 |
| React 不再构建组件栈。栈只进 `onError` 的第二个参数 `errorInfo`，tifa 给 `renderToString` 的处理函数丢掉这个参数 | shop 少 1.2% 到 4.2%，纯文字页面和落地页少 7.2% 到 7.8%，小页面少 2.3% 到 2.6% |

| seroval 从 2 个 UTF-16 码元起就用 `JSON.stringify` 转义字符串 | 小页面少 6% 到 10%，大页面最多 2.5% |
| 每个 `Load` 的数据以 Go 写的 JSON 文本交给浏览器（[数据协议](build.zh-CN.md#数据协议)） | TanStack 默认的序列化处理同样的数据要慢好几倍 |

### 从基线到现在

基线是 tifa 0673723 配 quickjs v0.26.8。它已经有转义缓存、裁掉的渲染器和 JSON 文本适配器，没有另外三项改写，也没有 v0.26.12、v0.26.13 和 v0.26.15。现在是 tifa 790b746 配 v0.26.15。两边都不带 PGO，在同一时段交替测：

| | 基线 | 现在 | 快了 |
| --- | --- | --- | --- |
| 1 个 VM，单次渲染，六个页面各自 | 19.3 到 64.2 ms | 10.4 到 35.6 ms | 1.80 到 1.88 倍（时间是 0.532 到 0.555） |
| 1 个 VM，走 HTTP 一次一个请求 | 一个订单列表 65.1 ms | 同一列表 36.3 ms | 六个页面 1.79 到 1.86 倍 |
| 3 个核 6 个 VM，六个页面，6 个在途 | 每秒 68.5 个请求（64.8 到 72.2） | 每秒 174.3 个（170.6 到 176.5） | 2.5 倍 |
| 同上，P50 和 P99 | 53.7 到 56.1 ms，239 到 285 ms | 21.6 到 22.6 ms，74.9 到 78.4 ms | |

基线没有压缩，所以走 HTTP 的两行两边都要的是 identity，各测三轮。

单核整体约快 1.83 倍。多核快得更多，是因为基线被一把锁拖住了。原来每次 JavaScript 调用都经 libc 分配内存，libc 的分配器只有一把全局锁。6 个 VM 时 20% 的 CPU 耗在 `sync.Mutex.Lock` 上，一次渲染要 81 ms 的 CPU，1 个 VM 时只要 38 ms。v0.26.12 去掉了这次分配，锁的争用也跟着没了。只有 1 个 VM 的基准测试看不出这一点。

## 试过但没做的

每项写了能带来什么、为什么放弃。再试其中某项之前先看这里。

### 引擎

- **再给 135 个小函数去掉 TLS 帧**（TLS 帧是 libc 的 TLS 栈里的一块，引擎翻译成 Go 后把函数里取了地址的 C 局部变量放在这里）：约占渲染时间的 0.24%，测不出来，却要多维护 135 条。
- **让调用空间在 TLS 帧里放到 768 字节以上**：1024 字节只多覆盖 0.02% 的调用，却让 Linux 每层调用深度留的块从 2 KB 翻到 4 KB。
- **把不常用的 opcode 搬出解释器主循环**：在 amd64 上单做最多 8%，这是把 shop 从没跑过的 56 个 opcode 的 handler 换成空桩测出的上限，叠在「让 15 个值留在栈槽里」那项改写上只剩 1.4%，arm64 上 0.5%。还得把主循环的局部变量收进一个结构体。
- **用闭包或函数表分发 opcode**，有些 Go 写的解释器这么做：等于重写解释器，违背 fork 只做机械改写的规矩。没试。
- **等 Go 1.28**：开发版让没改的引擎在 amd64 上快 5%、arm64 上快 2%，却让改写后的引擎在 amd64 上慢 5% 到 6.5%，原因没找到。在开发版上改写仍然赢，amd64 4.2%，arm64 15.5%。
- **留住对象字面量的所有中间形状**（形状记录一个对象有哪些属性、按什么顺序）：在新属性快路径之上再快约 2%，但两个列表页跑到 VM 内存上限失败了，因为留下的形状拉着原型和原型能连到的一切。v0.26.16 换了一种方式留形状，见[引擎](#引擎)：只留最近 2048 个，只留原型是 `Object.prototype`、最多 32 个键、没有未注册 symbol 键的形状，而且只有对象找到过留下的形状、攒了额度，才复制形状而不是就地扩展，所以键和别的对象都不一样的对象只慢一点。它的状态放在 fixlib 给引擎 runtime 结构体末尾加的一个字段里，不用从 C 重新生成 Go 代码。
- **字节码里放字面量模板**，像 V8 那样复制一个建好的对象：要改编译器和字节码格式，quickjs-ng 试过，没看出明显差别。
- **按最终大小分配字面量的属性数组**：建对象的 opcode 不知道属性数，换一种增长方式会让每个小对象都更占内存。只有和留住形状一起做才划算，v0.26.16 已经留住形状，还没在它上面试过。
- **读属性的内联缓存**：quickjs-ng 加了又删了。在 17 个真实工具上从慢 11% 到快 54% 都有，平均只快 4%，还更占内存。没试。
- **在解释器主循环里给 `===` 加快路径**：反而慢 1.0% 到 1.3%，是在 tifa a2084b4、quickjs v0.26.14 开 PGO 时测的，下面两项也是。解释器函数太大，Go 只往里内联最小的函数，所以在那里加一个辅助函数就多一次真调用。把中断检查的倒计数挪进一个小函数，也因为同样的原因没有变化（时间是原来的 0.998 到 1.001）。v0.26.16 把它写成 `pollDue`，小到 Go 能内联进去：开 PGO 少 0.6%，不开基本不变，见[引擎](#引擎)。
- **新对象的位字段从 9 次写合成 2 次**：没有变化（0.991 到 1.010）。时间花在第一次写新对象时的缓存缺失上，少写几次只是把它挪了地方。
- **对象展开的快路径**（`JS_CopyDataProperties`）：Apple M4 上的微基准里一次展开从 415 ns 降到 240 ns，shop 却没变（0.997 到 1.005）。
- **每个 VM 一个 libc 分配器**，绕开它的全局锁：Linux 上 8 个 VM 时这把锁只占 0.4% 到 0.9% 的 CPU，v0.26.15 起 Apple M4 上 10 个 VM 等锁的时间约占 0.7%。
- **从字节码里去掉函数源码**（`JS_SetStripInfo`）省 VM 内存：seroval 用 `toString` 读自己辅助函数的源码写进页面，去掉后浏览器端会坏。现在改成池子里的 VM 共用一份源码，见[内存](#内存)。
- **用 Go 实现 `TextEncoder`、`URL` 等兼容代码**：渲染时几乎不调用它们，渲染时间没有可省的。
- **在 arm64 上去掉保存字节码位置的那条写入**：它看起来最多占解释器自身时间的 11.6%，其实是采样器把等下一个 opcode 的时间记在了它头上。这条写入是 Go 把局部变量 `pc` 存到栈上，留给之后要读回它的调用，正好在每个 opcode 都走的路径上。只调整指令顺序，采样就从它移到读 opcode 的那条指令上（8.8% 降到 0.4%），指令数、周期数和渲染时间都不变。

### 构建

- **把静态 JSX 提到组件外**，像 Babel 的 transform-react-constant-elements：shop 的页面每次少建 44 到 83 个元素，渲染只快 0.5% 到 0.9%，几乎全静态的页面快 5.4%。每少建一个元素约省 0.8 µs，时间主要花在 React 遍历和拼字符串上。它管不到 `node_modules` 里库的 JSX，要么得装 Babel，要么得自己写一个转换。提上去的元素被一个 VM 的所有请求共用，某个库要是改了它，改动会带到下一个请求。
- **降低 SSR 包的语法目标**：ES2021 到 ES2018 差 1% 以内。从 ES2017 起对象展开变成辅助函数，shop 慢 33% 到 45%。目标保持 ES2022。
- **SSR 包不压缩**：包本来就压缩了。在加店面之前的 shop 上，不压缩时渲染慢约 1%，包从 772 KB 变成 1,799 KB，VM 加载后从 7,634 KiB 变成 9,133 KiB。
- **对 React 的小改写**，每项都不到 1%：`push(x)` 改成按下标赋值（0.1% 到 0.9%），`jsxProd` 和 `createElement` 里的 `for...in` 拷贝改成展开（会多拷 symbol 键，语义不同），`startChunkForTag` 和 `endChunkForTag` 的 `Map` 换成对象（不到 0.5%），`for...in` 换成 `Object.keys`（微基准里更慢），`hasOwnProperty.call` 换成 `Object.hasOwn`（每个键省约 25 ns）。
- **React 转义和它查找要转义字符的别的写法**：`indexOf` 查五次、逐字符循环都比它的正则慢，查找时五次 `indexOf` 和 `search` 也都比 `exec` 慢。每个字符串都先查转义缓存再跑正则，纯文字页面慢 4%，在只测转义的基准里，一个订单列表的 1,188 次转义慢 22%，因为多数字符串不用转义，而 `Map` 查一次比搜一次更贵。所以缓存只收需要转义的字符串。搜索剩下的开销在引擎里。要是缓存满了就不再收，早先请求的文本会一直占着位置。要是淘汰最久没用的那条，每次命中都要多一次删除和一次写入。在 Go 里转义（转义在跑正则之前先调一个 builtin）让 shop 慢 1.3% 到 2.0%，HTML 不变：每次调用都要把字符串从引擎拷出来，再把结果拷回去，比搜一次加查缓存还贵。
- **把 React 的组件栈和 key path 里的名字换成更省的写法，而不是去掉**：把 `pushComponentStack` 内联到调用处，或者对字符串和函数类型不调 `getComponentNameFromType` 直接取名字，都在 1% 以内（shop 上 0.994 到 1.024）。花时间的是建对象和字符串，不是函数调用。
- **在插件里改写 react-spring 和 TanStack Table**：react-spring 做颜色插值时拿每个值去匹配一个有 148 个颜色名的正则，QuickJS 里一次 24 µs，Node `--jitless` 是 0.175 µs（占订单列表 2.1%）。TanStack Table 通过 `fn(this, ...args)` 调用，约 1 µs，对比 67 ns（占 1.2%）。改写它们就把插件绑在两个库的写法上。两处都该在引擎里做：正则的每个分支先比首字符再试，展开普通数组时不走迭代器。
- **渲染后由 Go 把页面数据放进 HTML**：`tifa.data` adapter 只写一个占位符，Go 再把 JSON 文本作为 JavaScript 字符串填进去。1,000 行的表格 JSON 文本约 80 KB，渲染从 34.2 ms 降到 32.3 ms，Go 这边约 0.2 ms，合起来少约 5%。shop 六页不变。这样 VM 写出的就不再是完整页面，每条写页面和缓存页面的路径都得填占位符，还要按 script 元素的规则转义。
- **把请求之间不变的页面片段缓存成 HTML**：tifa 不知道页面是怎么写的。`Cache = true` 按数据缓存整个页面。
- **React Compiler**：`@vitejs/plugin-react` 的 `reactCompilerPreset()` 只编译浏览器端的构建，开不开 SSR 包都逐字节相同，shop 的 20 个页面渲染相差 1% 以内（0.994 到 1.010），两个 VM 的吞吐也一样。浏览器端 JS 压缩后大 6.1%（31 KB），HTML 和 hydration 不变。tifa 默认不开。应用想在浏览器端用，可以在自己的 `vite.config.ts` 里打开，再量自己的交互速度和包大小。
- **构建时预先写好静态开始标签**：SSR 插件在构建时让 React DOM 自己生成字符串，预先写好属性全是常量的 JSX 元素的开始标签。shop 工作台 6 页、店面 12 页和 MUI 5 页渲染时间不变，每轮比值都在 1 的两边。只有 `test/apps/bench` 里专门为它写的两个页面变快（列表 8.1%，螺旋 7.3%）：真实页面里这些标签只占渲染的一小块，时间主要花在组件、hooks 和样式上。它让 shop 的 SSR 包大 4.9%，每个 VM 多占约 200 KB，还要按哈希校验 React DOM 的内部函数，React 每发一个版本都要跟着改。

### 服务端

- **调高回收阈值**，设成活大小的两倍、三倍或固定 32 MiB，仍由引擎在渲染中途回收：一次回收花的时间差不多跟着它释放的垃圾走，回收次数减半只省下约 15% 的回收时间，不到渲染的 1%，量不出来。P99 和 P999 反而变差，一个 VM 多占 40% 到 50% 的内存，`ssr.vm_memory` 设得低时更早用完内存。
- **在年轻回收之外每 64 次或 1024 次渲染做一次完整回收**，和每 256 次比：每 64 次让 shop 的 P99 高 1.5% 到 4%，每 1024 次的 P99 和内存都和 256 次一样，一轮做 2 次完整回收，256 次时是 8 次。
- **两次渲染之间要到活大小的两倍才回收**，渲染中途到三倍：P99 和 1.5 倍时一样，但一个 VM 多占 22% 到 45% 的内存，`ssr.vm_memory` 设得低时更早用完内存。
- **`onError` 没收到错误时，跳过对交给浏览器的 Suspense 边界的查找**：运行时每次渲染后在整页 HTML 里找 `<!--$!-->`，约占商店渲染的 1%，MUI 页面的 0.4%，跳过后商店耗时为原来的 0.987，MUI 页面为 0.995。但在 React 19.3 里，组件调用 `use(browser())` 时，边界交给了浏览器却不调 `onError`：`renderToString` 把它报给一个自己不接收的 `onBrowserBailout` 选项。所以查找留着，把它变快是引擎的事。
- **用 React 的流式渲染器渲染，让页面等懒加载组件**：`react-dom/static` 的 `prerender` 和等到 `allReady` 的 `renderToReadableStream` 给出同样的 HTML，但在 tifa 6e062d6 上商店慢到 8.7 到 8.8 倍，MUI 页面慢到 4.2 倍，每个 VM 最多多占 1.7 MiB。先用 `renderToString` 渲染，只在它把边界交给浏览器时再用流式渲染器渲染一次，普通页面一样快，但这些页面要渲染两遍。tifa 改用 `prerenderToString`：插件给 React DOM 加的字符串渲染，会等 VM 的任务能完成的事。在 GCP 机器上不开 PGO，3 种布局各 6 轮，商店耗时为 `renderToString` 的 0.995，MUI 页面为 1.001，HTML 一样，每个 VM 大约多 20 到 40 KiB。

## 怎么复测

[docs/testing.md](testing.md#performance-comparisons) 有渲染基准和 VM 内存的命令，[Reading BenchmarkShopParallel](testing.md#reading-benchmarkshopparallel) 讲怎么检查多个 VM 是否还能扩展（英文），[The engine profile](testing.md#the-engine-profile) 讲升级 slowjs 或 modernc.org/libc 后怎么重采 PGO 剖析（英文）。让数字能比的规矩：

- 在同一台机器上比，新旧两个构建一轮一轮交替跑。只有同一批轮次的比值能比：机器忙的时候绝对时间能差好几倍。
- 每次跑都钉在一个核上，并让它的超线程兄弟空着。Linux 上 `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list` 写着兄弟是谁。记下每轮的机器负载，别的任务占了约 10% 以上的 CPU 就重测。
- 比较两个构建每个页面的 HTML。路由会把渲染的时刻写进每个 match（`u:` 后面跟 13 位数字），先遮掉它。
- 只有 1 个 VM 的基准看不出 VM 之间的争用。改动碰到内存分配时，还要同时用多个 VM 渲染，看 mutex profile。

完整请求：构建 `examples/shop`，用 `taskset` 把 `bin/shop --server-addr 127.0.0.1:0 --cache-size 0` 钉在几个核上，从另一个物理核压测，在途请求数等于 VM 数。每次先热几秒，测扩展曲线时服务钉的 CPU 数等于 VM 数。

Node：SSR 包是 ES 模块，把同一份 `.tifa/dist/ssr.js` 复制成 `ssr.mjs`，用 `import()` 加载，渲染同样的输入，先热几百次，在 QuickJS 基准用的那个核上各跑一遍有 JIT 和 `--jitless`。找下一个该改的地方时，比较每个函数在 QuickJS 和 `--jitless` 的 Node 里各花多少时间：倍数远高于整体的函数就是候选。

## 还能从哪里继续

单次渲染的时间几乎就是全部成本：quickjs v0.26.13 时整个程序 99.5% 的 CPU 在用户态，v0.26.15 上解释器函数自己就占约 36%。渲染快多少，吞吐就涨多少。按可能的收益大致排序：

1. **引擎里的属性访问。** v0.26.15 上读属性约占一次渲染的 16%，光 `find_own_property` 就占 5.5%。赋值（`o.x = v`、`Object.assign`）还走慢路径，约占 2%，做快路径要检查原型上的 setter 和只读属性。
2. **建对象和释放对象。** v0.26.15 上，引擎的 malloc 和 free、建对象和释放对象、引用计数合计约占一次渲染的 13%。v0.26.16 留住释放的小块和形状再用，省掉了其中一部分。React 给每个元素、hook 和组件栈都建对象，所以 `createHook`、`pushComponentStack`、`jsxProd` 当时比 `--jitless` 的 Node 慢 6 到 12 倍。插件现在让 React 不再建没人读的组件栈，其余的只能在引擎里解决。
3. **剩下的 TLS 帧。** v0.26.16 只给 8 个热函数做了按语句取帧。在 v0.26.15 上加这项改动后，分配和释放 TLS 帧仍占一次渲染的约 3.5%，原来是 4.2%（见 [Engine hotspots](studies/engine-hotspots.md#data)）。另一条在做的方向是消掉 libc 的 TLS 栈（它替代 C 的栈）上剩下的分配。
4. **每个 VM 少占内存。** 所有 VM 共用一份只读的函数源码和行号表，指向字节码，`toString` 照常能用。估计每个 VM 省约 380 KB。要改 C 补丁（fork 对 QuickJS 的 C 源码做的改动）、fixlib（fork 里改写生成的 Go 代码的工具）和 Go API。
5. **用 C 改动给留住的形状省内存。** v0.26.16 留住形状让渲染少花 3.6% 的时间，但 shop 的每个 VM 为此多占 647 KiB。等引擎的 Go 代码能从 C 重新生成时，在 C 里改，比如让子形状引用父形状，可能拿到同样的速度又少占内存。也可以提给上游。
6. **amd64 上的 Go 1.28。** 正式发布后重测改写后的引擎。如果还是比 Go 1.27 慢，做一个最小复现报给 Go。
7. **转义缓存。** QuickJS 给 `Map` 的键算哈希时不加盐，同一哈希的字符串一多查找就变慢。每条按多 64 个码元算，把链长压在约 3,700 条以内，再加一个条数上限可以更短。不是 Latin-1 的长串（8,192 码元起）实际占内存约是内容的 4 倍：查一下字符串拼接是否留了多余的空间。
8. **还没做的对比。** Node 自己的 HTTP 服务和 Node cluster，以及同一台机器上用 TanStack Start 和 Next.js 跑同样的页面。

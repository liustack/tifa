# 哲学

tifa 应用就是一个 Go 程序。它的代码怎么组织，由四条理念决定。这篇讲这些理念、为什么，以及每条给你带来什么。每个文件放在哪、东西怎么初始化，见[应用的代码结构](structure.zh-CN.md)。

## 按领域组织

代码按它讲的是什么来分（订单、店铺、客户），不按它是哪类代码来分。这来自[按组件组织](https://developer20.com/how-to-structure-go-code/)：一个组件装着它需要的一切，存储、HTTP 处理和业务模型。在 tifa 里，`app/` 下的目录本来就是 URL，URL 本来就按业务分，所以一个领域就是 `app/` 下的一个目录，代码和展示它的页面放在一起。没有哪个包从每个领域收集同一类代码。

你得到的：

- 一个领域能整体拿走、评审或删除。改一个功能从它的目录开始，大多也停在这里。伸到外面的部分会表现为一条 import，或者共享表结构里的一张表，一眼就能看到。
- 浏览器里的 URL 告诉你代码在哪。
- Go 不允许循环引用，所以两个领域不能互相依赖：领域之间的 import 总是单向的。

## 依赖手动组装

依赖就是普通的 Go 值：包级变量和函数，在 `OnStart` 里初始化，在 `OnShutdown` 里释放。没有依赖注入容器，没有反射，也没有替你组装依赖的生成代码。

你得到的：

- 跳转到定义，总是落在真正运行的代码上。
- 什么先启动、按什么顺序，就是 `OnStart` 从上到下的代码。
- 启动时不按名字或类型去查找依赖，所以用到一个没有声明的资源是编译错误。声明了但 `OnStart` 还没初始化的，运行时仍是 nil。
- 除了 Go 本身，没有别的要学。

## 从小开始

一个领域从一个文件开始。有代码要放了，才拆成更多文件或更多包。有第二个实现要藏在后面了，才引入接口这样的抽象。具体怎么拆，见[应用的代码结构](structure.zh-CN.md#领域做大了)。

你得到的：

- 不用在还没有代码可放的时候，先维护一堆空的分层。
- 结构跟着代码长，而不是跟着第一天定的计划。

## 按 Go 的方式

- **少魔法。** 约定只有目录名，和几个函数、常量的名字。其他都是普通的 Go，tifa 生成的代码也是能读的 Go 和 TypeScript。
- **构建只读代码。** `tifa build` 分析源码，从不运行它：应用里的 `init()` 在构建时不会执行。
- **平台差异用 Go 的构建约束。** 构建按 go 命令的方式，为目标平台选文件。
- **纯 Go。** 应用用 `CGO_ENABLED=0` 构建成一个可执行文件。

你得到的：

- `go test ./...`、`go vet ./...` 和编辑器对待应用，就像对待任何一个 Go 模块。
- 构建在哪里跑都安全，CI 也一样，不需要应用运行时才要的数据库或密钥。
- 应用能为它用的 QuickJS 引擎支持的每个平台构建（常见 CPU 上的 Linux、macOS、Windows 和 FreeBSD），结果是一个可以直接拷走的文件。

# 哲学

tifa 应用就是一个 Go 程序。它的代码怎么组织，由四条理念决定。这篇讲这些理念，以及每条给你带来什么。每个文件具体放在哪，见[应用的代码结构](structure.zh-CN.md)。

## 按领域组织

代码按它讲的是什么来分（订单、店铺、客户），不按它是哪类代码来分。一个领域就是 `app/` 下的一个目录。这来自[按组件组织](https://developer20.com/how-to-structure-go-code/)：一个组件装着它需要的一切，存储、HTTP 处理和业务模型。在 tifa 里，`app/` 下的目录本来就是 URL，URL 本来就按业务分，所以一个领域的目录里放着它的类型、查询、规则和测试，旁边就是展示它的页面。

不设 `models/`、`services/`、`repositories/`、`handlers/` 或 `utils/` 这种从每个领域收集同一类代码的包。

你得到的：

- 一个领域能整体拿走、评审或删除。改一个功能只动一个目录。
- 浏览器里的 URL 告诉你代码在哪。
- Go 不允许循环引用，所以两个领域不能互相依赖：领域之间的 import 总是单向的。

## 依赖手动组装

依赖就是包级变量和函数。数据库连接是根包里的 `var DB`，在 `OnStart` 里打开，在 `OnShutdown` 里关闭，每个领域直接用。没有依赖注入容器，没有反射，也没有生成的组装代码。只有部分调用方要传不同的值时，函数把它作为参数。测试替换变量，或者传一个假实现。

你得到的：

- 跳转到定义，总是落在真正运行的代码上。
- 什么先启动、按什么顺序，就是 `OnStart` 从上到下的代码。
- 启动时不按名字或类型去查找依赖，所以一个不存在的依赖是编译错误。
- 除了 Go 本身，没有别的要学。

## 从小开始

一个领域从它页面旁边的一个文件开始。做大了，就在同一个目录里按主题拆成多个文件。有自己页面的一块，变成下面的一个目录。接口等到真有两个实现时才出现，比如真实的和测试用的假实现。

你得到的：

- 不用在还没有代码可放的时候，先维护一堆空的分层。
- 每一步长大都只是在一个目录里挪动，结构跟着代码长，而不是跟着第一天定的计划。

## 按 Go 的方式

- **少魔法。** 约定只有目录名，和几个函数、常量的名字：`Load`、`Layout`、方法函数、钩子。其他都是普通的 Go。不用写 main，tifa 生成的代码放在 `.tifa/`，打开就能读。
- **构建只读代码。** `tifa build` 分析源码，从不运行它：应用里的 `init()` 在构建时不会执行。
- **平台差异用构建约束**：`limit_windows.go` 这样命名的文件，或者 `//go:build` 行。构建按 go 命令的方式，为目标平台选文件。
- **纯 Go。** 应用用 `CGO_ENABLED=0` 构建成一个可执行文件。

你得到的：

- `go test ./...`、`go vet ./...` 和编辑器对待应用，就像对待任何一个 Go 模块。
- 构建在哪里跑都安全，CI 也一样，不需要应用运行时才要的数据库或密钥。
- 应用能为 Go 支持的平台构建，结果是一个可以直接拷走的文件。见[给别的系统构建](build.zh-CN.md#给别的系统构建)。

# Render switches and caches

## SSR and cache

```go
const SSR = false              // the page, default true
const Memo = false             // the page, turns the render memo off, default on
const Cache = true             // the page, the same for everyone, a CDN may keep it for cache_control.s_maxage, default off
// const Cache = 10 * time.Minute
const LayoutSSR = false        // the Layout of the folder, default true
```

`SSR`, `Memo` and `Cache` apply to the page of `page.tsx`. In a `route.go` without one they fail the build. `Memo` can only be `false`: the render memo is on by default, so you never write `true`. `Cache` is `true`, `false` or a `time.Duration` constant of at least a second, see [Cache for CDNs](#cache-for-cdns). Write the names with the capitals shown. A constant named `ssr`, `cache`, `memo` or `layoutssr` fails the build, since it would be skipped.

- `SSR = false`: middleware and every `Load` run as usual, but QuickJS is skipped. The response is a minimal document with the data, and the browser renders it. `LayoutSSR = false` applies to every page the Layout wraps.
- The render memo is on for every page (see [The render memo](memo.md) for why it is a memo, why it is safe for signed-in pages and what it does not cover). Each request runs its middleware, its `Load`s and its Layouts. The rendered HTML is then kept by build version, SSR bundle, the path and the query parameters the Loads read (see [Query parameters in the server render](#query-parameters-in-the-server-render)), the data of every `Load` and Layout, and the session the browser gets, in a memo of `ssr.memo_size` (see [config.md](config.md)). When none of these changed, the HTML is returned without a render. The answer says which: `X-Tifa-Render` is `vm` for a render of this request, `memo` for a hit and `shared` for a render another request started (see [Page requests](build.md#page-requests)). `ssr.memo_size` 0 turns the memo off, and shared renders stay.
- Components must not put a value into the HTML that changes on every render, such as `Date.now()` or `Math.random()`. Hydration needs this too, and the memo would freeze such a value for later visitors. Under `tifa dev` every page is rendered a second time with the clock 36 hours on, and when the two differ the terminal and the dev overlay say so, show the first place where they part and list the places in your code that read the time or a random number. The page is then not memoized until it is fixed. If a page has to show such a value on purpose, such as the time of the server, write `const Memo = false` in its `route.go`. That page renders for every request. The check does not run in a built app.
- A request that carries a render clock (`tifa.WithRenderClock`) skips the memo: it neither reads nor stores a page, because its HTML depends on a time the key does not hold.
- When requests miss the memo at the same time with the same build version, URL and data, such as a burst of visitors right after a deploy, they share one render. Each request still runs its middleware and `Load`s, keeps the headers they set, such as `Set-Cookie` and `Vary`, and gets the encoding it accepts. This also holds with `ssr.memo_size` 0, for a page too large for the memo, and under `tifa dev`. Requests with other data or another session render on their own, and a page with `Memo = false` renders for every request.
- When that shared render fails, every request that waited for it gets the same error and goes to `OnError`, a panic included. Nothing is kept, so the next request renders again, unless a component threw or the render used up `ssr.vm_memory`: the built app then remembers the failure for 5 seconds (see [Errors on a page](pages.md#errors-on-a-page)). A request whose client goes away stops waiting at once and its connection is cut, with no answer sent: `next(c)` in `OnRequest` returns an error that matches `context.Canceled`, but `OnError` is not called and nothing is logged. The render goes on for the others. A request whose own deadline passes while it waits fails like any other error. Once no request waits, a render still waiting for a VM is dropped, and one that already runs finishes and goes into the memo. If it fails then, no request reports it to `OnError`, so the error is logged.
- Every page response carries an ETag, a hash of the same things as the memo key. A second request with `If-None-Match` gets 304 when none of them changed, without a render and before the memo is asked. The ETag and the memo are separate: the ETag saves the transfer to a browser that has the page, the memo saves the render for everyone else. A page with `Memo = false` and a request with a render clock get no ETag, since their HTML is not a function of those things, and always render. A 404 page and the page of a failed `Load` are rendered for each request and never kept, so made-up URLs do not fill the memo. Requests for the same one at the same time still share a render. They get no ETag: a 304 only stands for a 200.
- A page does not carry the time its data was loaded, so the same data always gives the same HTML. Instead the answer of a page (a render, a 304, a 404 page of the app) carries `Server-Timing: tifa-age;dur=<ms>`, how old its data may be, from the start of its first `Load`. Only an answer that no cache may reuse without asking the server again carries it: its `Cache-Control` has `no-cache` or `no-store`, as the default `private, no-cache` does. A page with `Cache`, or one whose `Cache-Control` you set to let caches keep it (such as `public, max-age=60`), does not carry it, since a cache would hand out the same age later. The browser router takes the time the browser sent the request, less that age, as the time the data was loaded, which `staleTime` and `gcTime` count from. It sets that time on the matches of the page just before it first loads or preloads, so until then their `updatedAt` is 0, as the server rendered it, and a component that shows it hydrates without a mismatch. Where the answer has no age or the browser cannot read it (Firefox over plain HTTP, a page from the back and forward history), the data counts as old and loads again when you come back to the page. Navigation data does not carry it: the router dates what it fetches itself.
- Every answer of the app (pages, 304s, 404 pages, navigation data, method handlers, redirects) is sent with `Cache-Control: private, no-cache` unless you set `Cache-Control` yourself. A page with `Cache` is the exception, see [Cache for CDNs](#cache-for-cdns). A CDN or proxy does not store it, since the page may be meant for one visitor. The browser may keep it and asks again with the ETag, so an unchanged page ends in a 304. To change it, set the header in `OnRequest`, a `Load`, a `Layout` or a method handler with `c.SetHeader("Cache-Control", "...")`. Your value is sent as it is, except on navigation data (the requests with `_tifa`), which is never public: a value that is not `no-store`, or `private` with `no-cache`, is replaced by `private, no-cache`. JSON errors (including 405 and the 503 while the server shuts down), the plain error page from Go, the page with an error that the server renders again, and the busy answer are `no-store`, unless you set `Cache-Control` before the error. A 404 page that the app renders keeps the default. Files under `/assets/` keep their long cache, and files from `public/` keep `no-cache` (see [Page requests](build.md#page-requests)). The render memo only keeps the render inside the process and does not change the header.

### Query parameters in the server render

A page sees the query parameters its `Load` and the Layouts above it read with `c.Query` or `c.QueryValues`, as `tifa build` finds them. The server renders with the path and those parameters only, sorted by name, with the values of one name in the order of the request, and the memo key holds the same. Other parameters are dropped before the render and stay out of the key. The address bar keeps every parameter as the visitor wrote it (`a%20b` stays `a%20b`), with one language or several. `OnRequest`, every `Load` and the method handlers still see the whole request.

- Tracking parameters add no key to the memo and no server render. `?utm_source=mail`, `?fbclid=...` or `?x=random` give the same key as the page without them, so the memo answers. The `Load`s still run on every request. Another order of the parameters gives the same key too.
- To render by a parameter, read it in the `Load`. A parameter no `Load` reads cannot change the data, so the render does not need it. In components read it by its name, such as `page.useSearch().q` with the `useSearch` of the route from `route.gen`. That `useSearch` has the types of the parameters the `Load`s read and lets any other through, so it does not make another parameter safe, see [Query parameters in Link and navigate](pages.md#query-parameters-in-link-and-navigate).
- A component that reads another parameter while rendering hydrates differently: the server rendered without it, the browser has it, and React reports a hydration error and renders that part again in the browser. `tifa build` warns, with the file and line, of a read while rendering of a parameter the server does not render that code with: by its name from `useLocation`, `useRouterState`, `useSearch({ strict: false })` or the `useSearch` of a route, and of the whole `search`, `searchStr` or `href` of the location. It checks `page.tsx` and `layout.tsx` against their own parameters, and warns of every such read in other modules, which can render under any page. A read in `useEffect` or `useLayoutEffect` runs in the browser only and passes. The check reads one module at a time, so a read inside a helper it calls is not seen. Read such a parameter in the `Load`, or in an effect when only the browser needs it.
- A 404 page and the page of a failed `Load` are not kept by the memo, so random parameters and random slugs do not make it grow.
- When the router redirects another spelling of a URL (such as `/%6Eews` or `/news/`) to its own, the redirect puts the dropped parameters back.
- A page with `SSR = false` is not rendered on the server, and its document carries the URL as it came.

### Cache for CDNs

```go
// app/blog/slug+/route.go
const Cache = true             // s-maxage from cache_control.s_maxage, 1m by default
// or
const Cache = 10 * time.Minute // its own time
```

A page with `Cache` tells the CDN or proxy in front of the program that it is the same for everyone and may be kept for that long. Use it for pages that are public and that many visitors read: articles, docs, product and landing pages. `Cache = true` takes the time from `cache_control.s_maxage` (1 minute unless you change it, see [config.md](config.md)), a duration sets the time of this page, at least a second, and `Cache = false` is the same as no line. The program keeps nothing of the page itself. Its `Load`s run on every request, so what the origin answers is never old, and the [render memo](memo.md) still skips the render when their data is the same. A visitor behind a CDN sees a change up to `Cache` late.

- **Everyone is anonymous.** The GET and HEAD of the page, and the requests the browser sends for its data when you navigate to it, lose all request headers but a short list before `OnRequest`: `Host`, `Accept-Encoding`, `If-None-Match`, `If-Modified-Since`, `Cache-Control`, `Pragma`, `Content-Length`, `Connection`, `Origin` and `Sec-Fetch-*`. `Cookie` and `Authorization` go, and so do `Accept-Language`, `User-Agent`, `Referer`, `Forwarded`, `X-Forwarded-*` and a header that a proxy or login gateway sets such as `X-User-ID`, so none of them can reach a `Load` through `OnRequest` and the context. `tifa.Session` returns nil, `c.Cookie` finds nothing, `c.Header` and `c.Request().Header` have only the list, and the request is the same for `c.Request()`. `tifa.SetSession` and `tifa.ClearSession` return an error that says sign-in and OAuth callbacks belong on routes without `Cache`. A page can only be shared if what it says does not depend on who asks. A `Set-Cookie` on the HTML of such a page is removed, since a cookie in a shared answer would reach every visitor. The answer to a navigation (the request with `_tifa`) is for one browser and keeps its `Set-Cookie`, and it carries the session of that browser (see [Sessions](sessions.md#in-the-browser)). Method handlers of the same URL, a POST say, are not anonymous.
- **The edge of anonymous.** What Tifa guarantees is the request headers: on a page with `Cache`, `OnRequest`, `Load` and `Layout` see a request with only the headers of the list, and `tifa.Session` is nil. A `net/http` middleware set with `tifa.SetHTTPHandler` runs outside Tifa and gets the request as it came, and what it puts into the context of the request reaches `OnRequest` and the `Load` unchanged. Do not recognize visitors there: do it in `OnRequest` on routes without `Cache`. The address of the connection and the TLS state also remain, and values an outer middleware puts into the context and headers on the list (such as `Origin`) can still tell requests apart. None of them may be used to build personalized shared content.
- **The build checks it.** When the `Load` of such a page, the `Layout` function of a Layout around it, or a function they call reads `c.Cookie`, `c.Header` or `tifa.Session`, the build fails with the line, since the read can only see an anonymous request. For `c.Header` the message says which few headers are there. A page that needs to know who is signed in does not use `Cache`. Put what depends on the visitor into the browser, which can read it after the page has loaded (see [In the browser](sessions.md#in-the-browser)). Keep the Layouts around a page with `Cache` to data that is the same for everyone.
- **What `OnRequest` can do.** It runs for every request and sees the anonymous request. Use it for what depends on the path: redirects, security headers, logging, counting, rate limits by address. It cannot see who is signed in, so an `OnRequest` that redirects by login state belongs to routes without `Cache`, and one that sets a cookie when it does not see one would set it on every navigation. Cookies it sets on the HTML are removed.
- **Languages.** A page in several languages has one URL per language, so a CDN keeps each language apart. An entry point that picks the language from a cookie or from `Accept-Language` and redirects is a GET handler on a route without `Cache` (a page with `Cache` cannot read either), and the pages it leads to carry the language in their URL (see [A site in several languages](app.md#a-site-in-several-languages)).
- **Headers.** The HTML of the page carries `Cache-Control: public, max-age=0, s-maxage=<seconds>, stale-if-error=86400`. The browser asks every time and gets a 304 when the ETag matches, so a deploy shows at once. A shared cache keeps the page for the seconds of `s-maxage`, and may serve its copy for a day when the program fails (`stale-if-error`). If `OnRequest`, a `Load` or a `Layout` sets a `Cache-Control` with `private`, `no-store` or `no-cache`, or a `Vary` beyond `Accept-Encoding`, the page is not for everyone and your headers go out as they are. Navigation data is still `private, no-cache`. For what to set in a CDN, see the deployment notes of the Tifa skill.

To show a change before the CDN's copy runs out, purge it in the CDN. Tifa has no copy to expire.

### User-independent pages and private data

A full page is a user-independent page plus private data. Tifa splits by the kind of data, not by component:

- **Data that is the same for everyone.** `Load` and Layout see no user, so the page can be kept in a CDN.
- **The session.** Who is signed in and a small `Exposed` part of the session, carried by the session system (see [Sessions](sessions.md)). It is written into the page, and the browser keeps a copy.
- **Other private data.** A cart, recommendations, an unread count. It can be large, and the browser may write to it. Put it behind an API route of your app and fetch it from the browser.

Other systems draw the same line: HTTP caches call it `public` against `private`, Magento calls it private content, and donut caching keeps the shared page whole and fills in the holes.

For the third kind, make an API route (a `route.go` with a `GET` handler and no `page.tsx`). Its generated `GET` function is typed and works from the browser. Call it when the page needs the data: after the page has loaded, when a panel opens, or on hover to fetch ahead. The generated functions plug straight into TanStack Query if the app wants a cache. `examples/shop/app/store/mine.ts` is a worked example: the data of the storefront pages (products, journal, menu) is the same for everyone, and this module calls the `GET` of `/store/{lang}/mine` after a page has loaded to fill in the cart and the products the visitor looked at last, and calls it again after a write.

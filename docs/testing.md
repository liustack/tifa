# Testing and verification

## Before committing

Every Go change must pass:

```sh
go test ./...
go vet ./...
CGO_ENABLED=0 go build ./...
```

For packages with concurrency (request context, `tifa.Use`, config loading, the server), also run the race detector:

```sh
go test -race ./<package path>
```

The commands in the root only cover the framework. The example app `examples/shop` is a separate module. When you change it, run its own checks in that folder:

```sh
cd examples/shop
pnpm install --frozen-lockfile
go tool tifa build
go tool tifa check   # the analysis, go vet ./..., go test ./... and tsc --noEmit, stopping at the first failure
```

## End-to-end tests (`test/e2e`)

`test/e2e` builds the `tifa` CLI, runs `tifa build` on the apps in `test/apps/`, on `examples/shop` and on an app that `tifa new` creates, starts the outputs and checks them from outside. Skipped by default. First run `pnpm install --frozen-lockfile` in `test/apps/pages`, `test/apps/tailwind`, `test/apps/mui`, `test/apps/bench`, `test/apps/session`, `test/apps/upload`, `test/apps/pagecache`, `test/apps/content` and `examples/shop`, then turn them on (`test/apps/extreme` also needs `TIFA_EXTREME=1`, see [Extreme pages](#extreme-pages-testappsextreme)):

```sh
TIFA_E2E=1 go test -timeout 30m ./test/e2e/
```

A full run can take more than the default 10 minutes of `go test` on a laptop, hence `-timeout`.

The programs the tests start and leave running, the built apps and `tifa dev`, go through `testproc.Start`, so a killed run leaves none of them behind.

## Writing tests

- New behavior and bugs with a known cause: write the test first, see it fail with your own eyes, then write the implementation.
- Tests live in the same package as the code under test, in files named `*_test.go`. The exceptions test from outside: `test/e2e` the built CLI and apps, `test/ssr` the SSR pool of `internal/ssr` with the example app's real bundle. Framework behavior gets its test in its own package, with its own `testdata`, and does not depend on `examples/shop`.
- One assertion proves one thing. When a loop runs several cases, give each case its own state, and confirm the code under test really ran. Caching and deduplication logic is the easiest way for a later case to get an earlier case's result while the test still passes.
- A test that starts a program that keeps running, such as a server, `tifa dev` or a Node process, starts it with `testproc.Start` of `internal/testproc`, not with `cmd.Start`. `t.Cleanup` does not run when a panic in another goroutine, a test timeout or a SIGKILL ends the test process, and a program left that way runs on with the init process as its parent, holding its port, its memory and every file it inherited. `testproc.Start` makes the system end the program with the test process, however that ends: Linux sends it a SIGKILL (`Pdeathsig`, from a thread that lives as long as the process), and macOS, which has no such signal, hangs up the terminal the program runs on (the program is the leader of a session on a terminal whose master side only the test process holds), which stops a program that does not ignore SIGHUP. It also marks the files the test process inherited, such as the lock of a script that runs the tests under `flock`, to close when the program starts, so a program left behind cannot keep the lock. Only the program is bound, not what it starts in turn: on macOS what stays in its process group stops with it, and a program that starts others has to end them itself, as `tifa dev` does with its app and the driver of Vite when it is killed (`TestDevLeavesNothingBehind`). Keep the `t.Cleanup` that stops the program, which is what ends it when the test ends normally. `internal/testproc/orphantest` holds the check for a package that starts programs: a helper test starts a fake program the way the package does, the check ends the helper in the three ways a test process dies without cleanup (a panic in another goroutine, a SIGKILL, a SIGKILL while SIGHUP is ignored, as under `nohup`), and the program must be gone, and must hold none of the files the helper inherited. See `test/e2e/orphan_unix_test.go` and `test/compare/orphan_unix_test.go`.
- A test in `test/e2e` that needs a browser gets its `pw` function from `openBrowser` (`test/e2e/browser_test.go`), and does not run `playwright-cli open` and `close` itself. `playwright-cli open` starts a detached daemon (`cliDaemon.js <session>`) that outlives the test process, and `playwright-cli close` exits 0 even when it finds no session. So `openBrowser` registers the close before the browser opens (a failed `open` or a `t.Fatal` still closes), runs every command in one folder, reads the answer of `close`, and fails the test if a daemon of the session is still running after it, ending that daemon. `TestMain` fails the run if a daemon of any session the run opened is left. A session name must be short: the daemon listens on a unix socket at `<tmp>/pw-xxxxxxxx/cli/<16 characters>-<name>.sock`, and when that path is over 104 characters (the name is at most 17 characters under a 48 character `TMPDIR` as on macOS) the daemon fails to listen with EINVAL but keeps running, and `close` then answers "is not open" for it, so it can only be ended with a kill. `openBrowser` refuses a name that is too long for the `TMPDIR` in use. Two runs at once share the sessions of the same name, so do not run the e2e tests twice at once. A test that is killed or times out still leaves its daemon, because no cleanup runs. Find those by `ps -axo pid,command | grep cliDaemon.js` and end them with `playwright-cli -s=<session> close`.
- Verify browser behavior (extra requests during hydration, one request per navigation, horizontal overflow on narrow screens) with `playwright-cli`, and take screenshots of the results.

## HTTPS tests (`server`)

`server/tls_test.go` and `server/acme_test.go` run with `go test ./server/`, on the loopback and without a network. They make their certificates themselves, and the ACME server they ask is a fake one in the test process (`fakeACME`). It checks nothing a client signs, but it does what Let's Encrypt does with the challenges: it connects to the program over plain HTTP (http-01) or over TLS with `acme-tls/1` (tls-alpn-01) and checks the key authorization. ## Long SSR tests skipped by default

The default tests in `internal/ssr` only use small handwritten bundles, `testdata/app.js` and the bundles with source maps in `explain_test.go` for render errors (broken maps, and a bound on what explaining an error allocates), and finish in a few seconds. The soak tests skip by default:

```sh
TIFA_SSR_SOAK=1 go test -run Soak -v ./internal/ssr
```

They run normal reuse (2 VMs, 2 callers, 10,000 renders), OOM recovery (8 failures and replacements), and 16 proactive memory swaps. After shutdown, every VM the pool made must have closed without an error. `TestSoakVMMemory` loads every VM the way the pool does. It prints what Intl adds to an empty VM, unused and after formatting, and what the bundle adds after loading, formatting and a render. It fails when Intl adds more than 32 KB to a VM that never formats.

### Timing a build of quickjs against another

To time one build of quickjs against another at several code positions, with a `go.work` that uses this repository, `examples/shop` and a quickjs checkout whose engine is generated, use `go tool measure bench` in quickjs ([docs/testing.md](https://github.com/liustack/quickjs/blob/main/docs/testing.md#developer-tools-generate-check-time)), which also has the make targets that generate its engine and run its checks, here or on another machine: it builds this package's test binary against each checkout, runs them in turn and reads the `p50-ms` of the pages by the rule of its code positions. A binary that prints a line `vmhwm-kb: N` at the end (the child of `TestShopVMResident` does) also gets its peak memory reported.

The prototype's other experiments (per-stage timing, memory probes) stay in `internal/ssr` at the tag `prototype-baseline`. Check out that tag and build from it when needed.

Run performance comparisons on the same machine, alternating between the old and new builds, and record the machine load. Changes in machine load can make absolute times differ several times over. Only ratios measured in the same alternating round are comparable.

### Reading BenchmarkShopParallel

`BenchmarkShopParallel` catches what one VM cannot show: a lock that every VM takes. `BenchmarkShop` stays the same when such a lock comes back. Several VMs render in one process, so a lock in the engine's allocator or in the host calls would keep the program from using more cores, and only this benchmark shows it.

- Run both sub-benchmarks in one command. `speedup` only shows when `vms-1` ran in the same command. To repeat, run the command again: with `-count` every `speedup` is against the last `vms-1`, and `-cpu` changes `GOMAXPROCS` after the number of VMs is set.
- On Linux, set `GOMAXPROCS` to a number of physical cores and pin the test to them with `taskset`, one CPU per core. Two VMs on the two threads of one core render only about 20% more than one, so a speedup over hyperthreads says little about locks.
- Read `speedup` first. A Go mutex spins before it blocks, and spinning shows as CPU time (`runtime.procyield` in a CPU profile) and a lower speedup, not as lock wait. `lock-wait-%` then says whether a lock is the reason.
- The benchmark does not fail on these numbers, because machine noise moves them as much as the regression does. Compare against main on the same machine, alternating, as above. A speedup more than 10% below main's is worth a look. The runtime samples lock wait, so small values are noisy. On an AMD EPYC 7B13 with 4 physical cores (`GOMAXPROCS=4 taskset -c 4-7`, the other 4 threads idle), a lock wait above about 0.5% is worth a look. That level holds only for that machine, and Mac numbers compare only with Mac numbers.

To see which lock it is, take a mutex profile. Profiling makes the lock wait larger, so read the profile for where the wait is, not for how much:

```sh
TIFA_SSR_SHOP=1 GOMAXPROCS=4 taskset -c 4-7 go test -run '^$' -bench ShopParallel -benchtime 15s \
  -mutexprofile mutex.out -o ssr.test ./test/ssr
go tool pprof -top -cum ssr.test mutex.out
```


## Comparison with Next.js, TanStack Start and React Router (`test/compare`)

`test/compare` builds the six workbench pages of `examples/shop` as a Tifa program, as a Next.js app, as a TanStack Start app and as a React Router v7 app (framework mode, the successor of Remix v2). It checks that the four show the same pages and do the same work for each request, and measures how long whole page requests take from process start and how many each answers. It builds three apps with Node and the measurement needs a quiet machine, so CI does not run it. The method and the numbers are in [Tifa against Next.js and TanStack Start](studies/nextjs-and-tanstack-start.md).

| Where | What it holds |
| --- | --- |
| `test/compare/domain` | The domain code of the workbench pages, ported to TypeScript one function at a time from `examples/shop/app` (the Layouts, the three `Load` functions, the orders, the stats, the carriers and the seed data), shared by the three apps. Plain TypeScript with no packages, so Node runs it as it is |
| `test/compare/nextjs`, `test/compare/start`, `test/compare/reactrouter` | The three Node apps: `package.json` with a lockfile, the server components or routes that call the domain code, and a few shims. Git ignores what is built into them: `shop/`, `public/images/`, `node_modules` and the build output (the React Router app is run by `react-router-serve`) |
| `test/compare/overlay`, `nextjs/overlay`, `reactrouter/overlay` | Files that only exist in Tifa, written for the apps: `tifa/client`, the module the generated routes call handlers through, and for Next.js and React Router the stand-ins for TanStack Router's `Link`, `Outlet` and loader data |
| `test/compare/*.go` | Builds and copies (`build.go`), starts the servers (`serve.go`, through `testproc.Start`, so a killed run leaves none behind), reads the pages (`parity.go`), compares the port with Go (`domain.go`), counts work (`counted.go`), measures and reports (`measure.go`, `record.go`, `report.go`), reads the CPU topology (`topology.go`), lists the servers (`specs.go`) |
| `test/compare/cmd/compare` | The command that builds, measures, reports and diffs |

**Where the work is done.** In Tifa, every request runs the Go `Layout` and `Load` functions, which read the orders from memory, copy and sort them and work out the list, the order or the stats. In the three apps, every request runs the same functions in TypeScript on orders that the process builds in memory when it starts, from the same seed code. Nothing is kept from one request to the next. The components, the stylesheet, the root Layout, everything TypeScript under `app/projects`, the 160 pixel photos and the `+layout` and `+route` modules that `tifa build` generates from the Go types are copied from `examples/shop` into `shop/` and `public/images/` when the apps are built, so a change to a page of the shop reaches all four. A change to the Go code that loads the data does not reach the port by itself. The check below fails and names the fields, and you port the change.

The handlers (`POST`, `PUT`, `PATCH`) are not ported: the apps show pages. The forms render, but their calls fail. The one exception is a write endpoint for the measuring (below): `PATCH /compare-write/<project>/<order>`, which takes the body of the shop's `PATCH` on the order route and calls `updateRecipient` of the port, a copy of `UpdateRecipient` and `CheckRecipient`. It is one path in the three apps, since Next.js cannot put a route handler beside a page.

### Check that the pages are the same

```sh
TIFA_COMPARE=1 go test -count=1 -v ./test/compare
```

The tests build the shop and the three apps (`pnpm install --frozen-lockfile` and the builds, under a minute on a warm machine), start each server and check:

- `TestDomainMatchesGo`: for each of the six pages, the JSON that the Go `Layout` and `Load` functions answer, which the test asks the shop's own program for as the browser router does, equals the JSON that Node makes from the port (`node test/compare/domain/dump.ts`), compared as values, field by field. It does not build the three apps, and needs Node 22.18 or later, which runs TypeScript as it is. When it fails, the Go code of the shop changed and the port did not: change `test/compare/domain` to do what the Go code does, and run it again.
- `TestPagesShowTheSameText`: the six pages fetched without compression show the same title and text nodes in order, and have the same number of `tr`, `a`, `svg`, `button`, `li`, `time`, `img`, `table`, `h1` to `h3`, `nav` and `input` elements. Script, style and template elements do not count.
- `TestEveryRequestComputesAndRenders`: each request for a page runs the data code and renders the page again, shown by counting. See below.
- `TestNoCachingBetweenRequests`: the apps hold nothing that could keep a page between requests.
- `TestDomainMatchesGoAfterWrites`: the same as `TestDomainMatchesGo` after the writes of the first 60 reads of the scenario with writes, sent to the Go shop and applied in the port.
- `TestWriteChangesThePage`: in each server (Tifa with its render cache on too), a write of the address of an order shows on the page of the order, and a second write shows and the first no longer does. This is the check that the write endpoints of the Node apps work and that a cached page is not served after a write.

They work on macOS and Linux and skip when `go`, `node` or `pnpm` is missing. `TIFA_COMPARE_SKIP_BUILD=1` starts what the last run built. The tests of the parser run without the switch.

When a page check fails after a change to the shop, read the difference it prints. A new page needs a route in all three apps. A new package the shop's workbench imports needs a line in the `package.json` of all three apps, and `pnpm install` in each folder to update the lockfiles.

**What the count test shows.** It builds a second Tifa program with `go build -overlay`, which adds a counter to `ordersOf` (the filter, copy and sort that every query of the orders starts with) and a path `/compare-counts`, without changing a file of the shop. The Node apps count the same calls in the port (React Router shares the project between its parallel loaders per request, through the Request object), and also the runs of the root Layout, the project Layout and the page's `Load`, and the renders of the page on the server, and answer with them at `/compare-counts`. For each page the test asks once and reads what the counters gained, then asks five times more and checks that they gained five times as much. A render in Tifa is read from the header `X-Tifa-Render`, which says `vm` for a page rendered in a VM and `cache` or `shared` for one that was not. Then the calls of `ordersOf` for one request must be the same in all four: 4 for an order list, 6 for an order and 5 for the stats. `TestNoCachingBetweenRequests` adds what the code and the answers say. None of the three has `cacheComponents`, `use cache`, `unstable_cache`, a `revalidate` setting or a `QueryClient` in its sources or its package lists, and the React Router app has no `clientLoader`, `shouldRevalidate` or `headers` export. Next.js answers a page with `Cache-Control: no-store`, and Start and React Router answer with no `Cache-Control`, `ETag`, `Last-Modified`, `Expires` or `Age`.

### Measure whole requests

```sh
go run ./test/compare/cmd/compare measure -all -server-cpus 1 -load-cpus 2 -json out.json
go run ./test/compare/cmd/compare report out.json
go run ./test/compare/cmd/compare diff old.json new.json
```

`measure` builds first (add `-skip-build` to use the last build), then starts each server fresh for each round and times it from the start of its process. There is no warm-up for anyone. The client is the command itself, one request in flight, `Accept-Encoding: gzip` (`-accept-encoding identity` asks for no compression instead), the six pages in turn. A round of one server is:

1. **Cold part.** The time from process start to the end of the first answer, then the latency of the first 100 and the first 1000 requests (the mean of each), and the request from which latency settles: the first one after which the median of every window of 30 requests stays within 10% of the steady latency of their pages. `>1000` means it had not settled by then.
2. **Steady part.** `-steady` long (30 seconds by default) right after the cold part: requests per second, P50, P99, P99/P50 and the largest latency.
3. **Memory.** RSS right after the server listens (before any request), and the peak RSS over the whole run (the process and its children, sampled every 100 ms and, on Linux, the kernel's high-water marks).

There are two configurations. `default` is each framework as shipped: Tifa with its render cache at the default `cache.size`, Next.js, Start and React Router as they are. `engine` has every cache off: Tifa with `--cache-size 0`, so every request renders, and Node with `--jitless` next to each Node app, marked as a reference in the tables because it explains a gap and is not a contender. Both Tifa servers run `--ssr-vms 1` with `GOMAXPROCS=1`. No server gets a compression middleware or a changed setting: each answers as its default config does. Tifa compresses (it keeps one gzip form of each cached page), Next.js compresses, React Router compresses, and TanStack Start (Nitro) sends rendered pages uncompressed. The client reads the whole body and does not decode it, so decoding is not in the timing. Tifa's hit rate is the share of answers whose `X-Tifa-Render` is `cache` or `shared`, counted over the whole run.

| Subcommand | What it does |
| --- | --- |
| `measure` | Builds, measures and prints the tables. `-all` measures both configurations and runs the A/A check. `-config default` or `-config engine` measures one. `-json out.json` saves the record |
| `report out.json` | Prints the tables again as Markdown: out of the box, engine, memory, per page (requests a second with one request in flight and P50 of each page for each server, and each Node server against Tifa) and, when the record has `-render`, the render and the rest. Each cell is the median of the rounds, with their range in brackets when they differ. The A/A spread is printed under them |
| `diff old.json new.json` | Compares the Tifa servers of two records and prints each metric that got worse by more than max(2%, the A/A spread of either record). It exits with status 1 when any is flagged. Other frameworks are not compared |

| Flag of `measure` | Default | |
| --- | --- | --- |
| `-server-cpus`, `-load-cpus` | empty | The cpus for the server and for the client, as `taskset -c` takes them (`1` or `1,2`). Linux only. Leave them empty elsewhere: the numbers then only show that the command works |
| `-procs` | 1 | Tifa only. Gives Tifa that many VMs and `GOMAXPROCS`, and sends that many requests at once, each on its own connection. A connection runs the scenario by itself, starting on its own page and writing at its own reads, so the hit rate stays about the same. Requests/s are summed and the latencies merged. Give `-server-cpus` as many cpus, on other physical cores than `-load-cpus`. The cold series is the first connection's |
| `-unique-urls` | off | Adds `?_=<n>` to every timed read, so that no two requests share a render. With the cache off, requests for the same page that arrive together share one render, which several connections do often, and the run then answers more than the VMs can render. Use it with `-config engine` and `-procs` |
| `-conns` | `-procs` | Requests in flight, when they should not be as many as the VMs. A Tifa that has idle time because every connection waits for a render it asked for shows more throughput with more connections |
| `-rounds` | 3 | Rounds. Each round starts every server fresh, and the order of the servers rotates by one place from round to round, so that none is always first |
| `-steady` | 30s | Length of the steady part |
| `-cold` | 1000 | Requests of the cold series |
| `-config`, `-all` | `default` | The configuration, or both |
| `-scenarios` | `read` | A list out of `read`, `read-write` and `write-each`, or `all`. `-all` runs all three |
| `-aa` | off | Runs Tifa against Tifa (two identical servers) before the others in every round, and prints how far apart they were for each metric: the largest minus the smallest over the median. `-all` implies it. `diff` uses this spread as the noise floor |
| `-servers` | all | A list of spec ids, such as `tifa,tifa-nocache,nextjs` |
| `-accept-encoding` | `gzip` | What the client asks for in every request, `gzip` or `identity`. The record keeps it. The parity checks always ask for no compression, since they compare text |
| `-render` | off | Also runs `BenchmarkShop` of `test/ssr` once after the rounds, on `-server-cpus`: it renders the six pages in one warm VM without HTTP, and the report splits Tifa's request (cache off) into the render and the rest. It is a measurement of its own and does not touch the cold runs. Next.js, Start and React Router cannot be split like that from outside |

**Wire size and what gzip costs.** Every run records, for each page, the length of the body as it came over the connection and its `Content-Encoding`, and `report` prints a note under the out of the box table: for example that Start sends N KB a page uncompressed and the others about M KB. `-all` also runs two servers of the Next.js app, `nextjs-identity` and `nextjs-gzip`, that differ only in what the client asks for (whatever `-accept-encoding` says), in the `compression` configuration that is in no table, and the note says how many fewer requests a second Next.js answers with gzip than without. It is the estimate of what Start would pay if it compressed, and it is not measured for Start.

**Placement rule.** On Linux the command reads `/sys/devices/system/cpu/cpuN/topology` and refuses to run when a cpu of the server and a cpu of the client are the same cpu or two threads of one physical core. The client pins itself with `taskset` and the servers are started under it. With hyperthreads, cpus `n` and `n+4` on a 4-core machine usually share a core, and cpus 1 and 2 on the GCP machine do not. Off Linux nothing is pinned, nothing is checked, and the record says `not checked`.

The record (`-json`) keeps the Go, quickjs, Node, Next.js and Start versions, the Tifa commit, the CPU model, the kernel, the placement, the settings and every run of every round. Raw records stay out of the repository.

**Scenarios.** `read` is the six pages in turn and is what the engine table, the memory table, the per-page table and the A/A check use. `read-write` has the same timed reads and, before the first order page after each 10 reads, one untimed write: a `PATCH` of the address of that order (the shop's own call on the order route, with the customer and the phone it already has), with an address that carries the number of the read and always has the same length. So the data of the page is new every time, does not grow, and an earlier version cannot be served again, and the render cache of Tifa must miss there. Lists and stats show who an order is for but not where it goes, so a write cannot change them and writes come before order pages only. It runs for the default configuration, and the report has an out of the box table for it with the hit rate. `write-each` is for Tifa only, with the cache on and with `--cache-size 0`: it reads the two order pages in turn and writes the order before every read, so the cache never hits. The report prints the miss overhead of the cache from it: P50 and requests per second with the cache against without. Only reads are timed in all three.

The list of servers is the table `Env.Specs` in `test/compare/specs.go`: a new framework is one more entry there, and the run, the report and the diff take it from the table. What a run asks for is a `Scenario` (`scenario.go`): the requests of one unit of work, of which exactly one is timed and last. A scenario can send untimed requests before it, and says which specs and configurations it runs for.

Before each server starts, the command waits until the cpus it uses were idle for 3 seconds (Linux). It holds no lock on the cores. When other work shares the machine, take your own lock (`flock`) around the command and keep the whole run in a cgroup with a memory limit.

What is still not equal, and which way it leans, is in [the study](studies/nextjs-and-tanstack-start.md#what-is-not-equal).

### Whole visits (`compare plans`, `record` and `browse`)

The page-by-page measurement above does not show what a visitor costs a server. A visit is a full load of one page, then clicks on links of the page on screen and now and then a reload, and each framework does that differently: Tifa fetches JSON, Next.js fetches an RSC payload and prefetches the links in view, TanStack Start calls server functions, React Router fetches `.data` and discovers routes. The `browse` comparison plays visits that a real browser made against each framework and measures how many visits a second a one-core server carries.

- **Pages.** All 58 workbench pages of the shop: the two lists, the two stats pages and the 54 order pages (`AllPages`). `TestPagesShowTheSameText`, `TestDomainMatchesGo` and `TestEveryRequestComputesAndRenders` cover all of them in all four apps. `TestFanOutWriteChangesListsStatsAndOtherOrders` checks that a fan-out write changes the list, the stats and the page of another order of the customer in all four.
- **Plans** (`compare plans`, `plan.go`). Visit plans come from one seed and are the same for all four frameworks. The first page is a list or stats page with probability 1/2 (each of the four alike), else a random order of the 54. The page views of a visit are geometric with a mean of 4 (75% soft navigations) or 2 (50%). Each later page view is a reload of the page on screen with probability 10%, else a click on a link that page has: a list links to its newest 25 orders, its stats and the other shop, an order to its list, its stats and the other shop, stats to their list and the other shop (links that depend on the data, such as other orders of the same customer, are left out so writes do not change what can be clicked). These numbers are assumptions, varied in the runs, not measured baselines.
- **Writes** go into the plans: after a page view, with probability 1/500 (baseline) or 1/20, a write to one of the three orders that accept one (SH-1042, SH-1041, WK-0201, the others have shipped). The default write gives the order a new address, so only its page changes. The fan-out write gives it a new customer name through the same PATCH, which the lists, the stats and the other orders of that customer show. The writes of the lower rate are among those of the higher rate. The traffic of a page view does not depend on the writes, so the traces are recorded without them and the writes are put in at the replay.
- **Traces** (`compare record`, `test/compare/recorder`). A small Node tool with Playwright (`pnpm install` in that folder) plays every plan in Chromium (fresh context per visit, 1280x800, no hover, real clicks on the links, the browser's own reload) against each framework and keeps every request the browser sent: method, URL, the headers that matter (`rsc`, `next-router-*`, `x-tsr-serverfn`), whether it sent `If-None-Match`, and when it started and finished. The browser decides what is sent: prefetches, deduplication, the router cache and route discovery. Only dynamic traffic is kept (documents and data requests: no scripts, styles, images or fonts) and requests outside the workbench are dropped (the store links, which 404 in the ports), alike for all four. Back and forward are not in the plans, since the browser's back/forward cache cannot be measured here. Traces are tied to a build (Start's function ids, React Router's manifest version): record them against the build that is replayed. Raw traces stay out of the repository.
- **Replay** (`compare browse`, `replay.go`). Each user plays traces one after another with its own connections (at most 6, as a browser opens) and replays the requests in the order and with the parallelism the browser had: a request starts when every request that had finished before it started in the browser is done. A page view ends when its documents and data requests are done, and prefetches go on in the background until the end of the visit. Cookies are kept within a visit and not across visits, and `If-None-Match` carries only the ETag the visit got for that document. Tifa's build id in its navigation requests is replaced by the build id of the server. Before each search and after each series of rounds, `verifyWrites` writes both kinds of write and checks that the document and the navigation data of the order show the new data.
- **Load.** Per framework and scenario, users go 1, 2, 4, ... up to 64 in steps of 10 seconds (after a 3 second lead-in) until visits/s rises by under 3% in two steps in a row, or a step has errors, or the P99 of a full load or of a whole navigation (all requests of one click) passes 1 second. The whole curve is kept in the record, and the highest step that passes is used. Then three rounds at that step, each with a fresh server, the frameworks in a rotating order, a 10 second lead-in that is not counted and one common 30 second window for all users. The runs are `baseline` (4 page views, writes 1/500, address only), `mean2` (2 page views), `writes` (1/20) and `fanout` (1/20, new customer name). Server on one cpu and client on two, as in the rest of the comparison.
- **Report.** Per run and framework: visits/s and CPU ms per visit (processor time of the whole server process tree from `/proc`, user and system, including writes and prefetches), page views/s and CPU ms per page view, requests and body KB per visit, P50 and P99 of full loads and of whole navigations, and the counts of reloads, prefetches and writes (P99 only where a round has 100 samples), and peak RSS. Tifa adds, per visit, the renders, the cache hits, the shared renders and the 304 answers. The timings are when the answer reached the client, not when a browser would show the page. The conditions favor reuse of rendered pages: 58 pages that everyone shares, almost no personalization and rare writes.

```
go run ./test/compare/cmd/compare plans -dir traces -visits 300
go run ./test/compare/cmd/compare record -dir traces -workers 4
go run ./test/compare/cmd/compare browse -dir traces -server-cpus 1 -load-cpus 2 -json browse.json
```

## Render clock

`tifa.WithRenderClock(ctx, now)` supplies the source for Date, Temporal.Now and Intl date formatting without a date in one render. Use a closure returning a fixed `time.Time` for deterministic assertions. Set the context on the test request before calling `tifatest.NewCtx`, or set it in `OnRequest` with `c.WithContext`. `tifatest.NewCtx` tests route functions and preserves the context. It does not run SSR. The public API and the module initialization and cache boundaries are described in [app.md](app.md#render-clock).

`go test -p 2 ./internal/ssr ./server -run 'RenderClock|Temporal'` covers fixed time across promises, saved functions and formatters, live module initialization, VM reuse, replacement, parallel renders and middleware through a real server render. Repeat the touched packages with `-race`. `TestRenderClockFromMiddleware` also uses `tifatest.NewCtx` and a closure for `next` to exercise the same middleware in a route test.

The production default remains live. Test a fixed source rather than requiring separately sampled live timestamps to match. A fixed render clock does not change Go's time.Now or the monotonic timeout budget. A request with a clock skips the render cache and shared renders, and gets no ETag, so it always renders with its own clock.

A request with a render clock skips the render cache, so a test that sets one gets a render every time (`TestRenderClockSkipsTheCache`). `TestRenderKeyCoversEveryFieldOfTheInput` in `server` fails when a field is added to `ssr.Input` that is neither in the key of the render cache nor listed with the reason it cannot change a cached page. `TestDevWarnsAboutAPageThatRendersDifferently` covers the double render of `tifa dev`.

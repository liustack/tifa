# Testing and verification

## Before committing

Every Go change must pass:

```sh
go test ./...
go vet ./...
CGO_ENABLED=0 go build ./...
```

For packages with concurrency (request context, `tifa.Use`, config loading, the server), also run the race detector:

```sh
go test -race ./<package path>
```

The commands in the root only cover the framework. The example app `examples/shop` is a separate module. When you change it, run its own checks in that folder:

```sh
cd examples/shop
pnpm install --frozen-lockfile
go tool tifa build
go tool tifa check   # the analysis, go vet ./..., go test ./... and tsc --noEmit, stopping at the first failure
```

## End-to-end tests (`test/e2e`)

`test/e2e` builds the `tifa` CLI, runs `tifa build` on the apps in `test/apps/`, on `examples/shop` and on an app that `tifa new` creates, starts the outputs and checks them from outside. Skipped by default. First run `pnpm install --frozen-lockfile` in `test/apps/pages`, `test/apps/tailwind`, `test/apps/mui`, `test/apps/bench`, `test/apps/session`, `test/apps/upload`, `test/apps/pagecache`, `test/apps/content`, `test/apps/i18n` and `examples/shop`, then turn them on (`test/apps/extreme` also needs `TIFA_EXTREME=1`, see [Extreme pages](#extreme-pages-testappsextreme)):

```sh
TIFA_E2E=1 go test -timeout 30m ./test/e2e/
```

A full run can take more than the default 10 minutes of `go test` on a laptop, hence `-timeout`.

The programs the tests start and leave running, the built apps and `tifa dev`, go through `testproc.Start`, so a killed run leaves none of them behind.

## Writing tests

- New behavior and bugs with a known cause: write the test first, see it fail with your own eyes, then write the implementation.
- Tests live in the same package as the code under test, in files named `*_test.go`. The exceptions test from outside: `test/e2e` the built CLI and apps, `test/ssr` the SSR pool of `internal/ssr` with the example app's real bundle. Framework behavior gets its test in its own package, with its own `testdata`, and does not depend on `examples/shop`.
- One assertion proves one thing. When a loop runs several cases, give each case its own state, and confirm the code under test really ran. Caching and deduplication logic is the easiest way for a later case to get an earlier case's result while the test still passes.
- A test that starts a program that keeps running, such as a server, `tifa dev` or a Node process, starts it with `testproc.Start` of `internal/testproc`, not with `cmd.Start`. `t.Cleanup` does not run when a panic in another goroutine, a test timeout or a SIGKILL ends the test process, and a program left that way runs on with the init process as its parent, holding its port, its memory and every file it inherited. `testproc.Start` makes the system end the program with the test process, however that ends: Linux sends it a SIGKILL (`Pdeathsig`, from a thread that lives as long as the process), and macOS, which has no such signal, hangs up the terminal the program runs on (the program is the leader of a session on a terminal whose master side only the test process holds), which stops a program that does not ignore SIGHUP. It also marks the files the test process inherited, such as the lock of a script that runs the tests under `flock`, to close when the program starts, so a program left behind cannot keep the lock. Only the program is bound, not what it starts in turn: on macOS what stays in its process group stops with it, and a program that starts others has to end them itself, as `tifa dev` does with its app and the driver of Vite when it is killed (`TestDevLeavesNothingBehind`). Keep the `t.Cleanup` that stops the program, which is what ends it when the test ends normally. `internal/testproc/orphantest` holds the check for a package that starts programs: a helper test starts a fake program the way the package does, the check ends the helper in the three ways a test process dies without cleanup (a panic in another goroutine, a SIGKILL, a SIGKILL while SIGHUP is ignored, as under `nohup`), and the program must be gone, and must hold none of the files the helper inherited. See `test/e2e/orphan_unix_test.go` and `test/compare/orphan_unix_test.go`.
- A test in `test/e2e` that needs a browser gets its `pw` function from `openBrowser` (`test/e2e/browser_test.go`), and does not run `playwright-cli open` and `close` itself. `playwright-cli open` starts a detached daemon (`cliDaemon.js <session>`) that outlives the test process, and `playwright-cli close` exits 0 even when it finds no session. So `openBrowser` registers the close before the browser opens (a failed `open` or a `t.Fatal` still closes), runs every command in one folder, reads the answer of `close`, and fails the test if a daemon of the session is still running after it, ending that daemon. `TestMain` fails the run if a daemon of any session the run opened is left. A session name must be short: the daemon listens on a unix socket at `<tmp>/pw-xxxxxxxx/cli/<16 characters>-<name>.sock`, and when that path is over 104 characters (the name is at most 17 characters under a 48 character `TMPDIR` as on macOS) the daemon fails to listen with EINVAL but keeps running, and `close` then answers "is not open" for it, so it can only be ended with a kill. `openBrowser` refuses a name that is too long for the `TMPDIR` in use. Two runs at once share the sessions of the same name, so do not run the e2e tests twice at once. A test that is killed or times out still leaves its daemon, because no cleanup runs. Find those by `ps -axo pid,command | grep cliDaemon.js` and end them with `playwright-cli -s=<session> close`.
- Verify browser behavior (extra requests during hydration, one request per navigation, horizontal overflow on narrow screens) with `playwright-cli`, and take screenshots of the results.

## HTTPS tests (`server`)

`server/tls_test.go` and `server/acme_test.go` run with `go test ./server/`, on the loopback and without a network. They make their certificates themselves, and the ACME server they ask is a fake one in the test process (`fakeACME`). It checks nothing a client signs, but it does what Let's Encrypt does with the challenges: it connects to the program over plain HTTP (http-01) or over TLS with `acme-tls/1` (tls-alpn-01) and checks the key authorization. Its http-01 request carries the port in `Host`, as Pebble's does. The tests cover HTTP/2 with your own certificate, loading the files again after they change, a Kubernetes secret swapping its `..data` link while 8 goroutines keep handshaking (run it with `-race`: without the lock of `certFiles` it fails), the redirect and the names it serves, HSTS, compression and streams over HTTP/2, both addresses shutting down, a certificate from each challenge and from the cache after a restart, and that `tifa dev` serves plain HTTP.

`TestSSRWebAPILibraries` builds Zod's Base64 validation and encoding, uuid, serialize-javascript, react-hook-form's `useFieldArray`, and the hookform Ajv resolver through the SSR plugin, then runs them through `ssr.Compile` and `ssr.Load`. It checks module initialization, secure random calls without a `Math.random` fallback, and that resolver validation leaves its input unchanged. Their versions are pinned with the other bundle test dependencies. The Web API edge cases run without Node in `internal/ssr` (`TestHostBase64`, `TestHostDOMException`, `TestHostCrypto` and `TestHostStructuredClone`).

## Long SSR tests skipped by default

The default tests in `internal/ssr` only use small handwritten bundles, `testdata/app.js` and the bundles with source maps in `explain_test.go` for render errors (broken maps, and a bound on what explaining an error allocates), and finish in a few seconds. The soak tests skip by default:

```sh
TIFA_SSR_SOAK=1 go test -run Soak -v ./internal/ssr
```

They run normal reuse (2 VMs, 2 callers, 10,000 renders), OOM recovery (8 failures and replacements), and 16 proactive memory swaps. The OOM fixture fills memory within one render, repeatedly parsing input with long Chinese text, so an idle swap cannot preempt the failure. It exercises the input conversion and allocation cleanup where github.com/liustack/quickjs fixed a leak. If this test fails, first confirm the dependency is github.com/liustack/quickjs. After shutdown, every VM the pool made must have closed without an error. `TestSoakVMMemory` loads every VM the way the pool does. It prints what Intl adds to an empty VM, unused and after formatting, and what the bundle adds after loading, formatting and a render. It fails when Intl adds more than 32 KB to a VM that never formats.

### Timing a build of quickjs against another

To time one build of quickjs against another at several code positions, with a `go.work` that uses this repository, `examples/shop` and a quickjs checkout whose engine is generated, use `go tool measure bench` in quickjs ([docs/testing.md](https://github.com/liustack/quickjs/blob/main/docs/testing.md#developer-tools-generate-check-time)), which also has the make targets that generate its engine and run its checks, here or on another machine: it builds this package's test binary against each checkout, runs them in turn and reads the `p50-ms` of the pages by the rule of its code positions. A binary that prints a line `vmhwm-kb: N` at the end (the child of `TestShopVMResident` does) also gets its peak memory reported.

The prototype's other experiments (per-stage timing, memory probes) stay in `internal/ssr` at the tag `prototype-baseline`. Check out that tag and build from it when needed.

Run performance comparisons on the same machine, alternating between the old and new builds, and record the machine load. Changes in machine load can make absolute times differ several times over. Only ratios measured in the same alternating round are comparable.

### Reading BenchmarkShopParallel

`BenchmarkShopParallel` catches what one VM cannot show: a lock that every VM takes. `BenchmarkShop` stays the same when such a lock comes back. Several VMs render in one process, so a lock in the engine's allocator or in the host calls would keep the program from using more cores, and only this benchmark shows it.

- Run both sub-benchmarks in one command. `speedup` only shows when `vms-1` ran in the same command. To repeat, run the command again: with `-count` every `speedup` is against the last `vms-1`, and `-cpu` changes `GOMAXPROCS` after the number of VMs is set.
- On Linux, set `GOMAXPROCS` to a number of physical cores and pin the test to them with `taskset`, one CPU per core. Two VMs on the two threads of one core render only about 20% more than one, so a speedup over hyperthreads says little about locks.
- Read `speedup` first. A Go mutex spins before it blocks, and spinning shows as CPU time (`runtime.procyield` in a CPU profile) and a lower speedup, not as lock wait. `lock-wait-%` then says whether a lock is the reason.
- The benchmark does not fail on these numbers, because machine noise moves them as much as the regression does. Compare against main on the same machine, alternating, as above. A speedup more than 10% below main's is worth a look. The runtime samples lock wait, so small values are noisy. On an AMD EPYC 7B13 with 4 physical cores (`GOMAXPROCS=4 taskset -c 4-7`, the other 4 threads idle), a lock wait above about 0.5% is worth a look. That level holds only for that machine, and Mac numbers compare only with Mac numbers.

To see which lock it is, take a mutex profile. Profiling makes the lock wait larger, so read the profile for where the wait is, not for how much:

```sh
TIFA_SSR_SHOP=1 GOMAXPROCS=4 taskset -c 4-7 go test -run '^$' -bench ShopParallel -benchtime 15s \
  -mutexprofile mutex.out -o ssr.test ./test/ssr
go tool pprof -top -cum ssr.test mutex.out
```


## Comparison with Next.js, TanStack Start and React Router (`test/compare`)

`test/compare` builds the six workbench pages of `examples/shop` as a Tifa program, as a Next.js app, as a TanStack Start app and as a React Router v7 app (framework mode, the successor of Remix v2). It checks that the four show the same pages and do the same work for each request, and measures how long whole page requests take from process start and how many each answers. It builds three apps with Node and the measurement needs a quiet machine, so CI does not run it. The method and the numbers are in [Tifa against Next.js and TanStack Start](studies/nextjs-and-tanstack-start.md).

| Where | What it holds |
| --- | --- |

Plain TypeScript with no packages, so Node runs it as it is. **Where the work is done.** In Tifa, every request runs the Go `Layout` and `Load` functions, which read the orders from memory, with the indexes and running totals that every write keeps up to date, and work out the list, the order or the stats. In the three apps, every request runs the same functions in TypeScript on orders that the process builds in memory when it starts, from the same seed code, with the same indexes and totals. No answer is kept from one request to the next: what lasts between requests is the data, as a database keeps it. The components, the stylesheet, the root Layout, everything TypeScript under `app/projects`, the 160 pixel photos and the `+layout` and `+route` modules that `tifa build` generates from the Go types are copied from `examples/shop` into `shop/` and `public/images/` when the apps are built, so a change to a page of the shop reaches all four. The handlers (`POST`, `PUT`, `PATCH`) of the workbench are not ported: the apps show pages. The storefront (`/store`) is in all three apps with all its writes, see [The storefront in the three apps](#the-storefront-in-the-three-apps). The workbench forms render, but their calls fail. The exception is the write endpoints for the measuring (below), which take the body of the shop's handler of the same method and answer with the same status and order. Next.js cannot put a route handler beside a page, so they have paths of their own in the three apps: `POST /compare-write/<project>` places an order (the `POST` of `orders/route.go`, which gives it the next number of the project and the time of the server), and on `/compare-write/<project>/<order>` `POST` ships the order, `PATCH` changes the recipient and `PUT` adds a note, as on the order route. `domain/orders.ts` has the copies of `CreateOrder`, `ShipOrder`, `UpdateRecipient`, `AddNote` and their checks.

### Check that the pages are the same

```sh
TIFA_COMPARE=1 go test -count=1 -v ./test/compare
```

The tests build the shop and the three apps (`pnpm install --frozen-lockfile` and the builds, under a minute on a warm machine), start each server and check:

- `TestDomainMatchesGo`: for each page of `CheckedPages` (the 58 workbench pages and the four product pages of the back office, `ProductPages`: the product list of each shop and the edit page of one product of each), the JSON that the Go `Layout` and `Load` functions answer, which the test asks the shop's own program for as the browser router does, equals the JSON that Node makes from the port (`node test/compare/domain/dump.ts`), compared as values, field by field. - `TestPagesShowTheSameText`: the pages of `CheckedPages` fetched without compression show the same title and text nodes in order, and have the same number of `tr`, `a`, `svg`, `button`, `li`, `time`, `img`, `table`, `h1` to `h3`, `nav` and `input` elements. - `TestFilteredListsMatchGo` and `TestFilteredListsShowTheSameText` (`filters_test.go`): the same two checks for the order list with filters and a page in the URL (`FilterPages` in `filters.go`: a status, a page of a filtered set, a page past the end, a sort by the amount or the time, a search for an order number and for a customer, searches with white space around them or with U+0085 or U+FEFF in front (only ASCII white space is trimmed, in Go, in the port and in the search box), a carrier with a period and an amount, a filter that matches nothing, and values that are not choices). - `TestNoCachingBetweenRequests`: the apps hold nothing that could keep a page between requests.
- `TestStoreDomainMatchesGo`: the same for the storefront. Visitors with their own cookies (`StoreScenarios`) run against the Go shop and against `node test/compare/domain/store/dump.ts`: every page in both languages with filters, every product, carts that are filled, changed, given coupons, checked out and refused, and the bad bodies. - `TestDomainMatchesGoAfterWrites`: the same as `TestDomainMatchesGo` after the writes of the first 60 reads of the scenario with writes and then a staff edit of a product and one of each kind of write of the shop's admin (place three orders, one of them of the edited product, ship, add notes, change a recipient), sent to the Go shop and applied in the port (`domain/dump.ts` takes the list of writes). A note and a shipment of one order made within the same millisecond could be listed in the other order in the log of the order page. The test ships first and then adds the note.
- `TestWriteChangesThePage`: in each server (Tifa with its render memo on too), a write of the address of an order shows on the page of the order, and a second write shows and the first no longer does. This is the check that the write endpoints of the Node apps work and that a cached page is not served after a write.
- `TestPagesStayTheSizeOfAPageAsOrdersGrow` (`writes_test.go`): 40 orders placed for a customer who has orders already, in each server, after the restock gives the tray they order a stock of 40. The order list holds one page of 25 rows, the other orders of the customer on an order page are at most 10 and the page says how many earlier ones there are, and the four apps show the same pages. The shop sends the newest 25 rows of the order list with the numbers over all orders (the total, the oldest order waiting to ship, the carriers, the 14 days of the cards) and the port does the same (`listOrders` in `domain/orders.ts`), so a page does not grow with the orders a run places. Both keep the orders by time, by customer and by product with running totals that every write updates (`storage.go` in the shop, `domain/storage.ts`), so reading the data of a page costs about the same with 50 orders or 5000. The list without filters or a search, sorted by time, is cut from the orders by time. A filter, a search or the sort by amount still goes through all the orders. The page and the filters of the list are in the query string, so the port reads them the same way (`queryOf` in `domain/loaders.ts`).
- `TestWritesLandAndPagesChangeAlike` (`writes_test.go`): in each server, the four writes of the shop's admin (place an order, ship it, change the recipient, add a note), a checkout of the storefront, which must become order SH-1044 of the studio shop, and a staff edit of a product in each shop, which the next order of that product must take, with their refusals (a bad body, a field that fails, an unknown order, project or product, a product the other shop does not sell, an order that has shipped, an edit in the other shop, an order over the stock, which answers 409 as a checkout does, a body of `null`, which Go decodes into the zero value and so answers 422, and a whole number Go does not decode into an int: written with a fraction or an exponent, such as `1.0` or `52e3`, or past the range of an int, which answers 400). The Node apps read these bodies with the JSON reader of the storefront port (`domain/store/json.ts`), which follows the rules of `encoding/json/v2`, so they refuse the same numbers and also a name given twice in any object (an object the handler does not read too), bytes that are not UTF-8 and an escape of a lone surrogate, each with 400. The texts of the back office are trimmed as `strings.TrimSpace` trims (U+0085 is white space, U+FEFF is not) in the checks and in what is kept. An order staff place takes its pieces from the stock, so it changes the product pages of its shop too. Every server must answer the same status and the same order (instants left out, since the servers run one after another), and the pages a write reaches (the order, the list and stats of its project, the orders that share its product or customer, the product pages of the back office and the storefront) must change and then show the same text in all four. A refused write must change no page.


They work on macOS and Linux and skip when `go`, `node` or `pnpm` is missing. `TIFA_COMPARE_SKIP_BUILD=1` starts what the last run built. The tests of the parser run without the switch.

When a page check fails after a change to the shop, read the difference it prints. A new page needs a route in all three apps. A new package the shop's workbench imports needs a line in the `package.json` of all three apps, and `pnpm install` in each folder to update the lockfiles.

**What the count test shows.** It builds a second Tifa program with `go build -overlay`, which adds a counter to `ordersOf` (which every read of the orders of a project starts with) and a path `/compare-counts`, without changing a file of the shop. The Node apps count the same calls in the port (React Router shares the project between its parallel loaders per request, through the Request object), and also the runs of the root Layout, the project Layout and the page's `Load`, and the renders of the page on the server, and answer with them at `/compare-counts`. For each page the test asks once and reads what the counters gained, then asks five times more and checks that they gained five times as much. A render in Tifa is read from the header `X-Tifa-Render`, which says `vm` for a page rendered in a VM and `memo` or `shared` for one that was not. Then the calls of `ordersOf` for one request must be the same in all four: 4 for an order list, 6 for an order and 4 for the stats. `TestNoCachingBetweenRequests` adds what the code and the answers say. None of the three has `cacheComponents`, `use cache`, `unstable_cache`, a `revalidate` setting or a `QueryClient` in its sources or its package lists, and the React Router app has no `clientLoader`, `shouldRevalidate` or `headers` export. Next.js answers a page with `Cache-Control: no-store`, and Start and React Router answer with no `Cache-Control`, `ETag`, `Last-Modified`, `Expires` or `Age`.

### The storefront in the three apps

All three apps serve the storefront of the shop (`/store` in English and `/zh-CN/store` in Chinese: home, products with filters, product, cart, checkout, journal and posts) with its writes (add to cart, change a quantity, coupon, checkout, mark a product seen). Building copies the storefront components, translations, photos and generated `route.gen` modules from `examples/shop` into each app, the data comes from the port in `test/compare/domain/store`, and each app type checks (`tsc --noEmit`) as part of its build, so a type error stops every comparison.

What the apps share is written once. `domain/store/calls.ts` makes the answers of the writes the way Tifa gives them: for a call from the browser (`X-Tifa-Call`) the result in `{"result": ...}` and a redirect as a 200 with `X-Tifa-Redirect`, for a plain request the result as it is and a real 303, the 405 with `Allow`, and the 308 for a trailing slash. `overlay/runtime/storecall.ts` is the browser side of a call. Each app only says where its routes are and how it goes to a page. The port reads what Go reads the way Go does: a body with the rules of `encoding/json/v2` (a name given twice, `1.0`, `1e0` or a number outside int64 for an int, text after the value and bytes that are not UTF-8 are a 400, `domain/store/json.ts`), the `Cookie` header as `net/http` does (`ctx.ts`).

### Measure whole requests

```sh
go run ./test/compare/cmd/compare measure -all -server-cpus 1 -load-cpus 2 -json out.json
go run ./test/compare/cmd/compare report out.json
go run ./test/compare/cmd/compare diff old.json new.json
```

`measure` builds first (add `-skip-build` to use the last build), then starts each server fresh for each round and times it from the start of its process. There is no warm-up for anyone. The client is the command itself, one request in flight, `Accept-Encoding: gzip` (`-accept-encoding identity` asks for no compression instead), the six pages in turn. A round of one server is:

1. **Cold part.** The time from process start to the end of the first answer, then the latency of the first 100 and the first 1000 requests (the mean of each), and the request from which latency settles: the first one after which the median of every window of 30 requests stays within 10% of the steady latency of their pages. `>1000` means it had not settled by then.
2. **Steady part.** `-steady` long (30 seconds by default) right after the cold part: requests per second, P50, P99, P99/P50 and the largest latency.
3. **Memory.** RSS right after the server listens (before any request), and the peak RSS over the whole run (the process and its children, sampled every 100 ms and, on Linux, the kernel's high-water marks).

There are two configurations. `default` is each framework as shipped: Tifa with its render memo at the default `ssr.memo_size`, Next.js, Start and React Router as they are. `engine` has every cache off: Tifa with `--ssr-memo-size 0`, so every request renders, and Node with `--jitless` next to each Node app, marked as a reference in the tables because it explains a gap and is not a contender. Both Tifa servers run `--ssr-vms 1` with `GOMAXPROCS=1`. No server gets a compression middleware or a changed setting: each answers as its default config does. Tifa compresses (it keeps one gzip form of each cached page), Next.js compresses, React Router compresses, and TanStack Start (Nitro) sends rendered pages uncompressed. The client reads the whole body and does not decode it, so decoding is not in the timing. Tifa's hit rate is the share of answers whose `X-Tifa-Render` is `memo` or `shared`, counted over the whole run.

| --- | --- |
| `measure` | Builds, measures and prints the tables. `-all` measures both configurations and runs the A/A check. `-config default` or `-config engine` measures one. `-json out.json` saves the record |

Each cell is the median of the rounds, with their range in brackets when they differ. The A/A spread is printed under them |

**Wire size and what gzip costs.** Every run records, for each page, the length of the body as it came over the connection and its `Content-Encoding`, and `report` prints a note under the out of the box table: for example that Start sends N KB a page uncompressed and the others about M KB. `-all` also runs two servers of the Next.js app, `nextjs-identity` and `nextjs-gzip`, that differ only in what the client asks for (whatever `-accept-encoding` says), in the `compression` configuration that is in no table, and the note says how many fewer requests a second Next.js answers with gzip than without. It is the estimate of what Start would pay if it compressed, and it is not measured for Start.

**Placement rule.** On Linux the command reads `/sys/devices/system/cpu/cpuN/topology` and refuses to run when a cpu of the server and a cpu of the client are the same cpu or two threads of one physical core. The client pins itself with `taskset` and the servers are started under it. With hyperthreads, cpus `n` and `n+4` on a 4-core machine usually share a core, and cpus 1 and 2 on the GCP machine do not. Off Linux nothing is pinned, nothing is checked, and the record says `not checked`.

The record (`-json`) keeps the Go, quickjs, Node, Next.js and Start versions, the Tifa commit, the CPU model, the kernel, the placement, the settings and every run of every round. Raw records stay out of the repository.

**Scenarios.** `read` is the six pages in turn and is what the engine table, the memory table, the per-page table and the A/A check use. `read-write` has the same timed reads and, before the first order page after each 10 reads, one untimed write: a `PATCH` of the address of that order (the shop's own call on the order route, with the customer and the phone it already has), with an address that carries the number of the read and always has the same length. So the data of the page is new every time, does not grow, and an earlier version cannot be served again, and the render memo of Tifa must miss there. Lists and stats show who an order is for but not where it goes, so a write cannot change them and writes come before order pages only. It runs for the default configuration, and the report has an out of the box table for it with the hit rate. `write-each` is for Tifa only, with the cache on and with `--ssr-memo-size 0`: it reads the two order pages in turn and writes the order before every read, so the cache never hits. The report prints the miss overhead of the cache from it: P50 and requests per second with the cache against without. Only reads are timed in all three.

The list of servers is the table `Env.Specs` in `test/compare/specs.go`: a new framework is one more entry there, and the run, the report and the diff take it from the table. What a run asks for is a `Scenario` (`scenario.go`): the requests of one unit of work, of which exactly one is timed and last. A scenario can send untimed requests before it, and says which specs and configurations it runs for.

Before each server starts, the command waits until the cpus it uses were idle for 3 seconds (Linux). It holds no lock on the cores. When other work shares the machine, take your own lock (`flock`) around the command and keep the whole run in a cgroup with a memory limit.

What is still not equal, and which way it leans, is in [the study](studies/nextjs-and-tanstack-start.md#what-is-not-equal).

### Whole visits (`compare plans`, `record`, `links` and `browse`)

The page-by-page measurement above does not show what a visitor costs a server. A visit is a full load of one page, then clicks on links of the page on screen, and each framework does that differently: Tifa fetches JSON, Next.js fetches an RSC payload and prefetches the links in view, TanStack Start calls server functions, React Router fetches `.data` and discovers routes. The `browse` comparison plays visits that a real browser made against each framework. It is a replay of dynamic traffic (documents and the data requests of the client router: no scripts, styles, images or fonts, no rendering, no hydration), so it measures what a server does for a visitor, not how fast a browser shows a page. The mix of the visits takes published e-commerce numbers where there are some, and says which numbers are assumed.

#### Rules

These rules and the numbers in them change only with the explicit consent of the maintainer, and a proposed change first shows the old rule and the new one side by side. The principle: any gap with a real deployment that helps one side is cheating. The aim is an accurate test, not a winner.

The rules are of three kinds: what the code holds in every run, the defaults of a formal run (a run may change them, and its report then says at the top that it is not a formal run and how it differs), and what the operator does, which no code checks.

Held in every run:

- R1. One site, one scenario: the shop, shoppers and staff on the same server at once. Throughput is the page views of the whole site, a full load and a click each one page view.
- R2. A shopper visit is 4 page views on average, one full load and three clicks, exactly in every block, so the full loads are a quarter of the page views. The lengths are geometric, from 1 to 12. Sources: about 4.3 page views a session over 6,000 sites (Contentsquare 2025, https://contentsquare.com/press/2025-digital-experience-benchmarks/), and a click of a single-page app counted as a page view as Chrome measures it (https://web.dev/blog/crux-experimental-soft-navs). 6.6% of shopper visits add to the cart and 1.3% check out (Littledata 2026). On 15% of the shopper landings the URL carries a click id that is different for every click (gclid, fbclid or msclkid, by 60 : 30 : 10) and on 5% a parameter that is different for every recipient of an email (_kx or mc_eid, half each), never both: the 15% is a judgment below the published upper bounds (50.6% of the visits of retail sites come from paid sources, Contentsquare 2025, and 22% from paid search, gripsintelligence) and the 5% the lower end of the 7.3% to 7.6% of the visits that come from email (gripsintelligence). With no data, an assumption, listed as one: returning visitors 20%, landing on home, list, product 30/25/45, Zipf exponent 1.0, staff 2% of visits (4 page views on average, 20% of them edit a product, 30% ship an order).
- R3. Every framework plays the same visits: the same seed, visits, writes and setup data. The browser behaviour of each comes from a real browser recorded against it.
- R4. Private data is drawn per visit from (seed, visit): the cart of a returning visitor, the name, email and address of a checkout. A new visitor sees the demo cart, the same for everyone, as the empty cart of a real shop is.
- R5. Before the warm-up every server has the same data, and at the clock it has taken the same writes of the warm-up, in an order that concurrency may change. All frameworks are sized first, and every closed round is prepared for twice the largest size and the warm-up after it (an open round for the visits it plays and its warm-up): restock, the orders the ships take, the returning carts. No setup request renders a page.
- R6. What a run writes does not depend on how fast a server answers: a ship takes its pre-made order, an edit sends a value from the plan and reads nothing first. A 409 or 422 in a round makes it invalid.
- R7. Data lives in process memory in all four, with the same algorithms. Order times come from the server clock.
- R8. Each framework runs as shipped: one process, no proxy, its default settings. Differences are measured and stated, not fixed. TanStack Start sends its answers uncompressed, and above the throughput and latency tables the report says so in bold, with the body it sent a page view against the others, from the rounds. React Router flushes a compressed block per chunk.
- R9. No Node app sends anything a cache could keep (no `ETag`, `Last-Modified`, positive `max-age`, `x-nextjs-cache`), on the documents and the navigation data it replays, checked before the first round of a run, which stops when one does.
- R11. Every server gets the same warm-up before the clock of each measured round (the read-only control too, with no writes): the visits after the prepared ones, as many as the longest closed round any server of the scenario was sized to (an open round: as many as it plays), with the mix and the writes of the round, played as the round plays (its sessions, or its rate). It counts in no result. Tifa's memo must be empty before the warm-up (read from its metrics route), and what it holds after the warm-up is reported. No server gets another warm-up.
- R14. A round counts only when it passes its checks: the mix it played, no refused setup or write (the warm-up's included), the load generator kept up, the memo was empty before the warm-up. The warm-up is judged as the round: a failed visit, request or write in it fails the round, and a warm-up cut off fails an open round and makes a closed one not valid.
- R15. Tifa's answers are reported per page kind: from the memo, shared with a render in progress, and rendered in a VM, which add up to the answers. The renders are split into the first request of a URL and a URL answered before (in the warm-up too), as the client tells by URL, and private pages with and without a cart cookie, and the report states the limits of a split made on the client (requests at the same time share a render, answers are counted in the order they completed, a canceled request is not counted).
- R16. Body: the throughput table, the latency table and the assumptions. Every diagnostic goes to an appendix. It says where differences come from, not who wins.

Defaults of a formal run (`FormalBrowse`, the defaults of `compare browse` and of `browse.sh`, with the server and the load pinned, run by `browse.sh`, every server):

- R10. Tifa runs with its render memo on. A row of Tifa with the memo off is shown as a reference, not compared.
- R12. Throughput: closed loop, 8 sessions without think time, more only while the server's core is not used up. Server on one core, load on other physical cores. 3 rounds a cell.
- R13. Latency: open model at a fixed rate, half the rate Next.js sustains, rounds of at least 240 s. The Next.js rate is kept in `test/compare/rates.json` and reused only while what it depends on is the same (the method files, the Next.js server, app and version, the plans and the Next.js traces, the pass rule, the machine). It is searched again when one of those changed, when the file has no rate, or with `PROBE=1`.

#### How it runs

- **One site.** The shop is played as one site: shoppers on the storefront (`/store` and `/zh-CN/store`) and staff in the back office (the workbench pages under `/projects`), at once on the same server. Throughput is the page views of the whole site. There is one set of plans (`plans.json`), one trace file for each framework (`<framework>.jsonl`) and one stamp (`STAMP`).
- **Pages.** The staff visit all 58 workbench pages of the shop: the two lists, the two stats pages and the 54 order pages (`AllPages`). The shoppers visit the storefront pages (`StoreVisitPages`). `TestPagesShowTheSameText`, `TestDomainMatchesGo` and `TestEveryRequestComputesAndRenders` cover all of them in all four apps, and `TestFanOutWriteChangesListsStatsAndOtherOrders` checks that a customer-name write changes the list, the stats and the page of another order of the customer in all four.
- **The mix** (`mix.go`). Every number of the mix is a constant there that names its source next to it, or says that it is an assumption, and the plans are made from those constants. The report lists each with its value and its source (`MixFacts`), and `TestTheReportListsEveryNumberOfTheMix` reads `mix.go` and fails when a constant of it is missing from that list. A shopper visit has 4 page views on average, exactly in every block, one full load and three clicks, so the full loads are a quarter of the page views: a rule of the comparison, from about 4.3 page views a session over 6,000 sites (Contentsquare 2025, https://contentsquare.com/press/2025-digital-experience-benchmarks/), with a click counted as a page view as Chrome measures the client navigations of a single-page app (https://web.dev/blog/crux-experimental-soft-navs). The lengths are geometric, from 1 to 12. 6.6% of shopper visits add to the cart and 1.3% check out (the medians of 438 Shopify stores, Littledata, https://www.littledata.io/benchmarks). 20% of shopper visits are by a returning visitor (an assumption within the published 17% to 53%). A shopper lands on the home 30%, a product list 25% and a product 45% of the time, and half of the shoppers use English and half Chinese (assumptions). Of the landings 15% carry a click id and 5% an email parameter (`ClickIDShare`, `EmailParamShare`, with the names and the lengths of their values, in the mix table of the report): the names are shared 60 : 30 : 10 and half and half, and the shape of a value is an assumption. Products are seen by a Zipf law with exponent 1.0 over the order of the catalogue (an inference: sales follow a power law, and no data on product views was found). Staff visits are 2% of the visits, with 4 page views on average and at most 8, and of the staff visits 20% edit a product and 30% ship an order (assumptions).
- **Plans** (`compare plans`, `mix.go`, `plan.go`, `store_plan.go`). Plans are made in blocks from a seed and are the same for all four frameworks. A block holds 1000 shopper plans with the mix exactly, by quota: 4000 page views (1000 full loads and 3000 clicks, so the full loads are exactly a quarter of the page views of the shopper plans of a block), 66 visits that add to the cart of which 13 check out, 200 returning visitors, the landing pages and the two languages (the larger half of a language goes to each in turn from block to block). It also holds 50 staff plans with 200 page views. The landings with a parameter are by quota too: 150 with a click id (90 gclid, 45 fbclid, 15 msclkid) and 50 with an email parameter (25 `_kx`, 25 `mc_eid`), on the home, a list and a product alike (`putLandingParams` in `landing.go`, drawn apart from the pages so that the pages do not depend on them). The plan holds a placeholder of the length of the real value, and a click on a link of the page follows the links of the page without the parameter. The lengths of the visits are a geometric first draw, then corrected for the block: moved one view at a time until they add up, so they are not exactly geometric. A run takes 20 staff visits a cycle from the staff plans in turn, so they are not exactly 4 page views each, and a visit that fails or is cut off ends early: the quarter holds for the shopper plans of a block, not for all the traffic a run does. There are no reloads, so the full loads are the first pages of the visits, and every other page view is a click on a link of the page on screen, picked at random by weights. The product a visit lands on is picked by the Zipf law, and so is a product among the product links of a page. A visit that only adds to the cart adds after its first product page view, and one that checks out adds after its last product page view before the checkout page and checks out after the checkout page. Staff visits land on a list or a stats page half of the time and on an order the other half. A list links to its newest 25 orders, its stats and the other shop, an order to its list, its stats and the other shop, stats to their list and the other shop. Links that depend on the data are left out, so that writes never change what can be clicked. On the storefront a click goes to a link the page has, and `store_links.json` holds those: for every page a visit can be on (the home, the list with ten of its filters, the 150 products, the cart, the checkout, the journal, the 3 posts, in both languages) the links that lead to another of these pages, as a browser reads them. It is made by `compare links` (a crawl in Chromium against Tifa: run it again after the pages of the storefront change). Which kind of link a click picks is `StoreClicks` (and `StaffClicks` in the back office): relative weights by the kind of page and of link, such as product 30 : cart 25 : list 25 : checkout 10 : home 10 : journal 10 from a product. A page makes them shares among the kinds of link it has, so a kind it has no link to is left out, and a product among the product links is picked by the Zipf law. The report writes them as such weights, not as percents. The click weights are assumptions too.
- **Writes.** A shopper write follows the cart of the visit, so the shop takes it. An add buys the product of the page it follows (the plans put adds after product pages), in a colour and size it has, 1 to 3 pieces, and a checkout places the order of the cart (a body that `storeOrder` builds, in the language of the visit) for a visitor of its own: the name, email and address are drawn from the seed and the visit number (`storeShopper`), so no two checkouts of a round place the order of the same person. The colour, size and pieces of an add are drawn from the seed, the visit number in the global sequence and the page view, not from the plan, so a plan played again sends other writes: otherwise the cart page would see the same few carts and a render memo would answer it every time, which no real stream of visitors with their own carts does. `StoreVariants` gives the products with the stock, colours and sizes the adds pick from, read with their order (`StoreProducts`) from the catalogue file of the shop, and `TestStoreVariantsAreTheShops` checks them against the pages of the shop. The shop answers 200 to an add and 303 to the page of the order to a checkout, and the replay requires exactly that status of every framework and does not follow the 303. A write goes to the path each app takes it on (`Spec.StoreWrite`: Tifa and Start the path of the shop, Next.js `/store/compare-write/<lang>/...`, React Router `/store/<lang>/_write/...`), with the cookie jar of the visit. Of the staff visits of each block of a cycle, the share of the scenario edit a product and another share ship an order (by quota), each after a page view drawn from the seed and the visit number. Each ship of the plan ships an order of its own, placed for it before the clock (see Returning visitors and the orders of the ships below, `writepool.go`): the i-th ship of a round ships the i-th order placed, on every framework, whatever the servers answered first. No ship finds its order missing (that is an error of the run, not a write of another kind), and the orders that checkouts place and the orders of the data that wait stay out of the ships. An edit is what staff do on the edit page of a product: one PATCH through `Spec.EditProduct` that sets one field and reads nothing first (`productChange`, drawn from the seed, the visit and the page view, so every server gets the same edit). Half of the edits set a price in whole yuan from ¥19 to ¥999 (`EditPriceShare`, `EditPriceFen`), and the others set the stock to what the restock gave the product plus a delivery of 5 to 50 pieces (`EditDelivery`). The stock an edit sets is never below what the restock gave, so no checkout or order after it is refused for lack of stock. An edit is one write of one request, and the storefront shows the product as edited. Every round records the writes sent by kind, their latencies by kind and the orders each project holds at the end. The pages are bounded as the orders grow: the order list holds the newest 25 rows and the other orders of a customer the newest 10, with the counts over all (`TestPagesStayTheSizeOfAPageAsOrdersGrow`). The reads these pages make are kept with indexes and running totals, so they cost about the same at 50 and at 5000 orders (a few µs each). A filtered or searched list, or one sorted by amount, still goes through every order of the project. The traffic of a page view does not depend on the writes, so the traces are recorded without them and the writes are put in at the replay. A write is never cancelled, so it does not meet the cancels of the traces. `TestPlannedStoreWritesAreTakenByEveryApp` sends the shopper writes of a block, with the carts of its returning visitors, to Tifa and the three apps and requires the status of the plan from each.
- **Restock** (`restock.go`). Every order takes its pieces from the stock of its shop (a checkout from the studio shop, an order staff place from its own), so the orders of a long run would sell products out and the shop would refuse them. Every run with writes (a measured round, closed or open, and a sizing run) first restocks its server, before it places the orders of its ships and makes the carts of its returning visitors, and before its clock starts. `Restock` asks, for each shop the run orders from, for its product list in the back office (`Spec.Products`: for Tifa the navigation data of `/projects/<project>/products`, for the Node apps `/compare-write/<project>/products`) and then edits every product through the same PATCH staff use (`Spec.EditProduct`), with the fields it had and a new stock. The stock is `StockFor`: twice the pieces of the product that the orders of the prepared visits can take at most (see below: for a closed round, the same visits for every server of the scenario). For a checkout it follows the cart of the visit as the shop keeps it (the demonstration cart, the adds of the setup for a returning visit, then the adds of the visit, at most 10 of a line, a checkout empties the cart), and a line still in a cart at the end counts too, since the shop refuses an add of a product with no stock and holds a line to the stock. A ship counts with the items of the order placed for it before the clock (the items `AdminBody` gives a place-an-order write). A product keeps its stock when that is more. A sizing run plays for a time, not a number of visits, so it gives every product of the storefront and every product its plans can buy the most the shop takes (99,999), and the shop refusing one of its requests with 409 or 422 is an error of the run. All four servers get the same requests. None of them is timed, no redirect is followed, and none of them may render: every answer, the list as well as each edit, must be a 200 with no `X-Tifa-Render` or `none`, and a round whose restock fails is not valid. The restock edits change the stock shown on the product pages, alike for all four.
- **Returning visitors and the orders of the ships** (`setup.go`). After the server of a round starts and its restock, and before the clock, the runner makes the data the round needs, as a benchmark fills the rows of a database first, the same on every framework. The data is made for the prepared visits and the visits of the warm-up after them (see The warm-up below), not for the visits of the round alone, so that every server of a scenario starts its rounds with the same data and is sent the same writes (an edit of the stock is worked out from what the restock gave): for a closed round, every server of the scenario is sized at the base sessions first, and the prepared visits are twice the visits of the longest round any of them was sized to (`prepareHeadroom`, kept in the JSON as `prepared`). A closed round never plays more visits than that: a server sized to as many or more (one that stepped up far, or was resized) plays the prepared visits, the round is marked `capped` in the JSON, and when that ends it before the length window it is kept as it is, not resized, since it cannot be made longer. The report marks a cell of the body whose rounds include a capped one with ¹ and a note under the table, and the appendix lists every capped try of the scenario (at any number of sessions, valid or not) with its visits, how long it took and whether that was in the window of the target. An open round plays the same visits on every server, and is prepared for them. First it places one order for each ship of the prepared visits, in the order of the plan, with the place-an-order write of the staff (`AdminBody`), and keeps it for that ship. Then it makes one cart for each returning visit of the prepared visits through the shop's cart API (three adds on top of the demonstration cart, drawn from the seed and the visit number), and the visit then plays with the cookies of its cart: a returning visitor comes back to a cart of their own, and a new one starts with no cart and sees the demonstration cart of four lines. Making them must put nothing into a render memo: no redirect is followed, and every answer of the setup must have the status planned and no `X-Tifa-Render` or `X-Tifa-Render: none`, or the round is not valid and is not played. Last, for Tifa, it reads the render memo from the metrics route of the shop (`Spec.Metrics`, `/metrics`, open to the run with `SHOP_OPEN=1`, which renders nothing): the memo must hold no page, or the round is not valid. It reads the route again after the warm-up and after the round (the pages it holds and their bytes, its hits, misses, shared renders and the pages it dropped to make room), and the report gives what the memo held after the warm-up and at the end, the pages it dropped in the round and the hits the server counted from the clock on, for every try with the try and whether it was valid. A read that was not made or did not answer (a round its warm-up stopped before the clock, or one whose metrics route failed at its end) shows as not read, with no number worked out from it. The setup is not part of the round (its requests are `setupRequests` in the JSON). A sizing run makes the orders and carts of the visits it can play too (`sizingVisits`: 1000 visits for each second of its length). The warm-up plays visits of its own, after the prepared ones, so its ships take orders of their own and its returning visitors carts of their own: the i-th ship of the round still ships the i-th order placed.
- **The cart cap.** The shop keeps up to 100,000 carts and drops the one used longest ago beyond that, like a database that holds a bounded table. A round that can make more carts (one for each returning visit of its prepared visits, one for each other visit that writes to its cart, and the one of the check after it) fails when it is planned, before its server starts (`cartsFit`), so no round counts on a cart the shop dropped.
- **The servers.** The site runs on four servers: Tifa as it ships (its pages use the render memo alone), Next.js, TanStack Start and React Router. A fifth row, `tifa-nocache` (Tifa started with `--ssr-memo-size 0`, which turns off keeping finished renders: it may still answer navigation data with no render, share a render in progress between requests of a page at the same time, and answer 304), is in the throughput table and the latency table as a reference, labelled "Tifa, memo off (reference)" and listed after the four, with a line under each table saying so and that it is not one of the frameworks compared. It is in `SERVERS` by default and gets everything the others get: the same prepared data, the check of its metrics before the clock (its memo holds no page, as it always does) and after the round, and the check of the writes. Being slower than Tifa as it ships, it does not raise the prepared visits, which are twice the largest number any server of the run was sized to. It replays the trace recorded against `tifa` (whatever the cache, the browser sends the same requests): recording records each trace once, from the spec of its framework, and `browse.sh` names the trace of a spec by its id before the first dash. `TestTifaWithItsCachesOffNeverAnswersAStorefrontPageFromOne` checks that `tifa` answers a second request for a storefront page from the render memo (`X-Tifa-Render: memo`) and `tifa-nocache` never does (`X-Tifa-Render: vm`), and that neither sends a `Cache-Status`, since no storefront page has `Cache`. The ports render every request, which `TestEveryRequestComputesAndRenders` counts for the storefront pages too. `TestTheNodeAppsCacheNothing` (with `TIFA_COMPARE=1`) asks each Node app twice for every workbench and storefront page and checks that no answer carries an `ETag`, a `Last-Modified`, a positive `max-age` or `s-maxage`, or an `x-nextjs-cache` or `x-nextjs-prerender` header, so that nothing between them and the load could keep an answer. A run checks the same before its first round, on a fresh server of each Node app that it throws away: it asks twice for the documents and the navigation data the traces of that app replay (one of each path, with the headers the browser sent, not following redirects), and stops when an answer has one of those signs (`CheckNoCache`). The route manifest of React Router (`/__manifest`) is not asked: it holds the routes of the build and no data of a page, and React Router sends it with `max-age` of a year, as it does its assets.
- **Traces** (`compare record`, `test/compare/recorder`). A small Node tool with Playwright (`pnpm install` in that folder) plays every plan in Chromium (a fresh context for each visit, 1280x800, no hover, real clicks on the links) against each framework and keeps every request the browser sent: method, URL, the headers that matter (`rsc`, `next-router-*`, `x-tsr-serverfn`), whether it sent `If-None-Match`, a request body if it had one (the storefront remembers the product a visitor looked at with a `POST /store/mine`), and when it started and ended, in milliseconds from the start of its page view. A request the browser did not let finish keeps when and why (`cancel`: the network error Chromium reported, such as `net::ERR_ABORTED`, or `open-at-end` for one still open when the page view was over), whether a navigation was committed just before (`afterNav`) and when its headers arrived. Next.js cancels about 20 prefetches in every visit, almost all within milliseconds of their first answer. Only dynamic traffic is kept (documents and data requests: no scripts, styles, images or fonts), alike for all four. Reads that a browser makes after a write (the cart count, a refresh of the router) are not in the traces, as the traces have no writes, so they are not replayed. Back and forward are not in the plans, since the browser's back/forward cache cannot be measured here. Anything that goes wrong while recording a visit invalidates that visit's trace, and the replay refuses a set of traces that lacks a plan for any framework. Loading the traces also fails when a request that a router made with its own header lost it (a `_rsc=` URL without `rsc`, a server function call without `x-tsr-serverfn`), because the server would answer with a whole page. When a server stops during a recording, the error carries its output. Traces belong to the sources they were recorded against (Start's function ids, React Router's manifest version), so `browse.sh` records them again when the sources or the recorder change. Raw traces stay out of the repository.
- **Replay** (`replay.go`). Visits are played in the order of one global sequence, cycle after cycle. A cycle holds, for each block of plans, its 1000 shopper plans once with the staff visits of the scenario placed among them by a seeded shuffle, and the staff visits go through the staff plans in turn from cycle to cycle. A request starts when every request that had ended or been cancelled before it started in the browser is done, and no visit has more than 6 connections, as in a browser. A request the browser cancelled after the headers of its answer had arrived (Next.js does it to its prefetches and to about 4% of its clicks once its router has what it needs) is cancelled the same time after the headers arrive. One it cancelled before any answer is cancelled at the recorded offset from the start of its page view, but never sooner than it lived in the browser after it was sent, so a replay that is late (a slow server) still sends what the browser sent and the server does that work. The connection is released and the rest of the answer is not read. The status of an answer is checked as soon as its headers arrive, so a 500 whose body a cancel cuts off is a failure. Documents and navigation requests are foreground: a page view is successful when none failed and at least one finished or was cancelled after its answer arrived (a foreground request cancelled before any answer is not a page view), and it ends with the last of them. Prefetches are background: a failed one fails the visit, and the visit ends when the browser would have had them done or cancelled. A write is sent after its page view and is timed on its own. Cookies are kept within a visit and not across visits (a returning visit starts with the cookies of its cart), and `If-None-Match` carries only the ETag the visit got for that URL. Tifa's build id in its navigation requests is replaced by that of the server. A visit that lands with a click id or an email parameter sends a value of its own: the plan holds a placeholder of the length of a real value (`gclid` 95 characters, `fbclid` 61, `msclkid` 32 hexadecimal, `_kx` 40, `mc_eid` 10 hexadecimal), the recorder opens the landing page with it, and the replay puts a value drawn from (seed, visit number) in place of the placeholder in the URL, the body and the headers of every request of the visit (a router carries the URL of the page in a header too). The value is the same for every server, differs between visits, between cycles and between the warm-up and the round (`landingFor`, `landing.go`), and is one-to-one with the visit number for `mc_eid`, which is short enough to repeat by chance. Loading the traces fails for a plan that lands with a parameter when its document request lacks the placeholder.
- **The warm-up.** Before the clock of each measured round, closed or open (each trial and each confirmation round of a search too, and the read-only control), every server gets the same warm-up, Tifa and `tifa-nocache` as the Node servers, counted nowhere. It plays the visits after the prepared ones (the visits from `prepared` on in the global sequence, so whole cycles with the mix exactly), with their writes: adds, checkouts, edits of products and ships. A closed round warms up with as many visits as the longest round any server of the scenario was sized to at the base sessions (`prepared` divided by `prepareHeadroom`, kept in the JSON as `warmVisits`, the same for every server and at every number of sessions), at the sessions of the round. An open round, a trial or a confirmation warms up with as many visits as it plays, at its rate. The control plays the same warm-up as the closed rounds, with no writes, so it differs from them in the writes alone. The warm-up runs the code paths of the round, longer than the round of the fastest server, so the JIT of Node is warm at the clock, and the render memo of Tifa holds what the same traffic leaves in it. Its data is made with the data of the round: the restock covers what its orders can take, its ships have orders of their own and its returning visitors carts of their own. Before its traffic every server gets the restock, then the orders of the ships, then the adds that make the carts of the returning visitors, then for Tifa a read of its metrics route (its memo must hold no page), then the warm-up, then, once no request of it is in flight, a pause of 2 seconds (`settlePause`), then a second read of the metrics route (what the memo holds, `memo.warm` in the JSON), then the round, and nothing else. The pause is there because the client is done with a request the trace cancelled when it cancels it, while the server may still be at work on it: a render of Tifa goes on in its VM and lands in the memo, and a Node server may finish its handler. It is the same for every server and keeps that work out of the round. Where the cpu of the server is read, the warm-up keeps the cores the server used in the last second of the pause (`idleCores` in the JSON), and the appendix lists them with what each warm-up did. They are recorded and shown, not checked against a limit. `TestTheServerFinishesTheWarmUpBeforeTheClock` checks, with a server that goes on with a request after the client cancelled it, that the work ends before the memo is read and before the first request of the round. None of what comes before the warm-up renders. `TestNothingThatRendersPrecedesTheWarmUpOfTifa` checks that order and that the server got no other request, `TestEveryServerGetsTheSameWarmUp` that every server gets the same requests and writes in its warm-up, `TestARoundOfTifaReadsItsMemoBeforeAndAfterTheWarmUp` the reads of the metrics, and `TestTheWriteCheckNeverPrecedesTheTrafficOfTifa` that the check of the writes runs on a server of its own. What the warm-up did is kept in the round (`warmUp` in the JSON). The shop refusing a request of it with 409 or 422 makes the round invalid, as in the round. Otherwise the round is played whatever the warm-up did, and the warm-up is judged as the round is, since it is the same traffic: a failed visit or request in it, or fewer writes done than it planned, fails the round, which stays valid (the reason starts with `the warm-up: `). A warm-up cut off by its time (the round's timeout for each of its visits in a closed round, its schedule and 20 seconds in an open one) fails an open round, as it left a backlog, and makes a closed round not valid, as a closed round cut off is a matter of sizing. `TestAWarmUpThatDidNotEndAsPlannedDecidesTheRound` checks a 500, a write whose connection broke and a cut-off in both models, and `TestAWarmUpShortOfItsWritesFailsTheRound` the writes. Writes of the warm-up that run at once can land in another order on each server, so at the clock the servers have taken the same writes, not always in the same order.
- **The time series.** Every round records, in 10 second steps from the start of the round, the page views that completed, their rate and the P99 of their latency (`series` in the JSON of the round, the last step as long as the round has left). The report shows the first valid round of each server per scenario, closed (at the sessions of its result) and open, as two lines of numbers. It shows how throughput and latency change over the round, nothing more. An open round includes the ramp at the start (visits are offered from zero, and the actions of a visit are a second apart) and the drain at the end (no new visits, the last ones finishing), so its first and last steps differ from the middle even for a server whose cost per request never changes. A change over the round may come from the render memo filling up or from a JIT warming, but the steps alone do not show that, and it takes another measurement to tell. The median of a cell still counts the whole round.
- **Fresh data in every round.** Every round, closed or open (each trial and each confirmation round of a search too), starts a fresh server, so orders placed in one round never make the pages of the next heavier and every round starts with the same data. Once for each scenario and server, `verifyWrites` checks the writes of the scenario on a fresh server of its own that is thrown away, so that the server of a round and the one of a sizing run get no request before their timed traffic (a check there would put pages into the render memo of Tifa). After a round that passed it checks them again on the server of the round, once the timing has ended. For the shoppers (`verifyStore`) it is one visitor with the cookies a browser keeps: it adds a product to the cart, puts a coupon on it, changes the quantity of the line and checks out, requires the status of each, requires that the cart page (its document and the navigation data of a click to it, as a trace recorded it) is not what it was after each write and shows the coupon code, and that the 303 of the checkout leads to a page that shows the order number, and that the back office shows that order, on its page and in the order list of the studio shop. It then edits a product as staff do (`verifyProduct`): it gives the first product of the studio list a title of its own and a price one yuan higher, and checks that its storefront page and the product list of the back office show the title. `TestTheWritesShowOnEveryServer` (with `TIFA_COMPARE=1`) runs the whole check once against Tifa and the three apps. For the staff (`verifyAdmin`) it places an order with a note of its own and checks that its page and the list (the document and the navigation data of the list) show it, adds a note to a shipped order, changes the recipient of SH-1041, an order of the data that waits and that no ship of a round takes, and ships the order it placed with ZTO, checking that its page and the list show the tracking number, that the carrier table of the stats page counts one more ZTO parcel, and that the navigation data of the stats page changed.
- **One interval.** A round starts at the first scheduled action and ends when its last request has finished (or when it is cut off at its timeout). An action still in flight at the cut-off is counted with how long it had been in flight: one in flight for over 1 second fails the round, as the server did not answer it in time, and one cut off sooner is a matter of sizing. Page views are counted when each completes, requests when each completes, and server CPU (the whole process tree from `/proc`, user and system, with writes and prefetches), the load generator's CPU and the latencies are over that same interval, so the drain at the end is in every denominator and is published. The warm-up is apart from it. A closed workload is a finite number of whole blocks, sized so that a round takes 0.8 to 1.6 times `-target` (60 to 120 seconds by default). The first round of a cell is sized from a sizing run of its own, a fresh server that plays the mix with its writes for the length of `-sizing` (15 seconds) and is then thrown away (it counts the failed visits too). It never shares a server with a measured round, it has no warm-up, and it is not one: nothing it did is kept. A measured round starts after its warm-up, so a server that is faster warm than cold (the render memo of Tifa, the JIT of Node) can be sized to a round shorter than the target. Such a round is run again, resized from what it did. A closed round that still runs too long is stopped at twice the target.
- **Planned against done.** Every round records its visits planned, started, succeeded, failed and unfinished (cut off by the end of the round, the ones never started too), and the page views, clicks and writes planned against those done. A visit that fails ends there, so a server that fails visits does fewer page views and writes than planned. The mix is therefore checked on the visits as planned: the share of staff visits within half a point of the scenario, 4 page views a shopper visit within 1%, the returning visitors within half a point of 20%, the adds and the checkouts within 0.2 points of their shares, and the edits and the ships within 3 points of their shares of the staff visits. A round of whole blocks has them exactly. The shares done are kept as a diagnostic.
- **Valid and passing.** A round is valid when its plan has the mix, its restock, the orders of its ships and the carts of its returning visitors were made with the status planned and no answer that rendered a page, for Tifa its render memo held no page right before the warm-up and its metrics route answered after the warm-up and after the round, the shop refused no request of the warm-up or the round with 409 or 422 (a write or a page, `Round.Refused`, counted as soon as the status arrives, because after the restock the plan makes every write one the shop takes), and the load generator did its work: it started every visit it planned (unless the round was cut off), no visit of an open round started more than 250 ms late, and in every round, closed or open, the generator used under 0.8 of its cpus (checked only when `-load-cpus` gives it cpus of its own, and the report says when it was not). A round that is not valid is played again at the same sessions or rate (up to three tries) and stays in the JSON: it never moves the search of a rate, steps a rate down or decides a step of the throughput. Failures of the server (errors, a timeout, a backlog, a P99 over the limit), in the round or in its warm-up, never make a round invalid: such a round is valid and fails the rule, and it is kept. The one exception is a closed warm-up cut off by its timeout, which is a matter of sizing. A run that is stopped by hand keeps no round of what it was doing. The length window is calibration only: a closed round outside 0.8 to 1.6 times the target resizes its cell from the visits that ended in it (the failed ones too, as a visit that ends in a 503 is fast), and it is run again only if it passed the rule. A closed round outside the window that failed the rule stays a valid failed round, so the resize never discards a failure the server showed. A cell with no valid round says in the table how many it played and why the last one failed.
- **The rule.** A round passes when the P99 of full loads, of clicks (all the foreground requests of one click, counted from the click) and of writes is at most 1 second, nothing failed unexpectedly (an error, a trace request answered other than 200, 204 or 304, a write answered other than its planned status, a foreground request that did not finish) and, in the open model, no backlog was left. This is a benchmark threshold, not an industry standard.
- **One scenario.** The comparison has one scenario, `shop`: shoppers and staff in one mix (`mix.go`) on the same server, with a throughput table and a latency table. The share of staff visits and of their edits and ships are rows of the mix table of the report, with the other assumptions. `SCENARIOS` is refused.
- **Throughput** (closed loop: N concurrent sessions, no think time, each playing the next visit as soon as it ends one). Every server of a scenario with throughput starts at 8 sessions (`-sessions`, `SESSIONS`), three rounds in a rotating order, each on a fresh server. Then each server is stepped on its own, three rounds a step: up about 25% a step (10, 13, 16, 20 and so on, up to 640) while every round passes and the median of its server cores (server CPU seconds over the window, from `/proc`, with `-server-cpus` given) stays under 0.95 of its cpus, or down to 6 and then 4 sessions when it fails at 8. A cell stops at its first failed round, which decides it. A step passes (every round valid and passing), fails (a valid round failed the rule) or is not decided (too few valid rounds, as when the load generator ran out of cpus, and none failed): only a failure steps down. After a step that passed its cores are decided first, then its gain. The result of each server is typed: `core used` (every round passed and the median server cores reached 0.95, even when the gain over the step below is within the spread of the rounds), `plateau, core not full` (no reliable gain was measured: the slowest round of the step up was not faster than the fastest of the step below, which is reported), `highest passing step` (the next step failed the rule, so the step below it is reported: the next one up, or 8 when it stepped down to 6 or 4), `next step not decided` (the next step up was not decided, so the step below it is reported), `highest step tried` (still gaining at 640), `no passing step` (it failed at 8, 6 and 4), `not decided` (a step was not decided and no step below it passed) and `cores not known` (no pinning or no `/proc`, as on a Mac: the steps stop at the first step that passed with its cores not known). Every row says the sessions it was measured at, so servers are compared at their own working points, not at the same concurrency, and a failed round is never used as a capacity. The unit is successful page views a second (writes and prefetches are not page views). The table also reads page views a second as active people at one page per 5 to 10 seconds (page views a second times 5 to 10): a reading aid, not something the run measured, since a replayed session is not a person who stays signed in, and no long sessions or their memory are held. The throughput table of the body gives, for each server, its result, its sessions, its page views a second with that reading, and the P50 and P99 of full loads, clicks and writes with their samples. How the steps ran is in the appendix: the median server cores, why the steps stopped and the page views a second at each number of sessions played. The detail tables (for the base step and the step of each result) give CPU ms per page view, peak RSS, requests and bytes per page view, the P50 and P99 by class with their samples, what the server did a second and per visit, the writes by kind, and the visits, page views and writes planned against done. The steps are measured in every run: nothing about them is kept in a file.
- **Latency at the same arrival rate** (open model, in the scenarios with latency). Every server of the scenario runs at one arrival rate, half of the rate Next.js was confirmed to sustain on that scenario: the same rate for all, not half of each server's own capacity. The tool finds that rate for Next.js only, in visits a second (visits start on schedule whether or not earlier ones are done, the actions of a visit are planned one second apart, and within a visit an action waits for the one before it): it doubles the rate from 4 (or from `-max-rate` when that is lower, and the cap must be at least half a visit a second) while the rule holds, or halves it while the first rate fails, narrows it to within 10%, then requires the rule over three valid rounds and steps down 10% until it holds. Sustained here means the rule held over finite windows, not a physical limit. A server that cannot hold the rate fails at it: that is its result, and the rate is not lowered for it. The latency table of the body gives, for each server, the P50 and P99 of full loads, clicks and writes with their samples over every valid round it played at the rate, the failed ones too, and how many rounds passed, with why the others failed: a server with a failed round failed the rule. The appendix gives, for each server, its failures, its failed and unfinished visits against the planned ones, its server CPU per page view, and the rounds in which the load generator fell behind, which are invalid and run again. A trial or a confirmation round of the search that is not valid is played again at its rate, up to three tries. When the tries run out the search stops there and is marked as limited by the load generator: every round stays in the JSON and nothing is written into `test/compare/rates.json`. What is left depends on where it stopped. When a rate was confirmed below that point (the tries ran out while searching higher, or on the step 10% above the confirmed rate), that rate is a lower bound of what Next.js sustains, and every server runs at half of it. When no rate was confirmed (the tries ran out before any trial passed, or on the first rate the confirmation tried), there is no usable rate: the scenario has no open run, and the report says why. Every server of the scenario then runs at that rate, three rounds in a rotating order on fresh servers, long enough for at least 1,100 full loads and clicks. Latency is counted from the scheduled time of an action to the end of its foreground requests (of a write, to its answer), so waiting behind earlier requests is in it. A round also fails when the number of visits or of requests in flight keeps growing while visits are offered (a backlog that only drains after the offering stops would otherwise pass: a line fitted to the numbers in flight, leaving out the first samples while the visits in flight level off (as long as the longest visit), must not rise by more than a fifth of their mean plus a floor; the trial window is 45 seconds so that there is something to fit). Trials and rounds all play whole cycles of the plans of the site, since a part of a cycle has another number of page views a visit and another share of writes (a trial at a low rate therefore lasts longer than its window). The search tries the rate it found and then up to three rates 10% lower each (and, if the rate it found passes, one rate 10% above it too, unless that is above `-max-rate`), keeps every round in the JSON, and has no rate in range, and the scenario no open run, if none of them passes.
- **The rates of Next.js** (`test/compare/rates.json`, checked in after a run that searched them). A confirmed rate is written into the file, per scenario, with its unit (visits a second), every condition it was measured under and the run it came from (date, commit of Tifa, result file, and every confirmation round with its P99s). The conditions are what the rate of Next.js depends on and nothing else. The method is a hash of the method files, whole (`methodFiles`), from `test/compare`, its command `test/compare/cmd/compare` and `internal/testproc`, which starts the servers (`methodDirs`): what builds and prepares the apps and the data, the plans and the traces, the replay and its writes, the start, pinning and control of the servers (the server of Next.js is in `spec.go`), the command that sets a run up and counts its cpus, the rule, the search and the confirmation, and every file they call into. The report, the table of the servers of every framework (`specs.go`, with the list of servers), the sources of the other apps, the closed-loop steps of the throughput and what only the other comparisons use are left out (`rateExcluded`). Every source file of those folders is in one of the two lists, or `TestEverySourceOfCompareIsInOrOutOfTheMethod` fails, so a new file has to be put in one. A change to a method file is another method even when the search runs the same code: the hash can take in more than runs, never less. Then a hash of the program and arguments of the Next.js server and of every variable Node reads in the environment it starts with (`nextjsServer`: the names that start with `NODE_`, `UV_`, `V8_`, `NEXT_`, `__NEXT`, `MALLOC_` or `LC_`, and `GLIBC_TUNABLES`, `LD_PRELOAD`, `TZ` and `LANG`, taken from the environment it inherits with its own on top, built by the same function that starts it), the Go version the load generator is built with and the `GOGC`, `GOMEMLIMIT` and `GODEBUG` it runs with, as written, a hash of the sources of the Next.js app, the domain code it shares and the catalogue file of the shop that the domain code imports (the files git tracks, as they are on disk, and the pages copied from the shop), which the build of the app also writes into `.next/compare-source` (a rate is reused, searched or written only on a build that names the sources of the checkout, so a stale `.next` is refused, and the cache Next.js writes there changes nothing), a hash of the scenario and the seed of its writes, of the plans and of the Next.js traces, and of the lines of the stamp of the traces that the Next.js trace was recorded from (the trees of the shop, the Next.js app, the shared domain code and overlays, the recorder and the plan generators, the versions of Next.js and of the browser, the site and the plans, and not the trees of Tifa, Start or React Router), the cpu model, the server and load cpus with the number of load cpus the run counted (which judges whether the load generator kept up), the Node and Next.js versions, the spacing of actions, the rule, the search and the confirmation. A later run under every one of those conditions reads the rate from the file and searches nothing. A run under any other condition is refused with the conditions that differ, and asked for `-probe` (`PROBE=1` for `browse.sh`), which searches the rate again and rewrites the entry: a rate is never reused silently. A condition the run cannot tell never matches, and such a rate is not written: the sources of the traces are known only from a stamp that names the site and its trees with nothing uncommitted, and only in a run of `browse.sh`, which checks the stamp against the checkout (a run of `compare browse` by hand never reuses a rate), and a Mac has no cpu model. Reading the file refuses an entry in another unit than `visits/s`, with a rate of 0 or less, or without one of the conditions. The file is written whole, through a file that is then renamed, and one run at a time may write it: two runs that search at once would lose the entry of one. A scenario the file has no entry for is searched and written. A rate the load generator limited is not written. After a run that searched, copy the file back from the test machine and commit it.
- **Report.** `compare report browse.json` renders the JSON, which holds every round. A run that is not formal (other settings than `FormalBrowse`, the server or the load not pinned, not run by `browse.sh`, or not every server of `BrowseFrameworks`) says so at the top of the report, with every way it differs (`TestTheReportSaysWhenARunIsNotFormal`). The body holds the results alone: for each scenario its throughput table and its latency table, each with a link to the diagnostics behind it, then the mix with the value and the source of every number. `TestTheReportBodyHoldsTheResultsAndTheAppendixTheDiagnostics` checks the exact columns of both tables of the body, and that the diagnostic columns and the text on method are in the appendix alone. The appendix after it holds how the comparison is made and every diagnostic: for each scenario the page views a second at each number of sessions played, the detail tables (what a round did and cost, what the server did a second and per visit, the writes, what the rounds planned and did), the render memo hits of Tifa by kind of page, what its memo held (from its metrics route: the pages and bytes after the warm-up and at the end, the pages it dropped to make room in the round, and the hits it counted itself from the clock on, the end less the read after the warm-up), the read-only control, the time series, the rate Next.js sustains and the writes and plans of the latency rounds, then whether the traces replay on this machine and the plans. A result of the old format (users and not sessions, or no planned visits) is refused, by the report and by a run that would continue it. Every round also counts the answers by type of request, status and content type, and the report gives them for one round of each server, to show that traces recorded on one machine replay on another. The report says that the writes are requests put into the recorded visits and that what a browser fetches again after a write is not replayed. The render memo hits of Tifa are split by kind of page, from `X-Tifa-Render` on the documents and on the navigation data (a navigation answer can render the page in a VM too, so both count), and the answers of the private pages (the cart and the checkout, which show the visitor's own cart) that came from the render memo are counted apart next to them. A second table splits, for each Tifa server and kind of page, its answers into those from the memo, those that shared a render in progress of the same page and those it rendered in a VM, so that they add up, and the renders in a VM by why, as far as the client can tell from the URL, the cookies it sent and `X-Tifa-Render` (`vmWhy` in the JSON of a round): a private page (the cart and the checkout, the only pages of the shop whose `Load`s read cookies) by whether the visit sent its cart cookie, and any other page by whether it was the first request of its URL that Tifa answered in the round and its warm-up, or a URL it had answered before, in the warm-up too, which the client tells by URL alone. A landing parameter is left out of the URL (`TestALandingParameterIsNoPartOfTheURLTheRendersAreSplitBy`). The split has three limits, which the report states: requests of a page at the same time share a render in progress, the first and the URL answered before go in the order the answers completed, not the order Tifa started them, and a request the client canceled at the end of a round is not counted though Tifa may have rendered it. The client does not see the data of the `Load`s, so a URL answered before holds a page whose data changed since (a write, or data that changes by itself, such as the dates of a day) and one the memo dropped when it was full alike. The answers counted are those received whole with `X-Tifa-Render` saying vm, memo or shared. For Tifa with the memo off nothing comes from the memo, and the same split says how much the workload repeats its URLs. A third table counts the documents of the landings of the storefront by the parameter they carry (a click id, an email parameter or none), with how many of each the memo answered, a render in progress shared or a VM rendered: the parameters are no part of the page, so the three groups go to the same pages and should be answered alike, and the table is the evidence (`Round.Landing`, `TestTheLandingDocumentsAreCountedByTheParameterTheyCarry`). For the first scenario of a run there is one short read-only control: Tifa as it ships, at the base sessions, with the same traces and no writes, a round of about 30 seconds after the warm-up of the closed rounds with no writes, with the same split, against Tifa's rounds with writes (closed, or the latency rounds when the scenario has no throughput). A kind of page the render memo answers under half of the time in the control (with 20 answers or more) is a red flag at the top of the control table, to look into: the table does not tell the cause. Every round counts the answers of its page views by `Content-Encoding` (`encodings` in its JSON), and above the throughput table and the latency table the report names in bold each server that compressed no answer in their rounds, with the body it sent a page view against the range of the frameworks compared that compressed (the reference row is not in the range), all from the rounds. Each server answers as its framework ships. TanStack Start (its Nitro node server) compresses nothing, so it is the one named. React Router (`react-router-serve`) sends its documents and its `.data` navigation answers with gzip through express `compression`, but `@react-router/node` 8.5.1 flushes after every chunk of the stream and each flush ends a gzip block: the storefront home page is 556 KB of HTML, 253 KB as it sends it, and would be 116 KB gzipped in one piece. That is its default, and it is measured as it is. Timings are when the answer reached the client, not when a browser would show the page.

**Rerun it all.** `test/compare/browse.sh` does what the commands below do, from the build to the report (`all`), or one part (`build`, `record`, `run`, `report`). Run `test/compare/browse.sh` without arguments for the list of settings: the cpus of the server and the load (`SERVER_CPUS`, `LOAD_CPUS`, pinned with `taskset` on Linux, and without them nothing is pinned), the locks to hold (`LOCKS`, taken in the order given), the servers, the parts to run (`PHASES`: `throughput`, `control`, `sustain`, `latency`), whether to search the rates of Next.js again (`PROBE=1`), the blocks to record (`BLOCKS`) and the sessions (`SESSIONS`), rounds and windows. `USERS` and `EXTRA_USERS` are refused. The traces are bound to the trees of the shop, the three apps, the recorder and the plan generators (`mix.go` among them), the installed framework versions, the browser, the site and its plans (`STAMP`, shown by `browse.sh stamp`). A result is bound to those plus the contents of the trace files, the replayer and report sources, the toolchain, the executables that run (the shop's binary and the built output of the three Node apps) and the settings: `run` refuses traces that belong to other sources, plans or recorder than this checkout and sets that lack a plan, and refuses to continue a result written under another stamp. The command itself, run by hand too, reads a result back and checks it before any phase runs, whatever `-phases` asks for: it continues it only under the settings it was started with (sessions, rounds, windows, cpus, `-probe`, the seed, the cap of the rate, the cpu model, the trace and plan files, the method) and the same versions, and only when every rate it holds matches the conditions of the run and the Next.js build names the sources of the checkout, so a probe asked for again, other cpus, other traces or another machine never reuse the rounds of another run: give it a new `-out`. A result is written after every round, so a run that stopped continues where it was.

Recording needs a working Chromium (Playwright's, installed by the script) and the load run needs a Linux box, so they can be done on two machines on the same commit:

```
# on the machine with the browser: the 1050 visits of the plans for each framework (Next.js takes most of the time)
BROWSE_OUT=browse-out lockf ~/.cache/mac-locks/heavy.lock nice -n 10 test/compare/browse.sh build     # 1 to 5 minutes
BROWSE_OUT=browse-out lockf ~/.cache/mac-locks/heavy.lock nice -n 10 test/compare/browse.sh record
scp -r browse-out/traces linux-box:browse-out/

# on the Linux box, the same commit checked out. Timing holds the lock of the server's cpu pair (0 and 4 share a core) and of the load's pair
cd tifa
BROWSE_OUT=$HOME/browse-out test/compare/browse.sh build                                              # a few minutes on a cold box
BROWSE_OUT=$HOME/browse-out SERVER_CPUS=0 LOAD_CPUS=1,5 LOCKS="$HOME/cpupair-0-4.lock $HOME/cpupair-1-5.lock" \
  nohup test/compare/browse.sh run > $HOME/browse-run.log 2>&1 &                                       # about 5 to 6 hours, with a first search of the rates
```

A closed round takes about 1.5 minutes with its server start and checks, and its warm-up about as long again for the fastest server, about three times the target for a server three times slower (about 4 minutes). The throughput is 15 rounds at 8 sessions (about an hour with their warm-ups, with a sizing run of about 20 seconds before the first round of each cell), and each step of a server is 3 rounds more (about 4.5 minutes; a server that uses its core at 8 sessions takes none, and one that steps three times takes about 15 minutes). The latency rounds are 15 (5 servers, the reference among them, 3 rounds each) of at least 4 minutes (about 3 to 3.5 hours with their warm-ups, each as long as its round, and whole cycles), and the read-only control is one round of about a minute. The search for the rate of Next.js takes about 30 to 60 minutes with the warm-ups of its trials, and only the first run, or a run with `PROBE=1` or under other conditions than `test/compare/rates.json`, does it. `PHASES` runs a part. Pick a server cpu and load cpus on different physical cores (the command refuses cpus that share a core). A short trial that proves the script works: `SERVERS=tifa PHASES=throughput SESSIONS=4 ROUNDS=1 SIZING=3s TARGET=6s test/compare/browse.sh run`. The pieces by hand:

```
go run ./test/compare/cmd/compare plans -dir traces -blocks 1
go run ./test/compare/cmd/compare record -dir traces -workers 6
go run ./test/compare/cmd/compare links    # after the storefront pages change: writes test/compare/store_links.json
go run ./test/compare/cmd/compare browse -dir traces -server-cpus 0 -load-cpus 1,5 -out browse.json
go run ./test/compare/cmd/compare report browse.json
```

## Render clock

`tifa.WithRenderClock(ctx, now)` supplies the source for Date, Temporal.Now and Intl date formatting without a date in one render. Use a closure returning a fixed `time.Time` for deterministic assertions. Set the context on the test request before calling `tifatest.NewCtx`, or set it in `OnRequest` with `c.WithContext`. `tifatest.NewCtx` tests route functions and preserves the context. It does not run SSR. The public API and the module initialization and cache boundaries are described in [app.md](app.md#render-clock).

`go test -p 2 ./internal/ssr ./server -run 'RenderClock|Temporal'` covers fixed time across promises, saved functions and formatters, live module initialization, VM reuse, replacement, parallel renders and middleware through a real server render. Repeat the touched packages with `-race`. `TestRenderClockFromMiddleware` also uses `tifatest.NewCtx` and a closure for `next` to exercise the same middleware in a route test.

The production default remains live. Test a fixed source rather than requiring separately sampled live timestamps to match. A fixed render clock does not change Go's time.Now or the monotonic timeout budget. A request with a clock skips the render memo and shared renders, and gets no ETag, so it always renders with its own clock.

A request with a render clock skips the render memo, so a test that sets one gets a render every time (`TestRenderClockSkipsTheCache`). `TestRenderKeyCoversEveryFieldOfTheInput` in `server` fails when a field is added to `ssr.Input` that is neither in the key of the render memo nor listed with the reason it cannot change a cached page. `TestDevWarnsAboutAPageThatRendersDifferently` covers the double render of `tifa dev`.

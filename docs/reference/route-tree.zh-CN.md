# 路由树 {#route-tree}

- 框架自己的根路由没有组件。它的 `errorComponent` 是框架的默认组件，它的 `notFoundComponent` 用 404 显示那个组件。当根布局导出 `documentHead` 时，根路由的 `head` 返回那个常量。React 只在 `<body>` 里渲染 `<div id="tifa-root">`。渲染之后，SSR 入口把文档构建成一个字符串：`<html>` 带着根布局 `documentHead` 里的 `htmlAttributes`，匹配路由的 `head` 结果里的 `htmlAttributes` 合并覆盖在它们之上（见 [head.md](../pages-and-data/head.zh-CN.md#what-the-head-of-a-page-is-made-of)）。head 里按顺序放的是：字符集，`build.json` 的 `head`，匹配路由的模块预加载（见[预加载页面的代码块](route-modules.zh-CN.md#preloading-the-chunks-of-a-page)），以及在 `<!--tifa-head-->` 和 `<!--/tifa-head-->` 之间，由匹配路由的 `head` 结果写出的标签（挑选哪些标签遵循 TanStack 的 `HeadContent`，属性按 React DOM 的规则写出，见 [head.md](../pages-and-data/head.zh-CN.md#what-the-head-of-a-page-is-made-of)）。body 是应用根节点，加上路由器的脱水脚本。所以当任何一层失败、返回 404，或根 `Layout` 失败时，页面仍然是一个完整的文档。浏览器订阅路由器的匹配（TanStack 的 `HeadContent` 也读它们）。当一次导航结束，或 `router.invalidate()` 加载完数据，并且匹配发生了变化时，它按同样的规则比较两个注释之间的元素：没有变化的标签保留（nonce 通过读取元素的 `nonce` 属性来比较，因为在有 CSP 的页面上，nonce 这个 HTML 属性读出来是空的）。当顺序改变时，它只移动不在原位的元素，就像 React 移动带 key 的子元素那样（移动 style 会重新构建它的样式表，移动样式表链接会再次处理它）。新的标签用 DOM 方法创建（不解析 HTML），并按文档顺序插入。水合不会动服务器写出的 head。浏览器还根据同样的匹配设置 `<html>` 的属性。它只改变值有变化的那些，只拿掉它之前设置过的那些，所以别的东西设置的属性会保留。路由器水合完成后，浏览器会把 head 和属性与服务器渲染的匹配同步一次，这不会改变任何东西，只是记下服务器写出了哪些属性，然后才开始跟随匹配。浏览器入口渲染的是 TanStack 的 `RouterClient` 渲染的内容，并在路由器水合之后加上这一步。对没有 SSR 的页面，Go 写出的文档里只有字符集、`build.json` 的 `head` 和页面的模块预加载，`<html>` 不带属性。浏览器立刻设置根布局 `documentHead` 里的 `htmlAttributes`，在路由加载之后再设置路由的，并写出 head。
- 根布局（`app/layout.tsx`，以及 `app/route.go` 里的 `Layout`）是根路由之下的无路径路由 `_app`。
- 其他每个布局都是一个路由，它的路径是它的文件夹相对于它的父布局的文件夹的部分，所以它的路径参数是它的匹配标识的一部分。根布局之下的 `app/projects/project+` 是 `projects/$project`，路由 ID 是 `/_app/projects/$project`。`layout_.tsx` 里的布局没有父布局：它是根路由正下方的一个路由，它的路径是它相对于 `app/` 的整个文件夹，所以 `app/store` 是 `store`，路由 ID 是 `/store`，它的 `errorComponent` 是框架的默认组件。
- 每个布局路由都有一个 `notFoundComponent`，它显示这个布局的 `ErrorBoundary`，或最近的祖先布局的，带一个状态为 404 的 `TifaError`（运行时里是 `missing`）。路由器以 `notFoundMode: 'fuzzy'` 运行：对于没有任何路由匹配的 URL，它加载匹配 URL 开头部分的那些路由，并在其中最深的、有 `notFoundComponent` 的那个路由的 `Outlet` 里显示它。所以 404 显示在 URL 所匹配的最深的布局里面，服务器找到的也是这一个（见 [404](../pages-and-data/errors.zh-CN.md#404)）。
- 页面路径是它的文件夹相对于它的布局的文件夹的部分。位于布局自己的文件夹里的页面，是那个布局的 index 路由 `/`，路由 ID 是 `/_app/projects/$project/`。`name+` 变成 `$name`，`name++` 变成 `$`（参数名是 `_splat`）。字面的文件夹名只包含 ServeMux、路由器和 URL 读起来含义相同的字符，所以按原样写出。
- 如果任何两个生成的路由最终得到同一个 TanStack ID，构建会失败。
- 带 `Load` 的路由会得到一个 `loader`，并对它的数据多久算新鲜使用 TanStack 的默认值：立即过期（`staleTime: 0`），预加载的数据重用 30 秒，再次访问时显示缓存的数据，同时在后台重新加载（`defaultStaleReloadMode: 'background'`）。运行时里没有任何东西会在写入之后重新加载数据，见 [handlers.md](../pages-and-data/handlers.zh-CN.md#calling-method-handlers-from-the-browser)。`loaderDeps` 只包含 `Query` 里的查询参数，也就是 `Load` 的查询结构体的字段。`remountDeps` 是这个路由的文件夹和它上层文件夹的路径参数，不管 `Load` 读了什么，没有查询参数：另一个查询会重新加载数据，并保留组件和它的状态，就像 TanStack Router 默认做的那样。没有 `Load` 的路由也一样会重新挂载。
- 当 `Load` 失败，包括 404 时，loader 会抛出一个带状态和公开消息的 `TifaError`，由这个路由的 `errorComponent` 显示。页面路由的 `errorComponent` 是它自己的 `ErrorBoundary`，或最近的祖先布局的。布局路由的是它的父布局的，所以失败的布局会显示上一层的 `ErrorBoundary`。
- 路由器把路径当作区分大小写的，和 ServeMux 一样。查询参数按 Go 读查询字符串的方式解析：值是字符串，重复的键是字符串数组，没有东西会被当作 JSON 解析。路由的 codec 随后会按类型转换 `Load` 读的那些参数，见下一条。写回 URL 时，它们遵循浏览器和表单的风格（空格变成 `+`），常见的 URL 保持原样。Go 的 `url.ParseQuery` 会读成不同含义的字符（`;&=+%#`）总是被百分号编码，所以重新加载时 Go 得到同样的值。
- 一个路由，如果它的 `Load` 或 `Layout` 读取查询参数，就会得到一个由运行时的 `searchCodec` 按每个字段的种类生成的 `validateSearch`（`"page": "int"`、`"color": "string[]"`），还有按同样种类写出类型的 `PageSearch`（或 `LayoutSearch`），给 `Link`、`navigate` 和 `useSearch` 用，见[Link 和 navigate 里的查询参数](../pages-and-data/navigation.zh-CN.md#query-parameters-in-link-and-navigate)。codec 按 Go 解码器的规则转换值，遇到不合法的值就抛错，路由上的 `onError` 再把 TanStack 包出来的东西（一个 `SearchParamError`）换成状态为 400 的 `TifaError`，消息和 Go 返回的一样，所以 `ErrorBoundary` 不管错误来自哪边，看到的都是同一个错误。Go 不读的参数保持地址里的样子。TanStack 把结果盖在解析出的查询上，所以没传的参数，包括空值，会返回 `undefined`，下面的路由拿到的是上面路由转换过的值。接管页面之前，浏览器会把地址写成路由器读出来的样子，去掉空数字和空 bool，并把数字写成最短的写法，和服务端渲染页面时一样，这样路由器不会把页面再加载一遍。
- 服务器在路由之前，就会响应 public 文件夹里的文件，以及 `/assets/` 或 `/__tifa/` 之下的任何东西，但是 `app/` 根部的参数文件夹（比如 `app/lang+`）也会匹配像 `/favicon.svg` 这样的路径。所以 `routes.tsx` 里有 `publicPaths`，即 public 文件夹里文件的 URL 路径（`tifa build` 和 `tifa dev` 读取 `build.public` 文件夹），根路由会把每一次导航到其中之一、或到 `/assets/` 或 `/__tifa/` 之下路径的导航，变成一次文档加载，不请求导航数据。这涵盖 `<Link>`、`router.navigate` 和 `router.preloadRoute`（预加载什么都不做）。每个有 `page.tsx` 的路由都带 `staticData: { page: true }`，运行时里的 `isPage(router, pathname)` 只对被页面完整匹配的路径为真，对上面的路径、API 路由和显示 404 的 URL 为假。
- 为不匹配任何页面的 URL 添加了两种路由。在一个自己的 URL 上没有页面的布局之下，有一个 index 路由，它的 loader（`unmatched`）抛出 404，这样那个 URL 就在这个布局里面显示 404。在根布局之下，有一个路由 `$`，对应路径的其余部分，它的 `params.parse`（`outside`）只接受这样的 URL：根布局之下或某个 `layout_.tsx` 之下没有任何路由以它开头。根布局没有路径，所以路由器会只用根路由去匹配这样的 URL，而不带根布局。它的 loader 同样抛出 404。这些路由没有组件，也没有 `Load`，Go 里没有它们的路由。
- `page.tsx`、`layout.tsx` 和 `layout_.tsx` 必须有默认导出。可选的导出 `head` 和 `ErrorBoundary` 对应 `head` 和 `errorComponent`，布局的 `ErrorBoundary` 也对应它的 `notFoundComponent`。TanStack 只保留 `head` 返回的东西里的 `meta`、`links`、`scripts` 和 `styles`，所以每个 `head` 都经过运行时的 `routeHead`，它把 `head` 返回的 `htmlAttributes` 作为 `meta` 的又一个条目带着，而 head 会把它去掉。没有 `htmlAttributes` 的 `head` 返回它原来返回的东西。根布局还可以导出 `documentHead`，`<html>` 的 `htmlAttributes` 就放在里面。没有显式导出 `ErrorBoundary` 的路由，使用导出了它的最近的祖先的 `ErrorBoundary`，都没有导出时用框架的默认组件。服务器渲染错误时，使用路由自己的 `errorComponent`，在浏览器里则由最近的错误边界捕获它，所以两边显示的是同一个组件。TanStack 会把 `errorComponent` 可以预加载的路由包进 Suspense。在浏览器里，这指的是浏览器包懒加载、而 `routes.tsx` 以静态方式导入的模块的每个 `ErrorBoundary`（导出了 `head` 的那些，见[浏览器里的路由模块](route-modules.zh-CN.md#route-modules-in-the-browser)），而 SSR 包里有的是组件本身。这样的路由会得到 `wrapInSuspense: false`，所以浏览器水合的是服务器渲染出的那棵树。路由器在渲染路由之前，会加载 `ErrorBoundary` 的代码块，就像对路由的组件所做的那样。这些导出必须直接在文件里声明，或按名字导出（通过 `export *` 的重新导出不算）。

# Changelog

What changed in Tifa that apps and their users can see. From v0.0.1 on, changes are grouped by release. Older changes are grouped by the date they reached `main`. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). [Performance](docs/reference/performance.md) has how each speedup was measured. An entry that apps must act on ends its bullet with the word Upgrading, a colon and the steps, which `go tool tifa upgrade` prints.

## [Unreleased]

### Added

- `tifa check`, `tifa build` and `tifa dev` warn of a string that `OnRequest` compares with `c.Pattern()` (`==`, `!=`, `switch` or `strings.HasPrefix`) when no route of the app can have it, for example a guard left behind by a renamed folder. The warning names the file and line, the string and the closest routes. See [Check the app](docs/build-and-deploy/check.md#tifa-check).
- `tifa deploy rollback` takes an optional release ID, as `tifa deploy status` lists it (such as `20261120T110000Z`), and goes to that release, older or newer than the one that runs, with the same restart and health check. The release must still be on the server and have passed its health check when it was deployed, else nothing changes and the error lists the releases it can go to. See [Roll back](docs/build-and-deploy/deploy.md#roll-back).
- `tifa deploy status --json` works without `--all`: it prints one JSON object for the app of the folder, with the fields of an app of `--all`, the `server` it asked and the `releases` kept (`id`, `commit`, `checkPassed`). It exits as the text does. See [Logs, status and remove](docs/build-and-deploy/deploy-operate.md#logs-status-and-remove).

### Changed

- `tifa deploy` runs ssh with `BatchMode=yes` when there is no terminal, so it never waits for an answer no one can give, and gives a server it reaches directly 15 seconds to answer, unless your ssh configuration sets a `ConnectTimeout` (a `ProxyCommand` or `ProxyJump`, such as Cloudflare Access, gets no limit). A host key that is not in `known_hosts` yet, one that changed, and a server ssh cannot reach each get an error that says what to do. See [Deploy](docs/build-and-deploy/deploy.md#deploy-with-tifa-deploy).

### Fixed

- A handler called from the page that redirects to the page that is showing, such as a write that leaves a message in a cookie and returns `tifa.Redirect` to the same address, now loads the data of the page and its Layouts again, as `router.invalidate()` does. It used to stay as it was, so the new data showed only after a reload. See [Calling method handlers from the browser](docs/pages-and-data/handlers.md#calling-method-handlers-from-the-browser).
- With `deploy.front: nginx`, a WebSocket reaches the app: the site passes `Upgrade` and sets `Connection` to `upgrade` when the browser asks for one. Sites written before get it when you run `go tool tifa deploy setup` again. See [Behind nginx](docs/build-and-deploy/deploy-proxy.md#behind-nginx).

## [0.7.2] - 2026-11-27

### Added

- `tifa deploy` works on servers where root cannot log in, as on the images of AWS, Google Cloud and Azure. Name the user you log in with in front of the host, as `TIFA_DEPLOY_HOST=ubuntu@203.0.113.7` or `--host ssh://ubuntu@203.0.113.7:2222`. That user needs passwordless sudo: setup logs in as it for the steps that need root and runs them with `sudo -n`, and stops before it changes anything when sudo asks for a password. Deploys and the other steps still log in as `tifa`, which setup gives the keys of that user. The user stays with the host in `~/.tifa/config.yaml` and in `.env`. See [When root cannot log in](docs/build-and-deploy/deploy.md#when-root-cannot-log-in).
- `tifa deploy status --all` looks once at every server in `~/.tifa/config.yaml`, with no app checkout: for each its system, memory, disk, uptime and load, and for each app on it (also those set up from another machine) the release and its commit, the service and how often systemd restarted it, what `GET /healthz` answers and its memory. `--json` prints the same as one document. It exits with an error when a server cannot be reached or a deployed app is not active with a passing health check. See [Logs, status and remove](docs/build-and-deploy/deploy-operate.md#logs-status-and-remove).

### Changed

- A `tifa deploy` that went live remembers the server in `~/.tifa/config.yaml`, as setup does, so a server set up before that file existed or from another machine gets its entry on the first deploy from this machine, and `tifa deploy status --all` and the default server know it. A deploy in GitHub Actions writes nothing. See [The servers Tifa remembers](docs/build-and-deploy/deploy.md#the-servers-tifa-remembers).
- `tifa build` passes `-trimpath` to `go build`, so the program holds no folder of the machine that built it, and a panic names a file by its path in its module. `build.debug_info: true` keeps the full paths with the debug info, and `-trimpath=false` in `GOFLAGS` keeps them alone.
- Pages that use react-i18next 18 render faster. On the server, `useTranslation` no longer runs its hooks, which only keep its result between renders and listen for changes of the language or the strings, when the strings it asks for are loaded. On the example shop the storefront pages render in 6.2% less time (1% to 10% by page, cart and checkout 6.4%) and run 4.8% fewer instructions. The pages are byte for byte the same. The browser runs `useTranslation` as before.
- The build errors of the analysis, from `tifa build`, `tifa check` and `tifa dev`, now end with the doc section that explains the fix, as the messages about code from other frameworks already did. A few say more than one way out.

Heading ids did not change, so a link with an anchor only needs the new file name.

See [Method handlers with input and result](docs/pages-and-data/handlers.md#method-handlers-with-input-and-result). Upgrading: change the name to a parameter of the folder path.

### Fixed

- An address with a `$` as it is in its path, such as `/shops/$north`, which a browser keeps as typed, redirects to the spelling the router writes, `/shops/%24north`. It redirected to `/shops/undefined`, since the router read the `$` as the start of a parameter.

## [0.7.0] - 2026-11-26

### Added

- A `Validate` method on the struct a `Load` or `Layout` takes as its second parameter now runs once the query is decoded and before the function, with the signature of the `Validate` of a handler input, `Validate() error` or `Validate(c *tifa.Ctx) error`. Its error is the error of the function: a `tifa.Error` or `tifa.Fields` as it is, any other error through `OnError` as a 500. It failed the build before, so a page and a handler can now share one filter type.
- A [Breadcrumbs and the current page](docs/pages-and-data/layouts.md#breadcrumbs-and-the-current-page) section shows how a Layout follows the page below it, with `useRouterState` in `layout.tsx`. The build error for `c.Path()` in a `Layout` points to it.
- Under `tifa dev`, what a page prints with `console.log`, `info`, `debug` and `warn` while it renders on the server goes to the log of the app, with the page and the place of the call in your sources, and `tifa dev logs` shows it. A built program prints nothing. `console.table`, `dir`, `group` and `groupCollapsed` print as `log` under `tifa dev`. See [Console in `tifa dev`](docs/pages-and-data/server-render.md#console-in-tifa-dev).
- `tifa dev` writes a line for each request of a route: the method, the URL, the status, the time, the route and what the render memo did (`memo hit`, `memo miss`, `memo shared`, `memo off`), or `data` for navigation data. Files of the bundle and `public/` and the requests of `tifa dev` get none, and a built program has no request log, as before. See [Log](docs/build-and-deploy/dev-errors.md#log).
- `tifa version`, `tifa --version` and `tifa info`. `info` prints the versions of Tifa, Go, Node and pnpm, the system, and whether the folder has a `tifa.yaml`, with `--json` for scripts and agents. A program that is missing is `not found`. See [Version and info](docs/build-and-deploy/check.md#version-and-info).
- `tifa dev status` prints `app pid`, and `--json` has `appPid`: the process ID of the app, which a debugger such as Delve attaches to. New docs: [Debugging](docs/build-and-deploy/debugging.md) and [Testing pages](docs/pages-and-data/testing-pages.md), which covers Vitest and Testing Library for a page component and Playwright against `tifatest.StartPages`.
- Each type that `route.gen.ts` and `session.gen.ts` declare from a Go struct has a comment that names the Go package, the type and the file and line, such as `/** Go: example.com/app/projects.Project (projects/project.go:12) */`. The comment is not in the bundles, and it does not change the build ID. A `tifa gen` after a struct moved to another line writes the file again.

### Changed

- `Load`, `Layout` and the functions they call may pass the Ctx wherever Go lets them, as a `net/http` handler does with its request: to a library, an interface, a struct, a function value, a goroutine or an `errgroup`. The build follows the Ctx into the functions of the module it is passed to and reports the mistakes it sees there, and says nothing where it cannot see which function runs. The rule of the five places a Ctx may go is gone, and so are the build errors for a `go` statement, an interface method, a function value or a function outside the module that gets the Ctx, for a name of `c.Param` that is not a constant, and for `c.Param` or `tifa.Use` taken as a value. A constant name of `c.Param` is still checked against the path of the folder. See [How Load may use Ctx](docs/pages-and-data/loading-data.md#how-load-may-use-ctx).
- `c.Request()` and `c.Writer()` work in `Load` and `Layout`, where they failed the build. There `c.Request()` is a copy of the request with only the query parameters the function declares, each number spelled the shortest way, and no body, and in a `Layout` only the path parameters of its own folder. `c.Writer()` is the response, and writing to it from a `Load` breaks the page. See [The raw request in Load](docs/pages-and-data/loading-data.md#the-raw-request-in-load).
- `c.Query`, `c.QueryValues` and `c.BindQuery` no longer panic in a `Load` or `Layout` when the build could not see the call: they read that copy, which has the declared parameters only. The build still fails for a call it sees.
- `c.Param` in a `Layout` gives `""` for a parameter of a folder below the Layout, whose data stays while the visitor moves between the pages below it. The build still fails for such a name when it is a constant.
- `c.JSON`, `c.Text` and `c.NoContent` in a `Load`, a `Layout` or a function they call now fail the build where it sees them. They return an error at run time, as before.
- A `Layout` shared by pages with `Cache` and pages without no longer fails the build for reading `c.Cookie`, `c.Header` or `tifa.Session`: on a page with `Cache` it gets what an anonymous visitor has. The build still fails for such a read in code that runs only for pages with `Cache`, the `Load` of such a page and a `Layout` whose pages all have it.
- `tifa routes --json` no longer has `params`, `uses` and `allQuery` in a `load`. `query` lists the query parameters the data depends on. Upgrading: a script that read `params`, `uses` or `allQuery` reads `query` instead.
- The render memo drops pages differently when it is full. A page seen once goes first, and a page that was hit more than once is kept, so a run of addresses that come once, such as search terms or page numbers nobody asked before, no longer pushes the home page and popular pages out of `ssr.memo_size`. Nothing to change in an app.
- The warning about `import.meta.env.VITE_*` is one line for a build, with every name it found and the place of the first read, instead of a line for each name.
- `console.time`, `timeEnd`, `timeLog`, `table`, `dir`, `group`, `groupCollapsed`, `groupEnd`, `count`, `countReset` and `trace` no longer throw a `TypeError` in a server render. They do nothing in a built program. `console.error` and a failed `console.assert` still throw, in both modes.
- The next steps that `tifa new` prints, the READMEs and the tutorial say that `pnpm install` runs `go tool tifa gen`, which writes the types the editor reads, so open the editor after it.
- The `ci.yml` that `tifa new` writes installs the newest patch of the Go minor of `go.mod` (`go-version: '1.27.x'` with `check-latest: true`) and runs `govulncheck`, and the workflow of `tifa deploy` installs the newest patch the same way. `go-version-file: go.mod` installed exactly 1.27.0, which lacks the `net/http` fixes of later patches, and `net/http` is compiled into the program. The workflow of `tifa deploy` is written again by `tifa deploy setup`. `tifa deploy setup` stops with a message when `go.mod` has no `go` line. Upgrading: in the `ci.yml` of an app you have, replace `go-version-file: go.mod` with `go-version: '1.27.x'` and a line `check-latest: true` (the minor of your `go` line), and add the step `- run: go run golang.org/x/vuln/cmd/govulncheck@latest ./...` after `go tool tifa check`.
- The systemd unit of an app made by `tifa deploy setup` has `StartLimitIntervalSec=0` and `RestartSec=2s`. Before, systemd stopped restarting the program after 5 starts in 10 seconds and left it failed, so a request that crashed the program again and again took the site down. Now it keeps restarting. `tifa deploy setup` writes the unit again.

### Removed

- A constant in `route.go` that is near the name of a switch, such as `SSL`, `Demo` or `Cahce`, no longer fails the build with `did you mean`. `route.go` is your package, so such a constant is your own. A bool constant that spells a switch in lower case (`cache`, `memo`, `ssr`) still fails.
- The build no longer fails for the names of older versions. A module that exports `Document`, `NotFound` or `Error`, and a `const Path` in a `route.go`, are now your own code: they are not read, and nothing reports them. A 404 is shown by the `ErrorBoundary` export.
- A `form` tag no longer fails the build when it names the field as its `json` tag (or its Go name) does, such as `json:"email" form:"email"`, so a type shared with another framework works as it is. A `form` tag with another name still fails, in the input of a handler and in a struct passed to `c.Bind` or `c.BindQuery`, since Tifa reads the field by its `json` name.
- The imports and files of other frameworks that fail the build are only those that are surely wrong in a Tifa app. The packages of the Remix organization that stand alone (`@remix-run/headers`, `@remix-run/form-data-parser`, `@remix-run/file-storage` and the like) and a name below `$app/` that SvelteKit does not have are left alone, and so is an `_index.tsx` next to a `page.tsx`. `@remix-run/react`, `@remix-run/node` and the other packages of the Remix framework, `react-router`, the modules of Next.js, TanStack Start, SvelteKit and Astro still fail the build.
- A key in the front matter of an entry that is not a field of its type is now a warning with the nearest field name, and the entry is read without it. Before, it failed the build, so Markdown moved from Hugo or Jekyll, with `weight` or `categories` in its front matter, did not build.
- `const Memo = true` in a `route.go` is accepted and changes nothing, since the render memo is on by default. Before, only `Memo = false` was.

### Fixed

- A file under `/assets/` answers 412 for a failed `If-Match` with no `Cache-Control: public, max-age=31536000, immutable`, which a shared cache could have kept and handed to every client.
- A redirect that the router makes while it renders a page writes a tab, a line feed, a carriage return and other control characters of its address as `%09`, `%0A`, `%0D` and so on. A browser drops them from an address, so `/<tab>/evil.example` could be read as `//evil.example`.
- On a site with languages, a `Load` that redirects to another language and an address that is not an `http`, `https` or relative one (such as `javascript:`) is an error and no longer runs in the browser.


## [0.6.0] - 2026-11-26

### Added

- `deploy.front: nginx` in `tifa.yaml` puts several apps on one server without Cloudflare. `tifa deploy setup` installs an nginx that Tifa owns, as a line of the plan, writes one site for each app (the host of `site.url`, the app on a loopback port), and for an app with a domain gets a certificate with certbot, which renews it with its own timer. An app without a domain is served over plain HTTP on port 80, and one app per server can be that. Each change goes through `nginx -t` before nginx reloads, and a file nginx refuses is put back. Setup stops, and changes nothing, when the server has an nginx that Tifa did not install or another program holds port 80 or 443. `tifa deploy remove` takes the site and certificate of an app away, and nginx and certbot with the last app. See [Behind nginx](docs/build-and-deploy/deploy-proxy.md#behind-nginx).
- `build.public_dotfiles` in `tifa.yaml` lists the dot files and folders of `public/` that `tifa build` copies, such as `.nojekyll,.foo`. Until now none could be. A path that is not in `public/` fails `tifa build` and `tifa check`. `tifa build` now says which dot files it left out of `public/` (a `.DS_Store` is left out without a word), and the `/<file>` row of `tifa routes` counts them.
- `tifa routes` has a third table, `BUILT IN`, with the addresses the program answers that are not a folder of `app/`: `/sitemap.xml` and its parts, `/robots.txt`, `/llms.txt`, `/llms-full.txt`, the `.md` versions of content pages, `/__tifa/session`, `/assets/`, the files of `public/` and the ACME challenge. Each row says when the address is there, such as `site.url is set`, and says so when a file of `public/` or a route of the app answers in its place. See [Tifa routes](docs/build-and-deploy/check.md#tifa-routes).

### Changed

- A page or a Layout now remounts in the browser when a path parameter of its folder or of a folder above it changes, whatever its `Load` or `Layout` function reads, so a draft or the values of a form never carry over to another order or project. Before, it remounted only for the parameters its function read, and a page without a `Load` never did. A query parameter still only loads the data again. State that should outlive such a move, such as the scroll of a list beside the details of an item, belongs in a Layout above the folder of the parameter: see [Layouts](docs/pages-and-data/layouts.md).
- Server rendering runs on beastjs v0.33.1, with the fixes of upstream QuickJS up to November 2026: `Iterator.from`, the `ownKeys` trap of a `Proxy`, `Promise.allSettled`, `Math.sumPrecise`, `ArrayBuffer.prototype.transfer`, very long strings and a few `SyntaxError`s of the parser behave as the standard says. The API is the same. A render of the shop's workbench pages takes 0.6% longer on an M4 Mac.
- `site.url` takes only a plain host: a name of letters, digits, hyphens and dots (punycode `xn--` included), an IP address or `localhost`, with or without a port. The host goes into the configuration of nginx for `deploy.front: nginx` and into the request for a certificate, so a character such as `;`, `*` or `_` is refused when the settings load. Upgrading: write the host of `site.url` as a DNS name or an IP address.
- `/sitemap.xml`, its parts, `/llms.txt`, `/llms-full.txt` and the `.md` version of a page are kept in the render memo, by what the function of `tifa.SetSitemap` returned, with an `ETag` and 304. The function and `OnRequest` still run on every request, and a changed list shows on the next one. They were built from nothing each time: on a site with 600 entries, `/llms-full.txt` gave 95 answers a second and a client that looped on it slowed ordinary pages. The mistakes in what the function returned are logged when a list is checked, which is once per list and no longer on each request or file. The pages a list has are checked once for all its files, so the `.md` of each post does not check the whole list again. See [The render memo](docs/reference/memo.md#site-files).

- The `ci.yml` that `tifa new` writes has `permissions: contents: read`, so the token of its jobs can only read the repository. A `ci.yml` that an app already has is not changed.
- **Breaking.** `Load` and `Layout` take their query parameters as a second parameter, a struct with a field for each one, and `c.Query` and `c.QueryValues` no longer work there. The build fails for a call it can see, and a call it cannot see panics when it runs, with a message that says what to write. The page loads again when a field changes, the server render and the memo see these fields and no others, and the build tells a field that two Layouts or a Layout and a page declare with different types. Upgrading: declare a struct `Filter` with a field for each name, named by its `json` tag (`Page int` with the tag `json:"page"`), write `func Load(c *tifa.Ctx, q Filter) (T, error)` and read `q.Page` where you called `c.Query("page")`. A list from `c.QueryValues("tag")` is a field of type `[]string`. A test calls `Load(c, Filter{Page: 2})` and no longer runs it through `tifa.Use`. A Layout that takes a second parameter cannot be passed to `tifa.Use` yet: give a Layout whose result other `Load` functions need no query parameters, and read them in the `Load` of the page. A struct with a `Validate` method fails the build: check the values in `Load`.
- **Breaking.** The query string of a page, the one `Load` and `Layout` take as their second parameter, is read by the type of each field. A value that is not of that type answers 400 with `invalid query parameter "page"`: `?on=1` or `?on=TRUE` (a `bool` takes `true` and `false`), a text that is no number for a number field, `?page=2.5` or `?page=1e3` for a whole number, a number out of the range of its type or above 9007199254740991, and a name that comes twice for a field that is not a list. A number may be written the way a person types it (`?page=007`, `?rating=1.0`, `?price=.5`, `?price=10.50`, `?price=%2B1e3` for a `float64`): it is the same number, the page is rendered for the shortest text (one render, one cache entry and one canonical link for `?page=007` and `?page=7`), and the address bar is rewritten to it after the page loads. An empty value, as a form sends for a field left empty (`?page=`), counts as not passed and leaves the field at zero. The input of a `GET` or `DELETE` handler is decoded as before. Upgrading: a field that a visitor fills by hand needs nothing now, and a field declared as a `string` only to take `10.50` or `007` can be a number.

- **Breaking.** A page now gets the query parameters with the types of their Go fields. `useSearch()` and `PageSearch` give a `number` for a whole number or a float, a `boolean` for a `bool`, a `string`, and an array of them for a slice, where every value was a string or an array of strings. The browser converts the address by the declared type and by nothing else, with the rules Go reads it by (one table of cases tests both, in Go, in Node and in the engine that renders on the server), so `?q=1.0` is still the text `1.0` for a `string` field. A value that is not valid gives the `ErrorBoundary` a `TifaError` with status 400 and the message Go answers with (`invalid query parameter "page"`), whether the full page, the data request or the browser found it. An empty value of a number or a bool (`?page=`) counts as not passed: the server renders the page without it and answers 200 with no redirect, and after the page loads the address bar drops it, with no request for data. Upgrading: write the values of `Link`, `navigate` and `search` with their types (`page: 2`, `stock: true`, not `String(n)` or `'true'`) and read them as they are, with no `Number(search.page)`, `=== 'true'` or `[search.sort].flat()[0]` for a field that is not a slice. A `search` function that builds on `prev` needs `from` on the `Link` or `useNavigate` to give `prev` the types. Declare a `float32` field as `float64` (see the next entry).

- **Breaking.** A `float32` field in the struct a `Load` or `Layout` takes as its second parameter now fails the build, and so does a slice of them. A query value must be the same number in Go and in the browser, and the browser has only 64 bit numbers, so a float32 would round differently: `?price=1234567.89` is 1234567.9 in a float32, while the page would show 1234567.89. The input of a method handler still takes `float32`. Upgrading: declare the field as `float64`.

- The `AGENTS.md` of a new app is about a quarter smaller, some 2,850 tokens instead of 3,780, since a coding agent reads all of it at the start of every session. Its docs index now names the files only, and `go tool tifa docs` prints the whole summary of each doc, with the settings, commands and functions it covers, where it printed only the first clause. Run `go tool tifa agents` to get the smaller block in an app you have.

- **Breaking.** A `Validate` method that returns a plain error is now answered like a handler that returns one: it goes to `OnError`, the answer is 500, and its text stays in the log. It was answered with 400 and the text of the error, so an error from a database or another service that `Validate` called reached the visitor. `tifa.Fields` and `tifa.Error` are answered as before. Upgrading: where a `Validate` returns `errors.New("message")` or `fmt.Errorf(...)` for the visitor to read, return `tifa.Fields{"field": "message"}` for a message under one input, or `tifa.Error{Status: 400, Message: "message"}`.

- `c.SetReadTimeout(d)` gives the body of one request `d` to arrive, as the `ReadTimeout` of a route does, and the answer `server.write_timeout` after it. Call it in `OnRequest` next to `c.SetBodyLimit`. The constants `BodyLimit` and `ReadTimeout` keep working in this release, and `OnRequest` is the way to write them now.

### Changed

- A site with `site.url` serves `/sitemap.xml` with `lastmod` and the `hreflang` links of each page, a default `/robots.txt` that allows everything and names the sitemap, and `/llms.txt` and `/llms-full.txt` for language models. The pages without parameters are in them on their own. `tifa.SetSitemap` in `OnStart` lists the pages with parameters, leaves routes out with `Exclude`, and adds titles, dates and translations. A page that shows a content entry has a Markdown version at its URL with `.md`, which `llms.txt` links to. A `public/robots.txt` or a route of the app at one of these paths wins, and a site without `site.url` gets none of them. A site with pages with parameters and no `SetSitemap` logs one line at start. A mistake in what `SetSitemap` returns, such as a route with parameters it neither lists nor excludes (a blog with no posts yet), a path that matches no route, a wrong language or a page listed twice, leaves that page or pattern out: the files still answer, and each request logs one error line per kind of mistake naming them. Only an error the function itself returns answers 500 through `OnError`. See [Search engines and language models](docs/guides/seo.md).
- `tifa build` writes the Markdown of each content entry next to its HTML, with the URLs the HTML has. Drafts are left out, as before.

### Changed

- With `site.url`, every page has a canonical link, also on a site with one language and on a page with one version. Before, only a page with several versions had one. A 404 or an error page still has none.
- The canonical link keeps the query parameters the `Load` and Layouts of the page read, as the server renders the page, and drops the others. `/store/products?page=2&utm_source=news` now names `/store/products?page=2` when its `Load` reads `page`, where it named `/store/products` and told search engines that page 2 was a copy of page 1. The browser writes the same link after it hydrates and after a navigation. The `hreflang` links stay without a query.

### Fixed

- Server rendering runs on slowjs v0.31.10. An `await` on a promise whose `constructor` getter throws now throws at the `await`, so a `catch` or `finally` around it runs. Before, the async function stayed stuck there. The instructions of one render are within 0.03% of v0.31.9.

## [0.1.0] - 2026-11-18

### Added

- [Compatibility](docs/reference/compatibility.md) says what Tifa keeps stable from v0.1 and what may still change. A change that breaks what it promises now comes in a minor version, never in a patch.
- `tifa new --empty` writes a skeleton in place of the todo list app: the root files with the sessions table, a root Layout with its error component and a home page of one line. It builds, passes its own `go test` and `go vet`, and starts. Without the flag nothing changes.
- A sign-in over plain HTTP from a host that is not localhost logs a warning, once per process: browsers drop the `Secure` session cookie there, so the user stays signed out with no other sign. Requests over TLS, with `X-Forwarded-Proto: https` or `Forwarded: proto=https`, and to localhost do not warn.

### Changed

- The `content` package spells the language out, as the rest of Tifa does. `Entry.Lang` is `Entry.Language` (JSON `lang` becomes `language`), `Translation.Lang` is `Translation.Language`, and the parameters of `Get` and `In` are named `language`. A front matter key `language` is now one of the names Tifa sets, and `lang` is free again. The vfile data of a Markdown plugin has `file.data.tifa.language` in place of `lang`. Upgrading: rename `.Lang` to `.Language` on entries and translations, and `Lang:` to `Language:` in `content.Entry` and `content.Translation` literals (tests that use `tifatest.SetContent` have them). In TypeScript that reads an entry or a translation from a `Load` result, rename `lang` to `language` in the type and in uses such as `post.lang`. A remark or rehype plugin that reads `file.data.tifa.lang` reads `file.data.tifa.language`. A schema or front matter field of your own named `language` must be renamed.
- The names a page imports from Tifa are fixed for good: `tifa/client`, `tifa/i18n` and `@tanstack/react-router`. The `paths` of the app's `tsconfig.json` is now one line for all of them, `"tifa/*": ["./.tifa/tifa/*"]`, and `.tifa/tifa/` holds only the public entry files, so a module added later needs no change to any tsconfig. `tifa/client` also exports the `SessionData` type, so a page no longer imports `@/.tifa/session.gen`. Upgrading: in `tsconfig.json`, replace the lines `"tifa/client": ["./.tifa/runtime/client.ts"]` and `"tifa/i18n": ["./.tifa/runtime/i18n.tsx"]` with the one line `"tifa/*": ["./.tifa/tifa/*"]`. Run `go tool tifa build` or `go tool tifa dev` once so that `.tifa/tifa/` exists before the editor looks for it. In code, replace `import type { SessionData } from '@/.tifa/session.gen'` with `import type { SessionData } from 'tifa/client'`. Imports of `tifa/client` and `tifa/i18n` stay as they are. Tifa does not edit your code or your tsconfig for you.
- `RouteError` is gone. Pages have one error class, `TifaError`, with `status`, `message` and `fields`. A failed `Load`, a 404 and a failed handler call all give a `TifaError`, so one `instanceof` check covers them. `fields` is an empty object unless the answer came from a `tifa.Fields`. Upgrading: replace every `RouteError` in your pages with `TifaError`, and drop it from imports that list both (`import { TifaError } from 'tifa/client'`). Checks like `error instanceof RouteError && error.status === 404` become `error instanceof TifaError && error.status === 404`.
- The error and 404 component that `page.tsx`, `layout.tsx` and `layout_.tsx` export is now called `ErrorBoundary`. The old name `Error` hid the global `Error` in the whole file, so `error instanceof Error` compared against a component and was always false. A module that still exports `Error` fails the build and says to rename it. Upgrading: in every `page.tsx`, `layout.tsx` and `layout_.tsx` that has `export function Error(` or `export const Error =`, rename it to `ErrorBoundary`. Where another file imports it, such as `import { Error as RootError } from '../../layout'`, import `ErrorBoundary` instead (`import { ErrorBoundary as RootErrorBoundary } from '../../layout'`).
- **Breaking.** Three names changed before v0.1. `tifa.MemoryStore` and `tifa.NewMemoryStore` are no longer exported: the memory store is the default, sized by `session.memory_limit`, and `tifa.SetSessionStore(nil)` brings it back. `c.IsData()` is now `c.IsDataRequest()`. `tifatest.WithSession(c, &s)` is now `tifatest.SignIn(t, c, &s)`. Upgrading: replace `tifa.NewMemoryStore(n)` with the setting `session.memory_limit` (in a test of your own store, pass your store to `tifatest.TestSessionStore`), `c.IsData()` with `c.IsDataRequest()`, and `tifatest.WithSession(c, &s)` with `tifatest.SignIn(t, c, &s)`.
- **Breaking.** `cache_control.s_maxage` is now `cache.s_maxage`, with the flag `--cache-s-maxage` and the variable `CACHE_S_MAXAGE`. The old key, flag and variable still start the program and the build, but the value is not used: each prints one "no longer used" warning, and pages with `const Cache = true` get the default 1m until the new key is set. Upgrading: in `tifa.yaml`, the file of `-c`, `.env` and your deployment, rename `cache_control.s_maxage` (`s_maxage` under `cache_control:`) to `cache.s_maxage` (`s_maxage` under `cache:`), `--cache-control-s-maxage` to `--cache-s-maxage` and `CACHE_CONTROL_S_MAXAGE` to `CACHE_S_MAXAGE`.
- Retired settings no longer fail. A key or flag that Tifa dropped (`cache.size`, `cache.whole_page`, `cache.ignore_query`, `cache_control.s_maxage`) prints one "no longer used" warning that says what replaces it, and the program starts and builds. Before, the program refused to start. They are listed in the configuration page of that release. Tifa will use the same list for each key it drops later.
- **Breaking.** `c.Bind` and `c.BindQuery` name a field by its `json` tag, then its Go name, the same as the input of a typed handler. They no longer read `form` tags, and `tifa build` fails on a `form` tag in a struct passed to them, as it does for a typed input. Upgrading: in a struct you pass to `c.Bind` or `c.BindQuery`, move each `form:"name"` to `json:"name"` (a field with both keeps the json name), and remove the form tag.
- Pages that use MUI or emotion's `styled` render faster. A styled component no longer copies its array of styles when no registered class name adds to it, copies its props with a spread when they have a plain shape, and `processStyleVariants` of `@mui/system` reads each variant's props once. On the MUI test app the three pages run 2.5% to 3.2% fewer instructions per render (2.9% fewer over the three, counted with callgrind, not timed) with the same HTML, and the pages of the example shop, which has no MUI or emotion, are the same bundle.
- `tifa new` pins `github.com/liustack/sqlite` v0.1.5. The WAL file stops growing past 64 MiB (`_wal_limit` in the DSN changes it, 0 turns it off), writes next to overlapping reads are faster, queries of computing run 6% to 10% faster, and a connection that hit an out of memory, I/O or disk full error is dropped once its transaction ends. Two rules changed. A connection in a read transaction that tries to write while another holds the write lock gets `SQLITE_BUSY` at once, no longer after `busy_timeout`. When a group commit ends because one statement failed, the statements of the group that ran before get `SQLITE_ABORT_ROLLBACK`, and the caller decides whether to run them again. Errors are of the exported type `sqlite.Error`, with the result code. Existing apps: `go get github.com/liustack/sqlite@v0.1.5`.
- Pages with links render faster. The router no longer repeats work for each link that gives the same answer every time: it checks the first characters of an href before a regular expression, and writes a query into one string, leaving plain names and values as they are. The check that lets prefix links skip a `URL` is cheaper too. On the example shop the storefront pages run 0.4% to 4.7% fewer instructions per render (1.4% fewer over its seven pages in both languages) and the workbench pages 0.1% to 0.3% fewer. The MUI test app runs the same, within 0.04% (counted with callgrind, not timed). The pages are byte for byte the same.

### Fixed

- Server rendering runs on slowjs v0.31.6, a release of engine fixes: the garbage collector could stop while an array moved, WeakRefs and young WeakMap keys were mishandled during a collection, the shape cache had a fault, and some built-ins went wrong when they ran out of memory. The HTML is the same. Instructions of one render: -0.37% on the shop's workbench pages, -0.06% on the storefront, +0.19% on the MUI test app.
- `ssr.timeout` limited compiling the SSR bundle and loading each VM too, not only a render, so a busy or slow machine could fail to start a program whose `ssr.timeout` is short, with `ssr: compile bundle: InternalError: interrupted`. Starting now has a limit of its own of one minute, which only stops top level code that never ends, and `ssr.timeout` is the budget of a render, as documented.
- Pages render about 0.7% faster again on the shop's workbench pages and the MUI test app (0.6% on the storefront pages), with the same HTML. A change of 2026-11-13 that writes out small functions whose body throws, such as React DOM's `resolveCurrentlyRenderingComponent` that every hook calls, stopped working on 2026-11-16 when the Tifa host script got a `tifaThrow` of its own, so every SSR bundle kept those calls. The build now reuses a top-level `tifaThrow` that only throws its argument, and still leaves alone any other function of that name. Instructions of one render, 20 pages of the shop: -0.71% on the workbench, -0.56% on the storefront, -0.59% in all. MUI test app: -0.73%.

## [0.0.11] - 2026-11-16

### Added

- `tifa dev --background` starts the dev server detached from the terminal and returns once the app answers, so a coding agent or a script can start it and go on working. Every other flag and environment variable reaches the server, and everything it prints goes to `.tifa/dev.log`. `tifa dev status [--json]` says whether it runs, its address, process ID, start time and whether the last build worked. `tifa dev logs [-n lines] [-f]` prints the log. `tifa dev stop` stops it and waits until the lock is free. What runs is judged by the lock `.tifa/dev.lock`, not by the process ID in the file, so a leftover file after a restart or a crash is `not running` and nothing is signalled. A second `tifa dev` now says to use `tifa dev status` and `tifa dev stop`. The `AGENTS.md` that `tifa new` writes tells agents to use them. See [Agents and scripts](docs/build-and-deploy/dev-scripts.md#agents-and-scripts).
- `Validate` on a handler input may take the Ctx: `func (in SignUp) Validate(c *tifa.Ctx) error`. It can read the request, so a message can be in the visitor's language with `c.Language()`. `func() error` still works. `tifa build` fails when `Validate`, or a function it passes the Ctx to, writes the response, reads the body again, changes the session or calls `tifa.Use`. The forms and i18n guides say when to translate in Go and when to return codes that the page translates.
- `c.Path()` is the path of the page as the visitor sees it in the address bar, with the language prefix and without the query: `/en-US/store/items/a%20b`. A page load and the data request of a client navigation give the same path, a method handler gets its own, and `tifatest.NewCtx` and `tifatest.Start` agree. A `Load` can use it for a `next` address without `c.Request()`, which `Load` may not call. `tifa build` refuses it in a `Layout`, whose data is shared by every page below it.
- `tifa check`, `tifa build` and `tifa dev` recognize code written for Next.js, Remix, React Router, TanStack Start, SvelteKit and other Go web frameworks: imports such as `next/link`, the directives `'use client'` and `'use server'`, exports such as `getServerSideProps`, `loader` and `metadata`, folders such as `[id]` and `(group)`, files such as `+page.svelte` and `middleware.ts`, and `route.go` handlers that take `http.ResponseWriter`, `*gin.Context`, `echo.Context` or `*fiber.Ctx`. Each is reported with the file and line, the name of the framework and the Tifa way to write it, as an error (the app cannot be right) or a warning (it builds and does nothing). Names Tifa allows are not reported. See [Coming from another framework](docs/start/app.md#coming-from-another-framework).
- `go tool tifa agents` writes the Tifa skill into the app (`.claude/skills/tifa/`) and refreshes the block between the `tifa:begin` and `tifa:end` lines of `AGENTS.md`, both from the Tifa version the app uses. Before, the skill was a copy of a repository folder that stayed as it was after an upgrade, with links to the docs on GitHub `main`, and nothing ever refreshed the block. The skill now links to the docs of the installed version. Run the command again after an upgrade. `--check` changes nothing and exits with 1 naming the files that are out of date, for CI. A file Tifa wrote is overwritten, edits included, a file it did not write is left alone, and the text of `AGENTS.md` outside the markers is never touched. An `AGENTS.md` with no markers gets the block appended, and with no `AGENTS.md` one is written. `tifa new` runs the same code, and `tifa check` prints one line when the files of an app that has them are out of date. See [`tifa agents`](docs/build-and-deploy/upgrade.md#tifa-agents).

### Changed

- The sign-in guide has a `RequireUser` guard that sends a signed-out visitor to `/login?next=` with `c.Path()`, and tests the whole sign-in and sign-out with `tifatest.Start`.
- A call from the page to a handler with no input and no result, such as `func POST(c *tifa.Ctx) error { return tifa.ClearSession(c) }`, now brings the new session to the browser when the handler wrote nothing. Before, `SignedIn`, `SignedOut` and `useSession` kept the old state until the next navigation. The answer is 200 with `X-Tifa-Session: 1` and the session as its body, and the generated TypeScript does not change. A handler that writes its own response is unchanged.
- The skill in `skills/tifa` covers `tifa dev --background` with `status`, `logs` and `stop`, the check for other frameworks' idioms, and a sign-out handler with no input. Its links are paths into the docs of the installed version, not GitHub.
- The `README.md` that `tifa new` writes says what the app is: a working starter to replace with your own domain, not a todo list product.

### Fixed

- `tifa dev` rebuilds once for a file saved in place, also when the machine is busy or a poll looks at the file in the middle of the save. It could take the empty file for a settled change and rebuild twice, the second time for the finished file. Before it takes a batch, it now lets the file watcher catch up with its events and polls.

## [0.0.6] - 2026-11-16

### Changed

- A page whose component throws, or whose render uses up `ssr.vm_memory`, no longer slows the whole site when it is requested again and again. The built app remembers the failure and the error page for 5 seconds, so a request for the same page with the same data and session in that time gets the same answer without a render (`X-Tifa-Render: memo`), and requests that arrive together share the renders that place the error. `OnError` still sees every request, and after the first one it gets the first line of the error with a note that the page did not render again, so the log does not repeat the stack trace. `tifa dev` remembers nothing (see [Errors on a page](docs/pages-and-data/errors.md#errors-on-a-page)).
- A page whose render uses up `ssr.vm_memory` renders its error page once, in place of the outermost Layout, instead of once at every level with the same data, each of which used up the memory again and replaced another VM (see [Errors on a page](docs/pages-and-data/errors.md#errors-on-a-page)).
- Pages render a little faster: the engine now writes the start tag of every `a` whose `href` is not empty and of every `button` that has no `name` or form props, where React DOM wrote them itself. The 14 storefront pages of the example shop run 2.2% fewer instructions and the 6 workbench pages 2.4% fewer, with the same HTML.

### Fixed

- `tifa new` built with a Go development toolchain writes a valid `go` line to `go.mod`, such as `go 1.27`, not `go .0`.
- `tifa build`, `tifa dev`, `tifa gen` and `tifa check` stop at once with `tifa needs Node 20.19, 22.12 or later to run Vite, found Node X` on an older Node, instead of an error from inside Vite.
- A symbolic link in `public/`, to a file or to a folder, or a `public/` that is itself a link, is followed by `tifa build` and `tifa dev`. Such files were left out of the build without a word. A link that leads back into the folder being copied, or to nothing, fails the build.
- A file named `index.html` in `public/`, such as `public/docs/index.html`, is served at its own path. It was answered with a redirect to its folder.
- `tifa dev` no longer calls the app ready when another program holds its address, such as Vite's dev server on a port that was free when both were chosen. The dev server asked only whether the port was open, so a browser request could get Vite's `Cannot GET /__tifa/vite/` while the app had failed to listen. It now waits for the app itself to answer, and when the app exits instead, shows why.

## [0.0.5] - 2026-11-16

### Added

- `performance.now()` and `performance.timeOrigin` exist in the server render, so libraries that read the time while rendering, such as framer-motion's motion values (`useMotionValue`, `useTransform`, `useSpring`), render on the server instead of failing the page with `ReferenceError: 'performance' is not defined`.
- A `tifa` installed with `go install github.com/liustack/tifa/cmd/tifa@latest` hands the command to the version an app pins when run inside the app, like `go tool tifa`, so it never generates code for another Tifa version. `go tool tifa` stays the main way (see [Installing the command globally](docs/build-and-deploy/create-app.md#installing-the-command-globally)).
- `tifa gen` writes the generated code into `.tifa/` and builds nothing, so editors and `tsc` see the types of a fresh clone. The `package.json` of `tifa new` runs it from its `prepare` script, so `pnpm install` or `npm install` is enough. Existing apps: add `"prepare": "go tool tifa gen"` to the `scripts` of `package.json` (see [`tifa gen`](docs/build-and-deploy/check.md#tifa-gen)).
- Built-in languages. A folder of `app/` with a `_locales` folder holding `zh-CN.json`, `en-US.json` and so on is offered in those languages, with its pages and API routes. The default language, named by `i18n.default` in `tifa.yaml`, keeps the plain URL (`/store/cart`) and each other language is the first segment (`/en-US/store/cart`). `i18n.prefix: always` prefixes the default language too. Write `site.url` in `tifa.yaml` and Tifa writes `<html lang>`, the `hreflang` and `x-default` links and a canonical link. In code, `c.Language()` and `useLanguage()` give the language, `useAlternates()` gives the page's URL in each language for a language switch, `c.SetAlternates` says which versions a page has when its slug differs, `tifa.Languages()` gives the languages for a content collection (`Languages: tifa.Languages()`), and the new `tifa/i18n` adapter translates with one i18next instance for all languages and react-i18next, with formatters added in `onStart` of `hooks.ts`. Links such as `<Link to="/store/cart">` and root-relative links in Markdown get the prefix by themselves. See [A site in several languages](docs/guides/i18n.md). Apps that kept the language in their own `lang+` folder and have no `_locales` folder work as before. To move one over, put the strings in `_locales`, replace the `lang+` folder with its contents, delete the `Layout` that checked the language and the hand-written `hreflang` and `lang`, and drop the `Accept-Language` redirect unless you still want it. A top-level folder of `app/` named like a language of the site, and a `lang` in `htmlAttributes` on such a site, now fail the build.
- `hooks.ts` at the app root exports `onStart()`, which runs once before the first render in each VM of the server and in the browser before hydration, for what the whole app sets up once on the JavaScript side, such as i18next formatters or dayjs plugins. It is the JavaScript side of `hooks.go`. Another export fails the build, naming it. If `onStart` throws, the program does not start, and in the browser the page stays the HTML the server sent ([hooks.ts](docs/pages-and-data/hooks.md#setupts)).
- The build fails, naming the file and line, for an i18next formatter written in place in `add` or `addCached` that calls `Date.now()`, `Date()`, `new Date()` without arguments, `Math.random()`, `performance.now()`, `crypto.randomUUID()` or `crypto.getRandomValues()` itself. Such a formatter writes another text for the same call, so the server would keep the text of one request for the next ones and the browser would write a different one ([i18next cache](docs/reference/i18next.md#i18next-cache)).
- The two sides of the example shop share their data. The first shop of the workbench has the products of the storefront at `/projects/studio/products`, where staff change the price, the stock and the title and description in both languages, and the storefront shows a change on its next request: the render memo renders the page again because its data changed, and serves it from the memo after that. The second shop has a product list and edit page of its own. A checkout in the storefront becomes the next order of the first shop (`SH-1043` and on, where it was a random `SS-` number). Every order takes its pieces from the stock of its shop, a checkout and an order staff place alike, and an order of more than is left answers 409. The three comparison apps do the same.
- The example shop has `/metrics`, the counts of `tifa.Stats()` in the text format of Prometheus as [Deploy](docs/build-and-deploy/deploy.md) writes them, for signed-in staff. A PATCH of a product changes only the fields it sends (one that sends none is refused with 422), and the shop keeps up to 100,000 carts, was 10,000, as do the comparison apps.
- `tifa build` warns, with file and line, of app code that reads, while rendering, a query parameter the server does not render it with: by its name from `useLocation`, `useRouterState`, `useSearch({ strict: false })` or the `useSearch` of a route, and the whole `search`, `searchStr` or `href` of the location. `page.tsx` and `layout.tsx` are checked against the parameters of their `Load` and Layouts, which `.tifa/vite.js` now gives the plugin, other modules warn of every such read, and reads in `useEffect` or `useLayoutEffect` pass. The server renders with the parameters the `Load`s read only, so such a read can hydrate differently. The build goes on ([Query parameters in the server render](docs/pages-and-data/ssr-and-cache.md#query-parameters-in-the-server-render)).
- `tifa.Stats().Memo.Evictions` counts the pages the render memo dropped, least recently used first, to make room for another, so a memo that is too small for the pages it is asked for shows. The example shop writes it at `/metrics` as `tifa_memo_evictions_total` ([Deploy](docs/build-and-deploy/deploy.md)).
- The example shop has a `robots.txt`, in its `public` folder, that keeps crawlers out of the search results and the filtered product lists and lets them into the lists of the categories, the sorts and the pages of a list. The three comparison apps serve the same file.

### Changed

- Pages that highlight code with rehype-highlight render faster. rehype-highlight made a new highlight.js with its 37 languages on every render of a Markdown component, and the SSR bundle now keeps one for each `languages` object. The two article pages of the example shop run 15.9% and 20.0% fewer instructions in a render, with the same HTML. A call with the `aliases` option works as before. See [Build](docs/build-and-deploy/build.md).
- A URL that matches no route and whose last segment has a file extension (`/wp-login.php`) or that has a segment starting with a dot (`/.env`, `/.git/config`) now gets the plain text 404 that a missing file under `/assets/` gets, with no `Load` and no render, where it got the 404 page. Scanners ask for such paths by the hundred. A URL that a route matches, a catch-all route included, and navigation data requests are not affected, nor is a route or a public file under `/.well-known/`, and `OnRequest` still runs ([404](docs/pages-and-data/errors.md#404)).
- The server render takes `URL` and `URLSearchParams` from the engine, which parses URLs in Go, in place of the core-js polyfill the host script carried, so the host script is smaller and a VM holds less. On a site with languages the router makes a `URL` for each link it writes, so those pages render in less time, with the same HTML: on one core of an AMD EPYC 7B13, three storefront pages of the example shop take 0.703 of the time and its six workbench pages 0.886. A site without languages makes no `URL` in a render and gains nothing. What a page can see changes in three ways, each as in a browser: a `URL` has no property of its own, a host name that breaks the Bidi rule of UTS 46 is invalid, and an invalid URL throws `TypeError: Failed to construct 'URL': Invalid URL`. `URL.createObjectURL` and `URL.revokeObjectURL` are gone, as there is no `Blob` ([What the server render has](docs/pages-and-data/server-render.md#what-the-server-render-has)).
- The storefront of the example shop sells 150 products, was 28. The new ones are other colours and names of the first 28 and share their photos: a product names the folder of its photos (`photo` in its data), and the pages take the photos from there, not from the slug. The products are one file, `app/store/products/catalogue.json`, which the shop embeds and the comparison apps read too. The product list has 7 pages and each language 150 product pages.
- Upgrading from v0.0.4: a page with `const Cache` is no longer kept in the program. Its `Load`s run on every request and the render memo skips a render whose data did not change, so the origin never answers old data. The page keeps its anonymous request and the build check, and its HTML still sends `Cache-Control: public, max-age=0, s-maxage=<seconds>, stale-if-error=86400` for a CDN in front, unless `OnRequest`, a `Load` or a `Layout` made it private. A page with `SSR = false` and `Cache` no longer has an ETag. `Cache` is now `true`, `false` or a duration: `const Cache = true` takes its time from the new setting `cache_control.s_maxage` (`1m` by default, `--cache-control-s-maxage`, `CACHE_CONTROL_S_MAXAGE`), and a duration still sets the time of the page. Removed: `cache.whole_page`, `cache.ignore_query` (`--cache-whole-page`, `--cache-ignore-query` and their environment variables), `tifa.ExpirePages` (purge the CDN instead, Tifa has no copy to expire) and the `Age` and `Cache-Status` headers of such a page. Renamed, with no old names kept: the render cache is the render memo. `RenderCache = false` is `Memo = false`, `cache.size` is `ssr.memo_size` (`--cache-size` and `CACHE_SIZE` are `--ssr-memo-size` and `SSR_MEMO_SIZE`), `tifa.Stats().RenderCache` is `tifa.Stats().Memo` (`CacheBytes` and `CacheSize` are `MemoBytes` and `MemoSize`, the type `CacheStats` is `MemoStats`, and `PageCache` is gone), `X-Tifa-Render: cache` is `X-Tifa-Render: memo`, and `docs/render-cache.md` is [docs/memo.md](docs/reference/memo.md) The old names are errors, not silent defaults: a `route.go` with `RenderCache` fails the build, and `cache.size`, `cache.whole_page` and `cache.ignore_query` fail the start (and `tifa build` for `tifa.yaml`), whether they come from a file, a flag or the environment. A redirect from a `Load` of a page with `Cache` gets the shared policy too ([Cache for CDNs](docs/pages-and-data/ssr-and-cache.md#cache-for-cdns), [The render memo](docs/reference/memo.md)).
- `ssr.wait_timeout` now defaults to `3s`, was `1s`, the same as `ssr.timeout`. A request waits at most 3 seconds for a VM and then renders at most 3 seconds, 6 seconds in all for the SSR part, inside the 10 second `server.write_timeout`. `OnRequest`, `Load`, encoding, compression and writing the answer share the same timeout, so leave room for them when you raise either value. On a machine where 32 waiting renders take longer than 1 second to run, such as one core with pages that take more than 31 ms to render, a burst used to be answered 503 after 1 second and now waits up to 3 seconds, unless `ssr.queue_limit` is reached first. Set `ssr.wait_timeout: 1s` to keep the old limit ([Render queue](docs/build-and-deploy/tuning.md#render-queue)).
- The SSR bundle of an app on react-i18next 18 no longer prints `tifa rewrite not recognized`. react-i18next 18 wraps the i18n object in a `Proxy` instead of copying it, so the plugin leaves `useTranslation` as it is. The end-to-end tests of the i18n app now run i18next 27.0.1 with react-i18next 18.0.0 ([The i18next adapter](docs/reference/i18next.md#the-i18next-adapter)).
- The i18next cache of the server render now also keeps the strings of calls that run a formatter or post-processor of the app, which it translated on every render before. The example shop's storefront pages, whose amounts and dates go through its formatters, take 0.937 of the time they took, and 0.778 of the time without the cache, with the same HTML. Such code must give the same text for the same language, options and value, as a React component does for the same props. A formatter or post-processor that reads the request or the time should take that value from the options of `t` instead ([i18next cache](docs/reference/i18next.md#i18next-cache)).
- The file where an app defines its own options with `tifa.String` and the like is now `options.go`, not `config.go` (see [Options of the app](docs/build-and-deploy/config.md#options-of-the-app)). Existing apps: rename `config.go` to `options.go` with one `git mv`. A `config.go` that still calls `tifa.String` or the like fails the build, naming the file and saying to rename it. What an app defines there is now called the options of the app, and the settings of Tifa are the ones in `tifa.yaml`.
- The [performance doc](docs/reference/performance.md#against-nextjs-and-tanstack-start) and the README now compare with React Router as well as Next.js and TanStack Start, and measure with gzip requested, as browsers do. The new [render memo doc](docs/reference/memo.md) says what the render memo is, why it is safe on every page, signed-in ones included, and what Tifa does with cookies, the session and `Authorization` for each kind of answer.
- A client that takes both gzip and zstd, as browsers do (`Accept-Encoding: gzip, deflate, br, zstd`), now gets gzip. zstd is sent only to a client that takes no gzip or ranks zstd higher with `q`. This holds for pages, cached pages, navigation data and everything else `server.compress` compresses.
- The render memo keeps one form of a page: gzip with `server.compress` on, HTML otherwise. A page was kept as HTML with a gzip and a zstd copy before, and compressed twice on every miss, which cost about 8% of a miss. Now it is compressed once, a page takes about a fifth of its HTML in the memo, and a hit for a client that takes gzip sends the stored bytes. A client that takes no compression gets the HTML unzipped as it is written, with its `Content-Length`, and a client that takes zstd and no gzip, or ranks zstd higher, gets zstd made as it is written.
- Server rendering runs on `github.com/liustack/quickjs` v0.30.1, the new path of the engine that was `github.com/liustack/slowjs` from v0.28.0 to v0.29.11. The HTML is the same. If an app builds with the engine's build tags, `slowjs_intl_nonames`, `slowjs_intl_nocjdict` and `slowjs_anygo` are now `quickjs_intl_nonames`, `quickjs_intl_nocjdict` and `quickjs_anygo`. Errors of the engine's root package start with `quickjs:` where they started with `slowjs:`. Since v0.30.1 the render timeout (`ssr.timeout`) also stops a page that is flattening a long string, running `String.prototype.repeat`, or compiling a very long regular expression or a very large character class. Compiling a very long regular expression under a timeout could kill the VM before.
- Server rendering runs on quickjs v0.30.2, whose register interpreter replaces the stack interpreter of QuickJS. Pages render the same HTML in less time, and each VM holds more memory, since the engine keeps the register code of every function that ran. `WeakRef` now keeps its target to the end of the job, as in Node.
- Server rendering runs on quickjs v0.30.3, the second batch of the register interpreter. The HTML is the same. `Intl` and `Temporal` now throw a `RangeError` for a very long locale tag or option, where they read it whole, and a destructured array no longer makes an iterator. A closure now holds the value of a variable nothing changes, so a `WeakRef` to an object only a suspended async function held can empty sooner.
- Server rendering runs on quickjs v0.30.5, the third batch of the register interpreter, now built with a profile of page renders. The HTML is the same and pages render in less time: on one core of an AMD EPYC 7B13, the six workbench pages of the example shop take 0.894 of the time they took on v0.30.3, three of its storefront pages 0.905 and three pages of an MUI app 0.885. `{..."ab"}` now gives the characters, as in Node. `ssr.timeout` now also stops a call of `Intl` on a very long text, a list of locales with a tag longer than 16,384 characters is a `RangeError`, and a VM that would pass its memory limit with one large block collects garbage first.
- Server rendering runs on quickjs v0.30.6, which answers more built-in functions inside the interpreter loop, such as `Array.isArray`, `push`, `includes`, `indexOf`, `startsWith`, `Object.hasOwn` and `has` and `get` of a `Map` or `Set`. The HTML is the same. On one core of an AMD EPYC 7B13, three storefront pages of the example shop take 0.986 of the time they took on v0.30.5 and its six workbench pages 0.996, and three pages of an MUI app take as long as before.
- Server rendering runs on quickjs v0.30.7. The HTML is the same. Timed by quickjs on an AMD EPYC 7B13 as the mean of 16 code layouts, the workbench pages of the example shop take 2.3% less time than on v0.30.6, three pages of an MUI app 1.7% less and the storefront pages 1.6% less. A spread no longer calls `return` on an iterator whose step threw, as in Node, and `Object.defineProperty` with a descriptor whose getter or `has` trap throws now ends with that error.

The key of every render no longer copies the data it hashes, about 98 KB less garbage a request for 92 KB of data ([Optimizations](docs/studies/optimizations.md#server)).

- A server that formats many different amounts, dates or names with i18next no longer grows without end. i18next keeps a formatter for each value it formats through `number`, `currency`, `datetime` and the other formats, and through those added with `addCached`, and never lets them go (i18next/i18next#2227): 20,000 new values took 28 MB in a VM, which the server then replaced. The SSR bundle now keeps at most 1,024 for each format, with the same text ([i18next](docs/reference/build-output.md#frontend-output)).

Only the last one was kept, so a page in light mode showed the dark `theme-color`. A deeper route that writes the name still replaces them all.

It now keeps exactly sized copies and counts what it keeps, so the live heap of the cache stays within `ssr.memo_size`. The peak memory of a program that fills the cache with writes drops with it.
- The 308 the server sends for another spelling of a URL (`/%6Eews?utm_source=mail&page=2`, `/news/?page=2`) keeps the query parameters the render did not see. The render memo also keeps the redirect for each spelling of the parameters it saw, and every request gets its own parameters back.
- On a site with languages, a page opened with a query the router spells another way, such as `?q=a%20b`, `?next=%2Fa` or a key given twice around another, no longer asks for its data again right after it hydrates, and under a language prefix keeps that spelling in the address bar. The router replaced it with its own (`?q=a+b`, `?next=/a`). A site without languages never did either. A URL that differs in its path still goes to the router's own.
- A page with `SSR = false` opened with a key given twice around another (`?x=1&y=2&x=3`) takes its first data from the document again. It asked the server for that data once more, with one language or several.

They wrote `.tifa/` as a build does, which replaced the `main.go` and the reload client of `tifa dev`, so the app did not start after the next Go change. While `tifa dev` or `tifa build` runs in the app, `tifa gen` now leaves `.tifa/` alone and prints one line saying so, and `tifa check` still checks the app but writes nothing into `.tifa/` (see [`tifa gen`](docs/build-and-deploy/check.md#tifa-gen)).

It rebuilt only for `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.css` and `.json` files, so the server render kept the old text while the browser showed the new one ([What each change triggers](docs/build-and-deploy/dev-reloads.md#what-each-change-triggers)).

- A `FinalizationRegistry` callback runs right after the collection between renders that queued it, under the time budget and memory limit of a render, and no longer in the render of the next request, which a callback that threw made fail. One that throws or runs out of time now retires its VM and is logged. A callback of the bundle's own top level code runs when the VM loads.
- `i18n.t` of `tifa/i18n` in the `head` of a route translates in the language of the page. On the server it used the language of the last page the VM rendered, or none in a fresh VM, which gave the key, and the render memo kept that title. In the browser the title became the key once the page hydrated.

Tifa adds the hashes of the inline scripts it writes into a page to the policy of that page, so pages hydrate, and the render cache, the whole-page cache and ETags work as before. `server.csp_policy` changes the policy, and `report-only` only reports (see [Content-Security-Policy](docs/build-and-deploy/headers-and-origins.md#content-security-policy)).

### Changed

- **Breaking:** Tifa writes and reads the JSON of apps with `encoding/json/v2` (the data of `Load` and `Layout`, the arguments and results of handler functions, `c.JSON`, `c.Bind` and sessions). The generated TypeScript types follow it. What changes for apps (see [JSON rules](docs/reference/json.md)):
  - A nil slice is written as `[]` and a nil map as `{}`, where both were `null`. Their TypeScript types lose `| null`, so `days?: string[] | null` is `days: string[]`.
  - A `[N]byte` array is a base64 string, as `[]byte` is, where it was an array of numbers. A slice or array whose element is a named byte type stays an array of numbers.
  - A type whose `MarshalText` has a pointer receiver is written as a string wherever it sits, also as a value in a field or slice, where only pointers to it were. Such types may be map keys.
  - `omitempty` leaves out only `null`, `""`, `[]` and `{}`, so it no longer drops `false` and `0`. Use `omitzero` to leave out zero values.
  - The `string` option is accepted only on number fields.
  - The build rejects `time.Duration`, also as a map key, which json v2 cannot write. Return a number in the unit you want, or a string.
  - The build rejects structs json v2 would fail on: two fields with the same JSON name in one struct, an unexported field with a json tag, a struct with fields but no exported field and no tag, an embedded field of a non-struct type without a JSON name, and an embedded struct with tag options or with JSON or text methods.
  - `<`, `>` and `&` are written as they are in JSON answers and page data, where they were `<`, `>` and `&`. Where Tifa puts JSON into the page HTML it still escapes them.
  - Bytes in a string that are not UTF-8 are written as U+FFFD, as before.
  - Reading is strict. `c.Bind` and handler arguments answer 400 for a name that matches a field only in another case, a name twice in one object, a string that is not UTF-8, a time that is not RFC 3339, base64 with line breaks, or an array of the wrong length for a Go array.
  - A session record kept in an outside store that does not read back under these rules signs the visitor out.
  - `GOEXPERIMENT=nojsonv2` is not supported.
  - The JSON of `tifa routes --json` and `tifa errors --json` has `[]` in place of `null` and no `<` escapes.
- **Breaking:** environment variables of settings have no `TIFA_` prefix: `TIFA_SERVER_ADDR` is `SERVER_ADDR`, `TIFA_SSR_VMS` is `SSR_VMS`. `tifa dev` gives the app its address in `SERVER_ADDR`. To update a deployment, drop the prefix from each variable.
- **Breaking:** the program reads only its own settings. A file key, an environment variable or a flag that is no setting is left alone, where an unknown key or `TIFA_*` variable stopped the program. A misspelt name now changes nothing, so check with `./bin/app config`. A `build.*` key in the file of `-c` is left alone too.
- **Breaking:** settings are YAML only. `tifa.json` and JSON deployment files are no longer read: rename `tifa.json` to `tifa.yaml` and write it as YAML (JSON is valid YAML). `tifa build` checks `tifa.yaml` and builds its values into the program as Go code, and no longer embeds the file.
- **Breaking:** Vite reads no `.env` (`envDir: false`), so the `VITE_` variables of `.env` files no longer reach the browser bundle. Pass such values from a `Load`. `tifa dev` no longer rebuilds the bundle for `.env.*` files.
- The example shop reads `SHOP_OPEN` as the setting `shop.open` of its `config.go`, so `./bin/shop config` lists it and `--shop-open` works too.
- **Breaking:** a handler function no longer loads the page data again after a successful POST, PUT, PATCH or DELETE, and the `invalidate` option of the call is gone. A call only sends its request and applies the session of the answer. A redirect only navigates, and a redirect to the page that is showing stays where it is. Tifa does not guess what a write changes, as TanStack Router does not. To show the result of a write, call `router.invalidate()` after the call (`await router.invalidate({ sync: true })` waits until the page shows the new data), or `refresh` your own state. To update, delete `invalidate: false` from calls, and add `await router.invalidate({ sync: true })` after each call whose page should show what it wrote.
- **Breaking:** the routes of `tifa build` use TanStack Router's default freshness, where they had `staleTime: Infinity` and `preloadStaleTime: Infinity`, and the router no longer sets `defaultStaleReloadMode: 'blocking'`. Data counts as stale at once, so going back to a page you visited shows its cached data and loads it again in the background with a `?_tifa=` request, and preloaded data is reused for 30 seconds. A page that must not show old data of someone else after a sign-out calls `router.clearCache()`.
- **Breaking:** `Session.In` and `Session.Out` of `tifa/client` are replaced by `SignedIn` and `SignedOut`. Each takes exactly one element as its child, renders no node of its own, and shows that element only to a signed-in or signed-out visitor, where the old components wrapped their children in a `<span>`. A typo in a component name fails the build, and a misspelled `data-session` attribute by hand failed without a word, so the attribute is now private to Tifa and the docs no longer tell you to write it. In development a child component that does not pass its props on to its DOM element fails when it mounts, with a message that says so. To update an app, replace `<Session.In className="x">…</Session.In>` with `<SignedIn><div className="x">…</div></SignedIn>`, and the same for `Session.Out` (see [In the browser](docs/pages-and-data/sessions.md#in-the-browser)).
- **Breaking:** the method of the session type that gives the browser its part is `Exposed() M`, where it was `Browser() M`. The new name says what it does: whatever it returns is written into the page HTML and kept in the visitor's `localStorage`, so it must hold no credentials and nothing secret. To update an app, rename the method. The build checks it as before (see [Sessions](docs/pages-and-data/hooks.md#sessions)).
- The text of `tifa.ErrSSRBusy` is `tifa: render queue busy`, where it was `ssr: render queue busy`, so every error value of Tifa starts with `tifa: `. A script or alert that matches the old text needs the new one.
- **Breaking:** `c.QueryAll(name)` is now `c.QueryValues(name)`. It returns a slice, and since Go 1.23 an `All` function returns an iterator, as `maps.All` and `slices.All` do. `http.Header.Values` is the closest name in the standard library. To update an app, rename the calls. The build check is the same (see [How Load may use Ctx](docs/pages-and-data/loading-data.md#how-load-may-use-ctx)).
- **Breaking:** redirects are `tifa.Redirect(url, status)`, a function of the package, where `c.Redirect(url, code)` was a method of `Ctx` that never used `c`. It panics when `status` is not 3xx, as `WriteHeader` does for a code it cannot send, where it returned a plain error that ended as a 500. The `Code` field of `tifa.RedirectError` is now `Status`, the name `tifa.Error` already uses. `c.Redirect` is gone. To update an app, replace `c.Redirect(` with `tifa.Redirect(` and `redirect.Code` with `redirect.Status`. The answer to the browser is unchanged (see [route.go](docs/pages-and-data/loading-data.md#routego)).
- **Breaking:** `OnStart` is `func OnStart(ctx context.Context) error`, like `OnShutdown`. The context is the one the program runs with, which ends on SIGINT or SIGTERM, so a start that waits for a database can stop when the program is stopped. To update an app, add the parameter. The build rejects the old signature (see [hooks.go](docs/pages-and-data/hooks.md#hooksgo)).
- New `Fields.Err()` returns the `Fields` as an error, or nil when it has no entries. A validator that collects messages in a `tifa.Fields{}` ends with `return fields.Err()` and needs no `len` check. The server still answers an empty `tifa.Fields` that is returned directly with 422, because it is an error (see [Method handlers with input and result](docs/pages-and-data/handlers.md#method-handlers-with-input-and-result)).
- The example shop's storefront uses the whole-page cache. Its home page, journal list and product pages are kept for 10 minutes, the product list for 5 and a journal post for an hour, so a visitor of a cached page gets the answer from memory with `Cache-Status: tifa; hit` and no `Load` runs. The pages no longer hold anything of the visitor: the storefront Layout has the language, the menu and the free delivery price, and the cart in the header and the recently viewed rows come from the new `/store/{lang}/mine` route, which the browser asks after the page has loaded. A product page tells it which product is open. See [The storefront cache](examples/shop/README.md#the-storefront-and-the-render-memo).
- Pages can opt in to a whole-page cache with `const Cache = 10 * time.Minute` in their `route.go`. For that long every visitor gets the same answer from memory, without the `Load` running or a render, and a CDN in front keeps it for the same time minus `Age`: `Cache-Control: public, max-age=0, s-maxage=<Cache in seconds>, stale-if-error=86400`, `Age` and `Cache-Status: tifa; hit`. Such a page is anonymous: its GET and HEAD, and the data requests of navigations to it, lose `Cookie` and `Authorization` before `OnRequest`, `tifa.Session` is nil, `SetSession` and `ClearSession` return an error, and the `Set-Cookie` of its HTML is removed. The build fails when its `Load`, a Layout around it or a function they call reads `c.Cookie`, `c.Header` or `tifa.Session`. Its request keeps only a short list of headers (`Host`, `Accept-Encoding`, `If-None-Match`, `Origin`, `Sec-Fetch-*` and a few more), so a header such as `X-User-ID` cannot reach a `Load`. The key is the scheme, the `Host` header, the path and the query without tracking parameters (`utm_*`, `gclid`, `fbclid` and the like, the list is the new setting `cache.ignore_query`), sorted. After the time is over the next request makes a new page and the others wait for it, and if that fails (a `Load` error, a failed or timed out render, a busy pool) the old page is served for up to a day. Only GET and HEAD answers with status 200, 301, 302 or 308 are kept, and not one that says `private`, `no-store` or `no-cache` or varies on more than `Accept-Encoding`. The answers to navigations stay `private, no-cache`. Pages share `cache.size` with the render cache. `tifa routes` has a `CACHE` column and the manifest of `--json` has `cache`. `Cache` must be a `time.Duration` of at least a second, and `Cache = true` still fails the build. See [The whole-page cache](docs/start/app.md).
- The browser asks for the data of a navigation with the page URL and the query parameter `_tifa=<build>.<digits>` (one digit for each `Load` on the chain, 1 for the ones it wants), where it sent the headers `X-Tifa-Route` and `X-Tifa-Build`. A page and its data now have two URLs, so a cache that keys by URL cannot mix them up, and the `Vary: X-Tifa-Route` line is gone. ### Fixed

- Under `tifa dev`, a page loaded right after a save now shows the new server render. Before, a request in the first 100 ms or so, before the files went quiet and the rebuild started, got the old one. Saving a `page.tsx` or `layout.tsx` that exports `head`, `htmlAttributes` or `documentHead` makes Vite reload the page at once, so the browser often hit that window: the page kept the old text and React reported `Hydration failed`. Such a request now waits for the rebuild (see [What each change triggers](docs/build-and-deploy/dev-reloads.md#what-each-change-triggers)).
- The pages of an app made by `tifa new` now show a new todo, and a todo marked done, at once. They did not: the comments said the page data loads again after a write, but Tifa never reloads it, so the list stayed old until a reload. The add form and the done button now call `router.invalidate()` after the write, and the comments say so (see [Calling method handlers from the browser](docs/pages-and-data/handlers.md#calling-method-handlers-from-the-browser)).
- `tifa dev` no longer puts the tags that a Vite plugin adds with `transformIndexHtml` into the head, except the Vite client and the React refresh runtime. `tifa build` never ran that hook, so such a tag was in the page under `tifa dev` and silently missing in production. `tifa dev` now prints a warning that names each tag it leaves out. Put the tag in the `head` of the root `layout.tsx` to have it in both.
- `tifa dev` gives the namespaces of React and React DOM plain values in its SSR bundle, as `tifa build` does, and no longer prints `tifa rewrite not recognized: react, react-dom`. The bundle of `tifa dev` is not minified and keeps the license comments of React, so the rewrite did not find the modules of React and pages in dev called a getter for each export they read.
- In an app with a parameter folder at the root of `app/` (such as `app/lang+`), a link to a file of the public folder no longer asks for navigation data. `/favicon.svg` matched the page `/{lang}` in the browser router, though the server answers public files first, so `<Link to="/favicon.svg">` and `router.navigate` fetched page data for it. The generated routes now list the public files, and a navigation to one of them, or to a path under `/assets/` or `/__tifa/`, loads the document. Every page route also carries a marker, and the new `isPage(router, pathname)` of the runtime tells a page from these paths and from URLs that show a 404 (see [Route tree](docs/reference/route-tree.md#route-tree)).
- `tifa dev` runs the bundle step when a file is added to the public folder or removed from it, since the generated code lists these files. Editing the content of one still builds nothing (see [what a change runs](docs/build-and-deploy/dev.md)).
- The error page that follows a component throwing during the server render now has the head of an error page. Its head was the one worked out for the page that failed, so tags of a page that rendered stayed on the 500 page: `hreflang` and canonical links, the `title`, and `htmlAttributes` such as `lang`. The browser works the head out again from the matches when it hydrates, so the two could differ. Now the route the error replaces runs its `head` without data, the routes below it give no tags, and the `head` of the routes above it runs again with the failed route in `matches`, as for a page whose `Load` failed. See [Errors on a page](docs/pages-and-data/errors.md#errors-on-a-page).
- The example shop no longer links a missing page to itself in other languages. A 404 under `/store/<language>/` (a product that does not exist, or a URL no page has) answered with `hreflang` alternate links to that URL in each language, which tell search engines the missing URL is a real page. The recipe in [A site in several languages](docs/start/app.md#a-site-in-several-languages) is fixed the same way: the `head` of the language Layout leaves the links out when the page shows an error.
- `tifa dev` rebuilds and restarts the app when a file that `go:embed` takes in changes, such as a Markdown post. It used to look only at Go, TypeScript, CSS and JSON files, so an edit to an embedded `.md` file did nothing until some other file changed. A new or removed embedded file runs the static analysis too, and an embedded front end file runs the bundle as well.
- A URL that is only another spelling of a page now answers 308, a permanent redirect, where it answered 307. That covers a trailing slash (`/store/en-US/` to `/store/en-US`), a double slash, a dot segment and a percent-encoded letter (`/%61` for `/a`). Search engines take a permanent redirect as the sign of the canonical URL and ignore a temporary one, and 308 keeps the request method, as 307 did. A redirect that `c.Redirect` or a `Load` asks for keeps its own status.
- Server rendering runs on slowjs v0.29.8, with the same HTML. `JSON.stringify` that runs out of memory throws, where it could keep an element alive or return text without the keys of a replacer list. A `space` argument built by joining strings indents with its text, not bytes of the engine. Setting the `length` of an array to fewer elements and then writing past it works as in Node, and is 17% faster on 100,000 elements. `Iterator.prototype.reduce` and `Iterator.concat` close their iterators as the specification says.
- Server rendering runs on slowjs v0.29.9, with the same HTML. A page that runs out of memory while it makes an array with the prototype of another class (`Reflect.construct(Array, [], F)`) or while it sets the prototype of an object whose shape is shared (`Object.setPrototypeOf`) now gets the out of memory error. The first used to write through a null pointer and end the process, and the second kept the new prototype alive.
- `tifa dev`: the app and Vite no longer outlive it. Closing the terminal that runs `tifa dev` (SIGHUP) now stops it as Ctrl-C does. When `tifa dev` is killed (SIGKILL), the app it started shuts down as it does on SIGTERM, where it used to keep running with its port until someone killed it by hand. A `tifa dev` started with `nohup` still ignores SIGHUP. The app and Vite also no longer hold the files `tifa dev` inherited, such as the lock a script keeps with `flock`.
- `tifa dev`: after Vite's dev server restarts (a change to `vite.config.ts` or a `.env` file, or the switch to polling), an edit made right away could be missed for good, and a module the dev server had already served stayed old until the file changed again. The dev server now answers requests once its file watcher has read the app's files.
- Files from the public folder get an ETag, so a browser that revalidates them gets a 304 instead of the whole file again. They go out with `Cache-Control: no-cache`, but the copy embedded in the program has no modification time and had no ETag, so every revalidation downloaded the file in full. `tifa build` now writes the content hash of each public file into `build.json`, and the server sends it as a strong ETag, which turns weak (`W/"…"`) when the file goes out compressed. Files of the browser bundle are unchanged, and `tifa dev` keeps the modification time of the files it serves.
- quickjs v0.26.17: Intl converts options, values and locale lists as ECMA-402 does, so a Symbol or a BigInt where a string or a number is wanted throws a `TypeError`, and `Intl.NumberFormat` formats a wrapped BigInt exactly where it rounded it through a double. A page that changes `Array.prototype`, `JSON` or other built-ins no longer changes what Intl does. Intl's functions have the shape of built-ins, and the formatters are shared by every VM of the process, so a VM that has used Intl holds a few KB less.
- The SSR bundle keeps every line of React DOM in place, so the places in render error stacks point at the right lines.
- A page no longer carries the time its data was loaded. TanStack Router wrote the time of the render into every page, so `tifa dev` warned that every page with the render cache read the time, and the render cache gave the time of the first render to later visitors, whose browser then dropped data it could have kept when they went back to the page. The page now carries a fixed time, its answer says how old its data may be in `Server-Timing: tifa-age;dur=<ms>`, and the browser dates the data at the time it sent the request less that age. Only an answer that every cache must check with the server again carries it, so a page of the whole-page cache, or one whose `Cache-Control` lets caches keep it, has none. Where the answer has no age or the browser cannot read it (Firefox over plain HTTP, a page from the back and forward history), the data counts as old and loads again when you come back to the page (see [SSR and cache](docs/pages-and-data/ssr-and-cache.md#ssr-and-cache)).

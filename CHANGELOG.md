# Changelog

What changed in Tifa that apps and their users can see. From v0.0.1 on, changes are grouped by release. Older changes are grouped by the date they reached `main`. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). [Performance](docs/performance.md) has how each speedup was measured.

## [Unreleased]

### Added

- A `tifa` installed with `go install github.com/liustack/tifa/cmd/tifa@latest` hands the command to the version an app pins when run inside the app, like `go tool tifa`, so it never generates code for another Tifa version. `go tool tifa` stays the main way (see [Installing the command globally](docs/build.md#installing-the-command-globally)).
- `tifa gen` writes the generated code into `.tifa/` and builds nothing, so editors and `tsc` see the types of a fresh clone. The `package.json` of `tifa new` runs it from its `prepare` script, so `pnpm install` or `npm install` is enough. Existing apps: add `"prepare": "go tool tifa gen"` to the `scripts` of `package.json` (see [`tifa gen`](docs/build.md#tifa-gen)).
- Built-in languages. A folder of `app/` with a `_locales` folder holding `zh-CN.json`, `en-US.json` and so on is offered in those languages, with its pages and API routes. The default language, named by `i18n.default` in `tifa.yaml`, keeps the plain URL (`/store/cart`) and each other language is the first segment (`/en-US/store/cart`). `i18n.prefix: always` prefixes the default language too. Write `site.url` in `tifa.yaml` and Tifa writes `<html lang>`, the `hreflang` and `x-default` links and a canonical link. In code, `c.Language()` and `useLanguage()` give the language, `useAlternates()` gives the page's URL in each language for a language switch, `c.SetAlternates` says which versions a page has when its slug differs, `tifa.Languages()` gives the languages for a content collection (`Languages: tifa.Languages()`), and the new `tifa/i18n` adapter translates with i18next and react-i18next. Links such as `<Link to="/store/cart">` and root-relative links in Markdown get the prefix by themselves. See [A site in several languages](docs/guides/i18n.md). Apps that kept the language in their own `lang+` folder and have no `_locales` folder work as before. To move one over, put the strings in `_locales`, replace the `lang+` folder with its contents, delete the `Layout` that checked the language and the hand-written `hreflang` and `lang`, and drop the `Accept-Language` redirect unless you still want it. A top-level folder of `app/` named like a language of the site, and a `lang` in `htmlAttributes` on such a site, now fail the build.

### Changed

- The [performance doc](docs/performance.md#against-nextjs-tanstack-start-and-react-router) and the README now compare with React Router as well as Next.js and TanStack Start, and measure with gzip requested, as browsers do. The new [render cache doc](docs/render-cache.md) says what the render cache is, why it is safe on every page, signed-in ones included, and what Tifa does with cookies, the session and `Authorization` for each kind of answer.
- A client that takes both gzip and zstd, as browsers do (`Accept-Encoding: gzip, deflate, br, zstd`), now gets gzip. zstd is sent only to a client that takes no gzip or ranks zstd higher with `q`. This holds for pages, cached pages, navigation data and everything else `server.compress` compresses.
- The render cache and the whole-page cache keep one form of a page: gzip with `server.compress` on, HTML otherwise. A page was kept as HTML with a gzip and a zstd copy before, and compressed twice on every miss, which cost about 8% of a miss. Now it is compressed once, a page takes about a fifth of its HTML in the cache, and a hit for a client that takes gzip sends the stored bytes. A client that takes no compression gets the HTML unzipped as it is written, with its `Content-Length`, and a client that takes zstd and no gzip, or ranks zstd higher, gets zstd made as it is written.
- Server rendering runs on `github.com/liustack/quickjs` v0.30.1, the new path of the engine that was `github.com/liustack/slowjs` from v0.28.0 to v0.29.11. The HTML is the same. If an app builds with the engine's build tags, `slowjs_intl_nonames`, `slowjs_intl_nocjdict` and `slowjs_anygo` are now `quickjs_intl_nonames`, `quickjs_intl_nocjdict` and `quickjs_anygo`. Errors of the engine's root package start with `quickjs:` where they started with `slowjs:`. Since v0.30.1 the render timeout (`ssr.timeout`) also stops a page that is flattening a long string, running `String.prototype.repeat`, or compiling a very long regular expression or a very large character class. Compiling a very long regular expression under a timeout could kill the VM before.
- `tifa new` pins `github.com/liustack/sqlite` v0.1.4. v0.1.3 fixed a nil pointer panic when one commit groups more than 64 different SQL statements, common when values are written into the SQL text. v0.1.4 brings group commit and fixes from a full review and for Windows, and one rule changed: with named arguments, every parameter number up to the largest needs a value, as with positional ones (`SELECT ?2, :x` needs `?1` too). Existing apps: `go get github.com/liustack/sqlite@v0.1.4`.

### Fixed

- A route that writes several meta tags of one name in its `head`, such as a `theme-color` for light and one for dark mode or several `og:image`, now gets all of them on the page. Only the last one was kept, so a page in light mode showed the dark `theme-color`. A deeper route that writes the name still replaces them all.
- The render cache held up to twice the memory of `cache.size` with `server.compress` on: it counted the length of the compressed pages but kept the larger buffers they were made in, and left out the Content-Security-Policy of each page. It now keeps exactly sized copies and counts what it keeps, so the live heap of the cache stays within `cache.size`. The peak memory of a program that fills the cache with writes drops with it.

## [0.0.4] - 2026-11-05

### Added

- A field of type `*multipart.FileHeader` or `[]*multipart.FileHeader` in the input of a POST, PUT or PATCH handler holds uploaded files. The generated function takes them as `Blob | null` and `Blob[]` and sends the input as a multipart form, so a page uploads a file as it sends any other input, with `Validate`, `tifa.Fields` and `TifaError` as usual. A JSON body for such an input gets 415 (see [Files in the input](docs/app.md#files-in-the-input) and [Uploads](docs/guides/uploads.md)).
- `BodyLimit` and `ReadTimeout` in a `route.go`, constants or variables such as a setting of the app, replace `server.body_limit` and `server.read_timeout` for the requests its method handlers answer. The read time is lifted before `OnRequest`, and the answer gets `server.write_timeout` after it (see [Body limit and read time of a route](docs/app.md#body-limit-and-read-time-of-a-route)).
- A request body that does not arrive before the read deadline is answered with 408, no longer with 400.
- `tifatest.File(t, name, data)` gives the `*multipart.FileHeader` of a file, for a test that calls a handler or `Validate` with an input that holds one.
- `route.gen` exports `PageSearch` and `LayoutSearch`, the query parameters the `Load` or `Layout` of the folder reads, and the route gets them, so `Link`, `navigate` and `useSearch` know them: every value a `string` or `string[]` when read, since a key can come more than once in a URL (`c.Query` in Go takes the first), every key optional, and other keys open. Only the types change: nothing runs on the query in the browser (see [Query parameters in Link and navigate](docs/app.md#query-parameters-in-link-and-navigate)).
- `tifa.Secret("smtp.password", "SMTP password")` defines a setting of the app for a password, a token or a key. It comes from the environment, `.env` or the file of `-c`, a flag for it stops the program and says where to put it, and `./bin/app config` writes where it came from and not its value. The [email guide](docs/guides/email.md) uses it.
- `server.csp: on` sends a Content-Security-Policy that lets only the site's own scripts run. Tifa adds the hashes of the inline scripts it writes into a page to the policy of that page, so pages hydrate, and the render cache, the whole-page cache and ETags work as before. `server.csp_policy` changes the policy, and `report-only` only reports (see [Content-Security-Policy](docs/config.md#content-security-policy)).
- `tifatest.Start(t, tifaapp.App)` runs the whole app in `go test` and returns an `*httptest.Server`, so a test can walk through what a browser does: open a protected page and get the redirect, sign in, see the session cookie, and read the page. `OnStart`, `OnRequest`, decoding, `Validate`, sessions, redirects and `OnError` run as in the program, `OnShutdown` runs when the test ends, and the client keeps cookies and does not follow redirects. Without a front end, pages answer the data of their Loads as JSON by route ID. `tifatest.StartPages` also renders the pages with the front end of `tifa build` or `tifa dev`, on at most two VMs in the test binary, which later tests with the same build reuse, and fails the test when `.tifa/dist` is missing or a file it was built from has changed since. Import the app from a test in a package of its own, such as `package login_test` (see [Testing a whole request](docs/app.md#testing-a-whole-request)).
- `tifa build` and `tifa dev` write `.tifa/dist/inputs.json`: a hash of each file the front end was built from, which `StartPages` checks.

### Changed

- A `multipart.FileHeader` anywhere but in a field of a POST, PUT or PATCH input, such as in a result, the data of `Load` or the session, fails the build. A `route.go` that declares `BodyLimit` or `ReadTimeout` with another meaning, or without a method handler, fails the build too.
- A value other than a string for a query parameter that Go reads, such as `search={{ page: 2 }}`, is now a type error. Write `page: String(n)`: the router wrote it as text anyway.
- Every answer now carries `Referrer-Policy: strict-origin-when-cross-origin` and `Content-Security-Policy: frame-ancestors 'self'`, next to `X-Content-Type-Options: nosniff`. Another site can no longer show the pages in a frame: change the header in `OnRequest` for pages that a partner shows (see [Security headers](docs/config.md#security-headers)).
- `tifa new` pins `github.com/liustack/sqlite` v0.1.2, which builds with Go 1.26.6 to 1.27 and stops the build on a newer Go. After upgrading Go, upgrade the driver too.
- The generated table of routes moved from `.tifa/routes.go` into the package `.tifa/tifaapp`, as `tifaapp.App`, so tests can import it. `.tifa/main.go` serves `tifaapp.App`. A test that imports it needs `.tifa`, so in a fresh checkout `go vet`, `go test` and `go mod tidy` fail until `tifa check`, `tifa build` or `tifa dev` has run.

### Fixed

- The docs said a page or Layout remounts when a query parameter its `Load` reads changes. It never did, and now the docs and the generated `remountDeps` say what happens: a route remounts for a path parameter it reads, and another query loads the data again and keeps the component and its state, as TanStack Router does by default. State set up from `Load` data follows a new query only through a `key` or an effect of the app.
- A slice type that reads and writes itself as text, such as `type Tags []string` with `MarshalText` and `UnmarshalText`, in a GET or DELETE input or a form input with files, passed the build: TypeScript sent it as one string such as `"a,b"`, Go put that string in one element without calling `UnmarshalText`, and a slice of numbers got 400. It now fails the build, like a field whose element has those methods. `c.BindQuery` and the decoding of an input with files return an error for such a field whatever the request holds, and a form sent to an input that also takes JSON answers 400 for a value of such a field instead of filling it wrongly (see [Method handlers with input and result](docs/app.md#method-handlers-with-input-and-result)).
- Under systemd socket activation with HTTPS, `server.addr` may stay unset when systemd passes its socket. The program refused to start on the default address, which it does not listen on then.
- With HTTPS on, the plain HTTP address `server.http_addr` now reads and writes under `server.read_timeout` and `server.write_timeout`, like `server.addr`. It kept 10 seconds whatever they said.
- A handler under `tifatest.NewCtx` that wrote a 1xx status, such as `103 Early Hints`, before `SetSession` and its answer left the recorder with the 1xx and without the `Set-Cookie`: `httptest.ResponseRecorder` takes any status as the final one. The recorder now keeps 1xx statuses out, as the server sends them before the answer.
- The test in [Sign-in](docs/guides/sign-in.md) read two requests from one recorder, whose `Result()` keeps the headers of its first call, so it never saw the cookie of the second. It now makes a `NewCtx` per request.

## [0.0.3] - 2026-11-05

### Changed

- The `tifa new` template uses the SQLite driver `github.com/liustack/sqlite` instead of `modernc.org/sqlite`. It is pure Go and needs Go 1.27 or later, on Linux and macOS (amd64 and arm64) and Windows (amd64). Moving an app over from `modernc.org/sqlite` needs two checks. The driver rejects DSN parameters it does not know, so `_foreign_keys=1` and the like must become `_pragma=foreign_keys(1)`. And double quotes in SQL only name columns and tables, so a string value written as `"text"` must become `'text'`. Both drivers register the name `sqlite`, so remove the old import completely.

## [0.0.2] - 2026-11-04

### Added

- `tifa.ExpirePages("/blog/"+slug, "/blog")` has the whole-page cache make those pages again on their next request, for every query string, host and scheme of each path. Call it after a write that changes what pages with `Cache` show. A page made from data read before the call is not kept, and the old page still stands in when making the new one fails. It clears the memory of the program only, not a CDN in front (see [Making a page again after a write](docs/app.md#making-a-page-again-after-a-write)).
- `tifa.Stats()` returns the VM pool (VMs loaded, rendering and waited for, renders, failed renders, their time, and renders refused with 503) and the hits, misses, shared makes and entries of the render cache and the whole-page cache, with the bytes they hold. Renders and cache lookups count with atomics and take no new lock. [Deploying](docs/deploy.md#health-checks-and-metrics) shows a health check route and a route that writes the numbers for Prometheus without a library, and what to read in them.
- `server.read_timeout` and `server.write_timeout` (flags `--server-read-timeout` and `--server-write-timeout`, variables `SERVER_READ_TIMEOUT` and `SERVER_WRITE_TIMEOUT`) set the time to read a whole request and the time to write its answer. Both stay 10s by default. A handler that streams or takes a large upload lifts them for its own request with `http.NewResponseController(w)`, which reaches the connection through Tifa and the compression (see [Long requests](docs/config.md#long-requests)).
- `tifa.ShuttingDown(ctx)` returns a channel that closes when the program starts to stop. A stream with no end of its own, such as server-sent events, returns when it closes, so a stop no longer waits the whole `server.shutdown_timeout` for it.
- Under systemd socket activation the program serves on the sockets systemd passes it (`LISTEN_FDS`), so a restart keeps the port open and queues new connections instead of refusing them. With HTTPS, the two sockets are told apart by `FileDescriptorName=server.addr` and `FileDescriptorName=server.http_addr`. Without these variables nothing changes. [Deploying](docs/deploy.md#restart-without-dropping-requests) has the `.socket` and `.service` units.
- The `tifa new` template keeps sessions in its SQLite database (`sessions.go`, set with `tifa.SetSessionStore` in `OnStart`), so a restart no longer signs everyone out.
- `tifatest.NewCtx` takes the deadlines a streaming handler sets through `http.NewResponseController`.
- [Streaming](docs/guides/streaming.md) shows server-sent events and an answer streamed piece by piece, with the browser code, the caches, the stop and a test.

### Changed

- Answers with `Content-Type: text/event-stream` are sent uncompressed. A compressed stream held an encoder of about 1 MiB for gzip for as long as it stayed open. Other streamed answers are still compressed and still flush.

### Fixed

- A page with `Cache` that a content entry expired early, sent as the old page because making the new one failed, kept the `s-maxage` of its whole time, so a CDN in front counted it as fresh until that time ran out. Its `s-maxage` is now no larger than its `Age`.
- A built program given a flag it does not know, such as `--addr` for `--server-addr`, started with the defaults as if the flag were not there. It now stops with `unknown flag: --addr`. Flags of the settings of the app still work, and other environment variables and other keys of a file are still left alone.

## [0.0.1] - 2026-11-04

### Added

- Content collections: an app keeps posts, docs and other writing as Markdown files under `content/` and reads them in Go as typed values. `content.go` at the root declares each collection, `var Blog = content.Define[Post](content.Source{Dir: "blog", Languages: []string{"zh-CN", "en"}})`, where `Post` embeds `content.Entry` and its json names are the front matter keys. A folder with an `index.md` is one entry with the files below it (a page bundle), every other `.md` file is an entry, and `Match` narrows the choice. `Blog.All()`, `Blog.In(lang)`, `Blog.Get(lang, id)` (`tifa.ErrNotFound` when there is none or the entry cannot be seen yet) and `Blog.Languages()` return the entries with their ID, slug, path, date, translations and word count. `tifa build` and `tifa check` check the declarations, the files and every front matter (required keys, types, keys that are not fields with the nearest name, slugs, duplicate IDs and paths, links that lead out of the collection, `.mdx` files), and fail on a folder of `content/` that no collection reads, also in an app without `content.go`. Entries without a version in some language get a warning. The program runs the `Validate` method of each entry before `OnStart` and does not start when one fails. Tests read the content with `tifatest.LoadContent(t)` or set it with `tifatest.SetContent` (see [Content](docs/content.md)).
- The bodies of content entries become HTML at build time. `entry.Body()` returns the HTML of an entry as `tifa.HTML` for `<HTML>`, and `entry.Headings()` its headings with the `id` each has in the HTML, for a table of contents. The conversion runs in the Vite plugin with unified and needs `unified@11 remark-parse@11 remark-gfm@4 remark-rehype@11 rehype-raw@7 rehype-stringify@10` in the app, and the build says which to add. It reads GitHub-flavored Markdown, keeps the HTML written in it, drops HTML comments and gives headings the ids of GitHub. Apps add their own plugins with `tifa({ markdown: { remarkPlugins, rehypePlugins } })` in `vite.config.ts`. Images and other files the body points to with a relative URL are found next to the entry or next to its version in the default language, and are served from `/assets/` with a hash in the name. A relative link to a `.md` file, a missing file and a file outside the collection fail the build. The bodies are put into the program under `dist/content/` and never served by themselves. An app without pages, such as one whose only route writes a full-text feed, converts too, with the plugins of its `vite.config.ts`. In `go test`, `Body()` returns a placeholder that names the entry and `Headings()` returns nil (see [Markdown to HTML](docs/content.md#markdown-to-html)).
- Drafts and dates of content entries. An entry with `draft: true` is not converted and is not in the program. An entry whose `date` is still to come is in the program but hidden: it comes out at its date while the program runs, without a new build or a restart, and from that moment `All`, `In` and `Get` return it and the `Translations` of its other versions list it. A date alone is midnight UTC, and a timer that wakes at least once a minute also catches a clock that was set or a machine that slept. Pages with `Cache` made before that moment are made again by the next request, so a list of posts shows the new one at once. The program logs `tifa: content: blog en/202611/release-notes is published (date 2026-11-20 09:00 +08:00)`, and `tifa build` and `tifa check` list the entries that wait for their date. `tifatest.SetContentTime(t, tm)` has a test see the entries of `tm`. Under `tifa dev` both drafts (with `Draft` true) and entries whose date is still to come are shown, so a writer sees them in lists and on their pages (see [Drafts and dates](docs/content.md#drafts-and-dates)).
- `tifa dev` follows `content/`: a change of a Markdown file, its front matter or a file next to it, such as an image, rescans the content in Go, converts only the entries it touches and has the running app load them, without go build or a restart. The app runs `Validate` again and takes the new content, the whole-page cache expires, and open pages reload. A change of `content.go` or a schema type, or of `vite.config.ts` and its plugins, converts every entry. A front matter error, an undeclared folder or a plugin error shows the message of `tifa build` in the overlay, and an entry that fails `Validate` shows `The app did not load the content`, while the app keeps the content it had, with its old bodies (see [`tifa dev`](docs/content.md#tifa-dev)).
- A field of type `tifa.HTML` holds markup the app trusts, such as an article turned from Markdown into HTML, and `<HTML value={post.body} as="article" />` of `tifa/client` shows it, in one of the elements of ordinary content `as` takes. Its TypeScript type is `HTML`, not `string`. A page the server renders carries each value once, in its markup, and its hydration data a small marker, so a long article is not sent twice. Navigation data and pages with `SSR = false` carry the string. `tifa.HTML` cannot be a map key, a handler input, in the session or the whole result of a `Load` or `Layout`. Sanitize HTML from users before you convert it (see [Showing HTML the app trusts](docs/app.md#showing-html-the-app-trusts)).
- Links inside `<HTML>` go through the router like a `Link`: a click on a link to a page of the app shows it without loading the whole document, and a hover or a focus of 50 ms, or a touch, preloads it. The browser still follows links with a modifier key, `target`, `download` or `rel="external"`, links to other sites and schemes, a `#hash` of the same page, public files, `/assets/`, `/__tifa/` and paths without a page such as API routes. Handlers of the app on `<HTML>` run first and keep the router out with `preventDefault` (see [Showing HTML the app trusts](docs/app.md#showing-html-the-app-trusts)).
- New `go tool tifa errors` prints the errors since the last build of the `tifa dev` that runs in the app, so a coding agent that sees neither the browser nor the terminal can check a change: a build that failed or an app that did not start, stopped or did not load the SSR bundle, unexpected request errors with the status, the message users see and the stack trace in your sources, the errors of the browser that open pages had (hydration mismatches, uncaught errors, unhandled rejections) with the page, and pages whose two renders differ. Each kind keeps the last 20 with a count for repeats, a build drops what came before it, and a run during a build waits for it. It exits with 0 without errors, 1 with errors and 2 when no `tifa dev` runs, and `--json` prints every field. The dev client now sends the errors of the panel to `tifa dev` as well. Built apps have none of this. The `AGENTS.md` that `tifa new` writes tells agents to run it (see [Tifa errors](docs/dev.md#tifa-errors)).
- Apps define their own settings in `config.go` at the root: `var DBURL = tifa.String("db.url", "app.db", "Database file")`, and `tifa.Strings` (comma-separated text), `tifa.Int`, `tifa.Bool`, `tifa.Duration` and `tifa.Size`. Each returns a plain value, read from the flag `--db-url`, the variable `DB_URL`, `.env` and the file of `-c` like the settings of Tifa, and the default in `go test`. A bad value stops the program before `OnStart` with every other bad value. `./bin/app config` lists the settings of Tifa and of the app with their values and where each value comes from. `tifa build` fails on a call anywhere else, on a key that is no string literal or no valid key, and on two settings with the same flag or variable (see [Settings of the app](docs/config.md#settings-of-the-app)).
- The program reads the file `.env` in the folder it runs in, below the real environment variables. One file per machine, no variants, not put into the program. Under `tifa dev` the app reads the `.env` of the app root, and a change of it restarts the app without a build (see [.env](docs/config.md#env)).
- The program reads `PORT` and `HOST` of hosting platforms for `server.addr`, below `SERVER_ADDR`. `PORT` alone listens on every interface, as Cloud Run and the like need (see [PORT and HOST](docs/config.md#port-and-host)).
- `-c` is the short form of `--config`.
- A second `tifa dev` in the same app no longer starts Vite and fails with a bare `address already in use`. It prints `tifa: tifa dev is already running in this app at http://<address> (pid <N>)` and exits with an error. `tifa build` stops the same way while a `tifa dev` runs, since both write `.tifa/dist`. Without `--addr`, a taken port 9527 moves `tifa dev` on to 9528 and up (ten ports in all), and a taken `--addr` fails with the address in the message. The lock is the file `.tifa/dev.lock` (see [`tifa dev`](docs/dev.md)).
- `tifa dev` shows errors of the browser in a small panel in the corner of the page: `Hydration mismatch` (with React's diff and the component stack), `Recoverable error`, `Uncaught error` and `Unhandled rejection`. The same error again raises a counter, the panel keeps the last 20, and each can be dismissed. The panel leaves the page usable, and the overlay of a build error stays on top of it. Built apps have none of this code (see [`tifa dev`](docs/dev.md#errors-in-the-browser)).
- A fresh clone of an app now says what to do. `tifa dev` and `tifa build` stop at once with the command to run (`pnpm install` when pnpm is on PATH, `npm install` otherwise) when the app has a `package.json` and Vite is not installed, where `tifa build` printed `Vite is not installed in the application, install it with: pnpm add -D vite @vitejs/plugin-react`, advice that was wrong for an app that already lists Vite, and `tifa dev` showed the same text in its overlay. An app without pages has no `package.json` and is not checked. The README of an app made by `tifa new` has a line on what to run after cloning (see [`tifa dev`](docs/dev.md)).
- `tifa docs` prints where the docs of the Tifa version the app uses are, found with `go list -m` so a `replace` works too, and an index of them in the format of `scripts/docs-list.sh`: each doc's summary and when to read it. The `AGENTS.md` that `tifa new` writes tells a coding agent to run `go tool tifa docs` first and no longer links to the docs on GitHub's main branch, which may be another version than the app uses. The part of `AGENTS.md` that Tifa writes sits between `<!-- tifa:begin -->` and `<!-- tifa:end -->`, with the notes about the app itself under `## This app` after it (see [Tifa docs](docs/build.md#tifa-docs)).
- `tifa check` runs every check of an app with one command: the analysis of the routing conventions, the code generation, `go vet ./...`, `go test ./...` and the TypeScript type check, with the `tsc` the app installs (npm and pnpm both work), and stops at the first step that fails with an error that names it and a non-zero exit status. An app without pages skips the TypeScript step and needs no Node (see [`tifa check`](docs/build.md#tifa-check)). The `AGENTS.md` that `tifa new` writes names this as the one command to run before finishing a change, in place of the separate test and type check commands.
- A folder can hold `layout_.tsx` in place of `layout.tsx`. Its pages, and the pages below it, show without any Layout above it, the root Layout included, and the `Layout` functions above do not run for them, neither for a page, nor for the navigation data of the browser, nor for the 404 of a URL below it. The root Layout's `htmlAttributes` and `documentHead` and `OnRequest` still apply. The `Layout` in its folder gives it data, Layouts below it nest inside it, and when it fails the framework's default page shows. The build fails for `layout_.tsx` in `app/`, for `layout.tsx` next to `layout_.tsx`, and for `tifa.Use` of a Layout that a `layout_.tsx` drops (see [A Layout without the Layouts above](docs/app.md#a-layout-without-the-layouts-above)). The storefront of the example shop uses it, so its pages no longer carry the root Layout's empty workbench data, a URL that matches no page shows the shops in the workbench sidebar, and a language the store does not have shows a 404 of the store in Chinese and English.

The storefront of the example shop follows it: `/store` redirects to `/store/zh-CN` or `/store/en-US` by the browser's `Accept-Language`, and its page for the rest of the path is gone.
- A package may import a Node module it uses only on Node, such as `node:fs` for code a render never reaches, and the app loads and renders. Each imported name is a stand-in that throws when a render uses it, with the export, the module, the package and the place in its source. The bundle used to turn such an import into a `require`, which failed as each VM loaded it, even when only an `import()` reached the module. `tifa build` still lists the Node modules left in the SSR bundle (see [Packages that import Node modules](docs/app.md#packages-that-import-node-modules)).
- A component that suspends on work promises settle by themselves, such as a `React.lazy` component of a module in the bundle or `use` of a promise, renders on the server: the server waits for it and writes the page whole, as the browser shows it once loaded. Such a page used to fail with the error that a component suspended. Work that waits for a timer or a request still fails with that error. Pages that do not suspend render the same HTML in the same time (see [Components that wait](docs/app.md#components-that-wait)).
- `AsyncLocalStorage` in the server render, as a global and from `node:async_hooks` with `AsyncResource`, as Cloudflare Workers has them: `run`, `exit`, `getStore`, `bind` and `snapshot`. A store follows `await` and promise callbacks. fumadocs, which keeps the state of a page in one, now builds and renders with no setting but its own `collections` alias.

Each VM waits for it while it loads, before its first render. It must settle with promises alone, such as `await import()` of a module in the bundle: one that waits for a timer or a request never settles, and the VM fails to load.
- The server render keeps the strings i18next translates and gives them again for the same key and options. The example shop's storefront pages take 0.798 of the time to render, with the same HTML. It is on by default, and `build.i18next_cache: false` in the project file turns it off. Calls that run a formatter or post-processor of the app translate each time, as do all calls of an instance made with `cloneInstance`, so such code may read the request. An app that changes i18next's resources or options without i18next's API after the first render, or gives i18next other functions that read the request, such as an `overloadTranslationOptionHandler`, should turn it off, or pages may show stale translations. For an i18next whose code the plugin does not know, the build prints a warning and the bundle is the one without the cache ([build.md](docs/build.md#i18next-cache)).
- The SSR pool replaces VMs whose live memory after collection has grown too far from their warmup baseline. It loads one spare at a time while the render queue is empty and exchanges it only with an idle VM, keeping render capacity during loading. Failed loads keep the old VM and retry with backoff. Allow memory for one extra VM during replacement, see [Memory](docs/performance.md#memory).

- `tifa.WithRenderClock(ctx, now)` gives one server render a fixed or controlled clock shared by Date, Temporal.Now and Intl. The clock is cleared before VM reuse, and also applies to replacement VMs. Production keeps the live clock by default. Module initialization still runs during prewarming.

- SSR VMs provide Temporal and `Date.prototype.toTemporalInstant`, installed on first use. `Temporal.Now` uses the live system clock and defaults to UTC, consistent with Date and Intl. Temporal locale formatting uses Intl. Browser support is still the app's responsibility.

- The SSR VM provides `atob`, `btoa`, `DOMException`, `crypto.getRandomValues`, `crypto.randomUUID` and `structuredClone`. Random bytes come directly from Go before or during rendering, including module loading. The host APIs retain the built-ins they use across VM reuse. getRandomValues rejects views on shared or resizable buffers with TypeError. Cloning preserves cycles, shared references and common JavaScript built-ins. Transfer, SharedArrayBuffer and views on resizable ArrayBuffers remain unsupported. Unlike browsers, transparent proxies of ordinary objects and arrays are cloned through their traps. There is no `crypto.subtle`.

- SSR waits are bounded by `ssr.queue_limit` (32) and `ssr.wait_timeout` (1s). A full queue or an expired wait answers 503 with `Retry-After: 1` and `Cache-Control: no-store`, without using a VM or calling `OnError`. Apps can match the rejection with `errors.Is(err, tifa.ErrSSRBusy)`. `ssr.timeout` still limits execution only.

HTTPS on the default `server.addr` refuses to start and says to set `addr: :443`, and another loopback address starts with a warning. `tifa dev` stays on plain HTTP.

- A route's `head` can return `htmlAttributes`, the attributes of `<html>` for its pages, such as `lang` on a site in several languages. They merge over the root Layout's `htmlAttributes` one attribute at a time, the deepest route winning, and `null` takes one away. The browser keeps them in step after each navigation, also on pages without SSR. It writes an attribute only when the value Tifa wants for it changes, and takes away only attributes Tifa wrote, so a class or `lang` that a script of the page set stays until a route wants another value. ### Changed

- **Breaking:** Tifa writes and reads the JSON of apps with `encoding/json/v2` (the data of `Load` and `Layout`, the arguments and results of handler functions, `c.JSON`, `c.Bind` and sessions). The generated TypeScript types follow it. What changes for apps (see [JSON rules](docs/app.md#json-rules)):
  - A nil slice is written as `[]` and a nil map as `{}`, where both were `null`. Their TypeScript types lose `| null`, so `days?: string[] | null` is `days: string[]`.
  - A `[N]byte` array is a base64 string, as `[]byte` is, where it was an array of numbers. A slice or array whose element is a named byte type stays an array of numbers.
  - A type whose `MarshalText` has a pointer receiver is written as a string wherever it sits, also as a value in a field or slice, where only pointers to it were. Such types may be map keys.
  - `omitempty` leaves out only `null`, `""`, `[]` and `{}`, so it no longer drops `false` and `0`. Use `omitzero` to leave out zero values.
  - The `string` option is accepted only on number fields.
  - The build rejects `time.Duration`, also as a map key, which json v2 cannot write. Return a number in the unit you want, or a string.
  - The build rejects structs json v2 would fail on: two fields with the same JSON name in one struct, an unexported field with a json tag, a struct with fields but no exported field and no tag, an embedded field of a non-struct type without a JSON name, and an embedded struct with tag options or with JSON or text methods.
  - `<`, `>` and `&` are written as they are in JSON answers and page data, where they were `<`, `>` and `&`. Where Tifa puts JSON into the page HTML it still escapes them.
  - Bytes in a string that are not UTF-8 are written as U+FFFD, as before.
  - Reading is strict. `c.Bind` and handler arguments answer 400 for a name that matches a field only in another case, a name twice in one object, a string that is not UTF-8, a time that is not RFC 3339, base64 with line breaks, or an array of the wrong length for a Go array.
  - A session record kept in an outside store that does not read back under these rules signs the visitor out.
  - `GOEXPERIMENT=nojsonv2` is not supported.
  - The JSON of `tifa routes --json` and `tifa errors --json` has `[]` in place of `null` and no `<` escapes.
- **Breaking:** environment variables of settings have no `TIFA_` prefix: `TIFA_SERVER_ADDR` is `SERVER_ADDR`, `TIFA_SSR_VMS` is `SSR_VMS`. `tifa dev` gives the app its address in `SERVER_ADDR`. To update a deployment, drop the prefix from each variable.
- **Breaking:** the program reads only its own settings. A file key, an environment variable or a flag that is no setting is left alone, where an unknown key or `TIFA_*` variable stopped the program. A misspelt name now changes nothing, so check with `./bin/app config`. A `build.*` key in the file of `-c` is left alone too.
- **Breaking:** settings are YAML only. `tifa.json` and JSON deployment files are no longer read: rename `tifa.json` to `tifa.yaml` and write it as YAML (JSON is valid YAML). `tifa build` checks `tifa.yaml` and builds its values into the program as Go code, and no longer embeds the file.
- **Breaking:** Vite reads no `.env` (`envDir: false`), so the `VITE_` variables of `.env` files no longer reach the browser bundle. Pass such values from a `Load`. `tifa dev` no longer rebuilds the bundle for `.env.*` files.
- The example shop reads `SHOP_OPEN` as the setting `shop.open` of its `config.go`, so `./bin/shop config` lists it and `--shop-open` works too.
- **Breaking:** a handler function no longer loads the page data again after a successful POST, PUT, PATCH or DELETE, and the `invalidate` option of the call is gone. A call only sends its request and applies the session of the answer. A redirect only navigates, and a redirect to the page that is showing stays where it is. Tifa does not guess what a write changes, as TanStack Router does not. To show the result of a write, call `router.invalidate()` after the call (`await router.invalidate({ sync: true })` waits until the page shows the new data), or `refresh` your own state. To update, delete `invalidate: false` from calls, and add `await router.invalidate({ sync: true })` after each call whose page should show what it wrote.
- **Breaking:** the routes of `tifa build` use TanStack Router's default freshness, where they had `staleTime: Infinity` and `preloadStaleTime: Infinity`, and the router no longer sets `defaultStaleReloadMode: 'blocking'`. Data counts as stale at once, so going back to a page you visited shows its cached data and loads it again in the background with a `?_tifa=` request, and preloaded data is reused for 30 seconds. A page that must not show old data of someone else after a sign-out calls `router.clearCache()`.
- **Breaking:** `Session.In` and `Session.Out` of `tifa/client` are replaced by `SignedIn` and `SignedOut`. Each takes exactly one element as its child, renders no node of its own, and shows that element only to a signed-in or signed-out visitor, where the old components wrapped their children in a `<span>`. A typo in a component name fails the build, and a misspelled `data-session` attribute by hand failed without a word, so the attribute is now private to Tifa and the docs no longer tell you to write it. In development a child component that does not pass its props on to its DOM element fails when it mounts, with a message that says so. To update an app, replace `<Session.In className="x">…</Session.In>` with `<SignedIn><div className="x">…</div></SignedIn>`, and the same for `Session.Out` (see [In the browser](docs/sessions.md#in-the-browser)).
- **Breaking:** the method of the session type that gives the browser its part is `Exposed() M`, where it was `Browser() M`. The new name says what it does: whatever it returns is written into the page HTML and kept in the visitor's `localStorage`, so it must hold no credentials and nothing secret. To update an app, rename the method. The build checks it as before (see [Sessions](docs/app.md#sessions)).
- The text of `tifa.ErrSSRBusy` is `tifa: render queue busy`, where it was `ssr: render queue busy`, so every error value of Tifa starts with `tifa: `. A script or alert that matches the old text needs the new one.
- **Breaking:** `c.QueryAll(name)` is now `c.QueryValues(name)`. It returns a slice, and since Go 1.23 an `All` function returns an iterator, as `maps.All` and `slices.All` do. `http.Header.Values` is the closest name in the standard library. To update an app, rename the calls. The build check is the same (see [How Load may use Ctx](docs/app.md#how-load-may-use-ctx)).
- **Breaking:** redirects are `tifa.Redirect(url, status)`, a function of the package, where `c.Redirect(url, code)` was a method of `Ctx` that never used `c`. It panics when `status` is not 3xx, as `WriteHeader` does for a code it cannot send, where it returned a plain error that ended as a 500. The `Code` field of `tifa.RedirectError` is now `Status`, the name `tifa.Error` already uses. `c.Redirect` is gone. To update an app, replace `c.Redirect(` with `tifa.Redirect(` and `redirect.Code` with `redirect.Status`. The answer to the browser is unchanged (see [route.go](docs/app.md#routego)).
- **Breaking:** `OnStart` is `func OnStart(ctx context.Context) error`, like `OnShutdown`. The context is the one the program runs with, which ends on SIGINT or SIGTERM, so a start that waits for a database can stop when the program is stopped. To update an app, add the parameter. The build rejects the old signature (see [hooks.go](docs/app.md#hooksgo)).
- New `Fields.Err()` returns the `Fields` as an error, or nil when it has no entries. A validator that collects messages in a `tifa.Fields{}` ends with `return fields.Err()` and needs no `len` check. The server still answers an empty `tifa.Fields` that is returned directly with 422, because it is an error (see [Method handlers with input and result](docs/app.md#method-handlers-with-input-and-result)).
- The example shop's storefront uses the whole-page cache. Its home page, journal list and product pages are kept for 10 minutes, the product list for 5 and a journal post for an hour, so a visitor of a cached page gets the answer from memory with `Cache-Status: tifa; hit` and no `Load` runs. The pages no longer hold anything of the visitor: the storefront Layout has the language, the menu and the free delivery price, and the cart in the header and the recently viewed rows come from the new `/store/{lang}/mine` route, which the browser asks after the page has loaded. A product page tells it which product is open. See [The storefront cache](examples/shop/README.md#the-storefront-cache).
- Pages can opt in to a whole-page cache with `const Cache = 10 * time.Minute` in their `route.go`. For that long every visitor gets the same answer from memory, without the `Load` running or a render, and a CDN in front keeps it for the same time minus `Age`: `Cache-Control: public, max-age=0, s-maxage=<Cache in seconds>, stale-if-error=86400`, `Age` and `Cache-Status: tifa; hit`. Such a page is anonymous: its GET and HEAD, and the data requests of navigations to it, lose `Cookie` and `Authorization` before `OnRequest`, `tifa.Session` is nil, `SetSession` and `ClearSession` return an error, and the `Set-Cookie` of its HTML is removed. The build fails when its `Load`, a Layout around it or a function they call reads `c.Cookie`, `c.Header` or `tifa.Session`. Its request keeps only a short list of headers (`Host`, `Accept-Encoding`, `If-None-Match`, `Origin`, `Sec-Fetch-*` and a few more), so a header such as `X-User-ID` cannot reach a `Load`. The key is the scheme, the `Host` header, the path and the query without tracking parameters (`utm_*`, `gclid`, `fbclid` and the like, the list is the new setting `cache.ignore_query`), sorted. After the time is over the next request makes a new page and the others wait for it, and if that fails (a `Load` error, a failed or timed out render, a busy pool) the old page is served for up to a day. Only GET and HEAD answers with status 200, 301, 302 or 308 are kept, and not one that says `private`, `no-store` or `no-cache` or varies on more than `Accept-Encoding`. The answers to navigations stay `private, no-cache`. Pages share `cache.size` with the render cache. `tifa routes` has a `CACHE` column and the manifest of `--json` has `cache`. `Cache` must be a `time.Duration` of at least a second, and `Cache = true` still fails the build. See [The whole-page cache](docs/app.md#the-whole-page-cache).
- The browser asks for the data of a navigation with the page URL and the query parameter `_tifa=<build>.<digits>` (one digit for each `Load` on the chain, 1 for the ones it wants), where it sent the headers `X-Tifa-Route` and `X-Tifa-Build`. A page and its data now have two URLs, so a cache that keys by URL cannot mix them up, and the `Vary: X-Tifa-Route` line is gone. The parameter is taken off the request before your code runs, so `c.Query`, `OnRequest` and the rendered URL never see it, and a `Load` that reads a parameter named `_tifa` fails the build. A preload of the router ends the value with `.p`, which tells it apart in a log (it is not a way to count page views). The answer to a navigation request is never public: a `Cache-Control` of the app that is not `no-store` or `private, no-cache` is replaced by `private, no-cache`. In a middleware set with `tifa.SetHTTPHandler`, `r.Pattern` is now the route template once the handler has returned, so metrics can count by route. A 400 answers a digit count that is not the number of `Load`s on the chain, and 409 still answers another build. Handler function calls are unchanged. See [Page requests](docs/build.md#page-requests).
- The render cache is on for every page, and `Cache = true` is gone. Pages whose `Load` and Layout data, URL, build and session are the same are rendered once and answered from the cache of `cache.size` (64 MiB by default, 0 turns it off), and requests that miss the same page at the same time share one render. This was only so for pages with `Cache = true`. A hit still runs the `Load` and Layout functions and hashes their data, and answers 2,865 requests a second against 38 for a render, with one VM and one request in flight on the machine of the [study](docs/studies/nextjs-and-tanstack-start.md#cache-hit-against-cache-hit), and 4.6 times as many as a Next.js ISR hit there. The new `const RenderCache = false` in `route.go` turns it off for a page that shows the time or a random number on purpose. **Breaking:** the build fails on `Cache` with the advice to delete it, and on the lower case names `cache`, `rendercache`, `ssr` and `layoutssr`, which were skipped without a word. Delete every `const Cache = true`. A page that read the time or a random number while rendering now keeps the value it had at the first render, so check such pages: `tifa dev` renders every page twice and says in the terminal and the overlay when the two differ, and where. A request with `tifa.WithRenderClock` skips the cache. `tifa routes` has a `RENDERCACHE` column where it had `CACHE`, and the manifest of `--json` has `renderCache` for `cache`. See [SSR and cache](docs/app.md#ssr-and-cache).
- The example shop has a sign-in. Its workbench under `/projects` needs the demo account `owner@shanhai.example` with the password `shanhai-demo`, and the storefront does not. A visitor who is not signed in goes to `/login` and comes back to the page they asked for. The top bar shows the name and a sign-out button, or a link to sign in. The shop keeps sessions in memory, with no store configured. Start it with `SHOP_OPEN=1` to see the workbench without signing in, which the comparison with Next.js and TanStack Start and the page benchmarks do. See [Sign in](examples/shop/README.md#sign-in).
- The session reaches the browser. A page carries who is signed in, and the server writes `<html data-session="in">` for someone signed in. `useSession()`, `Session.In` and `Session.Out` from `tifa/client` show it, any element with `data-session="in"` or `"out"` shows or hides itself from the first paint, and the browser keeps a copy in `localStorage`. Navigation data answers are now `{"routes": ..., "session": ...}` where they were `{route ID: result}`. A handler function call answers `{"result": ..., "session": ...}`, and `{"session": ...}` with 200 where an input-only handler answered 204 and the call signed someone in or out. Requests without `X-Tifa-Call` get the answers they got. New `GET /__tifa/session`. `data-session` on `<html>` is kept by Tifa. See [Sessions](docs/sessions.md#in-the-browser).
- The build checks the session of the app. `tifa build` and `tifa check` fail when `tifa.SetSession` and `tifa.Session` are called with different types, when `Session` or `ClearSession` is called with no `SetSession`, when the session type is not a struct that reads back from JSON, when `Load` or `Layout` reaches `SetSession` or `ClearSession`, and when a page, an API route or a file in `public/` uses the path `/__tifa/`. A session type with a method `Browser() M` gets its `SessionData` type in `.tifa/session.gen.ts` (see [Checks at build time](docs/sessions.md#checks-at-build-time)).
- New sessions. `tifa.SetSession(c, &s)` signs the request in with a new random token and a cookie that lasts 30 days, `tifa.Session[S](c)` returns who is signed in (or nil) in `OnRequest`, `Load`, `Layout` and method handlers, and `tifa.ClearSession(c)` signs out. The record is JSON of at most 4 KiB, stored under the SHA-256 of the token. Without a store the server keeps sessions in memory up to `session.memory_limit` and signs everyone out on restart. `tifa.SetSessionStore(s)` in `OnStart` switches to your own `tifa.SessionStore`, and `tifatest.TestSessionStore` checks it. The cookie is `__Host-tifa_session` (`tifa_session` without `Secure` under `tifa dev`), set by `session.cookie` and `session.max_age`. An answer that sets the cookie is `no-store` and never a 304. `tifatest.NewCtx` has a session store per test and `tifatest.WithSession` sets up a signed-in request (see [Sessions](docs/app.md#sessions)).
- New `tifa.SetHTTPHandler(wrap)`, called in `OnStart`, wraps the handler of the whole server with plain `net/http` middleware or handlers, such as `/debug/pprof/` or OpenTelemetry's `otelhttp`. The wrapper is outside static files, the cross-site check and the routes, so it sees every request, the 403 of a refused cross-site write included, with the original `http.ResponseWriter`. It does not go through `OnRequest`, `OnError` or the cross-site check, and a shutdown still waits for its requests. Calling it after the server listens panics (see [Setting up in OnStart](docs/app.md#setting-up-in-onstart)).
- Tifa logs through `log/slog` instead of `log`, with levels and fields. A failed request is `ERROR` with `method`, `path` and `err`, a refused cross-site write is `WARN`, the listening address is `INFO`, and a request's own context goes with the message where there is one, so a handler can add a trace id. The lines about startup are written after `OnStart` returns. `slog.SetDefault` in `OnStart` moves all of them to the new handler, and Tifa reads `slog.Default()` for every message. The text of the lines changed to `msg key=value`, so a script that reads the old lines needs an update, but the listening line still contains `tifa: listening on http://ADDR` (see [Changing the log handler](docs/app.md#changing-the-log-handler)).
- **Breaking:** `OnRequest` is `func OnRequest(c *tifa.Ctx, next func(*tifa.Ctx) error) error`. `next(c)` runs the matched route, once, where `c.Next()` did. `c.SetContext` is replaced by `c.WithContext(ctx)`, which returns a copy of `c` that carries `ctx` and leaves `c` alone, as `http.Request.WithContext` does: `return next(c.WithContext(ctx))`. `c.Next`, `c.SetContext` and `tifatest.SetNext` are gone, and a test calls `OnRequest(c, func(c *tifa.Ctx) error { ... })` with its own closure for `next`. To update an app, change the signature, replace `c.Next()` with `next(c)`, and pass the context you used to `c.SetContext` to `next(c.WithContext(ctx))`. The build rejects the old signature (see [hooks.go](docs/app.md#hooksgo)).
- `tifa.RedirectError` is exported. It is the type of the error that `c.Redirect` returns, so `OnRequest` and app tests can recognize a redirect with `errors.As(err, &redirect)` and read its `URL` and `Code`.
- A page left open across a deploy reloads once for the new build, whatever shows the mismatch. A 409 on a data request already did, and now it names the build the server runs in the `X-Tifa-Build` response header. A handler function sends the build of its page, and the server refuses a call from another build with the same 409 before the handler runs, so an old page cannot write with types the new handler no longer reads. The call throws a `TifaError` with status 409, the page reloads, and the call is not sent again. A 409 that your own handler returns reloads nothing, and a call without `X-Tifa-Build`, from curl say, is not checked. A code chunk that fails to load (Vite's `vite:preloadError`) reloads the page too. Each reload happens once per build, remembered in `sessionStorage`. A page reloads only after it has written the mark and read it back. Where the browser blocks the storage, the page does not reload and shows the failure, whose message says to reload the page. A page that comes back still stale does not reload again: navigation data fails with the 409, a call throws it, and a failed import reaches the `Error` of the route (see [Pages open while you deploy](docs/app.md#pages-open-while-you-deploy)).
- Every answer of the app is sent with `Cache-Control: private, no-cache` unless the app sets `Cache-Control` itself. Pages, 304s, 404 pages, navigation data, method handler answers and redirects had no header (navigation data had `no-cache`). CDNs such as CloudFront with its default policy keep an answer without `Cache-Control` for a day or more, and Azure Front Door for days, so a page for one visitor could reach another. Now a shared cache stores nothing, and the browser still keeps the page and asks again with the ETag, which ends in a 304. Set `Cache-Control` in `OnRequest`, a `Load`, a `Layout` or a handler to choose another value. Error answers, which are JSON errors, the plain error page from Go, the page with an error and the busy answer, say `no-store` unless the app set `Cache-Control` before the error. The 404 page of the app keeps the default. Files under `/assets/` and `public/` keep their headers (see [SSR and cache](docs/app.md#ssr-and-cache)).
- The Vite plugin makes three fewer rewrites of the SSR bundle, with the same HTML and the same render time. React's JavaScript cache of HTML escapes and its `replaceAll` chain were for a VM without the engine's escape, which every VM of the pool has, so no render ran them. Working out the key of an element only when something reads it saved less than the 0.11% by which two runs of one bundle differ. Every other rewrite was measured again on the C engine of slowjs v0.29.8 and still pays, see [Optimizations](docs/studies/optimizations.md#build).
- **Breaking:** a POST, PUT, PATCH or DELETE that a browser sends from another site is refused with 403 before `OnRequest` and before any route, for every app (see [Cross-site writes](docs/config.md#cross-site-writes)). It uses Go's `http.CrossOriginProtection`: `Sec-Fetch-Site` decides, an old browser is judged by its `Origin` against the `Host`, and a request with neither header, such as curl or a webhook, passes. ### Fixed

- Under `tifa dev`, a page loaded right after a save now shows the new server render. Before, a request in the first 100 ms or so, before the files went quiet and the rebuild started, got the old one. Saving a `page.tsx` or `layout.tsx` that exports `head`, `htmlAttributes` or `documentHead` makes Vite reload the page at once, so the browser often hit that window: the page kept the old text and React reported `Hydration failed`. Such a request now waits for the rebuild (see [What each change triggers](docs/dev.md#what-each-change-triggers)).
- The pages of an app made by `tifa new` now show a new todo, and a todo marked done, at once. They did not: the comments said the page data loads again after a write, but Tifa never reloads it, so the list stayed old until a reload. The add form and the done button now call `router.invalidate()` after the write, and the comments say so (see [Calling method handlers from the browser](docs/app.md#calling-method-handlers-from-the-browser)).
- `tifa dev` no longer puts the tags that a Vite plugin adds with `transformIndexHtml` into the head, except the Vite client and the React refresh runtime. `tifa build` never ran that hook, so such a tag was in the page under `tifa dev` and silently missing in production. `tifa dev` now prints a warning that names each tag it leaves out. Put the tag in the `head` of the root `layout.tsx` to have it in both.
- `tifa dev` gives the namespaces of React and React DOM plain values in its SSR bundle, as `tifa build` does, and no longer prints `tifa rewrite not recognized: react, react-dom`. The bundle of `tifa dev` is not minified and keeps the license comments of React, so the rewrite did not find the modules of React and pages in dev called a getter for each export they read.
- In an app with a parameter folder at the root of `app/` (such as `app/lang+`), a link to a file of the public folder no longer asks for navigation data. `/favicon.svg` matched the page `/{lang}` in the browser router, though the server answers public files first, so `<Link to="/favicon.svg">` and `router.navigate` fetched page data for it. The generated routes now list the public files, and a navigation to one of them, or to a path under `/assets/` or `/__tifa/`, loads the document. Every page route also carries a marker, and the new `isPage(router, pathname)` of the runtime tells a page from these paths and from URLs that show a 404 (see [Route tree](docs/build.md#route-tree)).
- `tifa dev` runs the bundle step when a file is added to the public folder or removed from it, since the generated code lists these files. Editing the content of one still builds nothing (see [what a change runs](docs/dev.md)).
- The error page that follows a component throwing during the server render now has the head of an error page. Its head was the one worked out for the page that failed, so tags of a page that rendered stayed on the 500 page: `hreflang` and canonical links, the `title`, and `htmlAttributes` such as `lang`. The browser works the head out again from the matches when it hydrates, so the two could differ. Now the route the error replaces runs its `head` without data, the routes below it give no tags, and the `head` of the routes above it runs again with the failed route in `matches`, as for a page whose `Load` failed. See [Errors on a page](docs/app.md#errors-on-a-page).
- The example shop no longer links a missing page to itself in other languages. A 404 under `/store/<language>/` (a product that does not exist, or a URL no page has) answered with `hreflang` alternate links to that URL in each language, which tell search engines the missing URL is a real page. The recipe in [A site in several languages](docs/app.md#a-site-in-several-languages) is fixed the same way: the `head` of the language Layout leaves the links out when the page shows an error.
- `tifa dev` rebuilds and restarts the app when a file that `go:embed` takes in changes, such as a Markdown post. It used to look only at Go, TypeScript, CSS and JSON files, so an edit to an embedded `.md` file did nothing until some other file changed. A new or removed embedded file runs the static analysis too, and an embedded front end file runs the bundle as well.
- A URL that is only another spelling of a page now answers 308, a permanent redirect, where it answered 307. That covers a trailing slash (`/store/en-US/` to `/store/en-US`), a double slash, a dot segment and a percent-encoded letter (`/%61` for `/a`). Search engines take a permanent redirect as the sign of the canonical URL and ignore a temporary one, and 308 keeps the request method, as 307 did. A redirect that `c.Redirect` or a `Load` asks for keeps its own status.
- Server rendering runs on slowjs v0.29.8, with the same HTML. `JSON.stringify` that runs out of memory throws, where it could keep an element alive or return text without the keys of a replacer list. A `space` argument built by joining strings indents with its text, not bytes of the engine. Setting the `length` of an array to fewer elements and then writing past it works as in Node, and is 17% faster on 100,000 elements. `Iterator.prototype.reduce` and `Iterator.concat` close their iterators as the specification says.
- Server rendering runs on slowjs v0.29.9, with the same HTML. A page that runs out of memory while it makes an array with the prototype of another class (`Reflect.construct(Array, [], F)`) or while it sets the prototype of an object whose shape is shared (`Object.setPrototypeOf`) now gets the out of memory error. The first used to write through a null pointer and end the process, and the second kept the new prototype alive.
- `tifa dev`: the app and Vite no longer outlive it. Closing the terminal that runs `tifa dev` (SIGHUP) now stops it as Ctrl-C does. When `tifa dev` is killed (SIGKILL), the app it started shuts down as it does on SIGTERM, where it used to keep running with its port until someone killed it by hand. A `tifa dev` started with `nohup` still ignores SIGHUP. The app and Vite also no longer hold the files `tifa dev` inherited, such as the lock a script keeps with `flock`.
- `tifa dev`: after Vite's dev server restarts (a change to `vite.config.ts` or a `.env` file, or the switch to polling), an edit made right away could be missed for good, and a module the dev server had already served stayed old until the file changed again. The dev server now answers requests once its file watcher has read the app's files.
- Files from the public folder get an ETag, so a browser that revalidates them gets a 304 instead of the whole file again. They go out with `Cache-Control: no-cache`, but the copy embedded in the program has no modification time and had no ETag, so every revalidation downloaded the file in full. `tifa build` now writes the content hash of each public file into `build.json`, and the server sends it as a strong ETag, which turns weak (`W/"…"`) when the file goes out compressed. Files of the browser bundle are unchanged, and `tifa dev` keeps the modification time of the files it serves.
- quickjs v0.26.17: Intl converts options, values and locale lists as ECMA-402 does, so a Symbol or a BigInt where a string or a number is wanted throws a `TypeError`, and `Intl.NumberFormat` formats a wrapped BigInt exactly where it rounded it through a double. A page that changes `Array.prototype`, `JSON` or other built-ins no longer changes what Intl does. Intl's functions have the shape of built-ins, and the formatters are shared by every VM of the process, so a VM that has used Intl holds a few KB less.
- The SSR bundle keeps every line of React DOM in place, so the places in render error stacks point at the right lines.
- A page no longer carries the time its data was loaded. TanStack Router wrote the time of the render into every page, so `tifa dev` warned that every page with the render cache read the time, and the render cache gave the time of the first render to later visitors, whose browser then dropped data it could have kept when they went back to the page. The page now carries a fixed time, its answer says how old its data may be in `Server-Timing: tifa-age;dur=<ms>`, and the browser dates the data at the time it sent the request less that age. Only an answer that every cache must check with the server again carries it, so a page of the whole-page cache, or one whose `Cache-Control` lets caches keep it, has none. Where the answer has no age or the browser cannot read it (Firefox over plain HTTP, a page from the back and forward history), the data counts as old and loads again when you come back to the page (see [SSR and cache](docs/app.md#ssr-and-cache)).
